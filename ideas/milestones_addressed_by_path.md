# Milestones addressed by path

A design draft, written 2026-10-28 and revised 2026-10-29, 2026-10-30, 2026-11-09, and 2026-11-10, the last revision recording the fifth and last of the milestones that carry it, giving one idea its shape: retire the `milestones/` root with its `README.md` pointer and history, let a milestone's artifact sit anywhere in the project, name it by path, and drop the notion of an active milestone, so that several milestones can be worked at once while a milestone standing above another in the directory tree still forces sequential execution. The idea is taken as the direction; the draft names its separable parts, records what the plugin does today where the shape builds on it, and proposes the shape that keeps what the idea is after at the least cost. It precedes any milestone; the questions a review pass would raise at design altitude are settled into the shape, Carrying it out splits the work into the milestones that carry it, and the closing section names the kind of question deliberately left to those milestones.

## Taking it apart

The idea bundles four changes that can be made independently:

1. **One file instead of four.** The artifact's format.
2. **History in git instead of in `milestones/README.md`.** Where finish records what a milestone did, and where "finished" is read from.
3. **No pointer; a milestone is named by path.** How a skill resolves `<MILESTONE_DIR>`.
4. **Placement anywhere, with a sequencing rule over the directory tree.** Where a milestone may live and what bounds concurrent execution.

Parts 3 and 4 are the goal. Part 2 is forced by part 3: once nothing activates a milestone the pointer has no reader, and the history section that shares its file is the one project-wide write per milestone left, so leaving it would keep the one conflict the change exists to remove. Part 1 is independent of the other three and is the one part the shape does not take (The artifact, below).

## What exists today

Grounding for the shape, read from the runtime files and from this repository's history on 2026-10-28.

- **Every tool already takes the resolved directory.** `open_questions.py`, `task_list.py`, and `requirements.py` take `<MILESTONE_DIR>` as their first argument and join their one file name onto it; none reads `milestones/README.md`. Only `define_milestone.py` hardcodes the `milestones` root: it numbers the new milestone as the maximum present plus one and creates `milestones/milestone_<NN>_<slug>/`.
- **Resolution has one seam.** `core/shared/get-current-milestone.md` is the single place `<MILESTONE_DIR>` is resolved, from the pointer or from a leading `--milestone <milestone_id>` (milestone 50). Seventeen skills resolve through it, and both dispatched agents take the directory as a prompt line. The override already lets every per-milestone skill run against a milestone the pointer does not name, so the addressing half of the idea is largely in place; what remains is the value's shape (an id under `milestones/` today, a path tomorrow) and the default when no flag is given.
- **`milestones/README.md` has six runtime readers or writers.** The resolution procedure reads the pointer; `goto-next-milestone` reads the pointer and the history headings and writes the pointer; `finish-current-milestone` prepends a history entry, appends a table row, and clears the pointer; `init-milestone-base-workflow` creates the file; `discuss-milestone-goal` reads the history for what has already been built; `ask-in-milestone-context` answers about past work from it when the pointer reads `none`. Outside the runtime, the contributor flow in `CONTRIBUTING.md` is built around the pointer: the maintainer reserves a milestone only while their pointer reads `none`, the contributor activates it on a branch, and syncs by merge only while `main`'s pointer reads `none`, because a live pointer conflicts on that line.
- **The shared file is written on every milestone.** Of this repository's 1848 commits, 107 touch `milestones/README.md`; 41 are `Milestone-activation:` and 43 are `Milestone-finish:` commits, so two commits per milestone exist only to move the pointer and the history. The file is 559 lines, and the 51 directories under `milestones/` hold 3.3 MB that every tree-wide search in this repository hits.
- **"Done" is read from the history headings.** `goto-next-milestone` treats a directory as undone when its number matches no `### Milestone N — Title` heading, and the `## Completed Milestones` table is never consulted. Numbers are unique and monotone so that pick is deterministic.
- **What the record is for.** Design claim 10 says the milestone files and the git log hold the full record. Capture walks a milestone's answer commits with a path-scoped `git log` and reconstructs every decision from commit diffs, never from the README; `derive-tasks` orders conflicting decisions by the commits that added them. The README's history is read by two conversational skills and by people; nothing mechanical depends on it except `goto`'s done set.
- **Two completion runs in one working tree are not safe today.** Checked in a scratch repository on 2026-10-28: the commit procedure stages path-scoped but commits without a pathspec, so a commit carries whatever the shared index holds, and when run B's agent has staged its change set and run A commits first, B's files ride into A's `Task-completion:` commit, A's subject names work it did not do, and B's orchestrator then finds nothing staged and records nothing. And every git write takes `.git/index.lock` with no wait: a second writer in the same moment fails outright, exit 128, which today is a `FAILED` return or a stopped run. Both are properties of how the workflow commits, not of what it edits.

## Proposed shape

### The artifact

The idea retires the `milestones/` directory, makes each milestone one artifact holding its goal, requirements, tasks, and questions, and lets that artifact be placed anywhere in the project and named by its path. The shape takes the placement and the naming and keeps both the container and the directory. A milestone is a directory `<scope>/milestones/<slug>/` holding three files, `requirements.md`, `open_questions.xml`, and `TASKS_TODO.md` (the completed tasks live in commits, below), live from its definition to its finish. `<scope>` is any directory in the project, the root included. The `milestones/` container is kept because it does two jobs the idea needs and a bare placement cannot: it gives the milestone a scope, the container's parent directory, which is what the sequencing rule compares, and it gives every runner one fixed pattern to find milestones by, `**/milestones/*/requirements.md` over tracked files (`git ls-files`), so discovery is one command and never a tree walk that meets `node_modules`. "Anywhere" is therefore any directory, at the granularity of a scope. The root container of every existing project already matches the pattern, so no directory moves at upgrade.

The number goes from the directory name: it existed for `goto`'s lowest-undone pick, which no longer exists, and under removal-at-finish a container holds only live milestones, where a count restarts and tells nothing. The slug is derived from the title as the definition tool derives it today, and the directory is created exclusively, so the one conflict check stays. Two scopes may hold the same slug; a commit subject that names a milestone names its path, so the subjects stay unique.

The one artifact is the part of the idea the shape does not take. A directory is as nameable as a file, and the files are already read whole where whole reads are wanted, so one file would buy one name and one document to read, and what it would cost is structural. The three sole-writer tools own one file each by construction: the task-list tool renders its whole file in one canonical layout, discards whatever stands above the first section, and treats every column-0 `## ` line as a heading with no fence exemption; the open-question tool rewrites its whole XML document in canonical form; the fold tool is a byte-preserving splice precisely because `requirements.md` keeps being hand-written. In one file each would need a region locator, tasks would move down one heading level, the XML would sit in a fence, and "the whole file in canonical form" would become "this region in canonical form", with hand edits able to break the region markers. The agents' read scoping holds by file: a dispatched agent reaches the question document only through the tool and reads `requirements.md` and `TASKS_TODO.md` whole as prose, and in one file every whole read of the requirements would also read every question with its alternatives, the longest text a milestone carries, on every task dispatch. And the commit guards are path-scoped, the sweep's stranded-fold guard checking two files and capture's log scoped to `open_questions.xml`, which one path collapses, so a dirty task list and a stranded fold would no longer be told apart. None of the addressing or sequencing changes depends on the file count, so the files stay as they are, and the single file is an idea of its own, to be revisited on its own if still wanted.

### Scope is the core of the work

A milestone's scope is the directory its artifact is placed under, and that directory is the one holding the core of the work: the code, module, or package the milestone is about. It is not the milestone's footprint. Work that reaches outside the core, documentation kept in another directory than the implementation, a shared configuration file, a test tree beside the package, is adjacent, allowed, and not part of the scope; nothing records it, and the gate never reads it.

The milestone's own writing says nothing about either. Its core scope is defined by its placement, so `requirements.md` does not restate it. Its adjacent footprint is not specified anywhere, not in the `## Goal` prose and not in a file or tool, because which edits outside the core the work needs is settled with the milestone's questions and may change as they are answered; the goal describes the work, and the footprint follows from the decisions. A recorded footprint the gate also read would make the gate cautious again.

The placement is proposed by `discuss-milestone-goal`, which gains one step: from the goal it names the directory that holds the core of the work, as deep in the tree as the core allows, with the root only when the core is the project itself. That one directory is the whole proposal. `define-milestone-goal` then takes it as given. The proposal is deliberately not cautious, because a milestone placed at the top for safety overlaps every other milestone in the project and so serializes them all. Two milestones whose cores are disjoint may both edit a directory that is the core of neither, and whatever collision follows is left to the agents, which are trusted to work out parallel edits where neither owns the ground; the sequential ordering exists only for the case where two cores collide.

### Resolving a milestone

The notion of an active milestone is dropped, as the idea proposes, and a skill is told which milestone it works on by pointing at the artifact, as the `--milestone` flag points at a milestone id today. `get-current-milestone.md` becomes the resolution of a path, and the path is required. `--milestone <path>` names the repo-relative path of the milestone directory exactly as the definition tool printed it, matched when `<path>/requirements.md` exists, with the same no-normalization rule as today. There is no default: a call that names no milestone, or names one that does not match, stops on one fixed line and lists every live milestone the milestones tool's `live` query finds, so a retry has the exact paths. Nothing stored and nothing computed picks a milestone, which is what makes two live milestones in one container, or in two packages, indistinguishable to the plugin except by the name the caller gives. What else the pointer did passes elsewhere, with nothing stored: it held "one milestone at a time" as a fact (design claim 9), which becomes the scope gate; it told a new session what is in progress, which is whichever milestone directories are present, the `live` query's print; and it stopped a user who forgot to finish, which becomes the gate refusing a second milestone's task entry in the same scope until the first is finished. Nothing the pointer recorded is unrecoverable from the tree and the log.

Every chain on the ways-of-using page then carries `--milestone <path>` on each per-milestone line, the path being what the definition line printed, and the `goto-next-milestone` line goes; the "prepare the next milestone while the current one runs" chain stops being a special case, since every chain is written that way. In interactive use the path is typed on every call, an accepted cost. An out-of-tree pointer (an environment variable, or an ignored file) would remove that typing and still conflict nowhere, but it stores a current milestone again, per shell rather than per branch, and there is to be none; it is a rejected variant.

### Defining

`define-milestone-goal --at <scope> <goal>` creates `<scope>/milestones/<slug>/` and commits it under `Milestone-definition: <path>`. `--at` is required and has no default, in the way the task-list tool's position flags are required: a definition that forgot its placement must fail rather than land at the root, where it would overlap every milestone in the project. Its value is the directory `discuss-milestone-goal` proposed, used verbatim. The tool takes the scope instead of assuming `milestones`, creates the container when missing, drops the numbering, and keeps everything else: the slug, the exclusive creation, the three files, the two output lines, the cleanup on failure. The path it prints is what every later line of the chain names.

### Finishing

`finish-milestone [--milestone <path>]`, renamed since nothing is current, keeps its two checks (no open question through the tool's `list`, no section in `TASKS_TODO.md`), composes the same summary, drawn from `requirements.md` and from the milestone's task commits through the milestones tool's `tasks` query since no `TASKS_DONE.md` exists, and records it as the body of its commit instead of in a shared file: it stages the removal of the milestone directory, edits the context file only for lasting changes as today, and commits under `Milestone-finish: <path>` with the summary as body. A milestone is finished exactly when its directory is gone, and its complete record stands at that commit's parent. Reverting the finish commit restores the directory and makes the milestone live again, the same correction path every other commit of the workflow has.

Removal at finish is what makes "finished" readable per milestone with no central index and gives a finished milestone's files a home, the commit's parent, which is also where capture already reads them from; and two milestones finishing on two branches no longer conflict, since a removal merges cleanly against an untouched tree. The variant weighed and set aside, a finish-written `## Outcome` section in `requirements.md` whose presence means finished, would have kept the files in the tree at the cost of a status to parse and a tree that grows by a milestone's files forever. That the record stays as easy to consult as the README was is the milestones tool's job (Reading the record, below): a record that moved into git and is read only by hand would trade a merge conflict for a worse loss, a record nobody consults.

The body is a contract, not free text, because the milestones tool prints it back: its first line is the milestone's title as the `requirements.md` heading carried it, then a blank line, then the summary bullets exactly as the README entry holds them today. Finish is the writer side of the record and the tool is the reader side, so the shape is stated once, in the finish skill, and the tool parses nothing else of it.

### Completed tasks live in commits

`TASKS_DONE.md` goes: a completed task's record is its `Task-completion: <Task Title>` commit, whose body carries the verified bar the completion procedure derives, the bullets `move` renders under `**Verified:**` today. The commit already holds the task's project changes and the removal of its section from `TASKS_TODO.md`, so one commit is the whole record of one task, with nothing in the artifact repeating it; the milestones tool's `tasks` query reads it back, bar included, for finish, for `ask-in-milestone-context`, and for `derive-tasks` when it checks what a live milestone has already completed.

The task-list tool's `move` becomes `remove <MILESTONE_DIR> <Task Title>`: it removes one section from `TASKS_TODO.md`, renders the file in its canonical layout as every write does, and renders no bar, since the bar is commit text now. The two-file atomicity `move` needed (write `TASKS_DONE.md` first, restore it when the second write fails) has nothing left to protect. The runner's chained call stays one shell call, the removal chained ahead of the git step behind `&&`.

The bar has to reach the commit, and so does the change set (Same-tree parallel runs, below). The inline `complete-task` skill holds both and writes the bar as the body of its own commit. The `complete-task` agent never commits, so under `complete-all-tasks` both travel as the alternatives agent's return does, as files and never as a message: the orchestrator creates one scratch directory per run with `mktemp -d` and passes it on every dispatch, the agent writes the commit message, subject line and bar, and the recorded paths as two files under `<scratch dir>/<Task Title>` and stages nothing, and the orchestrator's one commit call takes its message from the one file and its pathspec from the other, so neither passes through the orchestrator's context. Both runners' commits gain a body; the subject stays the task's heading copied exactly, so history is still searched by subject alone.

### Sequencing: the scope gate

The idea keeps execution sequential whenever an unfinished milestone stands in a directory above the one being worked. The shape keeps the sequencing and changes two things in the rule: overlap is read from scope in both directions, and only a started milestone holds its scope. Two milestones overlap when one's scope is the other's scope or an ancestor of it, in either direction: a root milestone overlaps every package milestone, two milestones in one container overlap each other, two packages' milestones do not. Scope is the core scope, the placement alone; a milestone's adjacent edits outside it never make two milestones overlap, so two packages' milestones that both touch a shared documentation directory run in parallel and sort that directory out between their agents. A milestone is **started** when it is live, its directory still present, and tasks were ever added to its list, which only `derive-tasks`' initialize and `submit-task`'s insert do; it stays started until finish removes the directory, so a milestone whose every task completed but which nobody finished still holds its scope, and the forgotten finish blocks the next milestone in that scope rather than letting it start beside a directory that still stands. A merely defined milestone, or one still deciding, holds nothing. Whether tasks were ever added is read from the log, never from the list's contents, because the list empties as tasks complete: one path-scoped command, `git log -1 --format=%h --diff-filter=M -- <MILESTONE_DIR>/TASKS_TODO.md`, prints a hash exactly when the file was written after the definition commit created it, which only a task entry does (the commit it finds is a `Task-derivation:` or `Task-submission:` one, or a later completion that presupposes one), and prints nothing otherwise. The gate is one check, the milestones tool's `gate` query, run by every writer that puts a task into the backlog, `derive-tasks` before it initializes the list and `submit-task` before it inserts, and by both completion runners before each task: if any other started milestone present in the tree overlaps this one's scope, the query prints the holders by path and the runner stops on one fixed line with those lines beneath it. The entry checks are where a second milestone is refused before it has a list to be refused on; the completion check catches an overlap no entry check saw, two started milestones brought together by a merge or a list written by hand after the other milestone's entry check ran, turning a silent collision into a stop. So the first milestone to take a task holds the scope until it is finished, a second one in the same or an enclosing or enclosed scope prepares freely (starting state, review, alternatives, recommendation, answers) and waits only at task entry, and no ordering between milestones has to be read from anywhere: no number, no definition time, no pointer.

Only started milestones block. The idea's rule as proposed, under which any unfinished milestone above blocks execution, would freeze every package milestone's execution on the definition of a root milestone, a root milestone defined only to be prepared while the packages run included, and would freeze a milestone mid-execution when one was defined above it. Gating on started milestones keeps the sequencing where overlap actually bites, at the writes, and leaves preparation unconstrained, as the current "prepare the next milestone" chain already is. Reading started from whether tasks were ever added, rather than from how they were added, closes the one edge a derivation-only test left open: a milestone that received its tasks through `submit-task` alone is started like any other. Reading it from the log rather than from the list's contents keeps a milestone started after its last completion, so an unfinished milestone is never mistaken for one that has not begun.

### Same-tree parallel runs

The parallelism the idea is after, a monorepo executing several milestones at once, is supported in one working tree as much as across worktrees. Several `complete-all-tasks` runs may execute in one working tree on one branch, one run per milestone, as freely as on separate worktrees: the plugin never requires a tree per milestone, and which milestones may execute together is the gate's question alone, evaluated in whichever tree the run is in against the milestones that tree holds. In one tree the gate sees every live milestone and refuses an overlapping scope the moment a task enters; on two branches each tree sees only its own milestones, which is right, since a milestone defined on another branch has not reached this tree, and an overlap between them surfaces at merge, where the completion check catches it. Both forms stay supported, nothing in a branch's tree being special, and the choice is the operator's. Two mechanisms carry the one-tree form, both in the commit step and neither in the work itself.

**A commit records exactly its own change set.** The completion procedure already records the paths a task creates or edits as each edit is made, never by diffing the tree, and the commit procedure already stages only the paths its caller names; what neither does today is bound the commit, which takes the whole index. The change set becomes the commit's explicit input end to end: the commit procedure's third step commits with the paths as its pathspec, `git commit -- <paths>`, which takes those paths' working-tree contents and leaves whatever else the index holds, another run's staged files included, exactly where it is, so the step's own promise, that nothing outside the paths is committed, holds by construction and not by the index happening to be clean. The step changes once, in the procedure, and every caller that writes the procedure's three steps into its own call gains the pathspec on its commit line: the sweep's batched call, both annotating passes' batch calls, the inline `complete-task` skill, `submit-task`, and `derive-tasks`; every caller that follows the procedure by reference changes nothing. It is plugin-wide and not confined to the completion runners because the leak is: in the draft's own chain, a second milestone preparing while the first executes, the answer sweep commits in the same tree as a completion agent, and a sweep that commits the whole index records that agent's staged task under a `Recommendation-answer:` subject, after which the orchestrator finds nothing staged and records nothing. Under `complete-all-tasks` the change set reaches the commit as the bar does, in the agent's return files, and the orchestrator's one commit call reads the paths from that file for its guard, its `git add`, and its commit (git's `add` and `commit` take a pathspec from a file; `status` and `diff` do not, so the guard's form is the milestone's to pick, a dry-run `add` from the same file, which prints exactly the paths that changed, being one), so the orchestrator holds no path and types none, a mistyped path being a change silently left out of a commit. The agent stages nothing: its staging contract existed only because the orchestrator had no path list, and the index stops being the channel between them. The orchestrator's whole-index guard goes with it. The pathspec is also what keeps the record the milestones tool reads exact under parallel runs: a `Task-completion:` commit touches one milestone's `TASKS_TODO.md` beside the project paths of one task, so the join of a task to its milestone, and of a path to the tasks that changed it, never sees another run's files.

**A git write waits for another run's lock.** Every write (`git add`, `git commit`, `git rm`) takes `.git/index.lock`, and `git commit` the ref lock besides; git gives up on the index lock at once when another process holds it (exit 128, `Unable to create '.git/index.lock': File exists`) and on a ref lock after a default tenth of a second, and no configuration makes it wait on the index. In one tree two runs' writes land within a second of each other often enough that an unguarded call turns that overlap into a `FAILED` return or a stopped run. The commit procedure's git steps therefore repeat a failed step a bounded number of times with a short pause before passing git's message on as the refusal it is, and each call that writes the steps into itself writes the retry too. The retry reads nothing of git's message, since a failed write lands nothing and repeating it is harmless, so the runner never classifies the failure. It is a retry on git's own lock and not a lock of the plugin's own, a `mkdir`-style mutex around the whole stage-and-commit, because a lock of our own adds state that a crashed run leaves behind with no message saying how to clear it, while git's lock already carries that message and the retry adds no state; and it is not a per-run private index (`GIT_INDEX_FILE` under the scratch directory), which would avoid the lock but leave the shared index stale for every path such a commit touched. The bound matters: a lock left by a crashed process must surface as git's message, never as a call that waits forever.

**What is left to the agents, as before.** The gate keeps cores apart; the adjacent footprint it never reads is where two runs can touch one file, a shared documentation directory or the context file finish edits. In two worktrees such a file conflicts at merge; in one tree it does not conflict at all, and the pathspec commit decides what the record says of it: the commit takes the file's working-tree content at commit time, so an edit the other run made in the meantime lands under whichever task commits first. The tree is the truth throughout, nothing is lost and nothing reverted, and the cost is attribution on that one file, which the two task bodies and the two diffs leave recoverable. The alternative, committing the content the agent staged rather than the working tree's, would attribute exactly and lose edits: a commit built on the later HEAD from an earlier staging would carry the file without the other run's edit, reverting it in history while the tree still held it. The completion procedure's resumption rule covers the other side of the same case, an agent that meets another run's uncommitted edit in a file it is about to change: uncommitted changes in the tree are now a previous run's partial work or another run's live work, and the rule for both is the one already written, continue from what bears on the task, touch nothing else, revert nothing. Two runs of one milestone are not supported and not detected up front: tasks in a milestone run in order by the procedure's own contract, and a second run on the same list takes the same top task, so the later of the two removals refuses, the section already gone, and that run stops on its `FAILED`; a run lock is not part of this shape.

**Cost.** One argument on each commit line, a retry around each git write, a second file in the completion agent's return, the agent's staging contract retired, and, if the orchestrator's call reads its pathspec through git's own flag rather than a pipe, a floor on git of 2.26 (2020), which the milestone places where the git probe lands.

### History

Milestone history moves entirely into git, as the idea proposes: a finished milestone's record is its finish commit, the summary as its body and the files at its parent, and `milestones/README.md` has no reader or writer left (the migration skill removes it, under Upgrade below). The two conversational readers of the README's history, `discuss-milestone-goal` and `ask-in-milestone-context`, read the finish commits instead, through the milestones tool, which prints the same bullets in the same order; `ask-in-milestone-context` answers about a finished milestone from those bodies, as it answers from the history section today. The landing page's self-dogfooding paragraph points at the log. Nothing else read the history, and what did not read it before now can: the starting-state skill and the review pass gain a history read, and the completion procedure gains one it takes at its own discretion (below).

### Reading the record: the milestones tool

Today the plugin is git-aware only at its edges: every skill commits, capture walks a path-scoped log, and `derive-tasks` reads blame; everything else reads files. Once finished work lives only in git, that stays true for live work and stops being enough for finished work. The stance the idea takes is: the files are the record of live work, git is the record of finished work, and one read-only tool is how a skill or an agent reads the second, in the workflow's vocabulary (milestone, task, decision) rather than git's (commit, path, hunk). Without the tool every runner that needs the record would compose its own `git log` pipeline, which is the pattern every tool in `core/tools/` exists to end: the fold tool replaced ad-hoc scripts in 42% of measured folds, the task-list tool in about three of four measured moves.

The tool, named `core/tools/milestones.py` here, is stdlib-only and Python 3.9+ like its siblings and the first tool that runs git, through `git` subprocesses that only read (`ls-files`, `log`, `show`): it writes nothing and commits nothing, so the writers' rule that a tool touches no git stays as it is, scoped to writers by the same reason it was made (the git step differs per runner and rides beside the call). It runs from the workspace root, prints plain text in one fixed shape per query, refuses with one `Error:` line on stderr and exit 1, and never lets a traceback through.

**What the log already gives it.** Every commit subject is a provenance marker, so the tool never guesses a commit's kind, and the tree-side facts it needs are structural. `Milestone-finish: <path>` with the body above marks a finished milestone, and the commit's parent holds its three files. `Task-completion: <Task Title>` touches its milestone's `TASKS_TODO.md`, the section it removed, beside the project paths it changed, so the milestone a task belongs to is the directory of that file in its file list, with no change to the subject, and its body is the verified bar. The three answer subjects mark the decisions, each body the lifted line and each `requirements.md` hunk the recorded text, which is what capture already reconstructs from. `Milestone-definition: <path>` adds the goal and the date a milestone began. A live milestone is a tracked `requirements.md` under a `milestones/` container, and a started one is a live one whose `TASKS_TODO.md` the log shows written after its creation, by a `Task-derivation:` or `Task-submission:` commit; `live` reads the tree alone and `gate` adds one path-scoped log per live milestone. The one join the subjects lack and the tool adds is the path: a task commit names the task, not the files, so "what changed this file" is a path-scoped log of task commits joined to the task file each one touched.

**Queries**, as a first cut; the review pass will reshape them:

- `live [PATH]` — every live milestone, filtered to those whose scope contains PATH or lies under it; one line each: path, whether it is started, title. The resolution procedure's stop, the gate, and the starting state's in-flight read read this instead of spelling the discovery pattern.
- `gate MILESTONE_PATH` — print nothing and exit 0 when no other started milestone overlaps its scope; otherwise print the holders, one path per line, and exit 1.
- `milestones PATH` — every milestone, finished or live, that changed PATH through a task commit or whose scope contains PATH; one line each: state, finish date, path, title; newest first.
- `summary MILESTONE_PATH` — the finish commit's body with its date, or, for a live milestone, its goal and the fact that it is live.
- `tasks PATH` — every task commit that changed PATH: date, milestone path, task title; newest first; with a flag, each commit's body beneath its line, the verified bar. PATH may be a milestone directory, which lists that milestone's completed tasks.
- `show MILESTONE_PATH FILE` — one of the three files as it stood at finish (the finish commit's parent) or as it stands now when live.
- `record PATH` — the composed answer to "what work was done here": for each milestone from `milestones PATH`, newest first, its title and date, its summary, and the tasks that changed PATH. `record .` is the whole project's history.
- `since MILESTONE_PATH [--milestones]` — the milestone's latest `Starting-state:` commit on the first line, then every later commit that touched its scope outside the milestone's own directory, the milestone's own task commits excluded by the join `tasks` uses, one line each: hash, date, subject, newest first; with `--milestones`, only other milestones' task and finish commits. No line means no starting state has been written; one line means nothing has changed since it was.

**Who calls it.**

- `discuss-milestone-goal` and `ask-in-milestone-context`, in place of the README read.
- The starting-state procedure, followed by `specify-milestone-starting-state` and, on a stale state, by the two task-entry writers, through three queries (The starting state, below): `since`, to tell a first run from a refresh and a refresh from nothing to refresh; the `milestones` overview on the scope, with `summary` and `show` for the milestones that bear, for "what was done here before and why", the summaries and recorded decisions of the milestones that touched the scope; and `live` on the scope, for what is in flight. The starting state is where a new milestone's decisions are grounded, so the past decisions that shaped the ground and the pending ones that are reshaping it belong there, and a review pass that reads them does not re-ask what an earlier milestone settled or a holder is settling.
- `review-milestone-requirements`, which is fed an overview and never the record itself: one fixed call at its inventory step, the `milestones` query on the milestone's scope bounded to the recent ones (the bound is the milestone's to set), printed by the tool from the log and read beside the two documents, so whether to look is never the pass's choice. What it does with the overview is its judgment. A listed milestone whose title and date say its work bears on a gap the pass is about to ask, or on a pair of decisions it is checking, gets a deeper read, its finish summary through `summary` or its recorded decisions through `show`, and one that does not is left at its line. The pass is never made to review every past decision: such a read grows with the project's history and repeats on every turn of a loop that runs until convergence, to catch the rare milestone whose settlement the starting state did not carry, while the overview costs one line per milestone and is enough to tell which milestone that is. It complements the starting state instead of repeating it: the starting state is written once, by a skill judging relevance at the milestone's start, and the overview is read on every pass, so a milestone finished since, on a branch merged in the meantime, or one the starting-state read did not weigh, still shows.
- The completion procedure, at the agent's discretion, through `record`: the one place the record can reach the code-changing work itself, and the one caller that reads it by choice rather than by a fixed step (The record in the completion procedure, below).
- The resolution procedure's stop, through `live`, and `derive-tasks`, `submit-task`, and both completion runners, through `gate`, the two task-entry writers also through `since --milestones`, ahead of the refresh they run themselves when it fires, so the discovery pattern, the scope rule, the started test, and the stale-state test live in one tested place rather than in prose each runner re-derives.
- `finish-milestone` writes what `summary` and `record` print back, so the body shape is the contract between them, and reads `tasks` on the milestone for the completed tasks its summary draws on; `derive-tasks` and `ask-in-milestone-context` read the same query where they read `TASKS_DONE.md` today.
- Capture keeps its own diff walk, which reconstructs removed block lines the tool has no reason to parse; a later milestone may move its existence test and its file reads onto `show`.

**Limits to state up front.** Presence wins over the log: a reverted finish leaves both commits in history, but the directory is present again, so the milestone is live. A milestone directory moved with `git mv` keeps its history only through the touched-path join, since subjects name paths as committed; moving a live milestone is not supported. A shallow clone's truncated log omits older commits without any sign, and no query checks for it: `tasks` prints whatever the path-scoped log yields, in a shallow clone and a complete one alike, with no stop line and no warning, the limit stated in its help text and the docs only, and whether the queries the third milestone adds detect the case is that milestone's to decide (Carrying it out), or no milestone's if no field run meets it. Milestones finished before the upgrade reach the record through the migration skill (Upgrade, below), which gives each one a finish commit in the new shape; their original finish subjects name an id rather than a path, which the tool does not match, and their tasks' bars are the one thing the migration leaves behind, in the removed `TASKS_DONE.md`.

### The starting state

The step stays, because what it does for a milestone depends neither on where the milestone lives nor on what else is being worked. Read from its readers rather than from its own description, the `## Relevant starting state` section does three jobs. It grounds every decider in one gathering of the facts: every review pass, one alternatives agent per question, the recommend pass, `discuss-open-question`, `derive-tasks`, and the completion procedure all read it, so one goal-filtered exploration serves them all and every pick and decision is formed against the same description. It is the as-of of the record: decisions are read back later, by capture, by `derive-tasks` when it orders a conflicting pair, by finish, and through `show`, and a decision such as "keep the parser as it stands" is unreadable without the parser it assumed, which this section is the only place the milestone's own record describes. And it is what the review pass surfaces gaps against. What it is not is the live truth at execution: the completion procedure reads the deliverables themselves and `derive-tasks` reads the files the section names. Dropping it would scatter one exploration across five sites and every run of each, and lose the as-of; and the benchmark draft already plans a chain without the step as one ablation, so what the step is worth is slated to be measured, not assumed away here.

**What moves under it.** Today nothing does: this repository's 41 milestones that have one have 41 `Starting-state:` commits and no re-run, and each was defined and finished within one day for most and four at the longest, so the one case the ways-of-using page names, the next milestone prepared while the current one runs, is handled by a sentence telling the operator to rerun the line and the review after it. The shape makes that case the ordinary one and adds three more. The ground has a scope, the core directory the placement names, so the exploration has a boundary where today it has only the goal as its filter, the root scope being today's case. Finished work lives in git, which is the history read above. The ground is scheduled to move while this milestone decides: an overlapping started milestone will finish before this one can take a task, since the gate fixes that order, and its converged decisions are the best available description of the state this milestone will execute against, so a section that described only the tree would describe a state already on its way out. And the ground has moved by the time tasks are derived, because the wait at the gate is exactly the period in which the holder rewrites the scope, so a waiting milestone's snapshot is stale at `derive-tasks` by construction. Adjacent files that a disjoint-scope milestone changes are not tracked, and stay with the completion procedure's live reads, as the adjacent footprint does everywhere in this shape.

**What the section reads.** The skill explores the scope first, then the adjacent material the goal reaches, as today; then the record, in the two tiers the review pass reads it in, the `milestones` overview on the scope and a deeper read through `summary` or `show` of the milestones whose title says they bear on the goal; then what is in flight: every live milestone overlapping the scope, from `live`, by path, whether it is started, and its goal in a sentence, and for each started one the decisions and remaining tasks that touch what this goal reaches, read from its `requirements.md` and `TASKS_TODO.md` as prose. The in-flight read is the sibling-scope rule at milestone grain: as an alternatives agent leaves to a sibling question what that sibling owns, a milestone deciding in a held scope leaves to the holder what the holder has decided, instead of re-deciding it against a tree the holder is about to change. A live milestone that is not started is listed by goal alone, since nothing of its decisions is settled and it holds no scope.

**A refresh is cheap and leaves a readable diff.** A re-run is an ordinary act, and there is one shape for a first run and a refresh, stated once as a shared procedure because three runners follow it, the skill and the two task-entry writers (Where the refresh runs, below), with the commit left to each runner as the committing rule has it. Its anchor is its latest `Starting-state:` commit, found in the log by subject and the milestone's `requirements.md` path and never stored as a line in the file; the procedure opens with the `since` query, which prints that anchor and every commit after it that touched the scope outside the milestone's own directory. One line, the anchor alone, means the ground has not moved: the run prints one fixed no-op line and explores nothing (a branch a task-entry writer never reaches, since its own narrower check has already fired), which also keeps the record quiet, since a model re-exploring an unchanged scope writes different prose for the same facts and that diff is noise to the next review pass. No line means no starting state yet, the first run. Otherwise the procedure explores and edits the section in place: it changes what no longer holds, adds what is new, and leaves byte-identical every subsection whose facts still hold, so the commit's diff is the change in the ground and nothing else; a first run edits the empty section into existence by the same rule, and the commit procedure's dirty-path guard still covers a scope that changed in nothing the goal reaches. The name, written for a first run, is the milestone's to keep or change.

**A refresh is a premise change.** A pick formed against the old ground would otherwise reach the answer sweep as given, which is the reason `modify-milestone-goal` clears picks, and a refresh is the third premise change beside a hand answer and a goal revision, so the procedure mirrors that one: in the same run it names, from a whole read of `open_questions.xml`, the standing picks the changed facts undermine by the same two tests, the option can no longer be carried out or the stated reason no longer holds, doubt stripping, clears them with one `strip --recommendation` call that keeps every `<alternative>`, and the runner commits both files under `Starting-state: <path>`. It rewrites no decision, as the goal revision rewrites none. On a first run and at a gate-open refresh after convergence the question document is empty, so the judgment is vacuous and the procedure carries no branch for it. Decisions are re-examined where decisions are always re-examined, by the review pass, which gains one bullet at its gap-surfacing step: a recorded decision that rests on a starting-state fact that no longer holds becomes an ordinary open question, not a conflict question, since there is no second entry to rewrite, and its answer supersedes or confirms the decision through the answer core's existing rewrite rule. With the overview read the pass already gains, that is the whole re-examination.

**Where the refresh runs.** Every execution chain on the ways-of-using page opens with the refresh line and one review pass, then the standard loop to convergence, then task derivation and completion: a milestone whose ground moved pays an exploration and a review, and one whose ground did not pays the `since` call and a converged pass. The sentence telling the operator to rerun the line after the in-progress milestone changes what it describes goes, replaced by that rule. A chain is a convention a hand-built chain can omit, a merge can land a holder's work after the refresh ran, and the wait at the gate ends with the holder's work in the scope, so the task-entry writers also check, and a stale state they find they refresh themselves rather than stop on: `derive-tasks` before it reads the documents it decomposes and `submit-task` before it authors run `since --milestones`, the same query narrowed to other milestones' task and finish commits, and a print beyond the anchor line makes the writer follow the starting-state procedure in place, commit the refreshed section under `Starting-state: <path>` as a commit of its own, and go on to its own write with the refreshed section in hand. The refresh is never a stop, because the shape exists for long uninterrupted execution and the worst interruption is one for work the skill could have done itself: the procedure gives the writer the whole shape to follow and the commit procedure gives it the commit, so what the stop would have asked the operator to run is exactly what the writer runs. The order inside the writer is the gate first, then the staleness check, since a refused gate is a wait in which the holder keeps rewriting the scope, and a refresh taken before it would be stale when the gate opens. The `Starting-state:` subject is part of the contract and not the writer's to vary, because `since` finds its anchor by that subject and a refresh committed under another would leave the anchor where it was. The refresh prints nothing of its own, its commit being its record, so each writer keeps its one status line; and an exploration that changed nothing in the section lands no commit and moves no anchor, so the next entry in the same stale window explores again, a repeat the milestone bounds. The pick judgment runs as the procedure states it: vacuous at `derive-tasks`, whose precondition is the empty question document, and live at `submit-task`, which has no such precondition and may meet standing picks. The narrowing to other milestones' commits stays although nothing stops on it, because what firing costs is now an exploration inside a writer, and a root-scoped milestone in a single-milestone project should not pay one on every hand commit; the skill's own check keeps the broad form, because an operator who re-runs it after a hand commit wants the refresh. In the documented chains the chain's refresh precedes the writers' check, so the inline refresh fires for the hand-built chain, the merge, and the milestone re-entered at task derivation after a gate wait, which picks up the holder's finished work there and re-runs nothing from the chain's top. The inline refresh records the ground and re-examines no decision against it: the writer derives against the refreshed section and the decisions as recorded, and the review pass stays the one place a decision is weighed against a fact. A re-examination inside the writer would bring back the stop the refresh removed, now behind an exploration, since the one outcome of the review pass that matters here is a new question, which `derive-tasks`' precondition then refuses; a writer letting the ground govern the brief where a decision cannot be carried out as written would judge a decision against a fact with nothing recording that it did, where the later-recorded rule reads an order and judges nothing. The exposure is bounded to the cases the inline refresh fires for, since the documented chains refresh and review before the decision loop, and it is small, because the in-flight read formed this milestone's decisions against the holder's recorded decisions and remaining tasks, so what the refresh at the gate's opening records is mostly that plan become fact; the completion procedure meets the live ground on every task through its deliverable reads and the record read.

### The record in the completion procedure

The completion procedure names the milestones tool's `record` query, with its full command, as the way to read why a file is the way it is, the decision that shaped it and the task that made it, before editing it, the way a careful engineer reads the log first, and writes no fixed call: whether a task reads the record is the agent's judgment, as the live-deliverable read is today. The required form, one `record` call on the paths the task is about to change at the step that derives the acceptance bar, was weighed and set aside, because it pays one call on every task when most tasks touch files with no past decision behind them, and because it has to run before the agent knows its paths: the bar is derived at step 2 of the procedure and the files are chosen at step 3. The query is named rather than left to the agent to choose among `record`, `tasks`, and `summary` per run; its bound is the milestone's to set, since `record` on a file touched by many milestones prints every one of them with every task and grows with the project's history.

**The trigger is testable without the record.** A file carries a past decision or it does not, and nothing in the file says which, so an agent judging whether to look has no signal until it has looked, and a read left to suspicion fires only when the agent already suspects a backstory, the case that needed it least. The procedure therefore names the trigger, and the one the draft sees is a file the task edits rather than creates whose shape the current milestone's `requirements.md` does not explain.

**The bar never re-derives on the record.** The read sits where the deliverable read sits: at step 2, beside it, for the files the task can already name, where a past decision it surfaces fixes a criterion as a prior task's real names and values do, and at step 3, where the agent knows its paths, informing the edits only. A decision surfaced at step 3 that would have bound the bar shapes how the work is done and leaves what counts as done as it was derived, held verbatim to the commit, with no exception to the no-drift rule. The exception weighed and set aside, re-deriving the bar before any edit when the record binds, would let the bar carry the decision in every case, at the cost of a bar that can change after it was derived, which is the drift the rule exists to forbid, and of a second derivation path the runner has to know when to take; the step-2 read gives the bar the decision wherever the task names its files up front, which the edited-not-created trigger mostly does.

**The full command is shown even though the call is optional.** Every tool under `core/tools/` exists because a step left to the runner was done ad hoc: three in four measured completion agents wrote their own move script, and 42% of measured folds were `str.replace` scripts. A discretionary read fails the same two ways, both silent: the agent never calls it, or it composes its own `git log -p` in place of the tool's command, the pattern the tool exists to end. The procedure shows the full fixed command under the same literal-command rule the other call sites carry, since an optional step is the one most likely to be written vaguely.

**The read leaves a trace only where it bore on the bar.** Nothing in a task's commit says whether the record was consulted, so a later reader cannot tell a deliberate override of a past decision from an oversight. Under the required form the read was at least certain; under this one the verified bar in the commit body is the only place it can show, as a criterion naming the past decision the bar was formed against, and only when the read bore on the bar, which under the rule above is a step-2 read on a file the task named up front.

**The protection stays where it is today.** The risk the read guards against, an agent fixing back what an earlier milestone chose on purpose, keeps relying on finish writing lasting changes into the context file and on the starting state carrying the past decisions that bear, both judgment steps upstream of the task. The discretionary read therefore puts weight on the starting-state skill's new history read being taken well, and on the refresh that precedes task derivation (The starting state, above), since that is the one place a past decision is read for the milestone's tasks with any certainty, and the refresh is what makes the state it reads the one the tasks will meet.

**Nothing in the suite can check it.** A fixed call could be pinned the way the sweep's two calls are, by a test that extracts the call from the rendered tree and runs it; a discretionary mention is prose, which no test follows. Only field measurement tells whether agents take the read or hand-roll it, so the milestone plans that measurement as earlier decisions were measured (The field measurement, below), and the read becomes a required step if measured runs show the call never made or made by hand.

### The principle store

`milestones/answer_decision_principles.md` stays at its fixed root path, read by the recommendation core and written by capture as today; the root container exists for it even in a project whose milestones all live in packages. A project-wide store is the right grain, since principles are about how the project decides, not about one scope. ### Upgrade

This is the first change since the open-question split that reaches existing projects, and unlike that split it cannot be ignored: every project with a `milestones/README.md` pointer and finished directories has to move its record into the shape the milestones tool reads. The split needed no migration because the pre-split milestones stayed readable in place, their files in the tree and no skill reading them. Here the record of finished work moves into git, and a milestone the README finished has a `Milestone-finish:` subject naming its id with no body, so without a migration the tool's `summary` and `record` would print nothing for every milestone finished before the upgrade, which is the record nobody consults. The upgrade is therefore a migration skill, named `migrate-milestones` here, invoked by a person once per project and never by a chain: it appears in no chain on the ways-of-using page and nothing dispatches it. It is upgrade scaffolding beside the record, in the way the literal answer skill's redirect guard is, not a mode of finish.

What it does is finish each historical milestone again, in the new form, one by one. It reads the README's `## Milestone History` entries, the same done set `goto-next-milestone` read (the `## Completed Milestones` table is not consulted, as it never was), and walks them oldest first, so the finish commits land in the order the milestones finished. For each entry it finds the directory by number and makes exactly the commit the new finish would make, without finish's two checks, since the history entry is the done fact: the directory removed with `git rm -r`, the subject `Milestone-finish: <path>`, the body the entry's title line, a blank line, and its bullets verbatim, with the author date copied from the original finish commit the log holds for that id, so the record's dates stay the finish dates rather than the migration's. One commit per milestone keeps the revert path: reverting one migration commit restores one milestone, as reverting a native finish does. A migrated milestone is then readable as a native one: `summary` and `record` print its entry, `show` reaches its files at the commit's parent, and `milestones` lists it with its date. What the migration cannot supply is the tasks' verified bars, which stay in the removed `TASKS_DONE.md` while their `Task-completion:` commits carry no body, so `tasks` lists a pre-upgrade task with an empty bar; that is the partial compatibility the migration settles for, since carrying the bars into history would mean rewriting commits.

Once the last entry is finished the skill removes what of the legacy layout remains, in one closing commit: `milestones/README.md`, its pointer and history now redundant with the commits, and the `TASKS_DONE.md` of a live milestone, if one is present, whose entries stay readable in history and whose tasks record their bars in their commits from then on. The live milestone itself stays in place, under its old numbered name, which is a valid name the pattern finds; a directory with no history entry is live by the old test and by the new one. The container directory is not removed as such: it is the root container the proposed shape keeps, where the principle store and any root-scoped milestone live, so it stands exactly when something new is in it and is gone otherwise, as git tracks no empty directory. A project without a README has nothing to migrate, and the skill says so on one fixed line. This repository's migration makes 51 finish commits and one closing commit; the `milestone_43` reference in `CLAUDE.md` then names history, which `git show` and the tool's `show` reach.

## Carrying it out

The draft is more than one milestone. Its Surface touched list runs to some forty tasks at the altitude `derive-tasks` writes them, against the 3 to 16 tasks of this repository's last eight milestones, each defined and finished within one to four days, so it is three or four milestones' worth of work before the breaking release it carries is weighed. Three things fix where the cuts fall, checked against the runtime files and the log on 2026-10-29; all five milestones have since landed, as this repository's milestones 52, 53, and 54 and as `milestones/starting-state-refresh/` and `milestones/completion-procedure-reads-past-work/`, and the plan below is revised against their record on 2026-10-30, after the third and this repository's own migration on 2026-11-09, and after the fourth and again after the fifth on 2026-11-10.

**What presupposes what.** The tree-side reads, `live` and `gate`, read "finished" as "directory gone": live is a tracked `requirements.md` under a container, and started is a `TASKS_TODO.md` the log shows written. On today's tree both tests are true of every finished milestone: the started test, `git log -1 --format=%h --diff-filter=M -- <dir>/TASKS_TODO.md`, prints a hash for milestone 51, and the live pattern matches all 51 directories. So neither query, nor the gate built on them, can land before finish removes directories and the migration has removed the finished ones; the gate rides with the pointer's removal or follows it, never precedes it. The history-side reads split the other way: `tasks` reads `Task-completion:` commits joined to the `TASKS_TODO.md` each one touched, which today's `move` touches too, so it works on the log as it stands, while `summary`, `milestones`, and `record` read finish bodies that exist only once finish writes them and the migration has written the old ones.

**Each milestone is a release the plugin can run.** The plugin runs its own pipeline on this repository and is released from it between milestones, so each milestone must leave every host tree able to finish the milestone that made it and to run a user's project with none of the later ones installed. The pointer has six readers and writers and goes when its last one goes, so the resolution, `goto-next-milestone`, finish, the bootstrap, and the two conversational readers change in one release, the migration beside them, because the record's readers switch from the README to the log in the release in which finish stops writing the README. That release is the one breaking release, with the upgrade step in its notes; everything that can land before it as an additive change should, so it stays as small as the pointer's removal allows, and everything that is worth nothing until the new shape stands lands after it.

**A query lands with its first caller.** The tools under `core/tools/` grew subcommand by subcommand, each with the runner that calls it (`fold` with the sweep in milestone 48, `replace` with the conflict section in 49), never as a tool with no reader; the draft's query set is a first cut for the review pass to reshape, and a line shape is tested only by a reader. So no milestone is "the milestones tool": the tool is born with its first query and grows by one milestone's callers at a time.

Five milestones follow, in an order the dependencies fix; all five are done, and their sections record what landed rather than what was planned. The numbers are the plan's own, not milestone numbers, which the third milestone retired.

### 1. Same-tree commits (done)

Landed as milestone 52, in twelve tasks against the seven planned, and larger than planned in two ways.

The commit mechanics became a tool rather than steps. `core/tools/commit.py`, stdlib-only and self-contained like the document writers, takes the paths as arguments or line-exact from a `--path-file`, the subject, and an optional body, and runs the dirty-own-path guard, the path-scoped `git add`, and `git commit` with the paths as its pathspec, repeating a git write only on exit 128, sixteen attempts a quarter of a second apart, so a held lock is absorbed within about four seconds and every other failure passes on at once with git's message in the tool's one `Error:` line; it prints nothing when a commit lands and exits 0 with one fixed line when none of the paths changed. `commit-procedure.md` reduced to that one command, the eleven skills following it by reference run it as their one git call, and the six fixed calls that inlined the three steps (the sweep's batched call, both annotating passes' batch calls, the inline `complete-task` skill, `submit-task`, `derive-tasks`) run it and echo their markers only when its captured print is empty. No call carries a retry of its own, which Same-tree parallel runs and Surface touched above still describe: the retry has one home, tested against a held lock in `tests/test_commit_retry.py` and, through the inline skill's fixed call, in `tests/test_completion_call_lock_retry.py`. **What each counted run is given.** One outcome, from an ordered list, the first matching class winning:

1. the `tasks <path> --with-body` command as shown: the full fixed command, written out literally, on an edited file's path, the host's own plugin-root reference standing as the procedure shows it or resolved to its absolute path;
2. the milestones tool in another form: `tasks` without `--with-body`, `record` or another query on the file, a relative or variable-held tool path, or an alias or function standing for the command;
3. a hand-composed `git log`, `git blame`, `git show`, or `git diff` naming the file, a `git show` of a tool-printed hash being the tool read's follow-up and not this class;
4. no history read.

A failed call counts under the form it was written in. The `show <milestone path>` follow-up is recorded beside the outcome as a yes or no, not as an outcome of its own.

**The result that makes the read required.** The rule is fixed in advance and pools both failure kinds, the call never made and the call made by hand: the read becomes a required step when the counted runs that took no history read or composed their own, the fourth class and the third together, reach one counted run in four. The share is stated, below half, and set low enough to fall under the earlier measured failure rates, those that justified the task-list and fold tools (about three in four measured completion agents wrote their own move script, 42% of measured folds were `str.replace` scripts), so the bar for making the read required is lower than the one those tools cleared. The second class is not pooled, being the tool's read taken in another spelling; the report gives its count beside the others.

**Where the evidence lives.** The measurement's scripts and its report are committed in this repository under `ideas/`, beside this draft, in one subdirectory named for the measurement, so the plan and its evidence stand together and the figures can be checked again. The raw transcripts are not committed, and what the report takes from other projects is kept to counts. Nothing of the measurement is kept under the git-ignored `temp/`, where the reports and scripts of the two earlier measurements stood and from which both are gone, their figures surviving only in their milestones' `requirements.md` and in `CLAUDE.md`.
