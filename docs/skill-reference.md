# Skill reference

What each of Cairn's skills and dispatched agents does. The phases they form, how they commit, and the [answer-principle-learning loop](workflow.md#the-answer-principle-learning-loop) are described in [workflow.md](workflow.md), and how to chain them as headless command lines is in [ways-of-using-cairn.md](ways-of-using-cairn.md).

### `init-milestone-base-workflow`

One-time bootstrap for a project. It checks the workflow's two runtime prerequisites on every invocation, each stopping on its own before anything is written with a message saying what it looked for, what it found, the remedy, and that a re-run completes the bootstrap. Git comes first: one `git rev-parse --is-inside-work-tree` probe of the workspace root, which passes anywhere inside a work tree (a subdirectory of a larger repository, or a fresh repository with no commits yet) and otherwise names the remedy (install git, or run `git init` in the workspace root) — the skill never prompts and never runs `git init` itself. Then Python: a 3.9 or later interpreter answering as `python3`, which the skills drive the plugin's stdlib-only Python tools with, probed by `python3 --version` and, only when that fails, `python --version` to make its message precise (remedy: expose the interpreter as `python3`, or install Python 3.9+). It then creates the `milestones/` directory and `milestones/README.md` with the current-milestone pointer (its template lists the four milestone files, `open_questions.xml` among them), and ensures `CLAUDE.md` carries the `## Milestone Workflow` guidance. Additive and idempotent — creates missing scaffolding and inserts missing sections into existing files, never overwrites existing content. It commits subject-only under `Workflow-bootstrap: milestones`: `milestones/README.md` always, plus `CLAUDE.md` only on runs where it created the file or appended the section, handed over unchanged so uncommitted changes already in those paths (such as a `CLAUDE.md` just written by `/init`) ride in the same commit. On success it prints the one line `Workflow bootstrapped.`, and on an already-initialized project the one no-op line `Workflow already bootstrapped — nothing changed.`, with no itemization and no next-step pointer — the commit diff shows what was created or appended. Run this before any other workflow skill.

### `discuss-milestone-goal <overall_goal_description>`

Facilitates a structured conversation to sharpen a vague goal into a clear, actionable statement. Produces a refined goal description ready for `/define-milestone-goal`. Creates no files.

### `define-milestone-goal <overall_goal_description>`

Creates a new milestone mechanically: the skill only chooses the milestone's title from the goal description and hands it, with the goal text on standard input, to the plugin's stdlib-only `tools/define_milestone.py`. The tool numbers the milestone max-plus-one over the existing `milestone_<N>_<slug>` directories, derives the slug from the title's first five words, refuses an existing target, and creates `milestones/milestone_<N>_<slug>/` with its four files from its own templates: an empty `open_questions.xml`, which the open-question tool then writes from that point on, `requirements.md` (the title heading and the Goal section filled, the other sections empty), plus empty `TASKS_TODO.md` and `TASKS_DONE.md`. It prints the commit subject `Milestone-definition: milestone_<N>_<slug>` and the directory path, which the skill passes unchanged to the commit procedure; on failure it prints one `Error:` line and leaves nothing behind. Does **not** activate the milestone.

### `specify-milestone-starting-state <milestone_id>`

Reads the milestone goal, explores the project's existing state using the environment documented in `CLAUDE.md`, and writes a concise summary into the `## Relevant starting state` section of `requirements.md`. Sets up the context needed to make informed decisions.

### `review-milestone-requirements`

The repeatable engine of the requirements-iteration loop. Each pass reads the current milestone's `requirements.md` and `open_questions.xml` whole to reason over them, then does three jobs: **reconciles** the existing question set against what's already decided (prunes a block a recorded decision now covers, dedups repeats — each removal one bare `remove` call to the open-question tool, which in the same write strips every surviving question whose `<depends-on>` assumed the removed block of its pick — its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children, the `<alternative>` children kept — transitively, leaving those questions for the next `/recommend-all-open-questions` pass to re-pick), **surfaces** genuinely new gaps the latest decisions exposed, authoring each finding as an ordinary `<open-question>` block through the tool's `add` — the pass writes only the two judgments a block carries, its self-standing question text and its unique Short Title, and the tool owns the block's shape; each question asks **one choice**, so a gap holding two choices becomes two questions, except that choices constraining each other so that not every pairing is viable are authored as a single multi-axis question asking both at once (no test for spotting a second axis is prescribed — that stays the author's judgment), which keeps the alternatives pass from multiplying one set across independent choices — and **reports convergence** from the tool's `list`: whether any `<open-question>` block remains (which `/derive-tasks` forbids) or the requirements are ready to derive tasks. It commits the two documents path-scoped under `Requirements-review: <milestone_id>`, committing nothing when a pass reshaped nothing. Run it after `/specify-milestone-starting-state` to open the questions, then re-run after every answer or two — earlier answers keep opening new ones. It never answers questions or records decisions itself, and it never edits `open_questions.xml` by hand; it shapes and reports the open-questions state for the answering skills to resolve.

### `discuss-open-question <question_name>`

Opens a structured conversation about a named open question in the current milestone's `open_questions.xml` — locating the block through the open-question tool's `locate`, then reading `requirements.md` and the question document whole for context. It works on a block in **any state**, and the state fixes only where the option set comes from: a block carrying the `<alternative>` elements the alternatives pass embedded has that **frozen set reused** as its options, exactly as embedded and never re-enumerated (a genuinely realistic option the set lacks may be put on the table only marked plainly as a departure from the frozen set, since recording it would be a literal answer matching no `<alternative id>`), while a bare block gets its honest alternatives enumerated inline first, through the shared enumeration core `core/shared/alternatives-procedure.md` — the same core the `provide-alternatives-to-open-question` subagent follows, so the set is built the same way: the axes the underlying decision turns on are named first, each option is one position on them, and the set must be **distinct** (every two options differ in substance on an axis) and **covering** (it covers the underlying decision rather than the question's wording, not doing the thing included where honestly viable), with no count guideline. Over that set it then follows the shared pick core `core/shared/recommend-procedure.md` (the same core `/recommend-all-open-questions` follows) and states **one recommendation of its own**, formed afresh from the set and its grounding; when the block also carries the `<recommendation>` the recommendation pass embedded, it shows that standing pick beside its own — option, rationale, the principles it cited, and the sibling options it assumed — and says plainly whether the two agree and why. When its pick leans on a still-unanswered sibling settling on one of its options it says so in prose, naming that sibling and the option assumed — the conversational rendering of the disclosure duty the recommendation pass renders as a `<depends-on>` element. On top it adds the layer that is its own: a "what would change your mind" section and the continue-the-conversation loop. On a decision it offers `/answer-open-question` (naming the matching `<alternative>` id when the answer is one of the frozen options) and, when the deliberation concludes the goal itself must shift, `/modify-milestone-goal` — run first, so the answer records against the revised goal. Purely conversational — it edits nothing.

### `answer-open-question <question_name>`

Records the resolution of a named open question: the decision is folded into `## Decisions` of `requirements.md` first, then the answered block is removed from `open_questions.xml` by the open-question tool's `remove`, and the two edits are **committed**. It follows the shared hand-answer procedure `core/shared/hand-answer-procedure.md`, which composes over the recording core `core/shared/answer-procedure.md`: before recording, the skill reads `open_questions.xml` whole, for reasoning only, and names the **undermined picks** — every other question's standing `<recommendation>` that the answer undermines, because the recommended alternative, as its what-it-is text reads, can no longer be carried out alongside the decision, or because the pick's one-line rationale states or plainly presupposes something the answer changed (a fact about the project, a constraint, a sibling's expected outcome). It judges only those two texts against the answer and what it directly entails, never re-forming the recommender's judgment, and it runs that judgment on **every** hand answer, whether or not the answer matches the answered block's own pick; a pick the answer does not bear on is left standing. Its cascade removes the siblings the decision moots (one bare `remove` each) and reconciles the **dependents** through the same `remove`, in **one write**: the siblings whose `<depends-on>` tag assumed this question's option, and the undermined picks it named, passed as `--undermined` whether or not any tag declares them. For the tagged ones, since a literal answer lifts no option id, the skill forms one further judgment, whether the answer plainly settles on one of the answered block's own `<alternative>` ids, and passes that id as `--option` (the tagged dependents that assumed it keep their pick, every other one is stripped of its pick) or passes nothing when the answer settles on none of them, or only arguably on one, so every tagged dependent is stripped. Every named block is stripped too — its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children deleted, the `<alternative>` children kept — and every strip is transitive over the blocks whose tags name the stripped one, for the next recommendation pass to re-pick; a named block that carries no pick is left as it stands. **Strip on doubt** covers both judgments: a pick only arguably untouched by the answer is named, because a stripped block costs one re-pick while a stale pick left standing would be recorded as a decision by the answer sweep. A named title matching no block, or the answered block's own, stops the `remove` on the tool's `Error:` line with the document unchanged, and the skill corrects the list and runs the call again. Nothing is printed about any pick the write cleared; the commit's diff is the record. The commit stages only its own two edits (`<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md`, never `git add -A`) under the subject `Manual-answer: <Short Title>`, with the decision's rationale in the commit body. A Short Title that matches no block stops the skill on the tool's `Error:` line, which lists the ids the document holds. It no longer chains to any capture skill — the reusable principle behind the answer is distilled later by `/capture-milestone-principle-updates <milestone_id>`, whenever you run it for the milestone. Its `Manual-answer:` subject is a provenance marker that capture reads alongside `Alternative-answer:` and `Recommendation-answer:`: a manual answer is an **override signal** — a decision the recommender did not make — whose body rationale capture distills, asking you for the reason only when the body records none (see [How skills commit](workflow.md#how-skills-commit)).

The answer text is recorded **literally** — recording a question's embedded recommendation now lives in the dedicated `/answer-open-question-with-recommendation` skill. As migration scaffolding, this skill keeps one small **redirect guard**: if the answer text is exactly the retired sentinel `record the recommendation` (whole-string, after trim + lowercase, never a substring), it stops without recording and points you at `/answer-open-question-with-recommendation` instead of committing the sentinel phrase as a decision.

### `answer-open-question-with-recommendation <question_name>`

Records a named open question's **embedded recommendation** as its answer, then **commits** — the dedicated home for the recording logic extracted out of `/answer-open-question`. It lifts the `<recommendation option="...">` element that `/recommend-all-open-questions` embedded in the question's `<open-question>` block with the open-question tool's `lift`, which prints the `<option> — <rationale>` answer form as plain text — folds it into `## Decisions` of `requirements.md`, then has the tool's `remove --option <lifted option>` delete the block and reconcile the **dependents** — siblings whose `<depends-on>` tag assumed this question's option — by an **exact id comparison** against the lifted `option`: a matching tag is simply removed, a differing one strips that dependent of its pick (its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children, the `<alternative>` children kept), transitively, for the next recommendation pass to re-pick; siblings the decision moots are removed the same way. The commit stages only its own two edits (`<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md`, never `git add -A`) under the distinct subject `Recommendation-answer: <Short Title>`, with the lifted line as its body — the provenance marker by which `/capture-milestone-principle-updates` reads it as an **accepted recommendation**: evidence about principles already in the store (a cited principle is reinforced, a contradicted one flagged for salvage), never a source of new principles, since its body is the recommendation pass's rationale rather than yours. If the targeted `<open-question>` block carries no `<recommendation>` element (the recommendation pass never ran, or the question was added afterward), the `lift` fails on one `Error:` line and the skill stops without changing anything and commits nothing. Runs **inline** in the conversation so the context survives for follow-up.

### `answer-open-question-with-alternative <question_name>. <alternative id>`

Records a **named `<alternative>`** from an open question's embedded analysis as its answer, then **commits** — the sibling of `/answer-open-question-with-recommendation`, differing only in *which* embedded element becomes the answer. Where the recommendation skill lifts the one `<recommendation>` element the recommendation pass picked, this skill lifts the `<alternative id="...">` **you** name — which lets you record a decision that *overrides* the recommendation, or resolve a question the recommendation pass left genuinely tied. Split the argument on the **first `.`**: the Short Title before it, the target alternative's `id` after it (both case-insensitive, both trimmed). The open-question tool's `lift --alternative <id>` prints the chosen alternative's `id` and its what-it-is text as the `<id> — <what-it-is>` answer form in plain text (the `<advantage>`/`<drawback>` children are trade-off analysis, not the decision, and are left out); the skill then follows the same shared hand-answer procedure as `/answer-open-question`, `core/shared/hand-answer-procedure.md`, with the chosen `id` as the recorded option. Before recording, it reads `open_questions.xml` whole, for reasoning only, and names the **undermined picks** — every other question's standing `<recommendation>` whose recommended alternative, as its what-it-is text reads, can no longer be carried out alongside the chosen alternative, or whose one-line rationale states or plainly presupposes something the choice changed — judging only those two texts, never re-forming the recommender's judgment, on **every** answer (choosing the alternative the block's own pick names is no exemption), and leaving standing the picks the choice does not bear on. It folds the answer into `## Decisions` of `requirements.md`, then has the tool's `remove --option <chosen id>` delete the block and reconcile, in **one write**, the **dependents** — siblings whose `<depends-on>` tag assumed this question's option — by an **exact id comparison** against the chosen `id` (a matching tag is simply removed, a differing one, the usual case when you override the recommendation, strips that dependent of its pick) together with the undermined picks it named, passed as `--undermined` and stripped whatever their tags say. A stripped block loses its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children and keeps its `<alternative>` children, transitively over the blocks whose tags name it, for the next recommendation pass to re-pick; a named block that carries no pick is left as it stands; siblings the decision moots are removed the same way. **Strip on doubt** covers the naming: a pick only arguably untouched is named, because a stripped block costs one re-pick while a stale pick left standing would be recorded by the answer sweep. Nothing is printed about any pick the write cleared; the commit's diff is the record. The commit stages only its own two edits (`<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md`, never `git add -A`) under the distinct subject `Alternative-answer: <Short Title>`, with the lifted line as its body — the provenance marker by which `/capture-milestone-principle-updates` reads it, like `Manual-answer:`, as an **override signal**: because the body carries only the alternative's text and no rationale of yours, capture asks you at harvest time why you preferred it (offering its own best guess) and distills the guideline the recommender lacked from that answer. If no question matches the Short Title, the block carries no `<alternative>` elements (the alternatives pass never ran), or no alternative matches the given id, the `lift` fails on one `Error:` line that lists the available ids, and the skill stops without changing anything and commits nothing. Runs **inline** in the conversation so the context survives for follow-up. There is deliberately **no** batch form: which alternative wins is per-question human judgment, not a rule a sweep could apply.

### `answer-all-open-questions-with-recommendation`

The **recommendation-answer sweep** — the batch form of `/answer-open-question-with-recommendation`, the recording counterpart to `/recommend-all-open-questions`, and an **inline skill that dispatches no agent**: it is the single writer of its run, recording every answer itself, in the conversation, one question at a time. It resolves the current milestone **once** and uses that one directory for every tool call, recording, and commit of the run. One call to the open-question tool's `walk` is its whole gather and ordering: it prints the Short Title of every `<open-question>` block carrying a `<recommendation>` element, each placed after every printed block its `<depends-on question="…">` tags name — the dependency graph walked from its origins, never a judgment of significance: an edge whose target is absent or carries no `<recommendation>` is dropped, questions with no resolvable edge are the **origins**, each further depth follows once all its targets are placed, same-depth questions keep document order, and a stranded set (a `<depends-on>` cycle, reachable only through the recommendation pass's `strip --recommendation` escape hatch) promotes its document-order-first member to an origin and walks on — deterministic and total for any graph shape. It then reads `requirements.md` and `open_questions.xml` **whole, once**, for reasoning only — the view of every sibling and recorded decision each recording reasons over — a snapshot that never gathers, orders, re-checks, or confirms a skip, and that yields to the tool's `locate` print and the live `requirements.md` once a cascade lands. It walks the printed order **exactly once**, **strictly sequentially**, and for each question follows the shared lift-and-record procedure itself, from its lift step: the tool's `lift` is the only lift the question gets — a failing `lift` (one `Error:` line, because a prior answer's cascade removed the block as moot or stripped it of its pick, leaving it for the recommendation pass to re-pick) is the re-check and the **silent skip** in one, and a succeeding one prints the `<option> — <rationale>` line held as the commit body, since the block is gone once recorded — then folds the decision into `## Decisions`, removes the block with the lifted option passed verbatim, and runs the cascade, exactly as the single-question skill does. It records **every pick as given** and never judges one; a pick that runs against an entry in the live `## Decisions` at fold time is recorded anyway and the pair is held. Each answer is **committed before the next question** — path-scoped to `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md` (never `git add -A`) under `Recommendation-answer: <Short Title>` with the lifted line as its body, **one commit per answer**, which is what lets a single answer be reverted and re-answered on its own. A tool failure after a question's decision has been folded **stops the whole run** at once, naming that Short Title with the tool's `Error:` line quoted verbatim and leaving the uncommitted edits as a resumable tree, with no rollback. There is no outer re-gather loop, because recording only removes blocks or strips their picks; instead one end-of-run `walk` is a **completeness check**, expected to print nothing, any id it prints being an anomaly — a recommendation-bearing block the run left unrecorded. It needs **no** clean-working-tree precondition — every commit is path-scoped. Its report is one fixed line, `Recommendations recorded.`, or the distinct no-op line with its reason, beside only two advisories, each when it fired: the contradiction pairs it noticed (the answered Short Title and the `## Decisions` heading it conflicts with) and the completeness anomaly. It names no skipped question and gives no new-question advisory, leaving new questions to the next `/review-milestone-requirements` pass. Run it after `/recommend-all-open-questions` to record every annotated recommendation at once.

### `modify-milestone-goal <new or revised goal text>`

Revises the `## Goal` of the **already-defined** current milestone — the one skill that mutates the goal of a live milestone (`define-milestone-goal` only seeds it at creation). In the same run as the Goal edit it **clears the standing picks the revision undermines**: from its whole read of `open_questions.xml`, for reasoning only, it names every block whose standing `<recommendation>` the revised goal undermines — the recommended alternative, as its what-it-is text reads, can no longer be carried out alongside the revised goal, or the pick's one-line rationale states or plainly presupposes something the revision changed, such as the scope or aim of the milestone — judging only those two texts, never re-forming the recommender's judgment, with doubt stripping and the picks the revision does not bear on left standing. It clears them all with **one** `strip --recommendation` call over their Short Titles, which deletes each named block's `<recommendation>`, `<depends-on>`, and `<applied-principle>` children and keeps every `<alternative>`, so the next recommendation pass re-picks under the revised goal and the answer sweep cannot record a pick formed under the old one. The clearing is **not transitive**: a block whose `<depends-on>` names a cleared block keeps its pick and its tag. Clearing those picks is the only change it makes to `open_questions.xml`, and it otherwise **never cascades** the downstream impact (which decisions, open questions, out-of-scope entries, and already-derived tasks the new goal may invalidate) — no block is removed, added, or reworded, and no other section of `requirements.md` is touched; reconciling that impact is left to you, via `/review-milestone-requirements` afterward. Offered by `/discuss-open-question` when a deliberation concludes the goal must shift, and directly invocable. It commits its Goal edit and the picks it cleared together, path-scoped to `<MILESTONE_DIR>/requirements.md` and `<MILESTONE_DIR>/open_questions.xml`, under a `Goal-revision: <milestone_id>` subject, and prints nothing about the cleared picks.

### `capture-milestone-principle-updates <milestone_id>`

The **on-demand** principle harvester — the **sole writer** of the project-wide principle store `milestones/answer_decision_principles.md`. It takes a **required** `<milestone_id>` (the milestone directory name under `milestones/`, e.g. `milestone_12_user-guide`, exactly as `/specify-milestone-starting-state` takes it) and runs against any milestone whose `milestones/<milestone_id>/requirements.md` exists — the current milestone, an unfinished one, or one long finished (backfill included); it never consults the current-milestone pointer or the milestone's finish status. Running it right after `/finish-current-milestone` is the natural moment, since the milestone's answer set is complete by then, but finish is never a precondition. Two start-of-run guards are each a one-line notice plus a single confirmation, never a stop: a milestone that already has a `Principle-capture:` commit, and a store carrying uncommitted edits (which then become the baseline the rewrite builds on). It walks the milestone's answer commits across **all three provenances** with a path-scoped `git log -- milestones/<milestone_id>/open_questions.xml` (every answer removes its block from that file, and the path is itself the lower boundary) and reads each commit with one `git show` naming both `open_questions.xml` and `requirements.md`: from the `open_questions.xml` hunk's removed lines — only those within the answered block's own `-<open-question id="…">` … `-</open-question>` boundaries, never a sibling block the cascade mooted or a stray line it cleared from a sibling that still stands — it reconstructs the `<question>`, the `<alternative>` elements, the cited `<applied-principle>` elements, and the `<recommendation>` you saw, and from the `requirements.md` hunk's added lines the decision you recorded. Manual and alternative answers that overrode the recommendation are the **override signal**: where such a commit carries no rationale of yours, it asks why you preferred your option — showing its best guess, one prompt per commit, each skippable, with a one-shot accept-every-guess / skip-every-prompt choice up front so backfill stays workable. Accepted recommendations are **evidence only**: a cited principle is reinforced (and shielded from pruning in that pass), a contradicted one flagged. From the override reasoning and deliberated manual bodies it distills generalizable keep/eliminate directives, dedups them against each other, and composes **one whole-store rewrite** — adds, revisions, prunes, merges, generalizations, and shortenings together, salvaging a contradicted entry by narrowing, generalizing, or replacing it before deleting it, and holding every directive to a roughly 40–80-word target under the "as short as it can be while still reading as an intuitive rule" test — written in place, printing no diff. You review the working-tree change with `git diff`, request changes in conversation, and **one confirmation gates the commit**: on acceptance it commits the store path-scoped under `Principle-capture: <milestone_id>`, with one body line per store change naming its kind and the answer that drove it; on rejection it restores the store to its pre-write snapshot and commits nothing. An empty commit range, a set that neither generalizes nor contradicts the store, and a rewrite identical to its baseline all yield the same single-line "nothing captured" report.

### `provide-alternatives-to-all-open-questions`

The **alternatives pass** — the first of the two annotating passes over a milestone's questions, which together are the argument-free batch form of `/discuss-open-question`. It gathers the current milestone's questions **once**, in two calls to the open-question tool: `list` (every block's id — an empty print stops the run) and `list --without-alternatives` (the ids of the blocks carrying no `<alternative>` element, the ones this run annotates — an empty print is the no-op); it runs no `locate` and holds no block. It dispatches one read-only `provide-alternatives-to-open-question` subagent per such question, passing each a prompt that carries only that question's Short Title and the resolved milestone directory — the two values the orchestrator already holds, no question text and no block, since the subagent fetches its own block and its sibling scope through the tool — **all of them together where the host can run several agent dispatches at once, one after another where it cannot**, with no ranking, no ordering, and no cap beyond one dispatch per question, because an alternative set is enumerated against the sibling questions as scope only, never against how a sibling will settle, so no dispatch reads what another wrote. Every subagent enumerates under the shared enumeration core's rules — axes named first, each option a position on them, the set **distinct** and **covering** the underlying decision (not doing the thing included where honestly viable), and no count guideline, so a set holds as many options as its axes and their viable combinations give it; the orchestrator itself states and checks none of them. It is the **sole document mutator**, and every write is the tool's. Each return is judged **as it lands**, in one fixed order. A last non-whitespace line beginning `FAILED:` is an explicit failure — that question is skipped with that reason and never repaired; this last-line verdict is the only judging the orchestrator does itself. Otherwise it pipes the subagent's **whole message**, unedited, to `embed --alternatives` on standard input as a quoted heredoc, and the tool does the rest: it slices the fragment from the first `<alternative` line through the last `</alternative>` line (a grounding summary above or a closing remark below is discarded, not a failure), parses and validates it — no `<open-question>` or `<question>` line, no text outside the elements, at least one `<alternative>`, no element of the recommendation half, no unknown element, a target block carrying no `<alternative>` yet — and writes those elements into the existing block re-rendered in canonical form, so indentation and escaping are the tool's, never the return's. A silent exit annotates the question; a refusal is one `Error: <reason>` line with the document unchanged, and that line buys the question **exactly one repair attempt**, made immediately (the orchestrator never drops or rewrites a returned element): where the host can continue the finished agent session — Claude Code's `SendMessage` to the agent id the dispatch returned — it asks *that same agent* to re-emit, sending a fixed one-paragraph corrective message whose single slot is that `Error:` line and which quotes both shape tests; where it cannot (no session-continuation equivalent, as under Antigravity, or the handle is gone) it re-dispatches **one** fresh agent with the same prompt plus that message as a shape reminder. Whatever comes back is judged the same way, and only a **second** failure is the skip — that question alone, its block left byte-for-byte untouched and its Short Title printed with the reason alongside the terse line, never a run stop; a question annotated only after the tool discarded surrounding text, or only after the repair, gets no console mention at all. It **commits per annotated question, the moment its `embed` writes**: a commit path-scoped to `<MILESTONE_DIR>/open_questions.xml` (never `git add -A`) under `Alternatives-annotation: <Short Title>` with no body; a skipped question commits nothing. It is **idempotent**: the `--without-alternatives` filter is the whole skip test, so a block already carrying `<alternative>` elements is never re-annotated — that set is **frozen** for the recommendation pass, which picks against it (to force a fresh set, run the tool's bare `strip` on that block — one or more Short Titles — which deletes every child but its `<question>`, the alternatives and any pick made against them alike, and re-run; `open_questions.xml` is never edited by hand). When such a regenerated block's new alternative ids differ from what surviving dependents' `<depends-on>` tags assumed of it, those dependents are left exactly as they are — no strip, no rewritten `option`, no mismatch advisory: only the answer-time cascade reconciles a tag against the option actually recorded. Because it records no decisions and triggers no cascades — the question set never shrinks under it — it needs no per-question live re-check, no re-gather loop, and no clean-working-tree precondition. Its report is one fixed line, `Alternatives embedded.`, or the distinct no-op line with its reason, plus the still-skipped advisory: the questions left without alternatives, which `/recommend-all-open-questions` stops on until a re-run annotates them.

### `provide-alternatives-to-open-question` (subagent)

Read-only alternatives subagent dispatched once per question lacking alternatives by `/provide-alternatives-to-all-open-questions` — not user-invocable. Given only one question's Short Title and its milestone directory — the prompt carries no question text and no block — it fetches the rest itself: it reaches `open_questions.xml` through exactly two tool calls, one `locate` of its own Short Title (whose verbatim print of the block is its primary source, and whose `Error:` line is its `FAILED:` reason) and one `list --with-question` (every block's id, a tab, then its question text, one per line in document order), which is its **only** source of sibling scope — it never runs `locate` on a sibling, so no sibling's embedded alternatives or pick reaches it, and it never reads `open_questions.xml` whole. It reads `requirements.md` whole with the file-reading tool as prose, grounds in the live project (read-only) — the sibling questions supplying scope and nothing more, since no sibling has settled on anything while alternatives are being enumerated — and enumerates the honest alternatives, sourcing that analytical core from the shared `core/shared/alternatives-procedure.md`: it first names the axes the underlying decision turns on — approaches, degrees or values wherever the trade-off changes, each premise the question's wording takes for granted, and on every axis a none position — weighs not doing the thing on every question (postponing counts as one form of it, so at most one such option), builds each option as one position on every axis (on a multi-axis question, every combination weighed and each viable one described), varies no axis a sibling question owns (naming such an axis as a condition in the drawback when an option's viability depends on it), and reworks the set until it is **distinct** (every two options differ in substance on at least one axis) and **covering** (it covers the underlying decision rather than the question's wording — every viable position and combination appears, the none position included). There is no count guideline — the set's size follows from its axes and their viable combinations — and an option's what-it-is text states only its position on each axis, however long that takes, every reason for or against it going in its advantage or drawback. It then returns the ready-to-embed `<alternative>` elements alone — one per option, each with child `<advantage>`/`<drawback>` — as its final message, never the `<open-question>` wrapper or `<question>` element (which the document owns) and never a `<recommendation>`, `<applied-principle>`, or `<depends-on>` element (which the recommendation pass writes later over the frozen set). The children must be well-formed XML (a literal `&` or `<` in text is written `&amp;` or `&lt;`), but their indentation and escaping are not load-bearing: the tool's `embed --alternatives` parses the fragment and re-renders the block in canonical form. Its return step is a **draft → self-check → emit**: the elements it renders are a draft, checked against the two shape tests the tool's extraction keys on — the draft's first non-whitespace text is `<alternative`, its last is `</alternative>` — and revised until both pass before it is emitted as the final message with nothing accompanying it (every grounding finding is spent inside the elements themselves — in an option's what-it-is text, its `<advantage>`, or its `<drawback>` — and the rest dropped). If it cannot produce that set, it ends instead with `FAILED: <reason>` as its last line and nothing else. It mutates nothing; the orchestrator owns all embedding and committing.

### `recommend-all-open-questions`

The **recommendation pass** — the second of the two annotating passes, the batch form of `/discuss-open-question`'s pick, and an **inline skill that dispatches no agent**. It gathers the current milestone's questions **once**, in three calls to the open-question tool: `list` (every block's id — an empty print stops the run), `list --without-alternatives` (the **stop test**: any id printed means a block has nothing to pick from, so the run stops without changing anything, prints those ids, and points at `/provide-alternatives-to-all-open-questions`), then `list --without-recommendation` (the ids of the blocks carrying no `<recommendation>` element, the ones this run annotates — an empty print goes straight to the end-of-run sort). It then reads `requirements.md` and `open_questions.xml` **whole** — every block's `<question>` and frozen `<alternative>` set, and every recommendation already standing on a sibling — and follows the shared pick core `core/shared/recommend-procedure.md` over **the whole recommendation-less set, held in view together as one judgment**: grounding once (the live project, the principle store as a weighted advisory factor, the sibling questions with their alternatives and standing picks) and forming one pick per block that names one of that block's own `<alternative>` ids, never adding to or dropping from the frozen set, so the picks cohere with one another and with the recommendations already standing. A pick that leans on a sibling settling on one of its options — a sibling with a standing recommendation, or one picked in this same pass — is declared as a `<depends-on question="…" option="…"/>` child naming that sibling and one of its alternative ids. A set a recorded decision has partly outdated still gets a pick — the best option still viable, the rationale naming the option the decision closed and why — and only a block **no** option of which survives is skipped, its advisory naming the remedy (the tool's bare `strip` on that block, then the alternatives pass, then this skill again). It is the **sole document mutator**, and every write is the tool's: it renders each block's `<applied-principle>` elements (one per confirmed principle that bore on the pick — a sibling of the recommendation, never baked into its text), its `<depends-on>` elements, and its single `<recommendation option="…">` carrying the one-line rationale, and writes them with one `embed --recommendation` call per block through a quoted heredoc, **in any order** — the tool resolves each `<depends-on>` against its target's alternatives, which every block already carries, checks that the fragment holds no `<alternative>` and exactly one `<recommendation>` naming one of the block's own ids, refuses a block already carrying a `<recommendation>`, and writes the block re-rendered in canonical form without adding, dropping, or editing an `<alternative>`; a refusal is a rendering slip the pass corrects and re-runs, never a skip. It **commits once per run**: after the last `embed` it runs the tool's `lift` for each annotated block, and those printed `<option> — <rationale>` lines are the body of one commit path-scoped to `<MILESTONE_DIR>/open_questions.xml` (never `git add -A`) under `Recommendation-annotation: <milestone_id>`. Then, as a **fixed end-of-run step of every run that found questions** — reached after that commit, at once when nothing was left to pick, and when every block was skipped — it runs the tool's `sort` once, which rewrites the document with the `<recommendation>`-bearing blocks first, in exactly the order the answer sweep's `walk` will dispatch them, and every un-annotated block last in its prior order (so a reader of the document meets the questions whose answers no dependency can nullify before the questions that build on them), and commits that reorder as its own `Question-ordering: <milestone_id>` commit behind the dirty-own-path guard — the sort's only no-op test, so the commit lands exactly when the sort moved a block, and a run that annotated nothing and moved nothing commits nothing. It is **idempotent**: the `--without-recommendation` filter, backed by the tool's refusal of an already-annotated block, is the whole skip test, so a standing recommendation is never re-picked and is read only as context a new pick may build on (to force a fresh pick, run the tool's `strip --recommendation` on that block — one or more Short Titles — which clears its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children and keeps its `<alternative>` children, and re-run; the answer-time cascade clears a dependent's pick the same way, so an override costs only a re-run of this pass). When such a re-picked block's new recommended option differs from what surviving dependents' `<depends-on>` tags assumed, those dependents are left exactly as they are — no strip, no rewritten `option`, no mismatch advisory: a `<depends-on>` records what a dependent assumed, and only the answer-time cascade reconciles it against the option actually recorded. Because it records no decisions and triggers no cascades, it needs no per-question live re-check, no re-gather loop, and no clean-working-tree precondition. Its report is the one carve-out from the one-success-line rule: it carries **two** fixed success lines and picks one by what the run committed, in strict order — an `embed` wrote, `Recommendations embedded.` (whether or not the sort also committed); else the sort committed, `Questions reordered.`; else the distinct no-op line with its reason — and prints the still-skipped advisory alongside whichever line is chosen. The embedded recommendations are later lifted and recorded as decisions — under `Recommendation-answer:` — by `/answer-open-question-with-recommendation` (or the `/answer-all-open-questions-with-recommendation` sweep).

### `derive-tasks`

Converts the current milestone's `requirements.md` into `TASKS_TODO.md` — a complete, dependency-ordered list of atomic, AI-completable **brief-level** tasks. Decomposes the milestone into high-level briefs, proves every requirement is covered with a traceability matrix, orders them by dependency, and writes those briefs into `TASKS_TODO.md` itself, in order, as the finished task sections. A brief and a task section are the same altitude, so writing the brief down *is* the authoring step: there is no second pass and nothing is handed off. Each section is a `##` title, a 1–3 sentence description of what is to be achieved, why the milestone needs it, and how it would be verified, and a trailing `---` — the completer derives the flow and the formal acceptance bar itself. Requires all open questions to be resolved first: the open-question tool's `list` over the milestone's `open_questions.xml` must print nothing, and it stops listing the Short Titles otherwise.

### `discuss-new-task <issue description>`

Clarifies a rough or oversized issue discovered mid-flight into one or more clear, task-sized briefs through a short conversation, then hands each off to `/submit-task`. Because tasks are brief-level, each brief maps near-1:1 onto the task section `/submit-task` writes — a title and a few sentences, with no further fleshing out. Use it when the affected system, desired behavior, or verification isn't yet clear, or when one issue is really several tasks.

### `submit-task <issue description>`

Adds a single, already-clear issue to `TASKS_TODO.md` as a **brief-level task section** — a `##` title, a 1–3 sentence description of what is to be achieved, why it is needed, and how it would be verified, and a trailing `---`, and nothing else. Triages for duplicates and decides where the task belongs, then authors and inserts the task **inline, in the current conversation** so the authoring context stays available for follow-up tweaks, and commits the inserted task path-scoped under a `Task-submission:` subject. It is the same format `/derive-tasks` writes, so every task in the list sits at one altitude. For vague or multi-task issues, route through `/discuss-new-task` first.

### `complete-all-tasks`

Orchestrator: completes all tasks in `TASKS_TODO.md` top to bottom, spawning one subagent per task and committing after each success — **once per task**, committing the index the agent staged (its change set, plus the two task-list files, never `git add -A`) under the subject `Task-completion: <task heading>` with no body — the same subject inline `/complete-task` uses. Stops on first failure.

### `complete-task <task_name>`

Completes a single named task from `TASKS_TODO.md` **inline, in the current conversation**. Running inline keeps the work context (what changed, why, how it was verified) in the conversation so you can ask follow-up questions or request tweaks right after. It commits the task's change set path-scoped — the files it created or edited plus the two task-list files, never `git add -A` — under the subject `Task-completion: <task heading>` with no body, the same subject `/complete-all-tasks` uses per task. Use `/complete-all-tasks` to run the whole task list unattended.

### `ask-in-milestone-context <question>`

Answers a free-form, informational question about the current milestone — its goal, recorded decisions, done and pending tasks, and the actual deliverables those tasks produced — grounding the answer in the live files and artifacts rather than memory. **Read-only and conversational**, usable any time: use it to look back on finished work ("how did task X end up handling Y?", "where did we put Z?"), to take stock ("what's left and why?"), or to surface context before deciding what to do next. When the answer reveals a concrete next step, it offers the right skill — `/discuss-open-question`, `/submit-task` or `/discuss-new-task`, `/discuss-milestone-goal`, `/complete-task` — but performs none of their work itself.

### `finish-current-milestone`

Verifies all tasks are done, writes a completion summary to `milestones/README.md`, and updates `CLAUDE.md` only for lasting changes to the project's environment context. Clears the current-milestone pointer — run `/define-milestone-goal` to define the next milestone, then `/goto-next-milestone` to activate it.

### `goto-next-milestone`

Activates the lowest-numbered undone milestone without asking: scans `milestones/` for the directories `/define-milestone-goal` created whose number has no heading under `## Milestone History`, and updates `milestones/README.md` to point at the lowest-numbered one as the current milestone. It stops only when the pointer does not read `none` (run `/finish-current-milestone` first) or when no undone milestone exists (run `/define-milestone-goal` first). Creates no files or directories. A defined milestone that is never finished is picked on every run, so an unwanted one is skipped by removing its directory, for example by reverting its `Milestone-definition:` commit.
