# Skill reference

What each of Cairn's skills and dispatched agents does. The phases they form, how they commit, and the [answer-principle-learning loop](workflow.md#the-answer-principle-learning-loop) are described in [workflow.md](workflow.md), and how to chain them as headless command lines is in [ways-of-using-cairn.md](ways-of-using-cairn.md).

### `init-milestone-base-workflow`

One-time bootstrap for a project. It checks the workflow's two runtime prerequisites on every invocation, each stopping on its own before anything is written with a message saying what it looked for, what it found, the remedy, and that a re-run completes the bootstrap. Git comes first: one `git rev-parse --is-inside-work-tree` probe of the workspace root, which passes anywhere inside a work tree (a subdirectory of a larger repository, or a fresh repository with no commits yet) and otherwise names the remedy (install git, or run `git init` in the workspace root) — the skill never prompts and never runs `git init` itself. Then Python: a 3.9 or later interpreter answering as `python3`, which the skills drive the plugin's stdlib-only Python tools with, probed by `python3 --version` and, only when that fails, `python --version` to make its message precise (remedy: expose the interpreter as `python3`, or install Python 3.9+). It then creates the `milestones/` directory and `milestones/README.md` with the current-milestone pointer (its template lists the four milestone files, `open_questions.xml` among them), and ensures `CLAUDE.md` carries the `## Milestone Workflow` guidance. Additive and idempotent — creates missing scaffolding and inserts missing sections into existing files, never overwrites existing content. It commits subject-only under `Workflow-bootstrap: milestones`: `milestones/README.md` always, plus `CLAUDE.md` only on runs where it created the file or appended the section, handed over unchanged so uncommitted changes already in those paths (such as a `CLAUDE.md` just written by `/init`) ride in the same commit. On success it prints the one line `Workflow bootstrapped.`, and on an already-initialized project the one no-op line `Workflow already bootstrapped — nothing changed.`, with no itemization and no next-step pointer — the commit diff shows what was created or appended. Run this before any other workflow skill.

### `discuss-milestone-goal <overall_goal_description>`

Facilitates a structured conversation to sharpen a vague goal into a clear, actionable statement. Produces a refined goal description ready for `/define-milestone-goal`. Creates no files.

### `define-milestone-goal <overall_goal_description>`

Creates a new milestone mechanically: the skill only chooses the milestone's title from the goal description and hands it, with the goal text on standard input, to the plugin's stdlib-only `tools/define_milestone.py`. The tool numbers the milestone max-plus-one over the existing `milestone_<N>_<slug>` directories, derives the slug from the title's first five words, refuses an existing target, and creates `milestones/milestone_<N>_<slug>/` with its four files from its own templates: an empty `open_questions.xml`, which the open-question tool then writes from that point on, `requirements.md` (the title heading and the Goal section filled, the other sections empty), plus empty `TASKS_TODO.md` and `TASKS_DONE.md`, which the task-list tool `tools/task_list.py` then writes from that point on. It prints the commit subject `Milestone-definition: milestone_<N>_<slug>` and the directory path, which the skill passes unchanged to the commit procedure; on failure it prints one `Error:` line and leaves nothing behind. Does **not** activate the milestone.

### `specify-milestone-starting-state <milestone_id>`

Reads the milestone goal, explores the project's existing state using the environment documented in `CLAUDE.md`, and writes a concise summary into the `## Relevant starting state` section of `requirements.md`. Sets up the context needed to make informed decisions.

### `review-milestone-requirements`

The repeatable engine of the requirements-iteration loop. Each pass reads the current milestone's `requirements.md` and `open_questions.xml` whole to reason over them, then does three jobs: **reconciles** the existing question set against what's already decided (prunes a block a recorded decision now covers, dedups repeats — each removal one bare `remove` call to the open-question tool, which in the same write strips every surviving question whose `<depends-on>` assumed the removed block of its pick — its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children, the `<alternative>` children kept — transitively, leaving those questions for the next `/recommend-all-open-questions` pass to re-pick), **surfaces** genuinely new gaps the latest decisions exposed, authoring each finding as an ordinary `<open-question>` block through the tool's `add` — the pass writes only the two judgments a block carries, its self-standing question text and its unique Short Title, and the tool owns the block's shape; each question asks **one choice**, so a gap holding two choices becomes two questions, except that choices constraining each other so that not every pairing is viable are authored as a single multi-axis question asking both at once (no test for spotting a second axis is prescribed — that stays the author's judgment), which keeps the alternatives pass from multiplying one set across independent choices — and **reports convergence** from the tool's `list`: whether any `<open-question>` block remains (which `/derive-tasks` forbids) or the requirements are ready to derive tasks. Before it commits and reports, it turns contradictions between recorded decisions into open questions, from two sources. The first is the **noted contradictions**: when `requirements.md` holds a `## Noted contradictions` section — the optional fifth section, between `## Decisions` and `## Out of Scope`, which no tool creates, a single-question answer skill opening it with its first note, and which stands only while a note does — the pass handles each note against **recorded state only**, never re-judging whether the noted pair conflicts. A note whose pair a standing block already flags, or one naming an entry that no longer stands as the note describes it (its heading gone from `## Decisions`, or its text rewritten so the two now hold together), is deleted with no block, as cleanup of recorded state like a prune; every other note becomes **one block** through the same `add`, asked as noted, and is then deleted. Each note goes in one targeted edit, the section's heading in the same edit as the last note, so the section is gone once no note stands — deleting notes is the pass's **only edit of `requirements.md`**. The second source is its own check of the recorded `## Decisions` entries against each other, from that same whole read: two entries conflict when both cannot hold as written — carrying out one breaks the other, or they fix different values for the same name, threshold, or behaviour — while an entry that only refines, narrows, or extends another is no conflict. For each conflicting pair that no standing block already flags, a block just authored from a note included, it authors one block the same way. Every conflict question, from either source, opens with **one fixed phrase** naming the `###` heading each entry sits under, in their `## Decisions` order — `Which conflicting decision stands: "<first heading>" or "<second heading>"?`, the opening `Which conflicting decision stands:` written exactly, since it is how the answer sweep recognizes a conflict question — followed by a brief statement of what each entry says, quoting enough of each one's lead or opening words to tell them apart where both share one heading or sit among several bullets. That flags the conflict without resolving it — it never edits, rewords, or removes either entry and never decides which one stands, since that is an answer's to record — and the blocks and note deletions ride in the pass's commit, each block showing only as a Short Title in the still-open list, with no advisory of its own, so it holds convergence and `/derive-tasks` until it is answered like any other question. This step is where a contradiction between two recorded decisions becomes an open question, whether a single-question answer skill noted it or the pass notices it here, because the answer sweep records every pick as given and forms no contradiction judgment. It commits the two documents path-scoped under `Requirements-review: <milestone_id>`, committing nothing when a pass reshaped nothing and found no note to handle. Run it after `/specify-milestone-starting-state` to open the questions, then re-run after every answer or two — earlier answers keep opening new ones. It never answers questions or records decisions itself, and it never edits `open_questions.xml` by hand; it shapes and reports the open-questions state for the answering skills to resolve.

### `discuss-open-question <question_name>`

Opens a structured conversation about a named open question in the current milestone's `open_questions.xml` — locating the block through the open-question tool's `locate`, then reading `requirements.md` and the question document whole for context. It works on a block in **any state**, and the state fixes only where the option set comes from: a block carrying the `<alternative>` elements the alternatives pass embedded has that **frozen set reused** as its options, exactly as embedded and never re-enumerated (a genuinely realistic option the set lacks may be put on the table only marked plainly as a departure from the frozen set, since recording it would be a literal answer matching no `<alternative id>`), while a bare block gets its honest alternatives enumerated inline first, through the shared enumeration core `core/shared/alternatives-procedure.md` — the same core the `provide-alternatives-to-open-question` subagent follows, so the set is built the same way: the axes the underlying decision turns on are named first, each option is one position on them, and the set must be **distinct** (every two options differ in substance on an axis) and **covering** (it covers the underlying decision rather than the question's wording, not doing the thing included where honestly viable), with no count guideline. Over that set it then follows the shared pick core `core/shared/recommend-procedure.md` (the same core `/recommend-all-open-questions` follows) and states **one recommendation of its own**, formed afresh from the set and its grounding; when the block also carries the `<recommendation>` the recommendation pass embedded, it shows that standing pick beside its own — option, rationale, the principles it cited, and the sibling options it assumed — and says plainly whether the two agree and why. When its pick leans on a still-unanswered sibling settling on one of its options it says so in prose, naming that sibling and the option assumed — the conversational rendering of the disclosure duty the recommendation pass renders as a `<depends-on>` element. On top it adds the layer that is its own: a "what would change your mind" section and the continue-the-conversation loop. On a decision it offers `/answer-open-question` (naming the matching `<alternative>` id when the answer is one of the frozen options) and, when the deliberation concludes the goal itself must shift, `/modify-milestone-goal` — run first, so the answer records against the revised goal. Purely conversational — it edits nothing.

### `answer-open-question <question_name>`

Records the resolution of a named open question: the decision is folded into `## Decisions` of `requirements.md` first, then the answered block is removed from `open_questions.xml` by the open-question tool's `remove`, and the two edits are **committed**. It follows the shared hand-answer procedure `core/shared/hand-answer-procedure.md`, which composes over the recording core `core/shared/answer-procedure.md`: before recording, the skill reads `open_questions.xml` whole, for reasoning only, and names the **undermined picks** — every other question's standing `<recommendation>` that the answer undermines, because the recommended alternative, as its what-it-is text reads, can no longer be carried out alongside the decision, or because the pick's one-line rationale states or plainly presupposes something the answer changed (a fact about the project, a constraint, a sibling's expected outcome). It judges only those two texts against the answer and what it directly entails, never re-forming the recommender's judgment, and it runs that judgment on **every** hand answer, whether or not the answer matches the answered block's own pick; a pick the answer does not bear on is left standing. Its cascade removes the siblings the decision moots (one bare `remove` each) and reconciles the **dependents** through the same `remove`, in **one write**: the siblings whose `<depends-on>` tag assumed this question's option, and the undermined picks it named, passed as `--undermined` whether or not any tag declares them. For the tagged ones, since a literal answer lifts no option id, the skill forms one further judgment, whether the answer plainly settles on one of the answered block's own `<alternative>` ids, and passes that id as `--option` (the tagged dependents that assumed it keep their pick, every other one is stripped of its pick) or passes nothing when the answer settles on none of them, or only arguably on one, so every tagged dependent is stripped. Every named block is stripped too — its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children deleted, the `<alternative>` children kept — and every strip is transitive over the blocks whose tags name the stripped one, for the next recommendation pass to re-pick; a named block that carries no pick is left as it stands. **Strip on doubt** covers both judgments: a pick only arguably untouched by the answer is named, because a stripped block costs one re-pick while a stale pick left standing would be recorded as a decision by the answer sweep. A named title matching no block, or the answered block's own, stops the `remove` on the tool's `Error:` line with the document unchanged, and the skill corrects the list and runs the call again. Nothing is printed about any pick the write cleared; the commit's diff is the record. Before the block is removed, the recording core also weighs every standing `## Decisions` entry the decision contradicts — one that cannot hold as written beside it — by the **note-versus-rewrite rule**. An entry the answer **plainly supersedes**, because the answer is clearly meant to replace it, has its conflicting text rewritten in place, under its own heading and in its own shape, in the same pass of targeted edits as the fold, and no note is written; that rewrite is the one exception to the core's ban on otherwise rewriting `requirements.md`. An entry the answer does **not plainly settle** stays as written and the pair is **noted** instead — **doubt notes**, so an entry the answer only arguably replaces is noted, never rewritten — as one `- ` bullet under `## Noted contradictions`, naming both entries by the `###` heading each sits under (with enough of each one's lead or opening words to tell it apart where it shares that heading or sits among several bullets) and saying in one sentence of the skill's own words what each says and why both cannot hold, with no question text. That section sits directly after `## Decisions` and before `## Out of Scope` and exists only while a note stands: no tool creates it, the first note inserts its heading, and the next `/review-milestone-requirements` pass turns each note into an open question or drops it, deleting the heading with the last note. A **conflict question** — one asking which of two `## Decisions` entries stands, as the review pass authors it — is recorded by rewriting the losing entry in place so it agrees with the entry that stands, which stays as written; that rewrite is the answer's whole record, and nothing is folded anywhere else under `## Decisions`. The commit stages only its own two edits (`<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md`, never `git add -A`) under the subject `Manual-answer: <Short Title>`, with the decision's rationale in the commit body. A Short Title that matches no block stops the skill on the tool's `Error:` line, which lists the ids the document holds. It no longer chains to any capture skill — the reusable principle behind the answer is distilled later by `/capture-milestone-principle-updates <milestone_id>`, whenever you run it for the milestone. Its `Manual-answer:` subject is a provenance marker that capture reads alongside `Alternative-answer:` and `Recommendation-answer:`: a manual answer is an **override signal** — a decision the recommender did not make — whose body rationale capture distills, asking you for the reason only when the body records none (see [How skills commit](workflow.md#how-skills-commit)).

The answer text is recorded **literally** — recording a question's embedded recommendation now lives in the dedicated `/answer-open-question-with-recommendation` skill. As migration scaffolding, this skill keeps one small **redirect guard**: if the answer text is exactly the retired sentinel `record the recommendation` (whole-string, after trim + lowercase, never a substring), it stops without recording and points you at `/answer-open-question-with-recommendation` instead of committing the sentinel phrase as a decision.

### `answer-open-question-with-recommendation <question_name>`

Records a named open question's **embedded recommendation** as its answer, then **commits** — the dedicated home for the recording logic extracted out of `/answer-open-question`. It lifts the `<recommendation option="...">` element that `/recommend-all-open-questions` embedded in the question's `<open-question>` block with the open-question tool's `lift`, which prints the `<option> — <rationale>` answer form as plain text — folds it into `## Decisions` of `requirements.md`, then has the tool's `remove --option <lifted option>` delete the block and reconcile the **dependents** — siblings whose `<depends-on>` tag assumed this question's option — by an **exact id comparison** against the lifted `option`: a matching tag is simply removed, a differing one strips that dependent of its pick (its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children, the `<alternative>` children kept), transitively, for the next recommendation pass to re-pick; siblings the decision moots are removed the same way. It records through the same recording core as `/answer-open-question`, so the same **note-versus-rewrite rule** applies before the block is removed: a standing `## Decisions` entry the decision plainly supersedes is rewritten in place in the same pass of targeted edits as the fold, with no note, while one the decision does not plainly settle stays as written and the pair is noted under `## Noted contradictions` — doubt notes — for the next review pass to ask; and a **conflict question**'s answer is recorded by rewriting the losing entry in place alone, nothing folded anywhere else. The commit stages only its own two edits (`<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md`, never `git add -A`) under the distinct subject `Recommendation-answer: <Short Title>`, with the lifted line as its body — the provenance marker by which `/capture-milestone-principle-updates` reads it as an **accepted recommendation**: evidence about principles already in the store (a cited principle is reinforced, a contradicted one flagged for salvage), never a source of new principles, since its body is the recommendation pass's rationale rather than yours. If the targeted `<open-question>` block carries no `<recommendation>` element (the recommendation pass never ran, or the question was added afterward), the `lift` fails on one `Error:` line and the skill stops without changing anything and commits nothing. Runs **inline** in the conversation so the context survives for follow-up.

### `answer-open-question-with-alternative <question_name>. <alternative id>`

Records a **named `<alternative>`** from an open question's embedded analysis as its answer, then **commits** — the sibling of `/answer-open-question-with-recommendation`, differing only in *which* embedded element becomes the answer. Where the recommendation skill lifts the one `<recommendation>` element the recommendation pass picked, this skill lifts the `<alternative id="...">` **you** name — which lets you record a decision that *overrides* the recommendation, or resolve a question the recommendation pass left genuinely tied. Split the argument on the **first `.`**: the Short Title before it, the target alternative's `id` after it (both case-insensitive, both trimmed). The open-question tool's `lift --alternative <id>` prints the chosen alternative's `id` and its what-it-is text as the `<id> — <what-it-is>` answer form in plain text (the `<advantage>`/`<drawback>` children are trade-off analysis, not the decision, and are left out); the skill then follows the same shared hand-answer procedure as `/answer-open-question`, `core/shared/hand-answer-procedure.md`, with the chosen `id` as the recorded option. Before recording, it reads `open_questions.xml` whole, for reasoning only, and names the **undermined picks** — every other question's standing `<recommendation>` whose recommended alternative, as its what-it-is text reads, can no longer be carried out alongside the chosen alternative, or whose one-line rationale states or plainly presupposes something the choice changed — judging only those two texts, never re-forming the recommender's judgment, on **every** answer (choosing the alternative the block's own pick names is no exemption), and leaving standing the picks the choice does not bear on. It folds the answer into `## Decisions` of `requirements.md`, then has the tool's `remove --option <chosen id>` delete the block and reconcile, in **one write**, the **dependents** — siblings whose `<depends-on>` tag assumed this question's option — by an **exact id comparison** against the chosen `id` (a matching tag is simply removed, a differing one, the usual case when you override the recommendation, strips that dependent of its pick) together with the undermined picks it named, passed as `--undermined` and stripped whatever their tags say. A stripped block loses its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children and keeps its `<alternative>` children, transitively over the blocks whose tags name it, for the next recommendation pass to re-pick; a named block that carries no pick is left as it stands; siblings the decision moots are removed the same way. **Strip on doubt** covers the naming: a pick only arguably untouched is named, because a stripped block costs one re-pick while a stale pick left standing would be recorded by the answer sweep. Nothing is printed about any pick the write cleared; the commit's diff is the record. Its fold follows the same **note-versus-rewrite rule** as `/answer-open-question`, before the block is removed: a standing `## Decisions` entry the chosen alternative plainly supersedes is rewritten in place in the same pass of targeted edits as the fold, with no note, while one it does not plainly settle stays as written and the pair is noted under `## Noted contradictions` — doubt notes — for the next review pass to ask; and a **conflict question**'s answer is recorded by rewriting the losing entry in place alone, nothing folded anywhere else. The commit stages only its own two edits (`<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md`, never `git add -A`) under the distinct subject `Alternative-answer: <Short Title>`, with the lifted line as its body — the provenance marker by which `/capture-milestone-principle-updates` reads it, like `Manual-answer:`, as an **override signal**: because the body carries only the alternative's text and no rationale of yours, capture asks you at harvest time why you preferred it (offering its own best guess) and distills the guideline the recommender lacked from that answer. If no question matches the Short Title, the block carries no `<alternative>` elements (the alternatives pass never ran), or no alternative matches the given id, the `lift` fails on one `Error:` line that lists the available ids, and the skill stops without changing anything and commits nothing. Runs **inline** in the conversation so the context survives for follow-up. There is deliberately **no** batch form: which alternative wins is per-question human judgment, not a rule a sweep could apply.

### `answer-all-open-questions-with-recommendation`

The **recommendation-answer sweep** — the batch form of `/answer-open-question-with-recommendation`, the recording counterpart to `/recommend-all-open-questions`, and an **inline skill that dispatches no agent**: it is the single writer of its run, composing every answer itself, in the conversation, and recording the whole run in **one fixed batched shell call**. It resolves the current milestone **once** and uses that one directory for every tool call, recording, and commit of the run. Its setup is two tool calls sent **in the same turn**, neither needing the other's output. One is a fixed shell call, shown in full in the skill and run exactly as shown, that is the whole gather, ordering, and **compact view** of the question document: the open-question tool's `list --with-question` prints every block's id, a tab, and its question text in document order, recommendation-less blocks included, and the tool's `walk` then feeds a loop that prints, for each block carrying a `<recommendation>` element, its id, its lifted `<option> — <rationale>` line, and its picked alternative's `<option> — <what-it-is>` line through `lift --alternative` (a walked id whose lift fails gets its `Error:` line in place of the pick and no alternative line). The other is one whole read of `requirements.md` with the file-reading tool, for reasoning only; `open_questions.xml` itself is never read with the file-reading tool. `walk`'s order places each block after every printed block its `<depends-on question="…">` tags name — the dependency graph walked from its origins, never a judgment of significance: an edge whose target is absent or carries no `<recommendation>` is dropped, questions with no resolvable edge are the **origins**, each further depth follows once all its targets are placed, same-depth questions keep document order, and a stranded set (a `<depends-on>` cycle, reachable only through the recommendation pass's `strip --recommendation` escape hatch) promotes its document-order-first member to an origin and walks on — deterministic and total for any graph shape. From those two prints the runner composes each walked question's section before writing the call: the decision, written from the question text, the lifted line, and the picked alternative's what-it-is under the fold-content rules of the shared answer core `core/shared/answer-procedure.md` (clean prose with no citation marker, the entry shaped like the subsection it lands in — a prose paragraph or a `- **Lead.** text` bullet); the `###` subsection of `## Decisions` it lands under, an existing one or a new heading; and the option, copied from the lifted line as a literal so it reaches `remove` as an exact id, never derived inside the call. A **conflict question** is told apart first, by one exact-prefix check of its question text as `list --with-question` printed it: when that text starts with exactly `Which conflicting decision stands:` — the fixed opening `/review-milestone-requirements` gives every conflict question it authors, followed by the two entries' `###` headings in double quotes — the question is a conflict question, and every other question, a block asking about a conflict but written before that opening existed included, is an ordinary one. A conflict question takes its option the same way, but in place of a decision and its subsection the runner composes the **losing entry's `###` heading**, copied exactly as the opening quotes it (the heading whose entry the pick does not keep as it stands), and the **whole new body** of that subsection: the losing entry with its conflicting text rewritten, by the same fold-content rules, to agree with the pick, and every other entry of the subsection carried unchanged — in a topical subsection every unchanged bullet — composed over the subsection as the earlier sections of the call will leave it. That rewrite is the answer's whole record: no separate decision is folded anywhere under `## Decisions`. The batched call opens with the **stranded-fold guard**: when `<MILESTONE_DIR>/open_questions.xml` or `<MILESTONE_DIR>/requirements.md` holds any staged or unstaged change — a stopped run's uncommitted fold or rewrite, or a hand edit alike — it prints `dirty before start` with the `git status --porcelain` lines beneath it and ends before any write, so no leftover rides into an answer's commit. It then carries one section per walked question, in walk order and never reordered, every one in the one call with no cap, so every commit that lands records a pick whose assumed siblings are already recorded. Each section runs the tool's `lift` as the question's live re-check, with only its stderr silenced: a failing `lift` — an earlier section's `remove` stripped the block's pick because its `<depends-on>` assumed another option — is the **silent skip**, printing nothing, the stripped block being the recommendation pass's to re-pick; a succeeding one's line is held as the commit body, since the block is gone once recorded. An ordinary question's section then folds the decision through the plugin's stdlib-only **fold tool**, `tools/requirements.py fold <MILESTONE_DIR> --section "<Heading>"` with the decision on standard input, which splices it verbatim at the end of the `###` subsection whose heading matches after whitespace and case folding — or under a new `### <Heading>` appended at the end of `## Decisions` when none matches — adding only the blank lines its two seams need and writing every other byte of the file back unchanged, so the commit's `requirements.md` diff is exactly the folded decision. A conflict question's section is the **conflict section**, identical to the ordinary one but for the one call standing where `fold` stands: the same tool's second subcommand, `tools/requirements.py replace <MILESTONE_DIR> --section "<Heading>"` with the new body on standard input, which replaces everything below the heading line of the existing `###` subsection whose heading matches, down to the next `###` heading or the end of `## Decisions`, with that body written verbatim, keeping the heading line and every byte outside the subsection, so the commit's `requirements.md` diff is exactly the rewritten entry; it never creates a subsection, refusing a heading no `###` subsection of `## Decisions` carries. Every section thus makes the same tool calls — one `lift`, one fold-tool call, one `remove` — and a conflict section holds exactly one `replace` and no `fold`, rewriting exactly one subsection: the entry that stands, and any clause elsewhere in `requirements.md` the pick bears on, stay as written, and any conflict left standing is the next review pass's `## Decisions` consistency step to flag. Telling a conflict question by its opening and rewriting its losing entry is still recording the pick as given — no contradiction is judged and no pick is weighed. Only after that fold or rewrite does `remove --option <option>` delete the block and, in the same write, strip the pick of every block whose `<depends-on>` tag assumed another option of it (its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children, the `<alternative>` children kept), transitively. The section then carries out the commit procedure's three steps itself, path-scoped to the milestone's two files (never `git add -A`), under `Recommendation-answer: <Short Title>` with the lifted line as its body — **one commit per answer**, which is what lets a single answer be reverted and re-answered on its own — and prints the fixed marker `answer commit landed` once that commit has landed. A failure after the lift — the fold tool refusing (a `replace` naming a heading `## Decisions` does not carry included), `remove` refusing the option, git refusing the commit — **stops the whole call** at that question: the tool's `Error:` line or git's message reaches the output unredirected beside one `stopped at` line naming the Short Title, no later section runs, every earlier answer stays committed, and the tree is left exactly as it stands, never rolled back, for the next run's guard to stop on until it is committed or discarded. It records **every pick as given** and never judges one: it runs no mooting cascade, so an entry a recorded decision moots stays in the document for the next `/review-milestone-requirements` pass to clean up or flag, and it forms no contradiction judgment and writes no note under `## Noted contradictions`, since that pass's `## Decisions` consistency step is where two conflicting decisions are noticed. There is no outer re-gather loop, because recording only removes blocks or strips their picks; instead the call closes with the fixed header line `completeness walk` and one more `walk` as a **completeness check**, expected to print nothing, any id it prints being an anomaly — a recommendation-bearing block the run left unrecorded; a stopped call never reaches it. It needs **no** clean working tree beyond the milestone's two files: the guard covers those, and every commit is path-scoped to them, so a dirty tree elsewhere stays out of it. Its report is one fixed line chosen by the markers, `Recommendations recorded.` when the call printed at least one, or the distinct no-op line with its reason, beside only the completeness anomaly when it fired; a dirty start replaces that line with the porcelain lines and the remedy (commit or discard those changes, then re-run), and a stop with the stopped Short Title paired with the error printed beside it, quoted verbatim. It names no skipped question and gives no contradiction or new-question advisory, leaving new questions to the next review pass. Run it after `/recommend-all-open-questions` to record every annotated recommendation at once.

### `modify-milestone-goal <new or revised goal text>`

Revises the `## Goal` of the **already-defined** current milestone — the one skill that mutates the goal of a live milestone (`define-milestone-goal` only seeds it at creation). In the same run as the Goal edit it **clears the standing picks the revision undermines**: from its whole read of `open_questions.xml`, for reasoning only, it names every block whose standing `<recommendation>` the revised goal undermines — the recommended alternative, as its what-it-is text reads, can no longer be carried out alongside the revised goal, or the pick's one-line rationale states or plainly presupposes something the revision changed, such as the scope or aim of the milestone — judging only those two texts, never re-forming the recommender's judgment, with doubt stripping and the picks the revision does not bear on left standing. It clears them all with **one** `strip --recommendation` call over their Short Titles, which deletes each named block's `<recommendation>`, `<depends-on>`, and `<applied-principle>` children and keeps every `<alternative>`, so the next recommendation pass re-picks under the revised goal and the answer sweep cannot record a pick formed under the old one. The clearing is **not transitive**: a block whose `<depends-on>` names a cleared block keeps its pick and its tag. Clearing those picks is the only change it makes to `open_questions.xml`, and it otherwise **never cascades** the downstream impact (which decisions, open questions, out-of-scope entries, and already-derived tasks the new goal may invalidate) — no block is removed, added, or reworded, and no other section of `requirements.md` is touched; reconciling that impact is left to you, via `/review-milestone-requirements` afterward. Offered by `/discuss-open-question` when a deliberation concludes the goal must shift, and directly invocable. It commits its Goal edit and the picks it cleared together, path-scoped to `<MILESTONE_DIR>/requirements.md` and `<MILESTONE_DIR>/open_questions.xml`, under a `Goal-revision: <milestone_id>` subject, and prints nothing about the cleared picks.

### `capture-milestone-principle-updates <milestone_id>`

The **on-demand** principle harvester — the **sole writer** of the project-wide principle store `milestones/answer_decision_principles.md`. It takes a **required** `<milestone_id>` (the milestone directory name under `milestones/`, e.g. `milestone_12_user-guide`, exactly as `/specify-milestone-starting-state` takes it) and runs against any milestone whose `milestones/<milestone_id>/requirements.md` exists — the current milestone, an unfinished one, or one long finished (backfill included); it never consults the current-milestone pointer or the milestone's finish status. Running it right after `/finish-current-milestone` is the natural moment, since the milestone's answer set is complete by then, but finish is never a precondition. Two start-of-run guards are each a one-line notice plus a single confirmation, never a stop: a milestone that already has a `Principle-capture:` commit, and a store carrying uncommitted edits (which then become the baseline the rewrite builds on). It walks the milestone's answer commits across **all three provenances** with a path-scoped `git log -- milestones/<milestone_id>/open_questions.xml` (every answer removes its block from that file, and the path is itself the lower boundary) and reads each commit with one `git show` naming both `open_questions.xml` and `requirements.md`: from the `open_questions.xml` hunk's removed lines — only those within the answered block's own `-<open-question id="…">` … `-</open-question>` boundaries, never a sibling block the cascade mooted or a stray line it cleared from a sibling that still stands — it reconstructs the `<question>`, the `<alternative>` elements, the cited `<applied-principle>` elements, and the `<recommendation>` you saw, and from the `requirements.md` hunk's added lines the decision you recorded. Manual and alternative answers that overrode the recommendation are the **override signal**: where such a commit carries no rationale of yours, it asks why you preferred your option — showing its best guess, one prompt per commit, each skippable, with a one-shot accept-every-guess / skip-every-prompt choice up front so backfill stays workable. Accepted recommendations are **evidence only**: a cited principle is reinforced (and shielded from pruning in that pass), a contradicted one flagged. From the override reasoning and deliberated manual bodies it distills generalizable keep/eliminate directives, dedups them against each other, and composes **one whole-store rewrite** — adds, revisions, prunes, merges, generalizations, and shortenings together, salvaging a contradicted entry by narrowing, generalizing, or replacing it before deleting it, and holding every directive to a roughly 40–80-word target under the "as short as it can be while still reading as an intuitive rule" test — written in place, printing no diff. You review the working-tree change with `git diff`, request changes in conversation, and **one confirmation gates the commit**: on acceptance it commits the store path-scoped under `Principle-capture: <milestone_id>`, with one body line per store change naming its kind and the answer that drove it; on rejection it restores the store to its pre-write snapshot and commits nothing. An empty commit range, a set that neither generalizes nor contradicts the store, and a rewrite identical to its baseline all yield the same single-line "nothing captured" report.

### `provide-alternatives-to-all-open-questions`

The **alternatives pass** — the first of the two annotating passes over a milestone's questions, which together are the argument-free batch form of `/discuss-open-question`. It gathers the current milestone's questions **once**, in two calls to the open-question tool: `list` (every block's id — an empty print stops the run) and `list --without-alternatives` (the ids of the blocks carrying no `<alternative>` element, the ones this run annotates — an empty print is the no-op); it runs no `locate` and holds no block. Before the first dispatch it creates the run's **scratch directory** once with `mktemp -d` — a fresh, uniquely named directory under the system temp location, outside the repository, that belongs to this run alone, so no other run's returns can reach it. It then dispatches one `provide-alternatives-to-open-question` subagent per such question, read-only toward the project but for one scratch file, passing each a prompt that carries only three values: that question's Short Title, the resolved milestone directory, and the scratch directory — the values the orchestrator already holds, no question text and no block, since the subagent fetches its own block and its sibling scope through the tool. The dispatches go out **all together** on Claude Code (one message of `Agent` calls, each run in the background) and on Antigravity (one `invoke_subagent` call with one entry per question), and on Codex in rounds of at most the session's `agents.max_threads` cap (6 by default), with no ranking and no ordering, because an alternative set is enumerated against the sibling questions as scope only, never against how a sibling will settle, so no dispatch reads what another wrote. Each subagent writes its `<alternative>` elements to `<scratch dir>/<Short Title>.xml` — under a temporary name, renamed into place, so no scan ever selects a half-written file — and ends with the bare token `DONE`, or `FAILED: <reason>` when it could not land that file: the orchestrator gets nothing back but that token, so a return never travels through its context. Every subagent enumerates under the shared enumeration core's rules — axes named first, each option a position on them, the set **distinct** and **covering** the underlying decision (not doing the thing included where honestly viable), and no count guideline, so a set holds as many options as its axes and their viable combinations give it; the orchestrator itself states and checks none of them. It is the **sole document mutator**, and every write is the tool's. As each agent ends, a last non-whitespace line of its final message beginning `FAILED:` is an explicit failure — that question is skipped with that reason and never repaired; this last-line verdict is the only judging the orchestrator does itself, and a `DONE` is never cross-checked against the scratch directory. Landed files are embedded and committed **in batches**, each batch **one fixed shell call** shown in full in the skill and run exactly as written: it scans the `*.xml` files directly inside the scratch directory (never a file still under its temporary name), takes each Short Title from the file name alone, redirects the file into `embed --alternatives`, commits each question the tool accepted, and moves every file it piped, accepted or refused, into a `processed` subdirectory, so the next scan sees only files that landed since and no file is piped twice — the record of what was piped lives on disk, never in the orchestrator's context. How often that call runs follows how the host collects returns, which reaches the pass only as named slots filled from each host's definition (the opening paragraph's concurrency phrase, the paragraph opening the dispatch step, and the repair lead-in with its two branches), so each host's tree describes only its own wait and repair mechanism and never names another host's. On Claude Code every dispatch runs in the background and each agent's ending wakes the orchestrator with its final message; on Antigravity the one `invoke_subagent` call returns at once and each agent's final message arrives as a message that wakes it; on both the call runs **once per wake-up** that brings landed returns, over whatever has landed by then, and no shell loop, timer, or event monitor serves as the wait. On Codex the orchestrator calls `wait_agent` again, with a long timeout, until every agent of the round has delivered its final message, and then runs the call **once per round**; a finished agent holds no thread, so the next round goes out at the full cap. A wait that ends with agents still unfinished skips nothing: it batches what landed and waits again for the rest, with no limit. Inside the call the tool does the validating: it slices the fragment from the first `<alternative` line through the last `</alternative>` line (text above or below is discarded, not a failure), parses and validates it — no `<open-question>` or `<question>` line, no text outside the elements, at least one `<alternative>`, no element of the recommendation half, no unknown element, a target block carrying no `<alternative>` yet — and writes those elements into the existing block re-rendered in canonical form, so indentation and escaping are the tool's, never the return's. The call prints nothing when every file embedded and committed, and otherwise one line per refused file or failed commit: the Short Title, a tab, then the tool's `Error:` line or git's first line. A refused file buys its question **exactly one repair attempt**, and all of one batch call's repairs go out **together, in the same turn**, immediately rather than held back as a second phase (the orchestrator never drops or rewrites a returned element): while the orchestrator still holds the dispatch's handle it asks *that same agent* to rewrite its file — on Claude Code with `SendMessage` to the agent id the `Agent` call returned, on Antigravity with `send_message` addressed to the conversation id `invoke_subagent` returned, on Codex with `followup_task` addressed to the task name `spawn_agent` returned — sending a fixed one-paragraph corrective message whose single fill is that `Error:` line and which quotes both shape tests; where the handle is gone it re-dispatches **one** fresh agent with the same prompt plus that message as a shape reminder (on Codex under a task name no earlier dispatch used). On Claude Code and Antigravity the repairs are sent without blocking and each later wake-up that brings a repaired return runs a batch; on Codex a round's repair set gets its own `wait_agent` wait and batch before the next round goes out. The repaired file lands at its Short Title's path, the refused one already moved aside, and the next batch call embeds it like any other; only a **second** failure — a second refusal or a repaired agent ending `FAILED:` — is the skip, that question alone, its block left byte-for-byte untouched and its Short Title printed with the reason alongside the terse line, never a run stop. A failed commit is noted the same way and never repaired, since its block already carries the alternatives. A question annotated only after the tool discarded surrounding text, or only after the repair, gets no console mention at all. It **commits once per annotated question, inside the batch call**: a commit path-scoped to `<MILESTONE_DIR>/open_questions.xml` (never `git add -A`) under `Alternatives-annotation: <Short Title>` with no body and git's success output silenced; a skipped question commits nothing. It **deletes nothing** — no scratch file, no `processed` subdirectory, no scratch directory: the run's directory and every return in it, embedded or refused, are left to the system's own temp handling, so a refused return the advisory reports stays available for inspection and no delete command meets a permission prompt in a headless chain. After the last batch call one more `list --without-alternatives` is the **closing check**: every gathered id it still prints that is not already in the advisory joins it with the fixed reason `no annotation landed` — an agent that ended without its file landing, whatever its final message said — and its block stays bare for the next run to re-dispatch. It is **idempotent**: the `--without-alternatives` filter is the whole skip test, so a block already carrying `<alternative>` elements is never re-annotated — that set is **frozen** for the recommendation pass, which picks against it (to force a fresh set, run the tool's bare `strip` on that block — one or more Short Titles — which deletes every child but its `<question>`, the alternatives and any pick made against them alike, and re-run; `open_questions.xml` is never edited by hand). When such a regenerated block's new alternative ids differ from what surviving dependents' `<depends-on>` tags assumed of it, those dependents are left exactly as they are — no strip, no rewritten `option`, no mismatch advisory: only the answer-time cascade reconciles a tag against the option actually recorded. Because it records no decisions and triggers no cascades — the question set never shrinks under it — it needs no per-question live re-check, no re-gather loop, and no clean-working-tree precondition. Its report is one fixed line chosen by the closing check's print, `Alternatives embedded.` when a gathered id is missing from it, or the distinct no-op line with its reason, plus the still-skipped advisory: the questions left without alternatives — an agent that ended `FAILED:`, a file refused again after its repair, a failed commit, or no annotation landed — which `/recommend-all-open-questions` stops on until a re-run annotates them.

### `provide-alternatives-to-open-question` (subagent)

Alternatives subagent dispatched once per question lacking alternatives by `/provide-alternatives-to-all-open-questions` — not user-invocable — read-only toward the project, its one write being its return as a single scratch file outside the repository. Given only three values — one question's Short Title, its milestone directory, and the run's scratch directory, which the orchestrator has already created — the prompt carries no question text and no block, and it fetches the rest itself: it reaches `open_questions.xml` through exactly two tool calls, one `locate` of its own Short Title (whose verbatim print of the block is its primary source, and whose `Error:` line is its `FAILED:` reason) and one `list --with-question` (every block's id, a tab, then its question text, one per line in document order), which is its **only** source of sibling scope — it never runs `locate` on a sibling, so no sibling's embedded alternatives or pick reaches it, and it never reads `open_questions.xml` whole. It reads `requirements.md` whole with the file-reading tool as prose, grounds in the live project (read-only) — the sibling questions supplying scope and nothing more, since no sibling has settled on anything while alternatives are being enumerated — and enumerates the honest alternatives, sourcing that analytical core from the shared `core/shared/alternatives-procedure.md`: it first names the axes the underlying decision turns on — approaches, degrees or values wherever the trade-off changes, each premise the question's wording takes for granted, and on every axis a none position — weighs not doing the thing on every question (postponing counts as one form of it, so at most one such option), builds each option as one position on every axis (on a multi-axis question, every combination weighed and each viable one described), varies no axis a sibling question owns (naming such an axis as a condition in the drawback when an option's viability depends on it), and reworks the set until it is **distinct** (every two options differ in substance on at least one axis) and **covering** (it covers the underlying decision rather than the question's wording — every viable position and combination appears, the none position included). There is no count guideline — the set's size follows from its axes and their viable combinations — and an option's what-it-is text states only its position on each axis, however long that takes, every reason for or against it going in its advantage or drawback. It then writes the ready-to-embed `<alternative>` elements alone — one per option, each with child `<advantage>`/`<drawback>` — as the whole content of its scratch file, never the `<open-question>` wrapper or `<question>` element (which the document owns) and never a `<recommendation>`, `<applied-principle>`, or `<depends-on>` element (which the recommendation pass writes later over the frozen set). The children must be well-formed XML (a literal `&` or `<` in text is written `&amp;` or `&lt;`), but their indentation and escaping are not load-bearing: the tool's `embed --alternatives` parses the fragment and re-renders the block in canonical form. Its return step is a **draft → self-check → write → `DONE`**: the elements it renders are a draft, checked against the two shape tests the tool's extraction keys on — the draft's first non-whitespace text is `<alternative`, its last is `</alternative>` — and revised until both pass before it is written with nothing accompanying it (every grounding finding is spent inside the elements themselves — in an option's what-it-is text, its `<advantage>`, or its `<drawback>` — and the rest dropped). It writes the checked draft to `<scratch dir>/<Short Title>.xml.part` and renames it with one `mv` to `<scratch dir>/<Short Title>.xml` — the Short Title exactly as given, never shortened or slugged, because the orchestrator derives the question from the file name alone — so the orchestrator's scan never selects a half-written file; a Short Title holding a path separator fails the write, and that failure is a `FAILED:` like any other. Once the rename has succeeded it ends its session with the bare token `DONE` and nothing else — not the path, which the orchestrator fixed at dispatch, and not the elements, which the orchestrator reads from the file. If it cannot land that file, it ends instead with `FAILED: <reason>` as its last line and nothing else, writing no file at `<scratch dir>/<Short Title>.xml`; `DONE` and `FAILED: <reason>` are its only two final messages. It mutates nothing in the project; the orchestrator owns all embedding and committing.

### `recommend-all-open-questions`

The **recommendation pass** — the second of the two annotating passes, the batch form of `/discuss-open-question`'s pick, and an **inline skill that dispatches no agent**. It gathers the current milestone's questions **once**, in three calls to the open-question tool: `list` (every block's id — an empty print stops the run), `list --without-alternatives` (the **stop test**: any id printed means a block has nothing to pick from, so the run stops without changing anything, prints those ids, and points at `/provide-alternatives-to-all-open-questions`), then `list --without-recommendation` (the ids of the blocks carrying no `<recommendation>` element, the ones this run annotates — an empty print goes straight to the batched shell call, which then carries no block and only sorts). It then reads `requirements.md` and `open_questions.xml` **whole** — every block's `<question>` and frozen `<alternative>` set, and every recommendation already standing on a sibling — and follows the shared pick core `core/shared/recommend-procedure.md` over **the whole recommendation-less set, held in view together as one judgment**: grounding once (the live project, the principle store as a weighted advisory factor, the sibling questions with their alternatives and standing picks) and forming one pick per block that names one of that block's own `<alternative>` ids, never adding to or dropping from the frozen set, so the picks cohere with one another and with the recommendations already standing. A pick that leans on a sibling settling on one of its options — a sibling with a standing recommendation, or one picked in this same pass — is declared as a `<depends-on question="…" option="…"/>` child naming that sibling and one of its alternative ids. A set a recorded decision has partly outdated still gets a pick — the best option still viable, the rationale naming the option the decision closed and why — and only a block **no** option of which survives is skipped, its advisory naming the remedy (the tool's bare `strip` on that block, then the alternatives pass, then this skill again). It is the **sole document mutator**, and every write is the tool's: it renders each block's `<applied-principle>` elements (one per confirmed principle that bore on the pick — a sibling of the recommendation, never baked into its text), its `<depends-on>` elements, and its single `<recommendation option="…">` carrying the one-line rationale, and writes them all in **one fixed shell call**, shown in full in the skill and run exactly as shown, which carries every picked block with no cap and no splitting rule. For each block, **in any order**, the call runs that block's own `embed --recommendation` process on a quoted heredoc — the tool resolves each `<depends-on>` against its target's alternatives, which every block already carries, checks that the fragment holds no `<alternative>` and exactly one `<recommendation>` naming one of the block's own ids, refuses a block already carrying a `<recommendation>`, and writes the block re-rendered in canonical form without adding, dropping, or editing an `<alternative>` — and, only when that embed exits 0, the block's `lift`, appending its printed `<option> — <rationale>` line to the commit body. A refused block is refused by its own process, with the document unchanged for that block while every other block still lands, and the call prints its Short Title, a tab, and the tool's `Error:` line. After the last block the call carries out the commit procedure's three steps itself and **commits once per batch call**: path-scoped to `<MILESTONE_DIR>/open_questions.xml` (never `git add -A`), under `Recommendation-annotation: <milestone_id>`, with the lifted lines as the body, and only when that body is non-empty. Then, inside the same call, as a **fixed step of every run that found questions** — so a run with nothing left to pick, or with every block skipped, runs the same call with no block in it, with no branch and no second form — it runs the tool's `sort`, which rewrites the document with the `<recommendation>`-bearing blocks first, in exactly the order the answer sweep's `walk` will dispatch them, and every un-annotated block last in its prior order (so a reader of the document meets the questions whose answers no dependency can nullify before the questions that build on them), and commits that reorder as its own `Question-ordering: <milestone_id>` commit behind the dirty-own-path guard — the sort's only no-op test, so the commit lands exactly when the sort moved a block, and a run that annotated nothing and moved nothing commits nothing. Each commit that lands prints one fixed, identifier-free marker line (`annotation commit landed`, `ordering commit landed`), with git's success output silenced. A refusal is a rendering slip: the pass corrects every refused block against the `Error:` line printed for it and re-sends them all together in **at most one** more call of the same shape, which commits and sorts again; a block that call refuses again is skipped and reported in the advisory with its Short Title, that second `Error:` line verbatim, and the remedy of re-running the pass, which re-picks it because it still carries no recommendation. A run is thus bounded at two batched calls and two annotation commits. The open-question tool is unchanged by the batching: one `embed` process per block is what confines each refusal to its own block. It is **idempotent**: the `--without-recommendation` filter, backed by the tool's refusal of an already-annotated block, is the whole skip test, so a standing recommendation is never re-picked and is read only as context a new pick may build on (to force a fresh pick, run the tool's `strip --recommendation` on that block — one or more Short Titles — which clears its `<recommendation>`, `<depends-on>`, and `<applied-principle>` children and keeps its `<alternative>` children, and re-run; the answer-time cascade clears a dependent's pick the same way, so an override costs only a re-run of this pass). When such a re-picked block's new recommended option differs from what surviving dependents' `<depends-on>` tags assumed, those dependents are left exactly as they are — no strip, no rewritten `option`, no mismatch advisory: a `<depends-on>` records what a dependent assumed, and only the answer-time cascade reconciles it against the option actually recorded. Because it records no decisions and triggers no cascades, it needs no per-question live re-check, no re-gather loop, and no clean-working-tree precondition. Its report is the one carve-out from the one-success-line rule: it carries **two** fixed success lines and picks one by what the run committed, read from the marker lines every call of the run printed and never from a test of the sort's outcome, in strict order — an `embed` wrote, `Recommendations embedded.` (whether or not the sort also committed); else the sort committed, `Questions reordered.`; else the distinct no-op line with its reason — and prints the still-skipped advisory (a block no option of which survived, and a block the re-send refused again) alongside whichever line is chosen. The embedded recommendations are later lifted and recorded as decisions — under `Recommendation-answer:` — by `/answer-open-question-with-recommendation` (or the `/answer-all-open-questions-with-recommendation` sweep).

### `derive-tasks`

Converts the current milestone's `requirements.md` into `TASKS_TODO.md` — a complete, dependency-ordered list of atomic, AI-completable **brief-level** tasks. Decomposes the milestone into high-level briefs, proves every requirement is covered with a traceability matrix, orders them by dependency, and writes those briefs into `TASKS_TODO.md` itself, in order, as the finished task sections. While building the briefs and the matrix it applies one **tie-break**: where two `## Decisions` entries cannot both hold as written, the **later-recorded entry governs** the brief, while an entry that only refines, narrows, or extends another is no conflict. Every pair listed under `## Noted contradictions`, when that section stands, is taken as conflicting as noted, without re-judging, and any other pair the runner itself finds conflicting is resolved the same way. Which entry is later is read from git, never from the entries' positions in the file and never from the note: the commit that added each entry's lines, found by `git blame` or a pickaxe search (`git log -S`) path-scoped to `<MILESTONE_DIR>/requirements.md`, the entry from the newer commit being the later-recorded one. Nothing is flagged for either kind of pair, neither in the plan it presents nor in its report: the earlier entry's conflicting text maps to no brief and counts as no gap in the matrix, while whatever else of that entry still holds maps as usual. A brief and a task section are the same altitude, so writing the brief down *is* the authoring step: there is no second pass and nothing is handed off. Each section is a `##` title, a 1–3 sentence description of what is to be achieved, why the milestone needs it, and how it would be verified, and a trailing `---` — the completer derives the flow and the formal acceptance bar itself. The whole ordered list goes in one fixed shell call: a single `initialize` call of the plugin's task-list tool reads every section on standard input, validates them all, and replaces `TASKS_TODO.md` with its heading and the list in one write — or, refusing any section (two titles that fold to the same title, an empty title or body), prints one `Error:` line and leaves the file byte-for-byte unchanged, so a partial or reordered plan never lands — chained with the commit procedure's guard, path-scoped add, and commit under `Task-derivation: <milestone_id>`. Requires all open questions to be resolved first: the open-question tool's `list` over the milestone's `open_questions.xml` must print nothing, and it stops listing the Short Titles otherwise. That empty `list` is the whole precondition, so a note standing under `## Noted contradictions` never blocks the run.

### `discuss-new-task <issue description>`

Clarifies a rough or oversized issue discovered mid-flight into one or more clear, task-sized briefs through a short conversation, then hands each off to `/submit-task`. Because tasks are brief-level, each brief maps near-1:1 onto the task section `/submit-task` writes — a title and a few sentences, with no further fleshing out. Use it when the affected system, desired behavior, or verification isn't yet clear, or when one issue is really several tasks.

### `submit-task <issue description>`

Adds a single, already-clear issue to `TASKS_TODO.md` as a **brief-level task section** — a `##` title, a 1–3 sentence description of what is to be achieved, why it is needed, and how it would be verified, and a trailing `---`, and nothing else. Triages for duplicates and decides where the task belongs, then authors and inserts the task **inline, in the current conversation** so the authoring context stays available for follow-up tweaks. The insert is the plugin's task-list tool's `insert` call — the title as an argument, the body on standard input, and exactly one position flag, `--end`, `--before "<Task Title>"`, or `--after "<Task Title>"` — chained in one shell call with the path-scoped commit of the inserted task under a `Task-submission:` subject. An anchor that names no section, or a title `TASKS_TODO.md` already holds, is refused with one `Error:` line and the file unchanged: the skill then inserts and commits nothing and stops, quoting that line, so a task never lands anywhere but the position it chose. It is the same format `/derive-tasks` writes, so every task in the list sits at one altitude. For vague or multi-task issues, route through `/discuss-new-task` first.

### `complete-all-tasks`

Orchestrator: completes all tasks in `TASKS_TODO.md` top to bottom, spawning one subagent per task — which moves its finished task with the plugin's task-list tool's `move` and stages its change set in the same shell call — and committing after each success — **once per task**, committing the index the agent staged (its change set, plus the two task-list files, never `git add -A`) under the subject `Task-completion: <task heading>` with no body — the same subject inline `/complete-task` uses. Stops on first failure.

### `complete-task <task_name>`

Completes a single named task from `TASKS_TODO.md` **inline, in the current conversation**. Running inline keeps the work context (what changed, why, how it was verified) in the conversation so you can ask follow-up questions or request tweaks right after. The task is moved from `TASKS_TODO.md` to `TASKS_DONE.md` by the plugin's task-list tool's `move` call, which takes the full task heading and the derived acceptance bar on standard input and writes that bar under the `**Verified:**` label itself; that call is chained in one shell call with the commit of the task's change set path-scoped — the files it created or edited plus the two task-list files, never `git add -A` — under the subject `Task-completion: <task heading>` with no body, the same subject `/complete-all-tasks` uses per task. A refused move prints one `Error:` line with both task files unchanged and commits nothing. Use `/complete-all-tasks` to run the whole task list unattended.

### `ask-in-milestone-context <question>`

Answers a free-form, informational question about the current milestone — its goal, recorded decisions, done and pending tasks, and the actual deliverables those tasks produced — grounding the answer in the live files and artifacts rather than memory. **Read-only and conversational**, usable any time: use it to look back on finished work ("how did task X end up handling Y?", "where did we put Z?"), to take stock ("what's left and why?"), or to surface context before deciding what to do next. When the answer reveals a concrete next step, it offers the right skill — `/discuss-open-question`, `/submit-task` or `/discuss-new-task`, `/discuss-milestone-goal`, `/complete-task` — but performs none of their work itself.

### `finish-current-milestone`

Verifies all tasks are done, writes a completion summary to `milestones/README.md`, and updates `CLAUDE.md` only for lasting changes to the project's environment context. Clears the current-milestone pointer — run `/define-milestone-goal` to define the next milestone, then `/goto-next-milestone` to activate it.

### `goto-next-milestone`

Activates the lowest-numbered undone milestone without asking: scans `milestones/` for the directories `/define-milestone-goal` created whose number has no heading under `## Milestone History`, and updates `milestones/README.md` to point at the lowest-numbered one as the current milestone. It stops only when the pointer does not read `none` (run `/finish-current-milestone` first) or when no undone milestone exists (run `/define-milestone-goal` first). Creates no files or directories. A defined milestone that is never finished is picked on every run, so an unwanted one is skipped by removing its directory, for example by reverting its `Milestone-definition:` commit.
