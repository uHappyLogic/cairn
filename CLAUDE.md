# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A plugin (`cairn`) for Claude Code and Antigravity that provides a milestone-driven development workflow. It ships as a set of skills, a few agents, shared procedures, and one stdlib-only Python tool (the sole writer of each milestone's open-question document) that move a project from a vague idea through discussion, planning, completion, and archival — one milestone at a time.

(each named block verbatim, in the order named); lift SHORT_TITLE [--alternative ID] (one line, "<option> — <rationale>" from the <recommendation>, or "<id> — <what-it-is>" from the named <alternative> with its <advantage>/<drawback> excluded); add SHORT_TITLE (appends a bare block whose <question> text is the stdin body; a duplicate id is refused); strip SHORT_TITLE... (deletes every child but <question> from each named block, touching no other block and no tag naming it); embed SHORT_TITLE (the recommend agent's whole message on stdin — slices from the first <alternative line through the last </recommendation> line, parses, validates: no wrapper or <question> line, no text outside the elements, at least one <alternative>, exactly one <recommendation> naming one of them, every <depends-on question="…" option="…"/> resolving one hop to an annotated block and one of its <alternative> ids, no unknown element, child order never checked — then writes the children grouped by kind into a block that must not yet carry a <recommendation>); remove SHORT_TITLE [--option RECORDED_OPTION] (deletes the block and, in the same write, reconciles its dependents: with --option — which must be one of the removed block's own <alternative> ids or the call is refused — a dependent whose <depends-on> assumed that option loses only the tag and every other dependent is stripped, without it every dependent is stripped, transitively over dependents of stripped blocks, so no tag is left naming a removed or stripped block); walk (the answer sweep's dispatch order over the <recommendation>-bearing blocks: edges from <depends-on question> values to gathered blocks, edges to an absent or un-annotated block dropped, origins first then by depth, same-depth ties in document order, a stranded cycle broken by promoting its document-order-first member). Every id — Short Title, alternative id, recorded option — is compared un-escaped and case-folded. Free text (add's question, embed's message) travels on standard input only, read once via sys.stdin.buffer and decoded as UTF-8 by the tool — a quoted-delimiter heredoc at every runtime site — and a terminal stdin is refused rather than blocking. Output contract: a read prints only bare un-escaped values, one per line (an empty set is empty stdout with exit 0 — emptiness is data, never a failure); a mutator prints nothing on success; every failure is exactly one Error: <reason> line on stderr with exit 1 and the document byte-for-byte unchanged (a malformed invocation gets argparse's own usage and exit 2); no traceback ever reaches the runner. Every write re-renders the whole document in one canonical form: a bare <open-questions> root with no XML declaration or attributes (the empty document is <open-questions/>), one element per line at 2 spaces per depth (root 0, block 2, children 4, an alternative's what-it-is text and <advantage>/<drawback> at 6), children grouped by kind in the fixed order <question>, <alternative> (returned relative order), <applied-principle>, <depends-on>, <recommendation>, every text and attribute value folded to one line, <tag/> self-closing with no space, all five predefined entities substituted in text and attributes alike, UTF-8 with LF line ends and one trailing newline — so write(read(x)) == x on a canonical file, git diffs and capture's removed-line reconstruction see one greppable line per child, and the recommend agent's indentation, escaping, and child order are never load-bearing
scripts/hosts/<host>/        — one declarative host definition per directory (scripts/hosts/claude/, scripts/hosts/antigravity/): a settings.toml holding the same key set for every host — plugin_name, the plugin_root literal that replaces {{PLUGIN_ROOT}}, prose_drop_patterns, strip_frontmatter_keys, renames, exclude, and the [layout] of core/'s four top-level directories (skills, agents, shared, tools — a layout that omits one fails validation) — beside that host's template files (its manifest or manifests and its distribution README.md, each with {{VERSION}} and {{NAME}} slots, plus a slot-free CONTRIBUTING.md pointer that sends distribution-repository visitors to the root repository for issues, pull requests, and vulnerability reports, and a slot-free .github/workflows/traffic-badges.yml, that host's copy of the traffic workflow), every one rendered to the same relative path in the host tree; adding a host means adding a definition directory, never host-specific Python

The runtime layer is Markdown plus one program: the skills, agents, and shared procedures are plain Markdown, and `core/tools/open_questions.py` is a stdlib-only Python script that runs on Python 3.9 or later with no dependencies of its own — the one runtime prerequisite the installed plugin has, checked once per project by `init-milestone-base-workflow`. Its pytest suite lives under `tests/` and runs with `uv run pytest`. The maintainer tooling is the two Python scripts under `scripts/`, run with `uv` (`pyyaml` is their one dependency, declared in `pyproject.toml` and pinned in `uv.lock`; pytest sits in the `dev` dependency group). The repository's automated checks are the build's validation gate and that pytest suite, run locally and by the `.github/workflows/drift-gate.yml` workflow on every push and pull request.

## Skills and the workflow they encode

The skills form a linear pipeline. Each skill's SKILL.md defines its exact behaviour:

```
init-milestone-base-workflow    ← one-time bootstrap: checks for a Python 3.9+ interpreter answering as python3 first (stopping before any write when none does), then creates milestones/ + milestones/README.md
discuss-milestone-goal          ← optional sharpening conversation, creates no files
define-milestone-goal           ← creates milestones/milestone_<N>_<slug>/ with an empty open_questions.xml (the tool's create, run first so a missing interpreter leaves nothing behind), requirements.md, TASKS_TODO.md, TASKS_DONE.md — four paths in one Milestone-definition: commit
specify-milestone-starting-state ← fills "Relevant starting state" in requirements.md
review-milestone-requirements   ← repeatable loop engine: each pass reads requirements.md and open_questions.xml whole, reconciles existing questions against recorded decisions (pruning or deduping a block with one bare tool remove call, whose write strips every `<depends-on>` dependent transitively, recording no decision), surfaces new gaps (each authored with one tool add call, the question text as a heredoc body), commits both files, and reports convergence from the tool's list (empty = converged); run repeatedly
recommend-all-open-questions    ← orchestrator (batch form of discuss-open-question): gathers once in three tool calls (list, list --unannotated, locate over the surviving ids — the verbatim blocks are both the ranking input and the dispatch prompt), ranks the surviving ones most-significant-first by judgment over that gather alone, dispatches one read-only recommend-open-question subagent each strictly sequentially in that order, reads only the last-line FAILED: verdict itself, and pipes every other return whole to the tool's embed through a quoted heredoc (which extracts the fragment, validates it, and writes the block in canonical form inside the existing `<open-question>` block) before the next dispatch, so later recommendations may build on already-embedded siblings and declare each such use as a `<depends-on question="..." option="..."/>` child (embed resolves it against a still-present annotated sibling); a refused embed's Error: line fills the one-slot repair template for one repair, a second failure is the per-question skip; sole mutator (through the tool), commits open_questions.xml once at the end of the run (subject Recommendation-annotation: <milestone_id>, path-scoped, behind the dirty-own-path no-op guard), idempotent via the --unannotated filter, stale recommendations cleared with the tool's strip then a re-run (no hand edit), no clean-tree precondition
recommend-open-question         ← (agent, in core/agents/) read-only recommendation subagent: grounds in the live project, the principle store, and the sibling recommendations already embedded in open_questions.xml (read whole) when it reads, returns one question's `<open-question>` child sub-elements as well-formed XML (bearing-principle `<applied-principle>` elements and self-closing `<depends-on question="..." option="..."/>` declarations — one per already-annotated sibling it builds on, never for an un-annotated one — sibling to the liftable `<recommendation option="...">` element; indentation, escaping, and child order are the tool's on write), never edits documents
discuss-open-question           ← structured conversation about one open question (located with one tool locate call, whose Error: line is the mismatch report; requirements.md and open_questions.xml then read whole for reasoning only); sources its alternatives+recommendation core from core/shared/recommend-procedure.md and adds its own "what would change your mind" layer; on a decision offers answer-open-question, and if the goal itself must shift also offers modify-milestone-goal — when both apply, modify-milestone-goal runs first so the answer records against the revised goal
answer-open-question            ← records a literal-answer decision — the decision under ## Decisions of requirements.md, the block removed from open_questions.xml through the tool's remove — AND commits both files (subject Manual-answer: <Short Title>, rationale in the body — the provenance marker capture-milestone-principle-updates reads as an override signal, distilling the body rationale and asking for the reason only when the body records none); no longer chains to capture. Literal-only: recording an embedded recommendation moved to answer-open-question-with-recommendation, and the retired sentinel "record the recommendation" (exact whole-string) is now a redirect guard that stops without recording and points there instead

Lets a user override the recommended option or break a tie. No batch/agent form (which alternative wins is per-question human judgment, not an orchestrator-sweepable rule); its Alternative-answer: subject is the provenance marker by which capture-milestone-principle-updates reads it, like Manual-answer:, as an override signal — the body carries no user rationale, so capture asks for the override reason at harvest time

## Milestone file structure

Each active milestone lives at `milestones/milestone_<N>_<slug>/` and contains exactly:

- `requirements.md` — Goal, Relevant starting state, Decisions, Out of Scope — prose Markdown; no question block ever lives here
- `open_questions.xml` — the open questions, one `<open-question id="Short Title">` block each under a single bare `<open-questions>` root, in the canonical form the tool writes; created empty by `define-milestone-goal` (the tool's `create`) and written only by `core/tools/open_questions.py`, never by hand — its "no `<open-question>` child remains" state is the review pass's convergence verdict and `derive-tasks`'s precondition
- `TASKS_TODO.md` — pending tasks ordered by priority (highest first), `##` headings + `---` separators
- `TASKS_DONE.md` — completed tasks appended in the same format

`milestones/README.md` is the source of truth for which milestone is current. Milestones defined before the split — this repository's own `milestone_01` through `milestone_27` — hold the three Markdown files only, their questions long answered under a now-empty `## Open questions` heading of `requirements.md`; there is deliberately **no migration of and no compatibility with** pre-split milestones: no skill reads that heading any more, and a question skill run against a milestone with no `open_questions.xml` stops on the tool's `Error: … does not exist` line.

## Invariants to preserve when editing skills

- `init-milestone-base-workflow` is the one-time bootstrap; it is additive and idempotent — it never overwrites an existing `milestones/README.md` or `CLAUDE.md`, only creating missing files and appending missing sections. It must leave `milestones/README.md` with a `Current milestone:` pointer line. It runs the plugin's one runtime prerequisite check **first, ahead of its state detection, on every invocation**: `python3 --version` must answer with Python 3.9 or later (probing `python --version` only when `python3` is missing or too old, so its message can say the interpreter exists under the other name and must be exposed as `python3`; `python`'s result decides nothing about passing), and when no interpreter passes it **stops before any write** — a clean stop, never a notice-and-confirm — with one full message: what it looked for, what it found, the install or expose-as-`python3` remedy, and that a re-run completes the bootstrap with nothing to undo. The stop is what makes the goal's checked-once clause hold: the scaffold exists only to enable the skills that follow, and the very next one, `define-milestone-goal`, runs the tool's `create`, so a scaffold written without an interpreter would fail at its first step as a raw shell error inside a skill kept check-free by design. Its `milestones/README.md` and `## Milestone Workflow` templates name the four milestone files.
- `review-milestone-requirements` (renamed from the old `highlight-milestone-requirements-open-questions`) is the repeatable engine of the requirements-iteration loop and the **sole author** of `<open-question>` blocks: each pass **reconciles** the existing blocks against the recorded `## Decisions`, **surfaces** new gaps (authoring each with one tool `add <MILESTONE_DIR> "<Short Title>"` call — the question text as plain prose in a quoted heredoc body, no XML and no entities; the tool appends the bare block after the existing ones, folds and escapes the text, and refuses a duplicate id with its `Error:` line, the retry), and **reports convergence** from one tool `list <MILESTONE_DIR>` call (converged when it prints nothing — exactly `derive-tasks`'s precondition, so `open_questions.xml` must hold no `<open-question>` block before `derive-tasks` can run; what it prints is the still-open list). It reads `requirements.md` and `open_questions.xml` **whole** with the file-reading tool and reasons over them (reconcile/author are cross-document judgment, the one thing done directly), while every listing of the blocks and every change to the question document is a tool call — it never edits `open_questions.xml` by hand, and what it authors is the two judgments a block carries: the standalone question text and the 2–5-word case-insensitively-unique Short Title. It is the **only** skill besides the answer path that may remove a question block, and only as *cleanup of already-recorded state*: it may remove a block (one bare `remove <MILESTONE_DIR> "<Short Title>"` call — no `--option`, since a prune or dedup records nothing) solely when it can cite a `## Decisions` entry that already covers it, or dedup an exact repeat (keeping the clearest) — when in doubt it flags ("possibly resolved — confirm") rather than deletes, and every removal is reported. Because that removal records **no option**, the tool's same write **strips the dependents** of the removed block — every surviving block whose `<depends-on question="…">` names it loses every child but its `<question>` (all `<alternative>`/`<applied-principle>`/`<depends-on>`/`<recommendation>` children), leaving the bare wrapper and `<question>` for the next recommend sweep to regenerate, **transitively** over dependents of stripped blocks until no `<depends-on>` names a block removed or stripped — the same uniform treatment `remove` gives every option-less removal on the answer path. That stripping decides nothing, never removes the stripped block, and adds nothing to the pass's report (the committed diff is its record); the runtime prose states it in one sentence as the tool's contract and restates none of its mechanics. It **never records a decision or answers a question**: folding a decision into `## Decisions` and cascading to mooted siblings stays scoped to `core/shared/answer-procedure.md` (used by `answer-open-question` and `core/shared/answer-with-recommendation-procedure.md`). This boundary — tidy the question set vs. record an answer — is the whole reason the two stay separate. The question set lives as XML in its own document, `<MILESTONE_DIR>/open_questions.xml` (one `<open-question id="Short Title">` block per question under a single `<open-questions>` root, in the tool's canonical form), beside the four prose sections of `requirements.md` (`## Goal`, `## Relevant starting state`, `## Decisions`, `## Out of Scope`), which stay Markdown with no `## Open questions` section; blocks are never placed inline next to the requirement they concern, because keeping the whole question set in the one document the tool owns is what lets the answering and recommendation skills operate on it deterministically, and it is also why each authored `<question>` must stand on its own. It commits both files under `Requirements-review: <milestone_id>`, its dirty-own-path no-op being both files unchanged.
- The answer-recording mechanism (locate the `<open-question>` block by Short Title with the tool's `locate` → fold the decision into `## Decisions` of `requirements.md` as clean prose → remove the block with the tool's `remove`, which reconciles every dependent's `<depends-on>` tag in the same write → cascade to mooted entries with bare `remove` calls) lives in exactly one place: `core/shared/answer-procedure.md`. `answer-open-question`, `core/shared/answer-with-recommendation-procedure.md`, and `answer-open-question-with-alternative` all reference it via `{{PLUGIN_ROOT}}` and never restate the steps. That shared file is **execution-neutral** — it never mentions arg-parsing, committing, or the capture chain — and its **input contract is three fields, the third optional**: a resolved SHORT TITLE, an ANSWER, and a **RECORDED OPTION** — the un-escaped `<recommendation option>` / `<alternative id>` value the caller lifted as the decision, when it lifted one. RECORDED OPTION is what step 5 passes to `remove` as `--option`, verbatim, so the dependents that assumed it are reconciled as an **exact id comparison**; both lifting callers already hold the id at the moment they delegate — `core/shared/answer-with-recommendation-procedure.md` passes the lifted `option`, `answer-open-question-with-alternative` the chosen alternative `id`, each the text before the first spaced em dash of the tool's `lift` print — and `answer-open-question` **explicitly passes nothing**; the core **never derives it by parsing ANSWER**, so the "`<option>` — `<rationale>`" form stays a caller-side rendering convention and never becomes a parse contract inside the core. **Judgment mode is one verdict, not a per-dependent walk**: with RECORDED OPTION absent (a literal answer), step 5 judges in prose — against the closed set of `<alternative id>` values step 2's `locate` printed, never by parsing ANSWER and never dependent by dependent — whether ANSWER **plainly settles on one of the answered block's own alternatives**; when it plainly does, that id is passed as `--option` (the tool's exact-id engine then untags the dependents that assumed it and strips the rest), and when it settles on none, only arguably on one, or the block carries no alternatives, nothing is passed and the bare `remove` strips every dependent. A dependent's tag records an option, not a claim about that dependent, so every per-dependent verdict the literal path could form collapses to this one comparison, which is exactly the one `remove --option` makes — one engine and one write for every answer path, a literal answer reconciling exactly as a lifted one would on the same document. **Strip on doubt** is the rule: the costs are asymmetric (an extra dispatch is cheap and self-healing; a kept stale rationale becomes a wrong recorded decision only a revert undoes), so whenever agreement cannot be affirmed the strip applies — and the accepted cost is that an answer agreeing in substance but matching no listed id (a refinement, a partial answer, a target regenerated with renamed alternatives after the tags were embedded) strips every dependent, a re-dispatch each. The tool **refuses** an `--option` naming none of the removed block's alternatives, document unchanged and the ids listed in its `Error:` line, so a mistyped judgment fails loudly rather than stripping silently. **The fold precedes the removal**: step 4 folds the decision into `## Decisions` and step 5 then removes the block located in step 2 with one `remove` call, whether or not the block carries embedded children — the tool deletes the whole block either way, and no re-query, line range, or boundary token is the procedure's concern. That order is deliberate and must not be swapped back: a failure or interruption between the two edits then leaves the harmless superset (the decision recorded while the question block still stands, which a later pass reconciles) instead of the lossy state where the block is gone and nothing records the decision, so the next sweep no longer gathers the question and it is silently lost. Step 2's `locate` fails as one `Error:` line listing the ids the document holds — the stop-without-changes, quoted verbatim by every wrapper — and step 3 (analyse) is unchanged. Step 6 (cascade) stays last: it folds each mooted entry's implied constraint before removing it with a bare `remove` — no `--option`, since nothing was recorded for it, so every dependent of a mooted entry is stripped (an option-less removal is exactly the inconclusive comparison, so it routes into the strip branch rather than adding a third outcome). **Reconciliation is the tool's, inside the same write as each removal**: every surviving block whose `<depends-on question="…">` names the removed block (ids compared un-escaped and case-folded) takes exactly **one of two outcomes** — **agreeing** (the tag's `option` equals the `--option` given): that one `<depends-on …/>` line is deleted and the block's other children stand; **disagreeing** (everything else — a differing option, or no `--option` at all): every child but the dependent's `<question>` is deleted, leaving the bare wrapper and `<question>` for the next recommend sweep to regenerate. Stripping is **transitive** over dependents of stripped blocks; a stripped block records no decision and is never removed; the comparison is against the option actually **recorded**, never against a target's live recommendation; and no removal ever leaves a dangling tag — there is deliberately **no separate `reconcile` subcommand** to forget, because `remove`'s one optional flag covers the answered block, a mooted sibling, a review prune, and a dedup with one call and one write each, and reconciling one removed block per call in any order reproduces the set-at-once outcome since a strip is monotone and subsumes the tag drop. The prose keeps only the `--option` decision and reports nothing about what the `remove` calls reconciled — a stripped or tidied dependent gets **no console advisory** from any answer skill (the answer commit's diff records it, and the cleared block is exactly the un-annotated state the next review or recommend pass surfaces by construction, so the note fails both halves of the git-absent-and-decision-critical test). The `## Decisions` folds and the `remove` calls stay separate, targeted edits, and the file stays execution-neutral and silent.
- `recommend-all-open-questions` is the batch form of `discuss-open-question`. It gathers the `<open-question>` entries **once** and walks them **strictly sequentially, most-significant-first**, deliberately omitting the machinery a decision-recording sweep would need — no per-question live-re-check/skip against a mutating document, no outer re-gather loop, and **no clean-working-tree precondition** — precisely because it records **no decisions** and triggers **no cascades**, so the question set never shrinks under it. It gathers in **three tool calls**: the bare `list <MILESTONE_DIR>` (empty output is the no-questions stop), `list --unannotated <MILESTONE_DIR>` (empty output is the nothing-to-annotate no-op — this filter **is** the whole idempotency skip, with no prose inspection of blocks for a `<recommendation>`), then one `locate` over every surviving id, whose verbatim print of each bare block is read once and spent twice — as the **ranking input** and as the block each dispatch prompt carries, nothing rebuilt or re-escaped by the orchestrator — and it **ranks the surviving questions most-significant-first by judgment over exactly what that gather yields** (each block's `id` and `<question>` text), reading nothing else, because the orchestrator never reads `open_questions.xml` itself (the subagent is what grounds in the documents); the ranking is a best-effort heuristic whose misses are absorbed by the prose fallback below. The `awk`/`sed`/`grep` boundary-line idiom (with its never-`xmllint` rule) that the runtime prose drove over the document before milestone 27 is **retired** everywhere — no runtime file greps, slices, or edits the question document; the tool does. **Dispatch is sequential and embedding is per-question, never parallel and never postponed to the end of the run**: it dispatches one question, judges its return (including the single repair attempt, run immediately for that question), and embeds it **before dispatching the next**, so every later dispatch reads an `open_questions.xml` that already carries every earlier question's embedded children. That is what lets a later recommendation **build on sibling recommendations already embedded** — the former "recommendation independence" rule (independent, parallelizable dispatches; never feed one question's recommendation into another) is **retired** and must not be restored. Each such use is declared as a self-closing **`<depends-on question="Short Title" option="Option"/>`** child of the block, emitted **only for a sibling that already carries embedded children in the document the agent read**, naming that sibling's `id` and one of its `<alternative>` ids; a coupling on a sibling **not yet annotated** gets **no element** — no option is ever guessed and there is **no option-less tag form** — and is expressed as prose inside the affected `<drawback>` or the rationale (the accepted residual: answering such a later sibling strips nothing, guarded only by that prose). The tool's `embed` resolves every returned `<depends-on>` **one hop** against the still-present annotated blocks and the target's `<alternative id>` values (**no cycle test** — a cycle is reachable only through the `strip` hatch and is tolerated, dissolving at the answer sweep's first cascade); a miss is an ordinary refusal (one `Error:` line, one repair, skip only on a second failure) and the orchestrator **never drops or rewrites a returned element** to make it pass — it pipes the return whole or not at all. It is the **sole document mutator, and it mutates only through the tool**: it pipes each return's whole message to `embed <MILESTONE_DIR> "<Short Title>"` on standard input through a quoted-delimiter heredoc (`<<'EOF'`, so backticks, `&apos;`, and `${…}` travel verbatim, one shell call, nothing escaped per call), and the tool slices the fragment, validates it, and writes the block re-rendered in canonical form inside the existing `<open-question>` wrapper with its `<question>` unchanged — indentation, escaping, and child grouping are the tool's, never the return's or the orchestrator's; the former whole-block-replacement `Edit` and orchestrator-side extraction are gone. It is **idempotent** — the `--unannotated` filter skips any block already containing a `<recommendation>` element, which keeps re-runs cheap and preserves an existing recommendation (the primary re-run motive being exactly the un-annotated set a later `/review-milestone-requirements` pass surfaces); the **escape hatch for a stale recommendation is `strip <MILESTONE_DIR> "<Short Title>" …` (one or more titles) followed by a re-run** — `strip` deletes every child but `<question>` of each named block, touches no other block and no `<depends-on>` tag naming it, rejects an unknown id with the document unchanged, and does nothing on an already-bare block, so the next run's `--unannotated` list yields it — with **no hand-edit exception** (`open_questions.xml` is always the tool's own output; the sole-writer clause carries no caveat anywhere it is stated, and a half-deleted block the tool would refuse at every later call cannot arise), no skill wrapping the subcommand (an additive step to take only if the hatch, unexercised in every commit to date, ever becomes routine), and deliberately **no** `refresh`/selectable mode (the sweep stays argument-free). **Stale tags after such a refresh are left alone**: when the regenerated block's new recommended option differs from what surviving dependents' `<depends-on>` elements assumed, the sweep leaves those dependents exactly as they are — no strip, no re-dispatch, no `option` rewrite, no mismatch advisory — because a `<depends-on>` records **what a dependent assumed**, not a pointer that must track its target, and reconciliation happens only in the answer-time cascade against the option actually recorded; a dependent the user also wants regenerated is named in the same `strip` call. Following the skill-layer commit rule it **commits its own annotations once at the end of the run** (never inside the dispatch loop) — path-scoped `git add <MILESTONE_DIR>/open_questions.xml` (never `git add -A`) then a single commit under subject `Recommendation-annotation: <milestone_id>` via `core/shared/commit-procedure.md`, behind that procedure's dirty-own-path no-op guard so a sweep that annotated nothing commits nothing. Its `recommend-open-question` subagent (one dispatch per question, the non-interactive twin of `discuss-open-question`) is **read-only** — it reads `open_questions.xml` and `requirements.md` whole, the live project, and the project-wide principle store to ground honest alternatives but returns only the ready-to-embed child sub-elements (the `<alternative>` elements, any `<applied-principle>` elements, any `<depends-on>` elements, then the single `<recommendation>` element — never the `<open-question>` wrapper or `<question>` element) as its final message. **Return judging is a three-stage per-return pipeline** — the orchestrator's last-line verdict, the tool's `embed` (extraction and validation in one call), then one repair — specified in full in the dispatched-agent-return invariant below; this sweep is the one dispatch site in the plugin that contacts an agent a **second** time, and that single repair attempt is what makes an otherwise valid recommendation recoverable rather than skipped. Recovery is **silent**: a question annotated only after the tool discarded surrounding text, or only after the repair, gets **no console mention at all** — under the terse-reporting rule a recovered return is reported exactly like a clean one (an advisory must be both git-absent and decision-critical, and a recovered return changes nothing the user must decide), so only questions **still** skipped after the repair path reach the step-5 advisory and its all-skipped no-op wording. The subagent's read-only grounding sees the sibling `<open-question>` blocks as they stand when it reads, embedded children included, and a sibling that already carries them is a **legitimate input** it may build on and must declare.
- `core/shared/answer-with-recommendation-procedure.md` is the single source of truth for the "lift the embedded recommendation, then record it" logic, referenced (never restated) via `{{PLUGIN_ROOT}}` by both the `answer-open-question-with-recommendation` skill and its agent. It is **execution-neutral**: given a resolved SHORT TITLE it runs one tool call, `lift <MILESTONE_DIR> "<SHORT TITLE>"`, which prints the block's `<recommendation option="...">` value and element text recombined as "`<option>` — `<rationale>`" (the old anchor form, un-escaped by the tool); that whole line is ANSWER and its text before the first spaced em dash (the whole line when there is none) is RECORDED OPTION, both derived from the print alone — never from a sibling `<applied-principle>` or `<alternative>`, which keeps the answer provenance-free by construction. The **no-`<recommendation>`-element guard** is that call failing — no block with the id, or a block the recommend sweep never annotated — as one `Error:` line, quoted in the clean stop with nothing changed. It then delegates to `core/shared/answer-procedure.md` with the derived ANSWER **and RECORDED OPTION passed separately**, so the core hands it to `remove --option` as an exact id rather than parsing ANSWER. It **composes over** the recording core exactly as the `complete-task` skill and agent layer their shared procedure — the lift lives here, not in `answer-procedure.md`, so that core's **inputs-as-given contract** (ANSWER plus an optional RECORDED OPTION the caller either passes or omits, shared with literal `answer-open-question`, which must never inherit lift behavior) stays unchanged. The `answer-open-question-with-recommendation` skill + agent follow the established skill+agent pattern (one execution-neutral shared procedure, run **inline** by the skill so context survives, **in isolation** by the agent with the `DONE`/`FAILED` return protocol), but with a deliberate divergence from the read-only-subagent design of the plugin's other per-question subagents (e.g. `recommend-open-question`): here the **mutation** is what's isolated into the agent, not the reasoning. The recommendation is **pre-computed** by the recommend sweep, so there is no candidate elimination worth isolating; what dispatching a per-question **file-editing** agent buys the sweep orchestrator is keeping the per-question recording out of its own context. It is the **recording** that is isolated into the agent, **not the committing** — under the layer rule the agent records the answer and stages both `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md` by name, and the orchestrator commits that staged index (see the next invariant). This inversion (mutation-in-agent, not read-only-subagent) is documented so a later editor does not "fix" the agent back toward the read-only-subagent norm.
- In `answer-all-open-questions-with-recommendation`, the file-editing **agent records and stages but never commits** — it folds the answer into `## Decisions`, removes the block through the tool, `git add`s its two edits `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md` path-scoped by name (never `git add -A`), and returns a **bare** `DONE`/`FAILED` with no hand-back payload (a `FAILED` reason is the tool's `Error:` line, verbatim after the prefix) — and the **orchestrator commits that staged index itself** after the agent returns: a nothing-staged no-op guard (`git diff --cached --quiet`, no `--allow-empty`), then a pathspec-less `git commit` under subject `Recommendation-answer: <Short Title>`, **one commit per answer** (preserving one-commit-=-one-answer). Because the agent hands nothing back, the orchestrator **lifts the `<recommendation>` text for the commit body itself, during its pre-dispatch re-check** — one tool `lift <MILESTONE_DIR> "<Short Title>"` call, whose printed "`<option>` — `<rationale>`" line is the body — while the block is still in the document; once the answer is recorded the block is gone, so that re-check is the only place the lift can happen. Staging is not committing, so the agents-never-commit rule holds: this is the **ordinary** skill-layer arrangement (dispatched agents never commit; an orchestrator commits its agents' work, exactly as in `complete-all-tasks`) — milestone 10 reversed the earlier milestone-7 inversion in which the agent committed and the orchestrator did not. The orchestrator gathers and orders with **one tool call, `walk <MILESTONE_DIR>`**, and never reads `open_questions.xml` itself to gather or to order: `walk` prints the bare ids of every `<recommendation>`-bearing block in dispatch order, and the graph it computes is the one the retired prose walk described — built **over the gathered set alone** (each gathered block a node, each of its `<depends-on question="…">` values an edge to the gathered block whose `id` matches; only the `question` value is read — the `option` value is `remove --option`'s to reconcile), an edge whose target is **absent from the document or present without a `<recommendation>`** **dropped** (the gather is never widened, the tag stays in the document for the cascade, and a question left with no resolvable edge is an ordinary origin, because a `<depends-on>` records what a dependent assumed and only a recorded option can reconcile it), placed **by depth** (origins first, then every question whose every resolvable edge is already placed, **same-depth ties in document order** — same-depth questions cannot depend on one another, so the tie order can never change a cascade outcome, which retired the old "loosely most-significant-first" proxy), and a **stranded set** (a `<depends-on>` cycle, reachable only through the recommend sweep's `strip` hatch) broken by **promoting its document-order-first member to an origin**, repeated whenever the walk strands again, so the order is **deterministic and total** for any graph shape, cycles included (the cycle dissolves at the promoted question's cascade, and the residual — its rationale may be stale when recorded — is the accepted forward-declaration risk shrunk to one question per cycle). Those rules live in the tool and `tests/test_walk.py`; the skill states none of them. The per-question **re-check is the `lift` call itself**: its failure (one `Error:` line — the block removed, or its children stripped, by an earlier answer's cascade) is the skip, with an explicit rule not to read the document to confirm it, and `core/shared/answer-procedure.md`'s step-2 `locate` stop is the backstop; dispatch runs **strictly sequentially** because cascades mutate the shared documents. Walking a target before its dependents is what lets each answer's cascade settle the dependents in turn (tag removed on agreement, children stripped otherwise), and a dependent so stripped is skipped by the re-check — the cascade doing its job, not a gap in the walk. That printed order is walked **exactly once** and never wrapped in an outer re-gather loop: recording only ever *removes* questions or their children (cascades moot or strip them) and nothing adds questions mid-sweep, so a single ordered pass is the fixed point. It needs no clean-working-tree precondition — the agent's staging is path-scoped, so a dirty tree elsewhere stays out of the per-answer commit. Documented as its own invariant so it is not reverted toward agent-commits.
- Recommendation-derived answers — from **both** the single-question `answer-open-question-with-recommendation` skill and the sweep (whose orchestrator commits each answer) — commit under the distinct subject `Recommendation-answer: <Short Title>`, and **alternative-derived answers** — from `answer-open-question-with-alternative` — under `Alternative-answer: <Short Title>`. These subjects are **provenance discriminators, not a harvest filter**: `capture-milestone-principle-updates` walks **all three** answer subjects on a milestone's `open_questions.xml` and reads the subject to tell them apart. A `Recommendation-answer:` body is the `recommend-open-question` agent's rationale (batch-accepted on the sweep path), not user-deliberated reasoning, so capture reads it as an **accepted recommendation** — **evidence only** about entries already in the store (a removed `<applied-principle>` citation reinforces the cited entry and shields it from pruning or narrowing in that pass; an accepted rationale that contradicts an entry flags it for salvage) — and **never mines it for a new principle**, because the recommender's own reasoning cannot supply the guideline the recommender lacked. A `Manual-answer:` or `Alternative-answer:` that recorded a different option than the removed `<recommendation option>` named is the **override signal** from which new principles come: an `Alternative-answer:` body is only the chosen `<alternative>`'s what-it-is text (the recommend agent's rendering, no user rationale), so capture prompts for the override reason at harvest time, while a `Manual-answer:` body is prompted only when it is a bare literal answer with no stated reason. A manual or alternative answer that recorded the very option the recommendation named is an **agreement**, not an override — never prompted, its citations read as reinforcement — and a `Manual-answer:` whose block carried no recommendation at all (every pre-sweep answer) stays a principle source through its body. The distinct subject is the honest git-log provenance discriminator, matching the house style where the subject *is* the provenance marker — it is what keeps a recommendation-derived answer from ever being mistaken for hand-authored rationale, without any per-subject harvest filter.
- `answer-open-question-with-alternative` is the **sibling** of `answer-open-question-with-recommendation`: same recommend-sweep annotations, same recording core, differing **only** in which embedded element becomes the answer — the recommendation skill lifts the one `<recommendation>` the sweep picked, this skill lifts the `<alternative id="...">` the **user names** (arg split on the first `.`, Short Title before / target alternative id after, both matched case-insensitively by the tool against the respective `id` attributes — mirroring `answer-open-question`'s first-`.` split). Its purpose is to let a user **override the recommended option** or break a genuine tie. Its lift is one tool call, `lift <MILESTONE_DIR> "<Short Title>" --alternative "<Alternative Id>"`, which prints the chosen alternative's `id` recombined with its **what-it-is text** as "`<id>` — `<what-it-is>`" (the recommendation form's exact analog), pointedly **excluding** the `<advantage>`/`<drawback>` children (trade-off analysis, not the decision); that whole line is ANSWER and its text before the first spaced em dash is RECORDED OPTION, which it hands separately to `core/shared/answer-procedure.md` (so the core passes it to `remove --option` as an exact id rather than parsing ANSWER). Three deliberate divergences from the recommendation path, documented so they are not "fixed" back toward it: (1) it is **skill-only** — there is **no** agent and **no** `answer-all-open-questions-with-alternative` batch form, because choosing *which* alternative wins is per-question human judgment, not a rule an orchestrator could sweep (a sweep that always picks the recommended option is just the recommendation sweep); (2) with only one runner, the lift-then-delegate logic is **inlined in the skill** (composing over the multi-consumer `core/shared/answer-procedure.md`) rather than extracted into a single-consumer `core/shared/answer-with-alternative-procedure.md` — a shared file here would contradict the plugin's "shared = source of truth across ≥2 runners" convention; (3) its clean-stop guards are that `lift` call's one `Error:` line, quoted verbatim — no block with the Short Title (the line lists the ids the document holds), a block with no `<alternative>` elements (the sweep never annotated it; point at the sweep), or no alternative matching the named id (the line lists that block's alternative ids) — each committing nothing. It commits both `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md` path-scoped under `Alternative-answer: <Short Title>` exactly as the recommendation skill commits under `Recommendation-answer:`, with the lifted line as the body. Its own `lift` is a **read to derive the answer** — not the recording core's locate/remove step, which runs later inside the delegated `core/shared/answer-procedure.md`.
- `core/shared/recommend-procedure.md` is the single source of truth for the "alternatives + single recommendation for one question" analytical core, referenced (never restated) by both the `discuss-open-question` skill and the `recommend-open-question` agent via `{{PLUGIN_ROOT}}`. It is **execution-neutral** and holds only logical content: the grounding discipline (the live project over memory), the **Alternatives** requirement (2–4 genuinely realistic options, no strawmen/padding, each carrying what-it-is / key advantage / key drawback), and the single **Recommendation** (one option, direct hedge-free rationale, plus the name-what-breaks-the-tie rule). It is **principle-aware**: its grounding step reads the project-wide principle store `milestones/answer_decision_principles.md` **in place** (naming that fixed `milestones/`-root path directly — the confirmed principles are not a caller-supplied input alongside QUESTION), and a confirmed principle that bears on the question is a **weighted advisory factor** — a strong default in favor of the option it supports, which **merit may override only for a specifically stated reason**, and which is **cited** in the recommendation whenever it influenced the pick (never a binding filter or veto, never a candidate drop, never silently applied). When no principle bears, the alternatives+recommendation contract is exactly as in a project with no principles. Its grounding step also carries the **caller-neutral disclosure duty** that replaced the retired independence clause: a recommendation already attached to a still-unanswered sibling — read from `<MILESTONE_DIR>/open_questions.xml` whole with the file-reading tool, for reasoning only, every locate, list, or lift of a block being the tool's — is legitimate input, and whenever the recommendation formed leans on such a sibling's recommendation it **names that sibling (its Short Title) and the option assumed** — the caller decides how that disclosure is rendered (`<depends-on>` elements in the agent, plain prose in the rationale for `discuss-open-question`), the same division of labor already used for principles, where the core states the citation obligation and the agent owns the markup. The core carries the duty without the sweep mechanics that give it teeth (the tool's `embed` dependency validation and the answer-time cascade), so a reader of the core alone sees the obligation without its enforcement; that is accepted. It carries **no** XML rendering markup and **no** "what would change your mind" section — the boundary is deliberate: `discuss-open-question` owns the WWCYM layer, the conversational framing, and the on-decision follow-up offers; the `recommend-open-question` agent owns the literal XML sub-element rendering (the element shapes — the sibling `<applied-principle>` elements, the `<depends-on>` elements, and the `<recommendation option="...">` element — as well-formed XML; indentation, escaping, and child order are the tool's, re-rendered on every write). This mirrors how `core/shared/answer-procedure.md` is execution-neutral while its wrappers own arg-parsing and committing. The store itself is consumed by this **recommendation core** rather than by an auto-answer engine: its data and per-entry format are unchanged, and `capture-milestone-principle-updates` remains its **sole writer**; only the consumer pointer moved, from a binding auto-answer sweep to the recommendation advisor that cites it.
- The `recommend-open-question` agent renders each confirmed principle that bore on the recommended pick as its own `<applied-principle>Short Title</applied-principle>` element — a **direct child of `<open-question>` and a sibling of `<recommendation>`, never a child of `<recommendation>`** — **one element per bearing principle** (the multi-principle case is pure repetition of the single-element form, with no multi-id element and no in-line list syntax, so each citation stays atomic and independently greppable), and **none at all** when no principle bears (the sub-elements then render exactly as they did before principle-awareness). The citation is **never** baked into the `<recommendation>` element text: because `/answer-open-question-with-recommendation` (and the `/answer-all-open-questions-with-recommendation` agent) lift only the `<recommendation>` element, keeping the citations structurally disjoint siblings holds the recorded `## Decisions` prose **provenance-free by construction**, and the tool's `remove`, which `core/shared/answer-procedure.md` calls, deletes the whole block on answer, clearing the sibling `<applied-principle>` elements with it. The same agent renders each sibling recommendation it built on as a **self-closing `<depends-on question="…" option="…"/>` element** — a direct child of `<open-question>`, one per such sibling, placed **after the alternatives and any `<applied-principle>` elements and immediately before `<recommendation>`** — the order the tool's serializer writes in any case, since it groups a block's children by kind (alternatives, applied-principles, depends-on, recommendation) on every write and `embed` never checks a fragment's child order, so a complete but misordered return embeds with nothing lost and the agent's order matters only at the two extraction anchors (an `<alternative` line first, a `</recommendation>` line last). The elements sit **strictly inside that extraction region**, which leaves the tool's slice, the two shape tests, and the whole-block `remove` untouched; the two-attribute self-closing form keeps each declaration a single greppable line in the canonical document and in capture's diff read (child order is a rendering property settled for the reader and the diff, not for any consumer — every locate, lift, strip, reconcile, and capture read keys on an element's tag, never its position). The `question` value is the sibling block's `id`, the `option` value one of that sibling's embedded `<alternative id>` values — never a guess — so every tag names an existing question and an existing alternative by construction, and, like the principle citation, the dependency is **never baked into the `<recommendation>` text**.
- `answer-open-question` splits its arg on the first `.` — title before, answer after, and is **literal-only plus a redirect guard**. The old **record-recommendation mode** — the whole-string `record the recommendation` sentinel that located a block and lifted its `<recommendation>` element as the `ANSWER` — is **removed** from this skill; lifting an embedded recommendation now lives in `answer-open-question-with-recommendation` (skill + agent, over `core/shared/answer-with-recommendation-procedure.md`). What survives here is a **targeted redirect guard**, not a live feature: after the first-`.` split, the parsed answer text is compared — trimmed and lowercased — against the retired sentinel `record the recommendation` as an **exact whole-string** match (**never a substring**, so a literal answer merely containing those words takes the literal path). On an exact match the skill **stops without recording or committing anything** and prints a redirect pointing at `/answer-open-question-with-recommendation`; this intercepts a migrating user's old command at the moment it would otherwise silently record the sentinel phrase as a decision, and its message doubles as discovery. It is targeted migration scaffolding that fits the skill's clean-stop-and-point pattern (like a Short-Title mismatch), not a revived mode. Any other (non-sentinel) answer text is a literal answer; the existing first-`.` split, the literal-answer path, and the `Manual-answer:` commit rules are unchanged. It hands `core/shared/answer-procedure.md` SHORT TITLE and ANSWER and **explicitly passes no RECORDED OPTION** — a literal answer lifts no option id — so the core's step 5 takes its **judgment mode**: one prose verdict on whether ANSWER plainly settles on one of the answered block's own `<alternative id>` values, passed to the tool's `remove` as `--option` when it plainly does and omitted otherwise, so the dependents that assumed that option are untagged and every other dependent is stripped (strip on doubt). Its Short-Title mismatch is the core's `locate` call failing, relayed by quoting the tool's `Error:` line, which lists the ids the document holds. It records a decision and then **commits** both `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md` path-scoped — it no longer chains to any capture skill. Principle capture has moved off the per-answer path to the on-demand `capture-milestone-principle-updates <milestone_id>` (conventionally run once the milestone is finished, never as a precondition); the rationale behind each decision is preserved in the commit body so capture can distill it later — a deliberated body is read as the user's own answer to the why and is never re-prompted, while a bare literal answer that overrode a recommendation is prompted for its reason at harvest time.
- `modify-milestone-goal` is the **only** skill that mutates the `## Goal` of an already-defined milestone (`define-milestone-goal` writes it once at creation; `discuss-milestone-goal` is conversational and pre-creation). It is **act-only**: it edits the `## Goal` section and nothing else — never `## Decisions`, `open_questions.xml` (which it reads whole, for the impact analysis only), `## Out of Scope`, or the task lists. Because the Goal is the root of the requirements tree, the skill **surfaces but never cascades** the downstream impact (which Decisions/questions/Out-of-Scope/derived tasks the new goal may invalidate) and points the user at `/review-milestone-requirements` to reconcile — folding those consequences in silently would have too large a blast radius. It is offered by `discuss-open-question` (which still edits nothing itself — it proposes the revised goal and the user confirms) and is **deliberately invisible to `answer-open-question`**: recording an answer and reshaping the objective are different acts, and the answer path must never reach goal mutation. It records no answering principle (a goal change yields none), but under the skill-layer commit rule it **commits** its own `## Goal` edit — path-scoped to `<MILESTONE_DIR>/requirements.md` (never `git add -A`) under subject `Goal-revision: <milestone_id>` via `core/shared/commit-procedure.md`, behind that procedure's dirty-own-path no-op guard.
- Correcting a bad recorded answer has no dedicated skill: it is the uniform **revert-then-re-answer** flow. Revert the answer's commit (by the one-commit-=-one-answer invariant the revert restores the reopened question block to `open_questions.xml` and removes the folded decision from `requirements.md` in one shot — the `Manual-answer:` commit for a manual answer, the `Recommendation-answer:` commit for a recommendation-derived one, the `Alternative-answer:` commit for an alternative-derived one), then re-record via `/answer-open-question` (or `/answer-open-question-with-recommendation` to re-lift a re-embedded recommendation, or `/answer-open-question-with-alternative` to record a different embedded alternative). Because a confirmed principle is now only a **weighted advisory factor** cited in recommendations — never a binding auto-answer — a principle that steered a recommendation wrong is reconciled the next time `capture-milestone-principle-updates` runs for that milestone (conventionally at its finish, never as a precondition): the corrective re-answer's `Manual-answer:` (or `Alternative-answer:`) commit is an override commit whose diff still carries the `<applied-principle>` citation that steered it, so capture reads the override rationale against that entry and takes the **salvage ladder** — narrow its scope clause, generalize it, replace it, and delete it only when nothing survives — inside the whole-store rewrite the user reviews with `git diff`. For an urgent "this principle is actively wrong, remove it now" case the user hand-edits the plain-Markdown store `milestones/answer_decision_principles.md` directly; capture imposes **no clean-store precondition** — it notices the uncommitted edits, asks once, composes its rewrite over the working-tree file rather than `HEAD`, and on rejection restores its pre-write snapshot (not `HEAD`), so the hand-edit survives either way.
- **Committing is a property of the skill layer.** The mechanics live in exactly one place — `core/shared/commit-procedure.md` (dirty-own-path no-op guard → path-scoped `git add` of the pass's own paths → `git commit` under its subject), referenced via `{{PLUGIN_ROOT}}` by every committer and never restated (the execution-neutral shared procedures `answer-procedure.md`, `answer-with-recommendation-procedure.md`, `complete-procedure.md`, `recommend-procedure.md` stay **commit-free**, as does the format-only `task-format.md`; commit logic lives in the wrappers). The two **agent-dispatching orchestrators** (`complete-all-tasks`, `answer-all-open-questions-with-recommendation`) are the one arrangement outside that reference: their agent has already staged the change set path-scoped, so they stage nothing and instead run the guard-and-commit half inline — a nothing-staged no-op guard, then a pathspec-less `git commit` under their subject. The rule: **every user-invoked skill that changes files commits exactly those changes**, staged path-scoped by explicitly named paths (**never `git add -A`**, no content inspection to choose the set), under its own distinct **function-derived `<Marker>: <descriptor>` subject** — a distinctive marker prefix, a colon and space, then a short descriptor, the marker derived systematically from that skill's distinctive function rather than drawn from an ad-hoc per-skill list and with no grandfathered exceptions, so the git log reads as self-describing provenance and every prefix is greppable — that stays clear of the three answer markers by construction (only the three answer skills carry a marker beginning `Manual-answer:`, `Alternative-answer:`, or `Recommendation-answer:` — the anchors `capture-milestone-principle-updates` greps for and reads as provenance — and a skill deriving a new marker picks one that names its function and does not collide with any of those anchors); **dispatched agents stage their own change set path-scoped but never commit** (staging is not committing; they return a bare `DONE`/`FAILED` with no hand-back payload); **an orchestrator commits the index its agent staged, after it returns.** **Dispatch naming:** an orchestrator addresses each dispatched agent by its **namespaced registry name** — the agent under this plugin's namespace, which Claude Code lists as `cairn:complete-task`, `cairn:recommend-open-question` and `cairn:answer-open-question-with-recommendation` — phrased descriptively at the dispatch site rather than frozen as a bare agent name, so resolution stays correct if the plugin is renamed or run under another host. The old role-based split ("a decision-recorder commits, a work-producer leaves changes staged," with its one-orchestrator/three-skills/one-agent counts) is **retired** — `complete-task`, `submit-task`, `derive-tasks`, `recommend-all-open-questions`, `modify-milestone-goal`, `define-`/`specify-`/`review-`/`goto-`/`finish-current-milestone`, and `capture-milestone-principle-updates` are all committers now. Per-skill subjects and paths: `Manual-answer:` / `Recommendation-answer:` / `Alternative-answer: <Short Title>` (the three answer skills, each staging both `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md`, as `Requirements-review:` does; `Recommendation-annotation:` stages `open_questions.xml` alone, `Milestone-definition:` the four files it created, `Goal-revision:` and `Starting-state:` `requirements.md` alone), `Task-completion: <task heading>` (`complete-task`), `Task-submission: <task title>` (`submit-task`), `Task-derivation:` / `Requirements-review:` / `Starting-state:` / `Recommendation-annotation:` / `Principle-capture: <milestone_id>`, `Milestone-definition:` / `Milestone-finish: milestone_<NN>_<slug>`, `Milestone-activation: milestone_<number>_<slug>`, `Goal-revision: <milestone_id>`. **Orchestrator commit granularity:** `complete-all-tasks` commits **per task** (subject `Tasklist-completion: <descriptor>`, the task `##` heading now in the commit **body**, not the subject, and committing the index the agent staged — its recorded change set plus the two task-list files — never `git add -A`), `answer-all-open-questions-with-recommendation` commits **per answer** (subject `Recommendation-answer: <Short Title>`, committed by the orchestrator), and `recommend-all-open-questions` and `derive-tasks` commit **once at the end of the run**. **No-op guard:** a committer whose pass changed none of its own paths (e.g. a `review-milestone-requirements` or `capture-milestone-principle-updates` pass that distilled nothing) stages nothing and commits nothing — no `--allow-empty` (the `core/shared/commit-procedure.md` dirty-own-path guard enforces this uniformly). **One exemption:** `init-milestone-base-workflow` stays **non-committing** (it leaves changes staged for the user) because a consuming project may not be a git repo or wants its own commit boundaries. Skills that change no files (`discuss-milestone-goal`, `discuss-open-question`, `discuss-new-task`, `ask-in-milestone-context`) are unaffected. **Still true:** the three answer subjects are the **only** markers `capture-milestone-principle-updates` walks — via a path-scoped `git log -E --grep='^(Manual-answer|Alternative-answer|Recommendation-answer): ' -- milestones/<milestone_id>/open_questions.xml` — and it reads the subject as a **provenance discriminator**, never as a harvest filter (`Manual-answer:` and `Alternative-answer:` mark the override signal it distills new principles from; `Recommendation-answer:` marks an accepted recommendation read as evidence only), while every other function-derived subject stays clear of those three anchors by construction, so capture never reads them.
- **Success-path console reporting is terse.** Every file-mutating, committing skill's success path prints **exactly one fixed terse status line** (e.g. "Milestone defined.", "All tasks completed.", "Recommendations embedded.") — carrying **no identifier** (no milestone id, task heading, Short Title, or commit subject) and **no next-step/handoff pointer** — instead of a prose re-narration of what it did, because the committed diff and `git log` are the durable record (re-narrating them to the console is redundant). An **orchestrator** prints **one such line for the whole run**, with **no per-item output** during its dispatch loop. Three classes of output deliberately **survive alongside** the terse line: (1) genuinely **git-absent decision-critical advisories** the commit never captured — `review-milestone-requirements`' convergence verdict and still-open list, `derive-tasks`' flag for any requirement it could not trace to a task, `submit-task`'s anchor-miss fallback advisory (nothing in the task list records that a `before:`/`after:` anchor missed), and the answer skills' newly-exposed-open-questions note — are still printed (only diff re-narration collapses), while a dependent block whose `<depends-on>` tag the cascade removed or whose embedded children it stripped gets **no** advisory from any answer skill (the answer commit's diff records it, and the cleared block is exactly the un-annotated state the next review or recommend pass surfaces, so it fails both halves of the git-absent-and-decision-critical test — and enumerating it would contradict the answer sweep's rule against listing recommendation-less questions); (2) a **no-op pass** whose `core/shared/commit-procedure.md` dirty-own-path guard fired prints a **distinct one-line** message stating nothing changed and briefly why (git holds no durable record of a no-op, so the console must carry it), never collapsing to the terse success line; (3) **failure and clean-stop paths** (parse errors, Short-Title/id mismatches and every other stop the tool's one `Error:` line drives — quoted verbatim, since it names the failed lookup and lists the ids to retry against — the `answer-open-question` redirect guard, the bootstrap's missing-interpreter stop) keep their **full explanatory messages**. Untouched entirely: the conversational skills (`discuss-milestone-goal`, `discuss-open-question`, `discuss-new-task`, `ask-in-milestone-context`) and the one non-committing exempt skill (`init-milestone-base-workflow`). Like the commit convention, this cross-cutting rule earns its **own standalone invariant** rather than a shared procedure file — there is **no** `core/shared/report-procedure.md`; the convention is authored **inline in each `SKILL.md`'s final reporting step**.
- `finish-current-milestone` must always run before `goto-next-milestone` — it records the completion and clears the current-milestone pointer to "none". `goto-next-milestone` checks for this "none" state and refuses to run without it. Finish's pointer-clear rides inside the **same** `milestones/README.md` edit as the completion summary, so the committed README already carries `Current milestone: none` and `goto-next-milestone`'s none-pointer precondition is recorded in git rather than left in a dirty tree. `capture-milestone-principle-updates` is **decoupled** from finish: it is an **on-demand** skill, runnable for any milestone id at any time, and its home in the "Ending a milestone" stage is a **convention** — finish is the natural moment to run it because a milestone's answer set is complete by then, and it is **never a precondition** (every answer commit lands during the requirements phase, so finish status carries no information the harvest needs; a run against a milestone still being answered harvests what exists so far, and a later run re-walks the same path to pick up the rest; backfill over long-finished milestones is explicitly allowed). It is a documented handoff, **not** a runtime recommendation `finish-current-milestone` prints (that runtime "recommends (never auto-runs)" print was retired under terse reporting), and `finish-current-milestone` never invokes it. It takes a **required `<milestone_id>`** — the directory name under `milestones/` exactly as `specify-milestone-starting-state` takes it, resolved as `milestones/<milestone_id>/` and validated **only** by the existence of that directory's `requirements.md` (a clean stop listing the present `milestone_*` directories otherwise); it never consults the current-milestone pointer, `core/shared/get-current-milestone.md`, or the `## Completed Milestones` table, and accepts no bare-number form. The id is consumed verbatim in three places: the path-scoped commit walk, the `Principle-capture: <milestone_id>` subject, and the repeat-capture guard's both-ends-anchored grep for that exact subject. Two **start-of-run guards** are each a one-line notice plus a single proceed confirmation, never a stop: a milestone that already carries a `Principle-capture: <milestone_id>` commit (only a committed capture is detectable — no empty commit records a no-op run, an accepted gap), and a store with uncommitted edits (on proceed the working-tree file, not `HEAD`, is the baseline the rewrite composes over). As the **sole writer** of `milestones/answer_decision_principles.md`, it walks the milestone's answer commits across **all three provenances** with a path-scoped `git log -E --grep='^(Manual-answer|Alternative-answer|Recommendation-answer): ' -- milestones/<milestone_id>/open_questions.xml` (the path is itself the lower boundary — the file does not exist before `define-milestone-goal`'s `create` call — and the only boundary on the harvest; the filter names `open_questions.xml` alone because every answer removes its block from that one file), reads each commit with one `git show <hash> --format='%s%n%n%b' -- milestones/<milestone_id>/open_questions.xml milestones/<milestone_id>/requirements.md` naming **both** files (one uniform show, never a provenance-conditional pathspec), and because the recording core removes the whole `<open-question>` block on answer, the `open_questions.xml` hunk's removed lines preserve the `<question>`, every `<alternative>`, the cited `<applied-principle>` elements, and the `<recommendation option>` the user saw, while the `requirements.md` hunk's added lines hold the `## Decisions` entry they recorded. **Capture keeps its diff-line reconstruction**, repointed at the new file and reading raw `git show` lines rather than the live document: it reverses the five predefined entities (`&amp;` last) on every value it reads — the one place that un-escaping rule remains in runtime prose, because the tool's serializer wrote those lines but no tool reads a diff — and the pre-split blockquote fallback is gone (no compatibility with pre-split milestones). That diff read is **scoped to the answered block**: it locates the block among the removed lines by the removed line carrying its `<open-question id="…">` tag (keyed on the tag, never its column — the canonical form indents every block two spaces) and reads through its `</open-question>` closing line, and **only the removed lines lying within those two boundaries feed the record** — every other removed line in the same diff, whether a whole sibling block the cascade mooted or a stray line the cascade cleared from a sibling block that still stands in the document (the orphan `<recommendation option>` / `<alternative id>` / `<depends-on>` lines its tidy and strip outcomes leave, exactly the tokens the reconstruct and agreement steps key on), is outside the answered block and contributes nothing. That one scoping sentence stays **element-agnostic** and never names `<depends-on>`, so no per-element "ignore this" list is started and the rule holds unchanged as further child elements are added. Each commit is classified by two tests: **agreement** (the recorded option against the removed recommended option — `non-override` when no recommendation existed, `agrees`, or `overrides`) and **body** (deliberated vs. bare, the same bare-cold-answer test phase 1 applies). **Override commits are the signal**: capture prompts for the override reason only where the body carries no user rationale (every non-agreeing `Alternative-answer:`, and a non-agreeing bare `Manual-answer:`), showing its best guess, one skippable prompt per commit, behind a one-shot accept-every-guess / skip-every-prompt / review-one-at-a-time choice so backfill over a forgotten milestone stays workable; a deliberated `Manual-answer:` is never re-prompted, an agreeing answer is never prompted (the why-did-you-prefer question would rest on a false premise), and a non-override `Manual-answer:` — every pre-sweep answer — is still a principle source through its body. **New principles come solely from override reasoning and deliberated manual bodies**; accepted recommendations (and agreeing alternative answers) are **evidence only** — a removed `<applied-principle>` citation reinforces that entry and shields it from pruning or narrowing in the pass, and an accepted rationale that contradicts an entry flags it for salvage. It distills those sources into generalizable keep/eliminate directives, drops the non-generalizable, dedups candidates **against each other** (a problem the retired per-answer capture never had), then composes **one whole-store rewrite** — adds, revisions, prunes, merges, generalizations, and shortenings together, so the store may **shrink as well as grow**: current reasoning takes precedence over an entry it contradicts, salvaged through a fixed ladder (narrow the scope clause → generalize → replace → delete only when nothing survives, tie broken by the shortest entry that still predicts both the prior citations and the override), every directive held to a soft 40–80-word target (flagged past about 100) under the "as short as it can be while still reading as an intuitive rule" test, no ceiling on entry count, and substantive changes gated on the harvested milestone's own evidence while form-only hygiene (shortening, merging plain duplicates) may reach any entry. It **snapshots** the baseline immediately before its one in-place write and prints **no diff and no store content**: the working tree is the review surface, the user reads `git diff`, requests changes in conversation (re-edited in place, no new snapshot), and **a single confirmation gates the commit, not the write** — there is no per-candidate or per-entry confirmation. On acceptance it commits path-scoped to `milestones/answer_decision_principles.md` (never `git add -A`) under `Principle-capture: <milestone_id>` via `core/shared/commit-procedure.md`, with a body of one short line per store change naming the change kind (add/revision/prune/merge/generalization) and the Short Title of the answer commit that drove it, composed at commit time against the final rewrite so it cannot drift from the diff; on explicit rejection it restores the **snapshot** (not `HEAD`, so a dirty-store proceed's hand-edits survive) and **exits without invoking `core/shared/commit-procedure.md` at all**, because that procedure's dirty-own-path guard would otherwise commit the user's surviving edits under capture's subject. The nothing-captured paths (empty commit range, no candidate and no flagged entry, a composed store identical to its baseline, a rejected rewrite) likewise never reach the shared procedure — they write nothing, commit nothing (no `--allow-empty`), and print one distinct line — which is what makes capture the second named no-op-pass case alongside `review-milestone-requirements`. Its restraint is deliberate: a principle informs *every* future recommendation, so a wrong or sloppy one corrupts the highest-value artifact in the loop, which is why it captures only genuinely reusable rules and never commits the store without the user's explicit review of the whole rewrite.
- `ask-in-milestone-context` is the on-demand, **read-only** Q&A skill: it answers an informational question about the current milestone and never mutates any file. It is not a pipeline step — it is usable any time across requirements/automation/follow-up. It grounds answers about finished work in the **live deliverables** (with the `TASKS_DONE.md` entry as intent and `git log`/`git show` as a supporting lens — the task→commit mapping is best-effort, since completions now land under a `Task-completion:` subject from the `complete-task` skill or a `Tasklist-completion:` subject with the heading in the body from `complete-all-tasks`, not keyed on the heading in the subject line). When a concrete next action surfaces it **offers** the owning skill (`discuss-open-question` to decide a question, `submit-task`/`discuss-new-task` to file an issue, `discuss-milestone-goal` to reshape the goal, `complete-task` to do a pending task) but performs none of their work itself — the asking/acting split is the whole point.
- `specify-milestone-starting-state`, `derive-tasks`, and the shared completion procedure (run by both the `complete-task` skill and agent) read the project's environment context (the project's domain context, working conventions, available tools, and how work is verified as done) from `CLAUDE.md`. Run `/init` once at project setup so `CLAUDE.md` documents it.
- `derive-tasks` owns decomposition, coverage, **and** the writing of the task list — it is the single writer on the derivation path. It proves every requirement maps to a brief (traceability matrix), orders the briefs by dependency, then writes them **itself**, in that order, into `TASKS_TODO.md` using the template and authoring guidelines from `core/shared/task-format.md`. Nothing on this path is delegated to a subagent, and there is no second authoring pass: a brief and a finished task section are the same altitude, so writing the brief down *is* the authoring step. What it must not do is push a section past brief altitude — never a flow, a low-level design, a contract surface, or a structured done-ness section; the completer derives all of that against the live project. It initializes `TASKS_TODO.md` to a clean header before writing the briefs, so its once-at-end path-scoped commit records exactly that run's derivation and its dirty-own-path no-op guard fires precisely when the run derived nothing.
- The **brief-level** task-section template lives in exactly one place: `core/shared/task-format.md`. That template is the `##` title heading, a 1–3 sentence description of what is to be achieved, why the milestone needs it, and how it would be verified (that last clause folded into the prose, never a labeled section), and the mandatory trailing `---` separator — and nothing else. There is deliberately **no** `Steps`, **no** `Provides`, **no** `Notes`, **no** `Success`, and no other structured done-ness heading under any name — see the altitude invariant below. The same file carries the four authoring guidelines, all format-independent and all carried over unchanged: unique 4–8 word title-cased **Title** (uniqueness is load-bearing — the completion procedure locates a task by case-insensitive partial heading match), **atomic scope**, **no open decisions**, and **quote numeric values, durations, thresholds, and configuration values** directly from `requirements.md`. Both authoring runners — `derive-tasks` and the `submit-task` skill — reference it via `{{PLUGIN_ROOT}}` and must never duplicate, restate, or vary it, and `core/shared/complete-procedure.md` parses exactly what it defines — the `complete-task` agent accordingly expects tasks as `##` sections in `TASKS_TODO.md`, each terminated by a `---` separator; two authors plus one parser is what keeps it shared and rules out drift between the batch and ad-hoc paths by construction. It holds the **format only**: where the task list lives, what context an author loads before writing, and where in the file a section is placed all belong to the runners.
- `submit-task` is a **skill only** — it has no agent counterpart, and `complete-task` is the plugin's only remaining skill+agent pair. The skill authors the task section **inline** in the user's conversation (so the authoring context survives for follow-up), and it additionally owns the triage (dedup + scope) and the position decision (`before:`/`after:`/`append`), because those need the whole-task-list view. `derive-tasks` never calls it: the batch path writes its own briefs, so the two authoring runners share the format file and nothing else.
- The completion procedure — find task, load environment and derive the acceptance bar, carry out, verify against that derived bar, move TODO→DONE augmented with it — lives in exactly one place: `core/shared/complete-procedure.md`. Neither the `complete-task` skill nor the agent may duplicate or restate those steps; both reference the shared file via `{{PLUGIN_ROOT}}`. The shared file is execution-neutral — it must not mention the `DONE`/`FAILED` return protocol, committing, or follow-up; those belong to the wrappers. `complete-task` exists as both a user-facing skill and an agent, differing only in *where* the shared procedure runs. The **skill runs it inline** in the user's conversation (so the work context survives for follow-up) and must never spawn the agent. The **agent runs it in an isolated subagent context** and adds the `DONE`/`FAILED` return protocol; it is what the `complete-all-tasks` orchestrator spawns per task. Choosing inline vs. isolated is the entire reason both exist — keep that the only difference.
- Every runner that reads or writes a milestone's task list resolves `<MILESTONE_DIR>` by following `core/shared/get-current-milestone.md` (which reads `milestones/README.md`) — `core/shared/complete-procedure.md`, `derive-tasks`, and the `submit-task` skill alike; none may use a hardcoded task-list path. `core/shared/task-format.md` resolves nothing: it defines the section format only, and milestone resolution now lives in its two authoring runners.
- Task altitude is split, and the dividing line is **what can be re-derived at completion time**. An authoring runner writes only what *cannot* be reconstructed from the milestone's goal + the live project: the title and the 1–3 sentence description (intent — what, why, and how it would be verified). Everything else belongs to `core/shared/complete-procedure.md`, which owns the flow and the **detailed design** (decided fresh against the live project and its deliverables) and, on top of that: it **derives the formal acceptance bar itself** from the task description plus the milestone's `requirements.md` — the task carries no authored acceptance criteria, so the derived bar, not anything in the task body, is what the work is verified against; it **resolves every cross-task reference by reading the prior task's live deliverable** in the project rather than a forward contract the task list promised (tasks run in dependency order, so that deliverable already exists by the time it is needed); and it **records the derived bar** in the `TASKS_DONE.md` entry, as a `**Verified:**`-labeled bullet list — one bullet per criterion, in the order verified, inside the same `##`/`---` section the TODO→DONE move writes — so every finished entry carries the brief plus the bar the work actually passed. The `**Verified:**` label is deliberately distinct from any authoring label, keeping the completion record from being read as an authoring contract and regrowing a done-ness section in `TASKS_TODO.md`. Keep task bodies minimal to save tokens; never push design detail — or a re-narration of the flow — back into authored tasks.
- **Skill Frontmatter**: Every user-facing skill (`SKILL.md`) must carry YAML frontmatter containing `name` and `description` keys. The host build (`scripts/build_hosts.py`) requires this on every host tree it renders — its `frontmatter-missing`/`frontmatter-invalid`/`frontmatter-keys` checks fail the whole selected build, writing nothing, if either key is missing or the block does not load. This bullet is the home of **every** rule governing the frontmatter `description` key, across all `core/skills/*/SKILL.md` and all `core/agents/*.md`. A description is **one short sentence of 25 words or fewer** naming only what that skill or agent does. **Shape:** a single independent clause — a qualifying rider set off by commas, an em dash, or parentheses is allowed, but the **semicolon and the colon are banned outright**, because those two marks introduce a second statement or an enumeration and are the route by which deleted material returns under the cap. **Parsing:** the raw frontmatter must load under `yaml.safe_load` with the `description:` line left **unquoted** (a plain YAML scalar — no colon-space, no leading indicator character, no trailing colon); the build has no re-quoting fallback — a `description:` line `yaml.safe_load` rejects fails its `frontmatter-invalid` check outright — and its `description-length` check enforces the 25-word cap below on every rendered tree. **Deleted, not relocated:** design provenance, mechanics (commit subjects, sequencing, dispatch counts, preconditions), cross-skill references, "Use when…" framing, and trigger-phrase lists are cut outright — a description is a **routing label, never a record**, so cut content carries no obligation to survive anywhere (cairn is invoked only by explicit slash command and is never auto-discovered, and `docs/skill-reference.md` and this file are the homes for that material). The 25-word cap is a hard pass/fail bar with **no exceptions**: a description that does not fit is reworded until it does, and overlap with a sibling skill is a wording problem to solve within the cap, never grounds for overage. An `core/agents/*.md` description keeps its **invocation contract**, compressed into that same sentence as a short clause naming what the prompt carries (the task's heading text, the question's Short Title); the separate "dispatched by X, not called directly by the user" note is provenance and is deleted.
- **Runtime files carry no editor-facing prose, and name no host.** The runtime layer (`core/skills/*/SKILL.md`, `core/agents/*.md`, `core/shared/*.md`, and the one program `core/tools/open_questions.py`) is loaded in full at run time, so it holds only what the runner acting on it needs. It is authored once for every host: every cross-reference uses the `{{PLUGIN_ROOT}}` placeholder that each host definition replaces with its own plugin-root literal (never a host's runtime syntax, and never followed by a resolve hint), and no `core/` file names a host — the build's `host-name-in-core` guard fails the whole build on one — so a sentence that depends on what a host can do names the **capability** (whether the host can continue a finished agent session; the agent's registry name under this plugin's namespace; the coding agent working in the repository) and never the host that has it. The one host-specific item is a field, not a sentence: the agents' Claude-only `color` frontmatter key stays in `core/` and is stripped by the Antigravity definition's `strip_frontmatter_keys` data, so the build carries structural rules only and no prose-rewrite rule that a rewording could silently stop matching. **Every tool invocation is the one fixed command** `python3 {{PLUGIN_ROOT}}/tools/open_questions.py <subcommand> <MILESTONE_DIR> …` — the already-resolved milestone directory as its argument (never the file path, never the pointer, which only `core/shared/get-current-milestone.md` parses), a free-text body (`add`'s question text, `embed`'s agent message) on standard input as a quoted-delimiter heredoc, no fallback interpreter expression at any site, and the runtime prose never consulting `python` — and each site states the tool's contract in at most one sentence (a read prints bare values, a mutator prints nothing, any failure is one `Error: <reason>` line with the document unchanged) rather than restating escaping, indentation, boundary tokens, or reconciliation mechanics, which are the tool's internals. **The tool is the file's sole writer, not its sole reader**: a consumer that needs the whole question set to reason over — the recommend agent's grounding, `core/shared/recommend-procedure.md`, `discuss-open-question`, `ask-in-milestone-context`, `modify-milestone-goal`, and the review pass — reads `<MILESTONE_DIR>/open_questions.xml` directly with the file-reading tool, exactly as it reads `requirements.md` beside it, carrying the one rule that the whole read is for reasoning only while every locate, list, or lift goes through the tool; a consumer that needs less than the whole set uses `list`. The tool source lives under the same rules as every other `core/` file: no bare `{{` (no f-string or `format` brace literal), no host name as a word even in a comment or docstring, no `{{PLUGIN_ROOT}}` slot of its own (so the rendered copy is byte-identical to the file the test suite imports), and the build applies substitution, prose drops, and every rendered-tree check to it uniformly — a file-kind branch copying non-Markdown byte-for-byte is the one-line remedy reserved for the day a `prose_drop_patterns` entry would run over code, not taken while both lists are empty. There are **no `## Rules` sections** anywhere in the layer: a rule that constrains one step lives in that step, and a rule that constrains the whole skill is a sentence in the file's opening description paragraph, never a bullet list under a heading. **Editor-facing rationale** — why a design is the way it is, what a later editor must not "fix" back — lives in these invariants and not in the runtime file, and a file **names its counterparts only in the one sentence its contract needs** rather than narrating their roles. Prose may be cut from a runtime file only where its content survives earlier in the same file, in a referenced shared procedure, in the tool and its tests, or in an invariant here; point-of-use constraints, worked examples, and templates rendered once stay. YAML frontmatter `description` fields are outside this rule — the **Skill Frontmatter** invariant above is the home of every rule governing them.
- **Dispatched-agent return contracts are resumable and shape-checked.** A `FAILED` return from `complete-task` (agent) does **not** promise an untouched working tree — that promise was unimplementable once the task had edited files — but a **resumable** one: a failed or interrupted run leaves its partial work uncommitted in the tree, and `core/shared/complete-procedure.md`'s carry-out step treats any already-uncommitted changes as a previous run's partial work to **continue from, never redo or revert**. Do not restore the old untouched-tree promise. The read-only `recommend-open-question` agent's success return is the bare XML sub-elements with **no `DONE` line**, and its failure return ends in `FAILED: <reason>` with nothing else. Its **step 4 — and step 4 only** — is a **draft → self-check → emit** step: it opens by naming step 3's rendering as the draft (so that rendering can never be treated as the final message), its only test list is the two shape tests the tool's `embed` extraction keys on (first non-whitespace text starts with `<alternative`, last non-whitespace text ends with `</recommendation>`), and the draft is revised until both pass. That rewrite **dropped the accumulated prohibition list whole** — the two tests subsume every entry of it — keeping only the positive "every grounding finding is spent inside the elements" redirect as drafting guidance. Step 3's rendering specification keeps the element shapes (the `<depends-on>` element joined them under milestone 21) but **carries no indentation rule and no entity-escaping bullet any more**: the children must be well-formed XML because the tool parses them before writing (a bare `&` or `<` in text or an attribute is written `&amp;`/`&lt;`, and that is what `embed` refuses as `not well-formed XML`), and beyond that indentation, escaping, and child order are re-rendered by the tool on write, so they are not the agent's to get right. `recommend-all-open-questions` judges every return in one fixed order as a single per-return pipeline — **last-line verdict, `embed`, then one repair**. (1) The **last non-whitespace line is read before anything else**, and a line beginning `FAILED:` is an explicit failure — skipped with that reason and **never repaired**, even when embeddable elements sit above it — which keeps one last-line-token convention across all three dispatch sites and is the only rule immune to a `FAILED:` token appearing legitimately inside element text; a `FAILED:` token anywhere else is then ordinary text. This verdict is the **only judging the orchestrator does itself**: it is agent protocol shared with the two tool-less dispatch sites, and its outcome (skip, never repair) is a control decision only the orchestrator takes, which is what rules out handing the tool the whole pipeline. (2) Every other return is piped **whole and unedited** to `python3 {{PLUGIN_ROOT}}/tools/open_questions.py embed <MILESTONE_DIR> "<Short Title>"` on standard input through a quoted-delimiter heredoc, and the tool does what the orchestrator's extraction step and seven-test acceptance gate used to do in prose: it slices from the **first `<alternative` line through the last `</recommendation>` line** and discards everything outside (the identity on a clean return — a discarded grounding summary or closing remark is not a failure in itself), then parses the fragment and validates it — no `<open-question>` or `<question>` line, no text outside the elements, well-formed XML, at least one `<alternative>`, exactly one `<recommendation>` whose `option` names one of the fragment's own alternatives (un-escaped, case-folded), every `<depends-on question="…" option="…"/>` **resolving one hop** to a block of the live document (other than the one being embedded) that carries a `<recommendation>` and to one of that block's `<alternative id>` values (the target's own tags are not followed, and there is **no cycle test** — a cycle is tolerated and handled by `walk`'s origin promotion), no element of a kind the format does not define, and **never child order** — and writes the block re-rendered in canonical form. Every miss, the two extraction misses included, is one `Error: <reason>` line on stderr with exit 1 and the document byte-for-byte unchanged, never echoing the offending prose; the reasons are pinned by `tests/test_embed.py`, and the skill restates none of them as strings. (3) Any refusal takes **exactly one repair attempt**, never an immediate skip; a returned `<depends-on>` that fails to resolve is **never dropped or rewritten** by the orchestrator, which pipes a return exactly as it arrived or not at all. The repair is **two-branch**: continue the **same** agent session where the host can continue a finished one (on Claude Code, `SendMessage` to the agent id the `Agent` tool returned, context intact, so the analysis is not redone), and only where the session cannot be continued — a host with no continuation equivalent, Antigravity today, or the handle is gone — **one fresh re-dispatch** with the same prompt plus the shape reminder; the runtime file keys the two branches on that capability and names neither host. The fresh re-dispatch is the continuation-**unavailable** fallback only; where continuation is available it is never the repair path. Repair happens **immediately, for that question** — the moment `embed` refuses, and before the next question is dispatched — never by holding refused returns back and running the repairs as a second phase once the last first return has landed; because dispatch is sequential, the next dispatch simply waits until this question's repaired return has been judged and the question embedded or skipped, and at most one repair is spent per question. The corrective message is a **fixed one-paragraph template rendered once in the skill with a single slot**, filled with the tool's `Error: <reason>` line verbatim (so the one attempt is aimed rather than blind, at no composition cost — the same line the skip advisory would carry), naming the element order (`<alternative>`, `<applied-principle>`, `<depends-on>`, `<recommendation>`), quoting both shape tests verbatim and **never quoting the offending prose back**; whatever comes back is judged by the same verdict-then-`embed` pipeline. Only a **second** failure is the **per-question skip** (block left byte-for-byte untouched — a refused `embed` never writes — sweep continues, still-skipped Short Titles and reasons printed as a git-absent advisory alongside the terse line), never a run stop — so a prose, partial, or explanatory reply still can never reach the document, while a valid recommendation merely wrapped in surrounding text is **recovered instead of dropped**. This **deliberately reverses** the earlier rule that a failing message "is discarded whole … never salvaged": the wording-only fix had already been applied once and the failure persisted (eight of ten dispatches in the milestone-19 sweep prefixed well-formed elements with a grounding summary and were skipped), so extraction plus one repair replaced it, and milestone 27 then moved the extraction into the tool — a short line-range slice before the parse `embed` performs anyway, the identity on a clean return so it needs no mode, and pytest-covered — do **not** restore the skip-only behaviour and do not move the extraction back into prose. The pattern is **scoped to this agent and this sweep**: `core/agents/complete-task.md`, `core/agents/answer-open-question-with-recommendation.md`, and the `complete-all-tasks` / `answer-all-open-questions-with-recommendation` orchestrators keep a **last-line token, not a whole-message shape** — prose above the token already passes, the returns carry no payload to salvage, and only trailing text *after* the token would reproduce the failure, which the repo records as never having occurred; extending extraction and repair to them would be precisely the general audit this change rules out.

## Development

This project supports both Claude Code and Google Antigravity from one source. The runtime layer — skills, agents, shared procedures, and the open-question tool — is authored **once, host-neutrally, under `core/`**'s four top-level directories (`skills/`, `agents/`, `shared/`, `tools/`), and every host plugin is generated from it. Cross-references inside `core/` use the placeholder `{{PLUGIN_ROOT}}` (e.g. `{{PLUGIN_ROOT}}/shared/commit-procedure.md`, `python3 {{PLUGIN_ROOT}}/tools/open_questions.py`) rather than any host's runtime syntax, and no file under `core/` names a host; the build guards both.

Each host is a **declarative definition directory** `scripts/hosts/<host>/` — `scripts/hosts/claude/` and `scripts/hosts/antigravity/` today. Its `settings.toml` declares, under one key set every host shares (a key with nothing to declare is left empty, never omitted): `plugin_name`; `plugin_root`, the literal that replaces `{{PLUGIN_ROOT}}` (`${CLAUDE_PLUGIN_ROOT}` for Claude Code, which resolves that variable to the installed plugin's root at load time; the workspace-relative path the Antigravity install extracts into, since Antigravity defines no plugin-root variable); `prose_drop_patterns`; `strip_frontmatter_keys` (the Antigravity definition strips the agents' Claude-only `color` key; the Claude definition strips nothing); `renames`; `exclude`; and the `[layout]` mapping each of `core/`'s four top-level directories (`skills`, `agents`, `shared`, `tools`) to its place in the host tree — a layout that omits one fails validation, and adding `tools = "tools"` to both hosts was the whole build change the tool needed. Every other file in the definition directory is a template rendered to the same relative path in the host tree with its `{{VERSION}}` slot filled from the root `VERSION` file and its `{{NAME}}` slot from `plugin_name`: the Claude definition carries `.claude-plugin/plugin.json` and a `.claude-plugin/marketplace.json` with source `"."` (so a marketplace add of the distribution repository works with the same layout the monorepo root has always used), the Antigravity definition carries its schema-bearing `plugin.json`, and each carries the `README.md`, the slot-free `CONTRIBUTING.md` pointer, and the slot-free `.github/workflows/traffic-badges.yml` traffic-workflow template that land in its distribution repository — the pointer sends visitors to the root repository for issues, pull requests, and vulnerability reports, because a mirror cannot disable pull requests and a change made there would be overwritten by the next release, while `SECURITY.md` and `CODE_OF_CONDUCT.md` stay root-only and are never rendered or copied into a host tree. Adding a host means adding a definition directory; no host-specific Python exists, and the build applies every definition uniformly.

`uv run scripts/build_hosts.py [<host> ...] [--check]` is the one generic build. With no argument it builds every host whose definition directory exists; one or more host names build only those. It renders each selected host from `core/` into a temporary directory (placeholder substitution, frontmatter-key strips, renames, exclusions, the templates filled from `VERSION`, and a copy of the root `LICENSE` — every file under `core/` treated alike, so `core/tools/open_questions.py`, which carries no placeholder and opens with no frontmatter, lands in `hosts/<host>/tools/` byte-identical to its source) and runs the **full validation gate** on the render before anything is written: `core/` names no host; every rendered `skills/<name>/SKILL.md` and `agents/<name>.md` has YAML frontmatter that `yaml.safe_load` accepts with `name` and `description`; every description is at or under 25 words; no `{{` is left anywhere in the tree outside a `${{` expression (the check is the one-character negative lookbehind `(?<!\$)\{\{` — a `{{` not immediately preceded by `$` — applied uniformly to every rendered file with no path-scoped exemption, template escape sequence, or definition key, so a GitHub Actions `${{ … }}` expression in a rendered workflow template passes while a bare `{{VERSION}}`, `{{NAME}}`, or `{{PLUGIN_ROOT}}` slot still fails the build); no other host's plugin-root literal appears in this host's tree; every occurrence of this host's own plugin-root literal followed by a path names a file in that tree; no frontmatter key the definition strips is still present; and every rendered manifest version slot, plus the root `marketplace.json` entry, carries exactly the `VERSION` literal. Any failure on any selected host exits non-zero listing every failing file and check, and no `hosts/<host>/` tree is touched; only when every selected host passes are the renders swapped into the committed `hosts/<host>/` trees. `--check` renders and validates the same way, then compares each render byte-for-byte against the committed `hosts/<host>/` tree, writes nothing, and exits non-zero listing the differing paths — the release's drift gate. The committed `hosts/claude/` and `hosts/antigravity/` trees are pure build output and are never hand-edited: rebuild after changing anything under `core/` or `scripts/hosts/` and commit the rebuilt trees with that change, so `main` always carries trees that match a fresh build. `--check` is what a maintainer or CI runs, never a git hook: the `.github/workflows/drift-gate.yml` workflow runs it on every push and pull request of the root repository, with no branch or `paths` filter (a `paths` list would be a hand-maintained second copy of the build's input set, the very drift the gate exists to catch), under `actions/checkout` and `astral-sh/setup-uv` pinned to full 40-character commit SHAs each followed by a `# vX.Y.Z` comment that is bumped by hand — no floating tag and no Dependabot — as the first of three `run:` steps in its one `check` job, followed by the tool's pytest suite twice (`uv run pytest`, then `uv run --no-project --python 3.9 --with pytest pytest`; see the next paragraph), never a matrix, a second job, or a second workflow file, so a pull request always carries one status covering the drift gate and both test runs and the README's `ci` badge, whose URL names this file, reports `main`'s pushed HEAD.

The open-question tool `core/tools/open_questions.py` is the one program in the runtime layer: stdlib-only, Python 3.9 or later (the installed plugin's one runtime prerequisite, documented for users and checked once per project by `init-milestone-base-workflow`), invoked by every skill, agent, and shared procedure that touches a milestone's `open_questions.xml` as `python3 {{PLUGIN_ROOT}}/tools/open_questions.py <subcommand> <MILESTONE_DIR> …`. Its pytest suite lives at the repository root under `tests/` (see the layout above) and runs as `uv run pytest` — under the interpreter `.python-version` pins (3.13 today) and the locked `dev`-group pytest — and as the floor run `uv run --no-project --python 3.9 --with pytest pytest`, which bypasses the build tooling's `requires-python = ">=3.11"` (the tool needs nothing from that project, and lowering the project floor would rewrite build tooling for an interpreter it never runs under) and resolves the last pytest supporting 3.9; both must pass before a change to the tool is committed, and the suite stays on the pytest API both majors share (8.4 under 3.9, 9 under 3.13 today). Because stdlib availability is monotone across minors, the two bracketing runs catch every too-new-for-the-floor slip (a `match`, an `X | None`) and every removed-by-the-pin one, which is why there is no version matrix; the pinned run carries no version literal, so a pin bump is one file, and the floor's literal `3.9` has three homes — the README prerequisite, the bootstrap check, and the CI floor run. The tool carries no `{{PLUGIN_ROOT}}` slot, no bare `{{`, and no host name as a word, so the build renders it byte-identical into every `hosts/<host>/tools/` and the suite imports the very file that ships; importing it leaves no `__pycache__` under `core/` (`tests/conftest.py` sets `sys.dont_write_bytecode`), and `__pycache__/` and `.pytest_cache/` are ignored.

The root `VERSION` file — the bare `MAJOR.MINOR.PATCH` literal on one line and nothing else — is the single source of truth for the plugin version. `uv run scripts/set_version.py <MAJOR.MINOR.PATCH>` writes it together with its three mirrored surfaces (`.claude-plugin/marketplace.json`'s entry, `pyproject.toml`, and `uv.lock`) in lockstep, all-or-nothing, and edits files only, never touching git or `gh`; it deliberately writes nothing under `hosts/`, because every host manifest and distribution README is rendered from its template with the version slot filled from `VERSION` by the build.

Releases are cut by the maintainer-only `/release-plugin <VERSION>` skill at `.claude/skills/release-plugin/SKILL.md` (outside `core/`, so no host build renders it). Its pre-flight runs `uv run scripts/build_hosts.py --check` and stops on any drift (remedy: rebuild, commit the sync as its own standalone commit, re-run) and checks with `gh repo view` that each host's distribution repository `uHappyLogic/cairn-<host>` exists, printing the exact creation commands rather than creating one; it then runs `set_version.py`, rebuilds, prepends the composed release notes to `CHANGELOG.md` as the `## <VERSION> — <YYYY-MM-DD>` entry (its milestone sections at `###`), stages `VERSION`, `pyproject.toml`, `uv.lock`, `.claude-plugin/marketplace.json`, `CHANGELOG.md`, and `hosts/` path-scoped, and makes one `Release: <VERSION>` commit that by construction changes only version slots and that changelog entry. From that commit on the committed entry, extracted from `HEAD:CHANGELOG.md`, is the notes' one source — shown at the pause and published to every release page on a fresh run and a resumption alike, so the changelog and the release pages carry identical text. After the monorepo push, bare `<VERSION>` tag, and GitHub release, it publishes each `hosts/<host>/` tree into its **distribution repository** — `uHappyLogic/cairn-claude` (the documented recommended install source) and `uHappyLogic/cairn-antigravity` — with git plumbing alone: `git commit-tree` on the tree object `HEAD:hosts/<host>` with the distribution `main` as sole parent (parentless on the first publish), pushed atomically to `refs/heads/main` and `refs/tags/<VERSION>`, followed by a GitHub release on that repository carrying the same notes. Those repositories are never hand-edited and carry no submodules; their issues, Discussions, wiki, and projects are disabled and each carries the rendered `CONTRIBUTING.md` pointer, so feedback routes here. Each of the three repositories (the monorepo included) also carries a `traffic-data` branch that only the `traffic-badges` workflow's daily `github-actions[bot]` pushes write (`totals.json` plus the two badge SVGs that the root README's first-screen adoption table reads for every repository and that each distribution README's two-badge strip above its title reads for its own) and that no build renders and no release touches, and holds the `TRAFFIC_TOKEN` repository secret — the maintainer's fine-grained PAT with Contents read-and-write on exactly these three repositories, kept in no local copy, so a re-set means regenerating the token on its settings page and running `gh secret set TRAFFIC_TOKEN` on all three together. The monorepo's own `.claude-plugin/marketplace.json` keeps pointing at `./hosts/claude` and is the maintainer's directory-marketplace source for running cairn straight from the working tree.

Outside contributions follow the proposal-first workflow `CONTRIBUTING.md` spells out, and the repository settings on `uHappyLogic/cairn` are set for it: Discussions and private vulnerability reporting are enabled, squash merges and the wiki are disabled, and blank issues are off so the issue chooser (bug, feature, and milestone-proposal forms plus the Q&A Discussions link) is the whole intake map. There is no plain-pull-request tier — a small fix is filed as an issue for the maintainer to make. A substantive change is filed as a proposal issue; the maintainer accepts it by running `/define-milestone-goal` on `main` **only while their own `Current milestone:` pointer reads `none`, and without activating it**, so the `Milestone-definition:` commit reserves `milestone_<N>_<slug>` and `main`'s pointer stays the maintainer's to hold; the contributor forks and branches from that commit, runs `/goto-next-milestone` first and the full pipeline through `/finish-current-milestone` on the branch (so its net change to the pointer line is nil), syncs from `main` by merge only — never rebase — and only while `main`'s pointer reads `none`, aborting a pointer conflict rather than resolving it, rebuilds `hosts/` and passes `--check`, and opens the pull request, which is merged as a merge commit so the milestone commits survive for release notes and for `/capture-milestone-principle-updates`, which the maintainer runs after the merge. An abandoned contribution leaves only its defined directory on `main`, reverted or left as a `/goto-next-milestone` candidate.

## Milestone Workflow

This project uses the milestone-driven workflow. Each milestone lives at
`milestones/milestone_<N>_<slug>/` with `requirements.md`, `open_questions.xml`,
`TASKS_TODO.md`, and `TASKS_DONE.md`. `milestones/README.md` is the source of truth for
which milestone is current. Never advance the pointer without first running
`/finish-current-milestone`.
