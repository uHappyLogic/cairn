# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A plugin (`cairn`) for Claude Code, Antigravity, and Codex that brings a milestone's important questions up to be decided before work starts, so execution can then be handed to agents. It ships as a set of skills, a few agents, shared procedures, and the stdlib-only Python tools under `tools/` (among them the open-question tool and the task-list tool, the only writers of each milestone's open-question document and of its task list once they are created, the read-only milestones tool through which the live milestones are listed from the tree and finished milestones and completed tasks are read back from their commits, and the fold tool through which the answer sweep records its decisions in `requirements.md`) that move a project from a vague idea through discussion, planning, completion, and archival — milestone by milestone.

## Commands

```bash
uv run scripts/build_hosts.py                           # rebuild hosts/ from core/ after any change under core/ or scripts/hosts/
uv run scripts/build_hosts.py --check                   # drift gate: fails if the committed hosts/ trees differ from a fresh build
uv run pytest                                           # Python tool suite under the pinned interpreter (.python-version)
uv run --no-project --python 3.9 --with pytest pytest   # the same suite at the 3.9 floor; run both before committing a tool change
uv run pytest host_tests --host <host>                  # on-demand host suite driving the chosen host's installed CLI against that host's installed plugin copy, <host> exactly one of claude, antigravity, or codex; run against each host whose trigger set a change touches (CONTRIBUTING.md ## Development)
uv run scripts/set_version.py X.Y.Z                     # bump VERSION and its three mirrors; releases go through /release-plugin instead
```

## Skills and the workflow they encode

The skills form a linear pipeline, every skill working inside one milestone given its path as a required leading `--milestone <path>`; `docs/skill-reference.md` describes each one and `docs/workflow.md` the phases. Each skill's SKILL.md is its exact behaviour.

```
init-milestone-base-workflow        ← one-time bootstrap of the context file's ## Milestone Workflow guidance only; probes nothing; commits it alone under Workflow-bootstrap: milestones
migrate-milestones                  ← one-time upgrade of an earlier release's project, run by a person: re-finishes each history entry as a Milestone-finish: <path> commit, then removes milestones/README.md
discuss-milestone-goal              ← conversational, creates nothing; reads the record and proposes the milestone's --at scope
define-milestone-goal               ← checks git, then python3 ≥ 3.9; creates <scope>/milestones/<slug>/ with its three files from a required --at
specify-milestone-starting-state    ← fills "Relevant starting state", or refreshes it in place once since prints past the anchor, through the shared procedure; clears the picks a refresh undermines
review-milestone-requirements       ← repeatable loop engine and sole author of <open-question> blocks; reads the milestones overview; reports convergence
provide-alternatives-to-all-open-questions ← annotating pass 1: one read-only subagent per block lacking alternatives, embedded through the tool
recommend-all-open-questions        ← annotating pass 2: picks inline over the whole set, then sorts the document
discuss-open-question               ← conversation about one question; offers answer-open-question and modify-milestone-goal
answer-open-question                ← records a literal answer (Manual-answer:)
answer-open-question-with-recommendation ← records one question's embedded recommendation (Recommendation-answer:), inline
answer-all-open-questions-with-recommendation ← inline sweep in the tool's walk order, dispatching no agent, one commit per answer
answer-open-question-with-alternative ← records a named embedded alternative (Alternative-answer:); skill only
modify-milestone-goal               ← edits ## Goal and clears the picks it undermines with one non-transitive strip, committed together; surfaces the rest, never cascades
derive-tasks                        ← decomposes requirements.md into brief-level tasks; precondition: no open question; checks the scope gate first and again before writing, refreshing a stale starting state in between
submit-task / discuss-new-task      ← ad-hoc task entry (author one brief, checking the scope gate first and again before inserting, refreshing a stale starting state in between / clarify into briefs)
complete-all-tasks / complete-task  ← orchestrator over the complete-task agent / inline single task; each checks the scope gate before a task
ask-in-milestone-context            ← read-only Q&A
finish-milestone                    ← removes the milestone's directory in one Milestone-finish: <path> commit whose body is its summary; capture is a conventional follow-up, never a precondition
capture-milestone-principle-updates ← on-demand harvester of one milestone's answer commits into the principle store, given its path, removed ones included
```

## Milestone file structure

Each live milestone lives at `<scope>/milestones/<slug>/`, under the `milestones/` container of the directory holding the core of its work (`milestones/<slug>/` when that is the root), and contains exactly `requirements.md` (prose only: Goal, Relevant starting state, Decisions, Out of Scope, plus an optional fifth section, `## Noted contradictions`, between Decisions and Out of Scope, present only while a note stands and created by no tool — a single-question answer skill inserts its heading with the first note and the review pass deletes it with the last, so the milestone-definition tool's template, headed `# <title>`, keeps the four), `open_questions.xml` (created empty with the milestone, then written only by the open-question tool, in its canonical form; empty means converged), and `TASKS_TODO.md` (`##` headings + `---` separators; created with the milestone, then written only by the task-list tool, in its canonical layout). A completed task leaves the list, and its whole record is its `Task-completion:` commit — the title in the subject, the brief as the section's removed lines in the diff, the verified bar as the body — read back through the milestones tool's `tasks` query rather than from any file in the directory. No milestone is current and no file says which ones exist: the directories the discovery pattern finds are the live milestones, every one addressed by its path, and a milestone is finished once `finish-milestone` removes its directory, its whole record then its `Milestone-finish: <path>` commit — the summary as the body, the three files at the commit's parent — read back through the milestones tool's `summary` and `record` queries. The principle store stays at `milestones/answer_decision_principles.md` in the root container whatever scopes the milestones use. Milestones defined before the XML split (this repository's `milestone_01`–`milestone_27`) hold no `open_questions.xml`, and those defined before completed tasks moved into commits (`milestone_01`–`milestone_53`) one more file, `TASKS_DONE.md`; the migration removes each such directory, files and all, in its finish commit, so they stand only in history, as the pre-split invariant and the task-list invariant's pre-flip note describe.

## Invariants to preserve when editing skills

These are the design decisions a later editor must not "fix" back. The mechanics they name live in the runtime files, the tools and their tests, and `docs/`; only the rationale lives here.

- **The open-question tool is the only writer of `open_questions.xml` once it exists, not its sole reader.** The milestone-definition tool creates the empty document with its milestone directory; after that, every listing of or change to the question document is a tool call, invoked at every site as the one fixed command `python3 {{PLUGIN_ROOT}}/tools/open_questions.py <subcommand> <MILESTONE_DIR> …` (the resolved directory, never the file path; free text on stdin as a quoted heredoc; never `python`). A user-invoked skill running inline in the conversation, or a shared procedure followed by one, that needs the whole set to reason over reads the file directly, for reasoning only; a dispatched agent never does — dispatched agents reach the question document only through the tool. That ban's placement scopes it to this one document, so it needs no carve-out for the other files an agent reads whole (the `complete-task` agent reads `TASKS_TODO.md` whole, both agents read `requirements.md` whole as prose). Runtime prose states the tool's contract in at most one sentence per site and never restates escaping, indentation, boundary tokens, or reconciliation mechanics. The pre-milestone-27 `awk`/`sed`/`grep` boundary-line idiom stays retired. There is no hand-edit exception anywhere: a stale alternative set or pick is cleared with the tool's `strip` / `strip --recommendation` and a re-run.
- **The task-list tool is the only writer of `TASKS_TODO.md` once it exists, and changes no read of it.** The milestone-definition tool creates the file with the milestone directory; after that every write is one fixed command `python3 {{PLUGIN_ROOT}}/tools/task_list.py <subcommand> <MILESTONE_DIR> …` (`initialize` for `derive-tasks`, `insert` for `submit-task`, `remove` for the completion procedure; free text on stdin as a quoted heredoc; never `python`), while every read of the list stays as it was — whole-file prose reads by the completion procedure, `complete-all-tasks`, `finish-milestone`, `derive-tasks`, the triage skills, and `ask-in-milestone-context` — because the reads never failed: the completion tail's section move was the one step runners rewrote as code each time (about three in four of 202 measured completion agents wrote an ad-hoc slicing script, one needing a second script to repair a blank line), so the `##`/`---` parsing moved into a tested tool and the chained call made the completion tail one turn. Runtime prose states the tool's output contract in at most one sentence per site and never restates its parsing or layout rules. Every write parses the whole file and renders it in one canonical layout, untouched sections included, because nothing ever checked the shared blank-line convention and drift is normalized silently on the first write rather than refused; the same render discards whatever stands above the first section and writes the file's fixed heading, never checking or refusing the preamble, since every writer commits its own write and a dropped line is in that commit's diff and recoverable by revert. A section ends at its `---` when one comes first and otherwise at the next heading or the end of the file, a section without one is accepted silently, and every section the tool writes carries its `---` (an insertion behind an unterminated section gets the separator that boundary needs). On re-parse a section's `---` is the one standing directly before the next heading or the end of the file — a `---` line is a separator only when the next non-blank line is a column-0 `## ` heading or the end of the file, every other `---` line is body text — and every column-0 `## ` line is a heading with no code-fence exemption: one bounded lookahead and no parser state, so a body `---` written verbatim never strands text between sections and no write refuses for it, while `insert`'s guarantee that piped body lines are never structure holds for its own call only. The tool matches every title (the section to remove, a `--before`/`--after` anchor) by exact equality after whitespace- and case-folding, refusing a partial or shared title, because a tool that guessed could remove the wrong section; the case-insensitive partial match stays in procedure prose, where step 1 resolves the user's name against its own whole read, lists the headings on no match, and passes the full heading on. Title uniqueness is checked in `TASKS_TODO.md` only, the one file the tool reads, never against completed tasks, so follow-up work may reuse a completed task's title, each completion listed by `tasks` under its own commit. `insert` takes the title as an argument and only the body on stdin, composing the heading and the `---` itself, and every call states exactly one of `--end`, `--before`, `--after` in a required group with no default and no append subcommand, because position encodes dependency order and a call that forgot its position must fail (argparse's exit 2) rather than land silently at the end; an anchor naming no section is refused, and `submit-task` then stops quoting the `Error:` line. `initialize` reads the whole ordered list in the file's own section form in one process and replaces `TASKS_TODO.md` with no flag and no refusal for what it held, so the `Task-derivation:` commit records the list whole and in order or nothing, and what was replaced is already in the previous commit, its drop visible in that diff and recoverable by revert; the guard stays the skill's Preconditions line. `remove` takes out the one matched section — its heading, body, and `---` — and nothing else: it reads no stdin and no bar, renders the section nowhere, and neither reads nor writes any other file in the directory, because a completed task's record is its `Task-completion:` commit (see the task-altitude invariant), whose diff already holds the brief as the removed lines and whose body carries the bar, so a copy rendered into a second file would be text re-typed where it could drift. It replaced `move`, which appended the section and the bar under a `**Verified:**` label to a done file, and with the second file went the two-file atomicity `move` needed (the done file replaced first and its original bytes written back when the list's replace failed, a failed restore leaving a duplicate): `remove` replaces one file through the atomic writer, and a failure leaves `TASKS_TODO.md` byte-for-byte unchanged. Because `remove` reads no bar, the empty-bar refusal `move` gave moved into the completion calls' own shell test (see the return-contract invariant), so the tool gained no bar check of its own. The tool is one self-contained file with its own copies of the stdin reader, error type, main, and atomic writer, importing neither sibling (a parity test asserts it, and conformance to the shared output contract is pinned behaviourally only), so every rendered tool stays one runnable file copied byte-identical into each host; a later milestone may still extract a module. Like every document writer the tool touches no git, because the git step differs per runner and rides beside the call (see the committing invariant). Beyond an empty title or body it validates nothing of `core/shared/task-format.md` and writes what it is given verbatim, so that file stays the format's only home and no authored brief is refused for its wording. The pre-flip note: every milestone defined before completed tasks moved into commits (this repository's `milestone_01`–`milestone_53`, the last holding the empty template, since none of its tasks was completed through `move`) held a `TASKS_DONE.md` beside its list, the record `move` wrote, each entry a section with its `**Verified:**` bar. Nothing reads or writes it any more — `remove` ignores one still standing, the milestone-definition tool creates none, and every former reader runs `tasks` instead — and `migrate-milestones` removes it rather than migrating it: each finished milestone's in that milestone's `Milestone-finish:` commit, its directory removed whole, and a live milestone's in the closing commit, so every one stands only in history, at the parent of the commit that removed it. For the tasks it records it stays the one record of the bar, because no completion commit of theirs carries one (each is subject-only, or a retired `Tasklist-completion:` commit `tasks` does not list) and carrying the bars into history would mean rewriting commits, so `tasks` lists such a task without its bar or not at all and no query reads the file: the partial compatibility the migration settles for. No runner is to read it again and no tool to recreate it. The retired four-call `Read`/`Edit` move, the ad-hoc move scripts (a Python slicing heredoc, `cat >>` plus a removal), `move` with its `**Verified:**` rendering and two-file rollback, `derive-tasks`' per-brief append, and `submit-task`'s append fallback on an unknown anchor must not be restored.
- **Live milestones are read from the tree, and finished milestones and completed tasks from their commits, through the read-only milestones tool.** `core/tools/milestones.py` exists because the record of finished work moved out of files and into commits — each completed task's into its `Task-completion:` commit, each finished milestone's into its `Milestone-finish:` commit — so every runner that once read a file of finished work needs the log, and a `git log` typed afresh at each site would be the hand-rolled code the tools exist to replace; it reads through `log`, `ls-files`, `rev-parse`, and `show` only, run from the workspace root, and writes nothing (see the committing invariant); the one file content it reads from a commit is a finished milestone's `requirements.md` at its finish commit's parent, read by `show`, every other file it reads being a live milestone's `requirements.md` in the working tree. Its eight queries, `live`, `gate`, `tasks`, `milestones`, `summary`, `record`, `since`, and `show`, are subcommands of the one file under one parser, one `Error:` contract and help text, and one git runner with fixed settings, because the tree-side and history-side halves share the discovery pattern, the join, and the scope rule, which two tools would each copy; a split is left to whichever later milestone finds a reason for one. A live milestone is a directory holding a tracked `requirements.md`, present in the working tree, that matches the discovery pattern `**/milestones/*/requirements.md`, defined once in the tool and read by every query, the `tasks` join included, with no exclusion rule; a nested project's milestones would therefore count, so this repository keeps the host suite's fixture project's container under a name the pattern does not match, `tests/fixtures/host_project/milestones.fixture/`, which the suite's `seeded_repo` renames to `milestones/` in the repository it seeds. A milestone's scope is the directory holding its container, compared by whole path components. A milestone is started when the path-scoped `git log -1 --diff-filter=M` on its `TASKS_TODO.md` prints a hash, which only a write after the definition commit created the file gives and only a task entry makes; started is read from the log, never from the list's contents, because the list empties as tasks complete and a milestone whose every task completed but which nobody finished must still read started. `live` with no argument prints one line per live milestone in path order, three tab-separated fields: the path with its trailing slash, `started` or `defined`, and the title from the first `# ` heading of its `requirements.md` with any legacy `Milestone <N>: ` prefix stripped (`-` when it has none); that print is the resolution stop's listing and stays exactly as it was. Its optional MILESTONE_PATH, read lexically and refused as `gate` reads and refuses its argument, narrows the print, in the same line and order, to the other live milestones, started or defined, whose scope equals, contains, or lies under the named one's, the named one left out as `gate` leaves it out: it is the starting-state procedure's in-flight read, its first caller needing a filter, and it lists a defined sibling beside a started one because a sibling still deciding is part of what is in flight although it holds no scope. Every caller that already holds a resolved milestone passes that path, never a scope it would compute itself, and the tool derives the scope, as it does for `gate`. `gate MILESTONE_PATH` prints, one bare path per line in path order, every other live, started milestone whose scope equals, contains, or lies under the named milestone's, and exits 0 whether or not anything is printed: it is an ordinary query under the unchanged contract, and holding the scope is the runner's test for empty output, made in the scope-gate procedure (see the scope-gate invariant). It refuses a path with no `milestones/` container, read lexically, so a matched milestone path outside any container, which resolution accepts, is stopped at the gate; and it checks for a shallow clone, one of the two queries that do, refusing when `git rev-parse --is-shallow-repository` prints `true` with the `git fetch --unshallow` remedy, because a truncated log reads every started milestone as unstarted and the gate would then hold no scope without sign. `tasks PATH [--with-body]` selects only subjects opening with `Task-completion:` and takes the title from the subject after the marker; the 222 retired `Tasklist-completion:` commits, which carry the heading in their body, are never read and no later reader is promised for them, because every reader moved onto `tasks` reads a milestone no legacy commit touches, and the help text states where the record starts (2026-09-02, `milestone_15`), so a path that lists nothing for being older is a documented limit, not a silent gap. Each line is four tab-separated fields, the abbreviated hash, the author date, the milestone directory, and the title last: the tab is the tools' listing separator and keeps a spaced title unambiguous, and the hash takes a reader to the diff, where the brief now lives, in one `git show` rather than a subject search. The date is the author date and the lines are sorted newest first by author timestamp after the read, never left in git's traversal order, so the printed column is monotone whatever the commit graph says, and a rebase or amend keeps the day the task was completed. The milestone is joined by the one task list in the commit's file list that the discovery pattern, read with `TASKS_TODO.md` as its last component, matches, one file-list read with no diff parse, the field keeping the path's trailing slash, and a commit matching none or several is still printed under one fixed placeholder, so a hand-made anomaly stays visible rather than dropping a commit from a query defined as every one that changed the path; `2202e59`, which changed its own milestone's list and the agy fixture's, keeps its placeholder, since history is not rewritten. Under the flag each body line is printed beneath its task line indented by four spaces and a body-less commit is its line alone, with no placeholder, so the next column-0 line is always the next task: the boundary needs no lookahead, cannot collide with anything a body holds, and one parser reads both forms. An empty result prints nothing and exits 0 when PATH exists in the working tree or in history, so a fresh milestone breaks no chained reader and a deleted path is never refused, and otherwise refuses with one `Error:` line naming PATH, which is most likely mistyped. `milestones PATH`, `summary MILESTONE_PATH`, and `record PATH` read finished milestones back from their finish commits. A milestone is finished when its path is not live and a non-merge `Milestone-finish: <path>` subject in the path form names it, the latest such commit being its finish commit, so presence wins over the log (a reverted finish reads live) and a finish subject naming an id is never read, a limit the help text states. `milestones` prints one line per milestone, live or finished, that changed PATH through a task commit or whose scope contains PATH or lies under it, four tab-separated fields: the state (`live` or `finished`), the finish commit's author date as YYYY-MM-DD (`-` for a live milestone, the placeholder `tasks` uses), the path, and the title last, every live line above every finished one, live lines in path order and finished lines newest first by finish timestamp. Because the file keeps being written by hand, the fold is a byte-preserving splice, not the task-list tool's whole-file render: it reads the file only to find the landing point and writes back every byte it did not insert, normalizing nothing, so each `Recommendation-answer:` commit's `requirements.md` diff is exactly the folded decision, or a conflict answer's rewritten subsection body. Either subcommand's body is opaque Markdown written verbatim with its outer blank lines trimmed, as the retired `move` wrote its bar, so every format rule (clean prose, no citation marker, the entry's shape matched to its subsection) stays in the answer core's fold step, its one home, and the tool has no rendering path. `--section` is required (argparse's exit 2), mirroring the task-list tool's required position group, because both recorded shapes of the section hold decisions only under a `###` heading and an optional one would add a placement branch that mis-files a decision or invents a third shape; a heading matching no subsection after whitespace and case folding is created at the end of `## Decisions`, never refused, so one call shape serves a fresh milestone's first decision and every later one, and a near-duplicate subsection stays visible in the commit diff; every column-0 `## ` line ends the section, so a subsection `fold` creates lands above a standing `## Noted contradictions` heading and the fifth section needed no change to it. - **An alternative set is distinct and covering, with no count.** Step 2 of `alternatives-procedure.md` maps the decision space rather than shortlisting candidates: it names the axes of the underlying decision first (values taken from the decision, not from the list the wording offers; a degree is an axis; each premise the wording takes for granted is an axis valued accept or reject; every axis has a none position), builds each option as one position on every axis, and tests the result — distinct (every two options differ in substance on at least one axis) and covering (the set covers the underlying decision rather than the question's wording, not doing the thing included wherever honestly viable, postponing being one form of it and never a second option). The set is the only menu every later pick chooses from and it outlives the decisions after it, so a direction it misses is invisible downstream; the failure patterns the rule targets are near-duplicate options that differ only in wording or emphasis, an answer taking a direction no option represented (most often not doing the thing the options vary), a combination on an axis the set never laid out, and a premise every option shared. - **Committing is a property of the skill layer, and its mechanics live in the commit tool.** `core/tools/commit.py` runs the dirty-own-path guard, the path-scoped `git add`, and `git commit` with the paths as its pathspec, and `core/shared/commit-procedure.md` is reduced to that tool's one fixed command over PATHS, SUBJECT, and an optional BODY and REMOVALS, run as the step's one git tool call with no git command of the runner's own beside it; the execution-neutral shared procedures stay commit-free. The pathspec is what makes a commit record exactly its own paths: a commit without one takes the whole index, so with two completion runs in one tree (checked on 2026-10-28) run B's staged files rode into run A's `Task-completion:` commit and B then found nothing staged, and an answer sweep or annotating pass of a milestone preparing beside a live completion run would record that agent's staged task under its own subject; with the paths as pathspec whatever else the index holds, another run's staged change included, stays staged and out of the commit. Each git write repeats only when git exits 128, its fatal-error code and the one a held index, ref, or `HEAD` lock produces (git gives up on the index lock at once), while exit 1 (a hook's refusal, nothing to commit, a pathspec matching no file) passes on at once; only the exit status is tested and no message text is read, so the tool retries no hook and no runner classifies a failure. The schedule is one constant, a fixed short pause between a bounded number of attempts, a window of a few seconds with no override, so another run's ordinary write is absorbed while a lock a crashed process left surfaces as git's message rather than as a call that waits forever. The tool takes two optional inputs beyond paths, subject, and body. `--remove PATH`, repeatable, runs `git rm -r -q -- PATH` for each removal the index still holds, inside the same retry schedule and before the other paths are staged, and records the removals in the same pathspec commit, its dirty-own-path guard covering them and `git rm` refusing a file with an uncommitted change, so no uncommitted work is discarded; it exists because finishing removes a directory, and a `git rm` typed beside the call would be the hand-rolled git step the tool replaced and would sit outside the retry. `finish-milestone` passes its milestone directory through it, as the commit procedure's REMOVALS, and `migrate-milestones` each directory it re-finishes and, in its closing commit, the files it retires. `--date DATE` is passed to `git commit --date` unchanged and sets the author date only, the committer date staying the time the commit is made, so the migration's re-finished milestones keep their original finish dates in everything the milestones tool prints; no other caller passes it, and a call without either option runs exactly the commands it ran before. The retry rides on git's own lock, not on a lock of the plugin's own, which a crashed run would leave behind with no message saying how to clear it, nor on a per-run private index, which would leave the shared index stale. The mechanics are a tool rather than steps written into each call because a retry loop re-typed by every caller is the hand-rolled code the tools exist to replace (a plain shell loop exits 0 after its last failed attempt), and one tested tool also absorbs the guard, the pathspec, and the path-file read, lets the retry be tested against a held lock, and keeps the pause out of a shell sleep. The tool prints nothing when a commit lands and, exiting 0, exactly one fixed no-op line on stdout when none of the paths changed, because a no-op is a success as every sibling mutator's is and a routine no-op must not end a call on a status a runner reads as failure; every refusal or git failure is one `Error:` line on stderr, carrying git's message when a git command failed. "Of its own" scopes the ban by origin, so the host-provided plugin-root reference in a rendered command falls outside it without being singled out and the clause reads the same in every host tree. The fix stays a prose rule although a commit tool now exists, because the failure lies in how a runner chooses to write a command, not in any command the files show: the commit tool was added for the pathspec, the lock retry, and the path-file read (see the committing invariant), not for this failure, and it is still invoked through a command line the runner writes, open to the same shortcut, so the rule now governs the commit tool's argument list as it governed `git status` and `git add`; only the orchestrator's commit-from-file call carries no path list on its command line at all, the tool reading its paths line-exact from the agent's path file. The invariant is scoped to those sites, not a general ban on shell variables: the `capture-milestone-principle-updates` snapshot (`SNAPSHOT="$(mktemp)"`, used quoted as `"$SNAPSHOT"`) is outside it, because it is one quoted value that word splitting never reaches, not a path list or a tool command, so it is neither removed nor cited as a loophole; its reliance on shell state surviving between calls is a separate failure this rule does not address. The alternatives pass follows the same scoping: `mktemp -d`'s print is held as a path and written out in full in every later command, never kept in a shell variable across calls, as `complete-all-tasks` holds its own run's scratch directory; its batch call is one fixed command shown in full and run exactly as shown, with only `<scratch dir>` and `<MILESTONE_DIR>` replaced by their paths, its commit-tool command naming `<MILESTONE_DIR>/open_questions.xml` literally and its `embed` and commit tool written as the full fixed tool commands; and the loop variables inside that call (the file, its title, the captured error and commit-tool output) are outside the ban for the snapshot's reason — each is one quoted value per file, set and used within the one call, never a path list or a tool command. The recommendation pass's batch call follows the same scoping: one fixed command shown in full and run exactly as shown, with only `<MILESTONE_DIR>` and each block section's Short Title and rendered elements replaced, its two commit-tool commands naming `<MILESTONE_DIR>/open_questions.xml` literally and every `embed`, `lift`, `sort`, and commit-tool call written as the full fixed tool command. Its per-block captured stderr and the commit tool's captured stdout are outside the ban for the snapshot's reason, and so is its commit body, although that value accumulates across the call rather than being set once per item: set empty at the top of the call, grown by each accepted block's lifted line through a literal-newline join (never `$'\n'` or `echo -e`), and passed quoted to the commit, it is still one quoted text value set and used within the one call, never a path list or a tool command, so word splitting never reaches it. The answer sweep's two calls follow the same scoping: each is one fixed command shown in full and run exactly as shown, the compact view with only `<MILESTONE_DIR>` replaced and the batched call with only `<MILESTONE_DIR>` and each question section's Short Title, heading, decision (a conflict section's new body), and option replaced, its commit-tool command naming `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md` literally and every tool call written as the full fixed command. The compact view's loop values (the walked id and its held lift line) and the batched call's per-section held line and captured commit-tool output are outside the ban for the snapshot's reason — each is one quoted value per item, set and used within its one call, never a path list or a tool command — and no shell variable carries anything from one section to the next. The chained task-list calls follow the same scoping: each runner's call (`derive-tasks`, `submit-task`, the `complete-task` skill and agent) is one fixed command shown in full in that runner's own file and run exactly as shown, with only its placeholders replaced (the milestone directory, the titles, the heredoc body, list, or bar, the recorded paths, the agent's scratch directory), the task-list tool and the commit tool written as the full fixed commands and every path named literally, on the commit tool's command line or, the agent's, on a line of its own in its path-file heredoc under its matching sentence; each call runs each of its tools once and holds no shell variable but the commit tool's captured stdout `out` and, in the two completion calls, the captured bar `bar`, each outside the ban for the snapshot's reason, so no multi-call clause is needed. Both completion calls capture the bar the same way, once, from one quoted heredoc in the group-fed form `{ bar="$(cat)"; } <<'EOF'`, the form the recommendation pass's batch call already uses, because the nested `bar="$(cat <<'EOF'` form fails to parse on bash 3.2 when the bar holds an apostrophe; the bar is typed once, tested as written, and passed on quoted (the inline call's `--body "$bar"`, the agent's write of the body file), so the runner escapes nothing and no file or turn is added. The orchestrator's commit-from-file call follows the same scoping: one fixed command shown in full and run exactly as shown, with only `<scratch dir>` and `<TASK_NAME>` replaced, the commit tool written as the full fixed command, naming no path, holding no path list, and typing no bar, the body read from the body file by a quoted command substitution, its `out` outside the ban for the same reason.
- **Success-path console reporting is terse.** One fixed identifier-free status line per run (no per-item output in a loop); `recommend-all-open-questions` alone has two, chosen in strict order by what the run committed, read from the fixed identifier-free marker line its batch calls print each time one of their commits lands (one for the annotation commit, one for the ordering commit), across every call of the run, re-send included, rather than from any test of the sort outcome by the runner. Its advisory carries, besides each block no option of which survives, each block its one corrected re-send refused again, with that second `Error:` line verbatim and the remedy of re-running the pass. The answer sweep reads its one status line the same way, from the marker its batched call prints per landed answer commit, and its two stops (the dirty start with its remedy, the stopped-at question paired with the error printed beside it) replace that line. Only git-absent decision-critical advisories survive alongside it (convergence verdict, untraceable requirement, the still-skipped questions the two annotating passes report, the answer sweep's completeness anomaly). The fixed-line rule extends past the success path, as one plugin-wide convention: every no-op and stop condition a skill states opens its report with one fixed, identifier-free line of its own, the whole first line, and whatever variable detail the condition needs follows on the lines below it — the tool's `Error:` line quoted verbatim, the Short Titles a precondition found, a remedy — so failure and clean-stop paths keep their full messages beneath that line. A condition is the check that ended the run, not the text of the refusal it relays: a tool call refused for any reason is one condition with one line, the `Error:` line beneath telling the reasons apart, so the runner never classifies an error's wording. Every line is unique across the plugin, a stop a shared procedure owns (the milestone resolution's one, the scope gate's one, the completion procedure's task lookup) having one line in that procedure, printed by every runner following it, and the success line the three single-question answer skills share being one listed line. The reason is the headless chain: no skill sets an exit code, so a harness running the skills one invocation after another knows how each ended only from its final message, and fixed lines let it match the success and no-op lines that continue a chain, record which stop ended one, and keep matching across versions. The review pass's convergence verdict is the one fixed line below a first line: whenever its closing `list` prints nothing it prints one fixed identifier-free convergence line under its still-open list, on a reshaping pass and a no-op pass alike, and never otherwise, because a harness repeating the review through the answer sweep as a bounded loop exits the loop by matching that line in the review's final message, and a verdict worded freely gives it nothing to match. The lines are a listed contract rather than prose: `docs/skill-reference.md`'s `## Fixed console lines` table lists every success, no-op, and stop line, and that convergence line as its one verdict line, with its source and kind, and `tests/test_fixed_console_lines.py` checks each listed line verbatim against every rendered host tree, as a whole line of a fenced block or a whole inline code span, and checks that no line repeats, so a line changes only together with its row. A message a fixed call prints to its own runner mid-run, never as a report's first line — the orchestrator's `path file empty`, the answer sweep's `dirty before start`, and `acceptance bar empty`, the one shared text both completion calls print when their test refuses an empty bar, a retry prompt for the runner — is outside the table, which is why that guard added no row and left the table, its preamble, and its test unchanged; the two fixed-call tests pin the message by behaviour instead. The alternatives pass's advisory carries, besides each `FAILED:` and post-repair skip and each failed commit, the result of one closing `list --without-alternatives` call after the run's last batch: every gathered id it still prints that is not already in the advisory goes in under the fixed reason `no annotation landed`, because no `DONE` is cross-checked against the scan and that print is the only place a file that never landed shows; the same print chooses between `Alternatives embedded.` and the no-op lines, so the status line is read from the document rather than from a count the orchestrator would have to hold. The rule is authored inline at each site that prints a line, a skill's reporting step or the step that stops it, and in the shared procedure that owns a stop; there is no `report-procedure.md`.
- **Task altitude.** Authoring runners (`derive-tasks`, `submit-task`, both over `core/shared/task-format.md`) write only what cannot be re-derived: a unique title and a 1–3 sentence brief. No `Steps`/`Provides`/`Notes`/`Success` sections ever. `core/shared/complete-procedure.md` derives the acceptance bar itself and hands it to its runner, which records it as the body of the task's `Task-completion:` commit, so the bar lives in a commit body, never in a task file, where it could be read as an authoring contract. The body holds nothing beyond the bar — exactly its `- ` bullets, one per criterion, with no brief, no label line, and no other field — because the brief is already recorded as the removed lines of `TASKS_TODO.md` in the same commit's diff and the subject carries the title, so subject plus bar is the whole handover a reader's judgment needs and no text is re-typed where it could drift; the retired `**Verified:**` label must not come back as a body line. The bar's record form (one `- ` bullet per criterion, in verification order, each as it stood when it passed, neither re-derived nor summarized) is stated once, in the procedure's step 5 beside the bare `remove`, worded as the form of the bar the procedure hands on and naming its destination only as the record the runner's own file writes, with no git step, commit, or body, so the procedure stays commit-free; the inline skill's call and the agent's body-file write show `- ` placeholders and refer to it, adding no rule of their own, and since the body is the bar alone that one sentence states the whole body's shape. `derive-tasks` delegates nothing; `submit-task` is skill-only; `complete-task` is the only skill+agent pair, differing only in inline vs. isolated. Every task-list runner resolves `<MILESTONE_DIR>` via `resolve-milestone.md` and checks the scope gate via `check-scope-gate.md` before its work (see the scope-gate invariant).
- **`derive-tasks` resolves a conflicting pair by recording order and is never blocked by one.** Its precondition stays the empty `list`, so a note under `## Noted contradictions` never stops it; where two `## Decisions` entries cannot both hold, the later-recorded entry governs the brief, every noted pair taken as conflicting as noted without re-judging and any pair the runner finds itself resolved the same way, and nothing is flagged for either. The rule fixes which entry wins where task derivation already let one win silently: of the 20 field runs that printed the sweep's old contradiction advisory, 12 went straight to task derivation, where one entry won with both left standing (in this repository's `milestone_43` the later one is what shipped), and no revert followed any advisory, so a flag would be an advisory nobody acts on and a block would make the run wait on a section the convergence check never reads. Later-recorded is read from the commit that added each entry's lines (blame or a pickaxe search path-scoped to `requirements.md`), never from file position, because a decision lands in whichever subsection fits rather than at the end of the file, so position says nothing about when it was decided, and never from the note, which records a pair, not its order.
- **Environment context comes from `CLAUDE.md`** (`AGENTS.md` in the Antigravity and Codex trees, through the `CONTEXT_FILE` slot; `/init` once per project) for the starting-state procedure (followed by `specify-milestone-starting-state` and, refreshing, by `derive-tasks` and `submit-task`), `derive-tasks`, and the completion procedure. The bootstrap writes only its `## Milestone Workflow` section into that file, and the migration only rewrites that section, both from `core/shared/workflow-guidance.md`; neither writes the environment context.
- **Dispatched-agent return contracts.** A `FAILED` from the `complete-task` agent promises a resumable tree (partial work continued, never redone or reverted), not an untouched one — do not restore the old promise; it writes neither the body file nor the path file and stages and commits nothing. The `complete-task` agent's success return is two files beside its last-line token, its bar and its change set never travelling in a message: `complete-all-tasks` creates its run's scratch directory once with `mktemp -d` before the first dispatch, and on `DONE` the agent has written its acceptance bar to `<scratch dir>/body.txt` and its task's whole change set — the paths the completion procedure's running list recorded plus `<MILESTONE_DIR>/TASKS_TODO.md`, one path per line, never built from `git status` or any tree-wide selection — to `<scratch dir>/paths.txt`, both chained behind its `remove`'s `&&`, with no payload above the bare `DONE`. The body file is the one place the bar crosses a process boundary: the agent derived and verified it, the orchestrator holds no work context and must not re-type it, and its commit-from-file call already reads one file the agent wrote, so the bar rides as a second fixed-name file beside `paths.txt` that the same call passes as `--body` and moves into `processed` with it. The agent's step-5 call opens exactly as the inline skill's does, capturing the bar once and testing that it holds a non-blank line ahead of `remove` behind `&&`, and only after `remove` succeeds writes the body file and then the path file, so nothing reaches the scratch directory unless the test and the removal both pass, both runners share one bar-handling form, and the write-nothing-else contract holds with no carve-out; an empty bar prints the call's one line and removes, writes, and commits nothing, and the runner fixes the bar and runs the call again, as it once did after a refused `move`. The orchestrator's call guards the crossing with `body file absent` and `body file empty` tests beside its two path-file tests, copying the pattern it already ran on the path file, each committing nothing and stopping the run under the existing `Task run stopped — a completed task could not be committed.` line with the task name and the test's own line below it, so no new fixed line was needed. The task list rides in the path file because the agent's fixed call already names it beside its recorded paths, so the file is the task's whole change set and the orchestrator's call names no path of its own, only the file. The names are fixed per run, written by every task's agent and taken from no task title, because a heading holding a slash or a double quote, both present among this repository's recorded headings, would otherwise end a run with its work done and its list unwritten; the orchestrator's commit call moves both files, once read and whatever the commit's outcome, into a `processed` subdirectory under names `mktemp` makes unique there, costing no turn and deleting nothing, so the fixed names are absent when the next agent starts, a missing file is detectable, and every task's bar and list stay on disk. The alternatives agent's return is a file, not a message. Its one write, the sole exception to its read-only contract, is `<scratch dir>/<Short Title>.xml` in the run's scratch directory, which the orchestrator creates once per run with `mktemp -d` (fresh and uniquely named under the system temp location, so no stale return or concurrent run collides with it; the same wording in every host tree, so it adds no slot; writable under Codex's workspace-write sandbox, which keeps `$TMPDIR` and `/tmp` writable by default). The agent writes under a temporary `.xml.part` name and renames into place with one `mv`, so a wake-up scan running while other agents still write never pipes a half-written file (the rename stays inside one directory, hence atomic). Its only final messages are the bare token `DONE` or `FAILED: <reason>`. The file is what stops a return travelling through the orchestrator's context twice — once arriving as the agent's final message, once re-typed into a heredoc for `embed` — so the orchestrator never holds a return at all. The final message is a token rather than the file's path because the path is fixed at dispatch (the Short Title exactly as given plus `.xml`, in a directory the orchestrator created), so the batch derives each title from the file name and has nothing to copy; a Short Title holding a path separator fails the write and surfaces as a `FAILED:` skip rather than a silent miss. The orchestrator's only judging is the last-line `FAILED:` verdict, which gets no repair; everything else is one fixed batch shell call that scans exactly the `*.xml` files directly inside the run directory, redirects each unedited into `embed --alternatives` (the tool slices and validates), commits each accepted question, prints one line per refused file or failed commit, and moves every piped file, accepted or refused, into a `processed` subdirectory, so no file is piped twice and the record of what was piped lives on disk, never in the orchestrator's context. Every refusal one batch call prints gets its one repair at once, all sent together in the same turn — continue the same agent session while its handle is still held, one fresh re-dispatch only once it is gone, the branches and the wait on the repairs written per host in the `ALTERNATIVES_REPAIR` slot — and the repaired file lands at the same path for a later batch with no special handling; whether a question has had its repair is the only thing tracked, and a second refusal or `FAILED:` is the per-question skip. A wait that returns before every awaited agent has ended waits again, without limit, so an expiry never skips a question. No `DONE` is cross-checked against the scan: a cross-check would need the per-agent list the batch exists to keep out of the orchestrator's context, and the closing `list --without-alternatives` call already catches every question whose file never landed, whatever its message said, leaving its block bare for the next run. The orchestrator deletes nothing — no scratch file, `processed` subdirectory, or run directory — and no delete or recursive-remove command enters the runner's prose, so a headless chain never meets a permission prompt for one and a refused return the advisory names stays on disk for inspection; the system's own temp handling reclaims the directory. The batch replaced, in milestone 43, the per-return pipeline, which judged, piped as a heredoc, repaired, and committed each return the moment it landed: across 21 measured runs that cost about 16 post-dispatch orchestrator turns per run, more than half of them text-only or silent, at a median 57k-token context with every return held twice, against an estimated 0.82M input tokens per milestone that batching and the smaller context save (1.17M counting one outlier run). Do not restore the per-return pipeline, a returned path, a `DONE` cross-check, or a cleanup step. The rule under both forms — pipe the whole unedited return to the tool, repair once, then skip — deliberately reversed the earlier discard-whole rule (eight of ten milestone-19 dispatches were lost to a grounding preamble), and the extraction moved into the tool in milestone 27; do not restore skip-only behaviour or move extraction back into prose. The batch pattern is scoped to that one agent: the one other dispatch site, `complete-all-tasks`, keeps a last-line token as its verdict and reads its agent's two fixed-name files only after a `DONE`, with no scan, repair, or batch, and the recommendation pass and the answer sweep dispatch nothing and have no return to judge.
- **A dispatch prompt carries only what the orchestrator already holds and the agent cannot fetch itself.** This holds for both dispatched agents without qualification: `complete-all-tasks` passes the task's `##` heading text, the resolved `<MILESTONE_DIR>`, and the run's scratch directory and nothing else, the alternatives orchestrator passes the question's Short Title, the resolved `<MILESTONE_DIR>`, and the run's scratch directory and nothing else, and each agent fetches the rest under the milestone directory itself (its task section; its own block by `locate` and its sibling scope by `list --with-question`; `requirements.md`). The milestone directory passes the rule at both sites because the agent cannot fetch the orchestrator's resolution: the `--milestone <path>` the orchestrator was given reaches the agent no other way, and nothing stored could tell the agent which of several live milestones the orchestrator commits for, so both prompt fences carry it as one fixed `Milestone directory: <MILESTONE_DIR>` line on every dispatch, one unconditional prompt shape at both sites, and the agent uses it as given with no resolution of its own. The scratch directory passes the rule at both sites because the agent cannot fetch it: each orchestrator creates its own with `mktemp -d` once per run, and both prompt fences carry it as one fixed `Scratch directory: <scratch dir>` line on every dispatch, the same directory for every agent of the run, passed on every host, unconditionally, so the prompt templates and the agent files stay host-neutral with no branch on whether the value is present. The body file added no prompt line: it lands in that same directory under its own fixed name beside `paths.txt`, so the `complete-task` prompt kept its three lines, and the bar travels in neither direction through a message — the orchestrator passes none, since the agent derives its own, and receives none in the agent's final message, the bar landing in the body file that the agent's empty-bar test and the orchestrator's body-file tests guard. The orchestrator holds no work context, so every extra slot is something it would have to gather and hold per dispatch only to hand over, and a value the agent can fetch is delivered twice when copied into the prompt (under the retired prompt with a `Question block:` slot the alternatives agent read its block in the prompt and again in its whole read of `open_questions.xml`); a fetch also gives the agent the live document rather than the orchestrator's snapshot. The retired `Question block:` slot and the orchestrator's per-question `locate` gather must not be restored, and the two `list` calls are the pass's whole gather. The rule constrains the prompt, not the agent's reading: what an agent may read whole is fixed per document by the invariants above.
- **Skill frontmatter.** Every SKILL.md and agent carries `name` and an unquoted `description` of one clause, 25 words or fewer, no colon or semicolon, loadable by `yaml.safe_load`; it is a routing label, never a record — provenance, mechanics, cross-references, and trigger lists are cut outright (their home is `docs/skill-reference.md`). No exceptions to the cap; an agent description keeps its invocation contract as a short clause.
- **Runtime files carry no editor-facing prose and name no host.** They hold only what the runner needs. The rule covers every rendered runtime file, slot values included: a value names no host, its own included, and reaches its host's mechanism through that host's own identifiers (tool names, config keys, file and command names), otherwise saying "this host" (the agents' Claude-only `color` key is stripped by the Antigravity and Codex definitions' data, the one structural exception). With it goes a development rule: a rendered tree never names another host's mechanism, in any file — the files rendered from `core/` and the host's own templates (README, CONTRIBUTING pointer, manifest, marketplace file, traffic workflow) alike, a contrastive mention of what this host does not use included; a link to the source repository is not a mechanism naming. It is a rule, not a check: `host-name-in-core` keeps scanning `core/` only, so a slot value or template that breaks it passes the build and is caught in review. A host's hands-on check is recorded in one place only, the dated block in the header comment of that host's `settings.toml`, naming the installed version checked and the points and values the run covered, which a later re-check updates; the comment above each slot entry says only what the value stands for and why, in mechanism terms, with no version, and no tool version or observed-behaviour fact enters this file. No `## Rules` sections: a rule lives in the step it constrains or in the opening paragraph. Rationale lives here. The tool sources follow the same rules (no bare `{{`, no host name even in a comment, no placeholder of their own) so each renders byte-identical into every host.
- **Host wording differences are named slots, never markers, duplicated files, or capability-conditional prose.** A sentence or phrase that differs between hosts is a `{{SLOT_NAME}}` placeholder in `core/`, filled from every definition's `[slots]` table; the `slot-declaration` check keeps the declared name sets identical across hosts and each name used in `core/`, and `unfilled-placeholder` catches a slot a host leaves undeclared. A slot is preferred over capability-conditional prose: `core/` never names a capability and leaves the runner to pick a branch at run time, because a branch the host lacks is dead text in its tree that a runner can still follow, so each host's tree describes only its own mechanism. Each value is written from that host's own hands-on check, never copied from another host's, and the trees of two hosts are not expected to agree: no byte-identity between host trees is kept or tested, and the build's rendering is tested by `tests/test_build_rendering.py` instead. The convention is one value file per slot under the definition's `slots/` subdirectory, bound inside `[slots]` as `NAME = { file = "slots/NAME.md" }` with the slot's comment above its entry, every value of every host held that way, the one-word and empty ones included; the build still accepts the inline string form and nothing refuses it, so the file form is a convention, not a check. A value carries no placeholder other than `{{PLUGIN_ROOT}}`, which is why `AGENT_TOOL` and `ALTERNATIVES_AGENT` were retired: their wording is written literally inside each host's `ALTERNATIVES_REPAIR` value. The alternatives pass's host-dependent passages are slots: `ALTERNATIVES_PARALLELISM`, the opening paragraph's phrase saying whether the per-question dispatches run together; `ALTERNATIVES_REPAIR`, the opening of the repair sub-step ahead of its fixed corrective message, fill rule, and one-repair cap (which stay in `core/`), holding the repair branches this host has and how the run waits on the repairs; and `ALTERNATIVES_CONCURRENCY`, the paragraph opening step 3, which also governs how the pass collects returns. Each host's `ALTERNATIVES_CONCURRENCY` is one single-mechanism paragraph describing only that host's dispatch and wait: the Claude Code and Antigravity values send every dispatch at once, none blocking, and run the batch call each time the run wakes with landed returns, no shell loop or event monitor serving as the wait; the Codex value dispatches rounds of at most the session's `agents.max_threads` cap, calls `wait_agent` until the round's last final message has arrived before batching once, and gives a refused round's repair set its own wait and batch before the next round, so repairs never share a wait or take a slot. `ALTERNATIVES_CONCURRENCY` and the repair wait in `ALTERNATIVES_REPAIR` are the pass's only host-dependent waiting wording; no slot was added for the batch, and the scratch directory, the dispatch prompt, and the agent file are host-neutral. The Antigravity values dispatch both agents by the bare names the tree's own `agents/` directory carries, with no file or build change added for agent loading. Codex runs both agents as its generic subagent told to read and follow the plugin's Markdown agent file, with no TOML file, registration step, or format conversion in the build, because Codex documents no way for a plugin to ship a custom agent.
- **Pre-split milestones** (`milestone_01`–`27`) get no compatibility: they hold no `open_questions.xml`, and `migrate-milestones` re-finishes them like every other finished milestone, removing each directory in its `Milestone-finish: <path>` commit, so they stand only in history, at those commits' parents, where `git show` and capture's diff walk reach them; their files are not converted, and a question skill pointed at such a directory, restored or in a project not yet migrated, stops on the open-question tool's `Error:` line.

## Development

The build loop, both test runs, the version bump, and the distribution repositories are documented in `CONTRIBUTING.md` under `## Development`; the release procedure in `.claude/skills/release-plugin/SKILL.md`. Points not recorded there:

- `hosts/<host>/` trees are pure build output: rebuild after any change under `core/` or `scripts/hosts/` and commit the rebuilt trees with that change, so `main` always passes `--check`. `--check` is run by a maintainer or CI, never a git hook; the CI workflow has no path filter (a `paths` list would be a hand-maintained copy of the build's input set) and is one job, never a matrix.
- The floor run bypasses the build tooling's `requires-python = ">=3.11"` on purpose; the tools need nothing from that project. Two bracketing runs replace a version matrix because stdlib availability is monotone across minors. The literal `3.9` has three homes: the README prerequisite, the `define-milestone-goal` check, and the CI floor run. `tests/test_build_rendering.py` is the suite's one pinned-only test: the build imports `tomllib` and PyYAML, so the module skips itself at module level below Python 3.11, keyed on the interpreter version and before any import of the build, and the floor run reports it skipped while the pinned run never does; no pytest command, `conftest.py`, or `pyproject.toml` setting excludes it. It renders a synthetic `core/` through one synthetic definition in-process and covers rendering and the file-backed slot refusals, not `main`'s orchestration or the check set.
- Adding a host means adding a definition directory under `scripts/hosts/`; no host-specific Python exists. A host definition's `[layout]` must map all four `core/` directories, every one inside its `plugin_dir` (the path from the tree root to the runtime plugin root: empty for Claude Code and Antigravity, `plugins/cairn` for Codex), and it must declare every wording slot the other definitions declare, each value held by convention in its own file under the definition's `slots/` subdirectory (which template discovery skips), the inline string form still accepted.
- `set_version.py` writes nothing under `hosts/` (manifests are rendered from `VERSION` by the build). `/release-plugin` makes one `Release: <VERSION>` commit that changes only version slots and the `CHANGELOG.md` entry, then publishes each host tree with `git commit-tree` into `uHappyLogic/cairn-<host>`; those repositories and every `traffic-data` branch are never hand-edited. `TRAFFIC_TOKEN` is a fine-grained PAT on exactly the four repositories, kept in no local copy.
- Outside contributions are proposal-first (see `CONTRIBUTING.md`): the maintainer reserves the milestone by running `/define-milestone-goal --at <scope>` with the accepted goal on `main`, choosing the scope, its `Milestone-definition: <path>` commit being the reservation; the contributor branches from that commit, runs the pipeline with `--milestone <path>` through `/finish-milestone`, whose removal commit carries the milestone's record, syncs by merge only, and the pull request, whose template names the reserved path, is merged as a merge commit so the milestone commits survive for release notes and capture. An abandoned contribution is cleaned up by reverting the definition commit.

milestone is current: every skill working inside one is given its path as
`--milestone <path>`, exactly as `/define-milestone-goal` printed it, trailing slash included.
A milestone directory is removed only by `/finish-milestone`, whose `Milestone-finish: <path>`
commit carries the milestone's record, so the directories standing are the live milestones and
the git log holds the finished ones.
