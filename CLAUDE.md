# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A Claude Code plugin (`cairn`) that provides a milestone-driven development workflow. It ships as a set of skills and a couple of agents that move a project from a vague idea through discussion, planning, completion, and archival — one milestone at a time.

## Repository layout

```
.claude-plugin/plugin.json   — plugin manifest (name, version, author)
.claude-plugin/marketplace.json — single-plugin marketplace manifest (installable via /plugin marketplace add uHappyLogic/cairn)
skills/<skill-name>/SKILL.md — one skill per directory; the SKILL.md is the full skill definition
agents/complete-task.md — task-completion subagent invoked by complete-all-tasks skill
agents/recommend-open-question.md — read-only recommendation subagent (non-interactive twin of discuss-open-question) invoked once per question by the recommend-all-open-questions orchestrator; returns the ready-to-embed `<open-question>` child sub-elements (one `<alternative>` per option with child `<advantage>`/`<drawback>`, zero or more sibling `<applied-principle>` elements, one liftable `<recommendation option="...">` element), never edits documents
agents/answer-open-question-with-recommendation.md — file-editing subagent (the divergent one): lifts a question's embedded recommendation and records it via shared/answer-with-recommendation-procedure.md, leaving the edit uncommitted for the orchestrator to commit, returning DONE/FAILED — invoked once per question by the answer-all-open-questions-with-recommendation orchestrator; isolates mutation (not reasoning) unlike the read-only answer/recommend subagents, and like every dispatched agent never commits
shared/complete-procedure.md — single source of truth for the complete-one-task procedure, followed inline by the complete-task skill and in isolation by the complete-task agent
shared/task-format.md — single source of truth for the brief-level task-section format (## title, 1–3 sentence description, trailing --- separator) and its authoring guidelines; referenced via ${CLAUDE_PLUGIN_ROOT} by the two runners that author task sections (the derive-tasks skill and the submit-task skill) and parsed by shared/complete-procedure.md, which is what turns those sections into work
shared/answer-procedure.md — single source of truth for recording an answer (locate the `<open-question>` block by Short Title via the boundary-line CLI → remove the whole `<open-question …>`…`</open-question>` block → fold decision into ## Decisions → cascade), referenced by answer-open-question and shared/answer-with-recommendation-procedure.md (which composes over it with a lifted ANSWER)
shared/answer-with-recommendation-procedure.md — single source of truth for the lift-then-delegate procedure (locate the `<open-question>` block via the CLI → lift its `<recommendation option="...">` element as "`<option>` — `<rationale>`" with reverse entity-substitution, with a no-`<recommendation>`-element guard → delegate to shared/answer-procedure.md with the derived ANSWER), composing over the execution-neutral recording core; followed inline by the answer-open-question-with-recommendation skill and in isolation by the answer-open-question-with-recommendation agent
shared/recommend-procedure.md — single source of truth for the principle-aware "alternatives + single recommendation for one question" analytical core (execution-neutral, reads the fixed-path principle store in place, no XML rendering markup), referenced by the discuss-open-question skill and the recommend-open-question agent
shared/commit-procedure.md — single source of truth for the skill-layer commit step (dirty-own-path no-op guard → path-scoped git add of the caller's own PATHS → git commit under the caller's function-derived <Marker>: <descriptor> SUBJECT), referenced via ${CLAUDE_PLUGIN_ROOT} by every committing skill and every committing orchestrator; execution-neutral about resolving those paths/subjects (the wrappers own that)
shared/get-current-milestone.md — single source of truth for resolving <MILESTONE_DIR> from the grep-able pointer line in milestones/README.md
milestones/answer_decision_principles.md — project-wide answering-principle store at the milestones/ root, shared across all milestones (above any <MILESTONE_DIR>); the loop's one fixed-path artifact
LICENSE                      — MIT license
README.md                    — authoritative workflow documentation and skill reference
```

No build system, no tests, no dependencies. Everything is plain Markdown.

## Skills and the workflow they encode

The skills form a linear pipeline. Each skill's SKILL.md defines its exact behaviour:

```
init-milestone-base-workflow    ← one-time bootstrap: create milestones/ + milestones/README.md
discuss-milestone-goal          ← optional sharpening conversation, creates no files
define-milestone-goal           ← creates milestones/milestone_<N>_<slug>/ with requirements.md, TASKS_TODO.md, TASKS_DONE.md
specify-milestone-starting-state ← fills "Relevant starting state" in requirements.md
review-milestone-requirements   ← repeatable loop engine: each pass reconciles existing questions against recorded decisions, surfaces new gaps, reports convergence; run repeatedly
recommend-all-open-questions    ← orchestrator (batch form of discuss-open-question): sweeps open/deferred questions once (gathered via the boundary-line CLI), dispatches one read-only recommend-open-question subagent each, embeds the returned `<alternative>`/`<applied-principle>`/`<recommendation>` child elements into the existing `<open-question>` block by whole-block-replacement Edit; sole mutator, commits its annotations once at the end of the run (subject Recommendation-annotation: <milestone_id>, path-scoped, behind the dirty-own-path no-op guard), idempotent skip of blocks already carrying a `<recommendation>` element, no clean-tree precondition
recommend-open-question         ← (agent, in agents/) read-only recommendation subagent: grounds in the live project and the principle store, returns one question's `<open-question>` child sub-elements (bearing-principle `<applied-principle>` elements sibling to the liftable `<recommendation option="...">` element), never edits documents
discuss-open-question           ← structured conversation about one open question; sources its alternatives+recommendation core from shared/recommend-procedure.md and adds its own "what would change your mind" layer; on a decision offers answer-open-question, and if the goal itself must shift also offers modify-milestone-goal — when both apply, modify-milestone-goal runs first so the answer records against the revised goal
answer-open-question            ← records a literal-answer decision in requirements.md AND commits it (subject Manual-answer: <Short Title>, rationale in the body); no longer chains to capture. Literal-only: recording an embedded recommendation moved to answer-open-question-with-recommendation, and the retired sentinel "record the recommendation" (exact whole-string) is now a redirect guard that stops without recording and points there instead
answer-open-question-with-recommendation ← (skill) user-facing entry for one named question: lifts its embedded `<recommendation option="...">` element and records+commits it inline (subject Recommendation-answer: <Short Title>, path-scoped git add), running shared/answer-with-recommendation-procedure.md so the context stays for follow-up; never spawns the agent
answer-open-question-with-recommendation ← (agent, in agents/) file-editing subagent: runs shared/answer-with-recommendation-procedure.md in isolation, records the answer but (like every dispatched agent) never commits — it hands the uncommitted edit back for the orchestrator to commit, returns DONE/FAILED — dispatched per-question by the answer-all-open-questions-with-recommendation orchestrator
answer-all-open-questions-with-recommendation ← orchestrator: sweeps open/deferred questions carrying an embedded recommendation, dispatches the file-editing answer-open-question-with-recommendation agent strictly sequentially (gather once most-significant-first, per-question re-read/skip on already-cascaded blocks); the orchestrator commits each answer itself after the agent returns — one commit per answer (subject Recommendation-answer: <Short Title>), the agent records but never commits
answer-open-question-with-alternative ← (skill only, no agent) user-facing entry for one named question: sibling of answer-open-question-with-recommendation, differing only in which embedded element becomes the answer — arg split on the first `.` (Short Title before, target `<alternative>` id after), it lifts that block's chosen `<alternative id="...">` (id recombined with its what-it-is text as "<id> — <what-it-is>", `<advantage>`/`<drawback>` children excluded as analysis) and records+commits it inline (subject Alternative-answer: <Short Title>, path-scoped git add), composing the lift inline over shared/answer-procedure.md so the context stays for follow-up. Lets a user override the recommended option or break a tie. No batch/agent form (which alternative wins is per-question human judgment, not an orchestrator-sweepable rule); its Alternative-answer: subject, like Recommendation-answer:, is excluded from capture's ^Manual-answer: grep
modify-milestone-goal           ← revises the ## Goal of an already-defined milestone (act-only); edits Goal only, surfaces downstream impact, never cascades; offered by discuss-open-question, invisible to answer-open-question
derive-tasks                    ← decomposes requirements.md into ordered briefs, proves coverage, then writes those briefs directly into TASKS_TODO.md itself as brief-level task sections (shared/task-format.md), delegating nothing
submit-task                     ← (skill only, no agent) user-facing entry for a single ad-hoc issue: triages + positions, then authors and inserts one brief-level task section (shared/task-format.md) inline so the authoring context stays for follow-up
discuss-new-task                ← clarifies a vague/large issue into briefs, then hands each off to the submit-task skill; a brief now maps near-1:1 onto the task section that skill writes
complete-all-tasks              ← orchestrator: spawns complete-task agent per task, commits after each
complete-task                   ← (skill) user-facing entry for one ad-hoc task: runs shared/complete-procedure.md inline so the work context stays for follow-up
complete-task                   ← (agent, in agents/) single-task completion subagent: runs shared/complete-procedure.md in isolation, returns DONE/FAILED
ask-in-milestone-context        ← (on-demand, read-only) answers a free-form informational question grounded in the current milestone — goal, decisions, done/pending tasks, and the live deliverables those tasks produced; never edits, offers a handoff when a concrete next action surfaces
finish-current-milestone        ← writes completion summary to milestones/README.md, clears current-milestone pointer to "none" in milestones/README.md, updates CLAUDE.md only for lasting changes; capture-milestone-principle-updates is the optional finish-time follow-up a user runs afterward (documented handoff, not a runtime recommendation the skill prints)
capture-milestone-principle-updates ← optional finish-time follow-up a user runs after finish-current-milestone: distills answering principles from the just-finished milestone's Manual-answer: commits into the principle store; new sole writer of milestones/answer_decision_principles.md
goto-next-milestone             ← activates an already-defined milestone: scans milestones/ for a defined-but-not-yet-active directory, updates milestones/README.md to point to it
```

## Milestone file structure

Each active milestone lives at `milestones/milestone_<N>_<slug>/` and contains exactly:

- `requirements.md` — Goal, Relevant starting state, decisions, open questions
- `TASKS_TODO.md` — pending tasks ordered by priority (highest first), `##` headings + `---` separators
- `TASKS_DONE.md` — completed tasks appended in the same format

`milestones/README.md` is the source of truth for which milestone is current.

## Invariants to preserve when editing skills

- `init-milestone-base-workflow` is the one-time bootstrap; it is additive and idempotent — it never overwrites an existing `milestones/README.md` or `CLAUDE.md`, only creating missing files and appending missing sections. It must leave `milestones/README.md` with a `Current milestone:` pointer line.
- `answer-open-question` splits its arg on the first `.` — title before, answer after.
- `review-milestone-requirements` (renamed from the old `highlight-milestone-requirements-open-questions`) is the repeatable engine of the requirements-iteration loop and the **sole author** of `<open-question>` blocks: each pass **reconciles** the existing `status="open"`/`status="deferred"` blocks against the recorded `## Decisions`, **surfaces** new gaps (authoring each as a well-formed `<open-question>` XML block appended under the single `## Open questions` section), and **reports convergence** (no `status="open"` blocks remaining is exactly `derive-tasks`'s precondition; `status="deferred"` blocks may carry forward). It reads the whole `requirements.md` and reasons over it (reconcile/author are cross-document work, not the deterministic locate the CLI is for). It is the **only** skill besides the answer path that may remove a question block, and only as *cleanup of already-recorded state*: it may delete a block (in full, from its `<open-question …>` opening boundary line through its `</open-question>` closing boundary line) solely when it can cite a `## Decisions` entry that already covers it, or dedup an exact repeat — when in doubt it flags ("possibly resolved — confirm") rather than deletes, and every removal is reported. It **never records a decision or answers a question**: folding a decision into `## Decisions` and cascading to mooted siblings stays scoped to `shared/answer-procedure.md` (used by `answer-open-question` and `shared/answer-with-recommendation-procedure.md`). This boundary — tidy the questions section vs. record an answer — is the whole reason the two stay separate.
- The answer-recording mechanism (locate the `<open-question>` block by Short Title via the boundary-line CLI → remove the whole `<open-question …>`…`</open-question>` block → fold the decision into `## Decisions` as clean prose → cascade to mooted entries) lives in exactly one place: `shared/answer-procedure.md`. `answer-open-question` and `shared/answer-with-recommendation-procedure.md` both reference it via `${CLAUDE_PLUGIN_ROOT}` and never restate the steps. That shared file is **execution-neutral** — it takes a resolved Short Title + answer and never mentions arg-parsing, committing, or the capture chain.
- `recommend-all-open-questions` is the batch form of `discuss-open-question`. It gathers the Open/Deferred entries **once** and walks straight through, deliberately omitting the machinery a decision-recording sweep would need — no gather-order (cascade-parent-first proxy), no per-question live-re-check/skip against a mutating document, no outer re-gather loop, and **no clean-working-tree precondition** — precisely because it records **no decisions** and triggers **no cascades**, so the question set never shrinks under it. It gathers the questions via the boundary-line CLI (`awk`/`sed`/`grep` on the `<open-question …>`/`</open-question>` boundary lines, never `xmllint`) over the single `## Open questions` section. It is the **sole document mutator**: it embeds each returned set of child sub-elements **inside the existing `<open-question>` block** by **whole-block-replacement** `Edit` (not a CLI splice — constructing correctly-indented nested children is read-whole structural construction, where the CLI is weakest), inserting them between the `<question>` element and the closing `</open-question>` tag at a 2-space-per-level indent and leaving the `<open-question …>`/`</open-question>` boundary tags and the `<question>` element unchanged. It is **idempotent** — it skips any block already containing a `<recommendation>` element and annotates only those lacking one; the escape hatch for a stale recommendation is to delete that block's embedded `<alternative>`/`<applied-principle>`/`<recommendation>` children (the `<open-question>` wrapper and `<question>` element intact) and re-run, and there is deliberately **no** `refresh`/selectable mode (it stays argument-free). Following the skill-layer commit rule it **commits its own annotations once at the end of the run** (never inside the dispatch loop) — path-scoped `git add <MILESTONE_DIR>/requirements.md` (never `git add -A`) then a single commit under subject `Recommendation-annotation: <milestone_id>` via `shared/commit-procedure.md`, behind that procedure's dirty-own-path no-op guard so a sweep that annotated nothing commits nothing.
- The `recommend-all-open-questions` orchestrator owns **all** document mutation and the staging; its `recommend-open-question` subagent (one dispatch per question, the non-interactive twin of `discuss-open-question`) is **read-only** — it reads `requirements.md`, the live project, and the project-wide principle store to ground honest alternatives but returns only the ready-to-embed child sub-elements (the `<alternative>` elements, any `<applied-principle>` elements, then the single `<recommendation>` element — never the `<open-question>` wrapper or `<question>` element) as its final message, and the orchestrator does all embedding and staging. **Recommendation independence:** the per-question dispatches are independent (a recommendation decides nothing, so nothing may build on one) and may be parallelized; "isolation" constrains the **orchestrator** — it never feeds one question's recommendation into another — and does **not** narrow the subagent's read-only grounding (which incidentally sees the sibling `<open-question>` blocks). What the subagent must never do is treat another question's recommendation as an input.
- `shared/answer-with-recommendation-procedure.md` is the single source of truth for the "lift the embedded recommendation, then record it" logic, referenced (never restated) via `${CLAUDE_PLUGIN_ROOT}` by both the `answer-open-question-with-recommendation` skill and its agent. It is **execution-neutral**: given a resolved SHORT TITLE it locates the `<open-question>` block via the boundary-line CLI, lifts its `<recommendation option="...">…</recommendation>` element — recombining the `option` attribute value with the element text as "`<option>` — `<rationale>`" (the old anchor form) under reverse entity-substitution (with a **no-`<recommendation>`-element guard** that stops without changes when the recommend sweep never annotated the block), then delegates to `shared/answer-procedure.md` with the derived ANSWER. It **composes over** the recording core exactly as the `complete-task` skill and agent layer their shared procedure — the lift lives here, not in `answer-procedure.md`, so that core's **ANSWER-as-input contract** (shared with literal `answer-open-question`, which must never inherit lift behavior) stays unchanged.
- The `answer-open-question-with-recommendation` skill + agent follow the established skill+agent pattern (one execution-neutral shared procedure, run **inline** by the skill so context survives, **in isolation** by the agent with the `DONE`/`FAILED` return protocol), but with a deliberate divergence from the read-only-subagent design of the plugin's other per-question subagents (e.g. `recommend-open-question`): here the **mutation** is what's isolated into the agent, not the reasoning. The recommendation is **pre-computed** by the recommend sweep, so there is no candidate elimination worth isolating; what dispatching a per-question **file-editing** agent buys the sweep orchestrator is keeping the expensive per-question edit out of its own context. It is the **recording** that is isolated into the agent, **not the committing** — under the layer rule the agent records the answer and hands the uncommitted edit back, and the orchestrator commits it (see the next invariant). This inversion (mutation-in-agent, not read-only-subagent) is documented so a later editor does not "fix" the agent back toward the read-only-subagent norm.
- In `answer-all-open-questions-with-recommendation`, the file-editing **agent records but never commits** — it folds the answer into `## Decisions`, hands the recorded-but-uncommitted `requirements.md` edit (and, for the commit body, the lifted recommendation text) back, and returns only `DONE`/`FAILED` — and the **orchestrator commits each answer itself** after the agent returns: path-scoped `git add <MILESTONE_DIR>/requirements.md` (never `git add -A`), subject `Recommendation-answer: <Short Title>`, **one commit per answer** (preserving one-commit-=-one-answer), via `shared/commit-procedure.md`. This is the **ordinary** skill-layer arrangement (dispatched agents never commit; an orchestrator commits its agents' work, exactly as in `complete-all-tasks`) — milestone 10 reversed the earlier milestone-7 inversion in which the agent committed and the orchestrator did not. The orchestrator sequences its own dispatches — gather once most-significant-first (a cascade-parent-first proxy), and before each dispatch re-read `requirements.md` and skip the question when a prior answer's cascade already removed its block, with `shared/answer-procedure.md`'s step-2 stop-on-missing-block as the backstop — running **strictly sequentially** because cascades mutate the shared document. It needs no clean-working-tree precondition — the per-answer commit stages path-scoped, so a dirty tree cannot contaminate it. Documented as its own invariant so it is not reverted toward agent-commits.
- Recommendation-derived answers — from **both** the single-question `answer-open-question-with-recommendation` skill and the sweep (whose orchestrator commits each answer) — commit under the distinct subject `Recommendation-answer: <Short Title>`, which does **not** match the `^Manual-answer:` grep that finish-time `capture-milestone-principle-updates` walks, so capture **never harvests** them. The rationale: a recommendation-answer's commit body is the `recommend-open-question` agent's rationale (batch-accepted on the sweep path), not user-deliberated reasoning, so it must stay outside the capture grep — with **no** change to capture's grep logic. The distinct subject is the honest git-log provenance discriminator, matching the house style where the subject *is* the provenance marker. **Alternative-derived answers** — from `answer-open-question-with-alternative` — commit under `Alternative-answer: <Short Title>` for the **same** reason and with the **same** `^Manual-answer:`-non-match: the recorded body is the chosen `<alternative>`'s what-it-is text (the recommend agent's rendering, not user-deliberated prose), so it too stays outside capture by construction. Both non-manual answer subjects are provenance discriminators that keep capture harvesting **only** user-deliberated `Manual-answer:` bodies, with no change to capture's grep.
- `answer-open-question-with-alternative` is the **sibling** of `answer-open-question-with-recommendation`: same recommend-sweep annotations, same recording core, differing **only** in which embedded element becomes the answer — the recommendation skill lifts the one `<recommendation>` the sweep picked, this skill lifts the `<alternative id="...">` the **user names** (arg split on the first `.`, Short Title before / target alternative id after, both case-insensitive against the respective `id` attributes — mirroring `answer-open-question`'s first-`.` split). Its purpose is to let a user **override the recommended option** or break a genuine tie. It derives ANSWER by recombining the chosen alternative's `id` with its **what-it-is text** as "`<id>` — `<what-it-is>`" (the recommendation form's exact analog), pointedly **excluding** the `<advantage>`/`<drawback>` children (trade-off analysis, not the decision), then delegates to `shared/answer-procedure.md` unchanged. Three deliberate divergences from the recommendation path, documented so they are not "fixed" back toward it: (1) it is **skill-only** — there is **no** agent and **no** `answer-all-open-questions-with-alternative` batch form, because choosing *which* alternative wins is per-question human judgment, not a rule an orchestrator could sweep (a sweep that always picks the recommended option is just the recommendation sweep); (2) with only one runner, the lift-then-delegate logic is **inlined in the skill** (composing over the multi-consumer `shared/answer-procedure.md`) rather than extracted into a single-consumer `shared/answer-with-alternative-procedure.md` — a shared file here would contradict the plugin's "shared = source of truth across ≥2 runners" convention; (3) it carries **two** clean-stop guards (no matching question id, or a block with no `<alternative>` elements / no alternative matching the named id), each listing the available ids and committing nothing. It commits its own path-scoped answer under `Alternative-answer: <Short Title>` exactly as the recommendation skill commits under `Recommendation-answer:`.
- `shared/recommend-procedure.md` is the single source of truth for the "alternatives + single recommendation for one question" analytical core, referenced (never restated) by both the `discuss-open-question` skill and the `recommend-open-question` agent via `${CLAUDE_PLUGIN_ROOT}`. It is **execution-neutral** and holds only logical content: the grounding discipline (the live project over memory), the **Alternatives** requirement (2–4 genuinely realistic options, no strawmen/padding, each carrying what-it-is / key advantage / key drawback), and the single **Recommendation** (one option, direct hedge-free rationale, plus the name-what-breaks-the-tie rule). It is **principle-aware**: its grounding step reads the project-wide principle store `milestones/answer_decision_principles.md` **in place** (naming that fixed `milestones/`-root path directly — the confirmed principles are not a caller-supplied input alongside QUESTION), and a confirmed principle that bears on the question is a **weighted advisory factor** — a strong default in favor of the option it supports, which **merit may override only for a specifically stated reason**, and which is **cited** in the recommendation whenever it influenced the pick (never a binding filter or veto, never a candidate drop, never silently applied). When no principle bears, the alternatives+recommendation contract is exactly as in a project with no principles. It carries **no** XML rendering markup and **no** "what would change your mind" section — the boundary is deliberate: `discuss-open-question` owns the WWCYM layer, the conversational framing, and the on-decision follow-up offers; the `recommend-open-question` agent owns the literal XML sub-element rendering (the 2-space-per-level child indentation, the sibling `<applied-principle>` elements, and the `<recommendation option="...">` element). This mirrors how `shared/answer-procedure.md` is execution-neutral while its wrappers own arg-parsing and committing.
- The `recommend-open-question` agent renders each confirmed principle that bore on the recommended pick as its own `<applied-principle>Short Title</applied-principle>` element — a **direct child of `<open-question>` and a sibling of `<recommendation>`, never a child of `<recommendation>`** — **one element per bearing principle** (the multi-principle case is pure repetition of the single-element form, with no multi-id element and no in-line list syntax, so each citation stays atomic and independently greppable), and **none at all** when no principle bears (the sub-elements then render exactly as they did before principle-awareness). The citation is **never** baked into the `<recommendation>` element text: because `/answer-open-question-with-recommendation` (and the `/answer-all-open-questions-with-recommendation` agent) lift only the `<recommendation>` element, keeping the citations structurally disjoint siblings holds the recorded `## Decisions` prose **provenance-free by construction**, and `shared/answer-procedure.md`'s whole-block removal clears the sibling `<applied-principle>` elements on answer.
- The principle store `milestones/answer_decision_principles.md` is now consumed by the **recommendation core** — read in place by the principle-aware `shared/recommend-procedure.md` that both `/discuss-open-question` and the recommend sweep's `recommend-open-question` agent run — rather than by an auto-answer engine. Its data and per-entry format are unchanged, and `capture-milestone-principle-updates` remains its **sole writer**; only the consumer pointer moved, from a binding auto-answer sweep to the recommendation advisor that cites it.
- `answer-open-question` is **literal-only plus a redirect guard**. The old **record-recommendation mode** — the whole-string `record the recommendation` sentinel that located a block and lifted its `<recommendation>` element as the `ANSWER` — is **removed** from this skill; lifting an embedded recommendation now lives in `answer-open-question-with-recommendation` (skill + agent, over `shared/answer-with-recommendation-procedure.md`). What survives here is a **targeted redirect guard**, not a live feature: after the first-`.` split, the parsed answer text is compared — trimmed and lowercased — against the retired sentinel `record the recommendation` as an **exact whole-string** match (**never a substring**, so a literal answer merely containing those words takes the literal path). On an exact match the skill **stops without recording or committing anything** and prints a redirect pointing at `/answer-open-question-with-recommendation`; this intercepts a migrating user's old command at the moment it would otherwise silently record the sentinel phrase as a decision, and its message doubles as discovery. It is targeted migration scaffolding that fits the skill's clean-stop-and-point pattern (like a Short-Title mismatch), not a revived mode. Any other (non-sentinel) answer text is a literal answer; the existing first-`.` split, the literal-answer path, and the `Manual-answer:` commit rules are unchanged.
- `shared/answer-procedure.md` step 4 removes the **entire `<open-question …>`…`</open-question>` block** located in step 2 — from its opening boundary line through and including its closing boundary line, whether or not it carries embedded `<alternative>`/`<applied-principle>`/`<recommendation>` children — as a deterministic line-range deletion driven by the boundary-line CLI. This covers both cases uniformly: a bare block with no embedded children shares the one `<open-question …>`/`</open-question>` boundary-token pair and is removed exactly the same way. Step 2's locating keys off the block's `id` attribute (case-folded, entity-unescaped, matched by attribute-name-anchored regex so attribute order is immaterial), steps 3/5/6 (analyse / fold / cascade) are unchanged, and the file stays execution-neutral.
- `answer-open-question` records a decision and then **commits** it — it no longer chains to any capture skill. Principle capture has moved off the per-answer path to milestone finish (`capture-milestone-principle-updates`); the rationale behind each decision is preserved in the commit body so finish-time capture can distill it later.
- `modify-milestone-goal` is the **only** skill that mutates the `## Goal` of an already-defined milestone (`define-milestone-goal` writes it once at creation; `discuss-milestone-goal` is conversational and pre-creation). It is **act-only**: it edits the `## Goal` section and nothing else — never `## Decisions`, the question blocks, `## Out of Scope`, or the task lists. Because the Goal is the root of the requirements tree, the skill **surfaces but never cascades** the downstream impact (which Decisions/questions/Out-of-Scope/derived tasks the new goal may invalidate) and points the user at `/review-milestone-requirements` to reconcile — folding those consequences in silently would have too large a blast radius. It is offered by `discuss-open-question` (which still edits nothing itself — it proposes the revised goal and the user confirms) and is **deliberately invisible to `answer-open-question`**: recording an answer and reshaping the objective are different acts, and the answer path must never reach goal mutation. It records no answering principle (a goal change yields none), but under the skill-layer commit rule it **commits** its own `## Goal` edit — path-scoped to `<MILESTONE_DIR>/requirements.md` (never `git add -A`) under subject `Goal-revision: <milestone_id>` via `shared/commit-procedure.md`, behind that procedure's dirty-own-path no-op guard.
- Correcting a bad recorded answer has no dedicated skill: it is the uniform **revert-then-re-answer** flow. Revert the answer's commit (by the one-commit-=-one-answer invariant the revert restores the reopened question block and removes the folded decision in one shot — the `Manual-answer:` commit for a manual answer, the `Recommendation-answer:` commit for a recommendation-derived one, the `Alternative-answer:` commit for an alternative-derived one), then re-record via `/answer-open-question` (or `/answer-open-question-with-recommendation` to re-lift a re-embedded recommendation, or `/answer-open-question-with-alternative` to record a different embedded alternative). Because a confirmed principle is now only a **weighted advisory factor** cited in recommendations — never a binding auto-answer — a principle that steered a recommendation wrong is reconciled at milestone finish: the corrective re-answer's `Manual-answer:` commit is picked up by `capture-milestone-principle-updates`, whose revise-vs-add-by-overlap discipline offers the corrected directive as a revision of the bad principle. For an urgent "this principle is actively wrong, remove it now" case the user hand-edits the plain-Markdown store `milestones/answer_decision_principles.md` directly.
- The `complete-task` agent expects tasks as `##` sections in `TASKS_TODO.md`, each terminated by a `---` separator.
- **Committing is a property of the skill layer.** The mechanics live in exactly one place — `shared/commit-procedure.md` (dirty-own-path no-op guard → path-scoped `git add` of the pass's own paths → `git commit` under its subject), referenced via `${CLAUDE_PLUGIN_ROOT}` by every committer and never restated (the execution-neutral shared procedures `answer-procedure.md`, `answer-with-recommendation-procedure.md`, `complete-procedure.md`, `recommend-procedure.md` stay **commit-free**, as does the format-only `task-format.md`; commit logic lives in the wrappers). The rule: **every user-invoked skill that changes files commits exactly those changes**, staged path-scoped by explicitly named paths (**never `git add -A`**, no content inspection to choose the set), under its own distinct **function-derived `<Marker>: <descriptor>` subject** — a distinctive marker prefix, a colon and space, then a short descriptor, the marker derived systematically from that skill's distinctive function rather than drawn from an ad-hoc per-skill list and with no grandfathered exceptions, so the git log reads as self-describing provenance and every prefix is greppable — that stays clear of capture's `^Manual-answer:` grep by construction (only genuinely user-deliberated manual answers carry a marker beginning `Manual-answer:`, and a skill deriving a new marker picks one that names its function and does not collide with that anchor); **dispatched agents never commit** (they hand their result — and, where relevant, the paths they touched — back); **an orchestrator commits its agents' work after they return.** The old role-based split ("a decision-recorder commits, a work-producer leaves changes staged," with its one-orchestrator/three-skills/one-agent counts) is **retired** — `complete-task`, `submit-task`, `derive-tasks`, `recommend-all-open-questions`, `modify-milestone-goal`, `define-`/`specify-`/`review-`/`goto-`/`finish-current-milestone`, and `capture-milestone-principle-updates` are all committers now. Per-skill subjects: `Manual-answer:` / `Recommendation-answer:` / `Alternative-answer: <Short Title>` (the three answer skills), `Task-completion: <task heading>` (`complete-task`), `Task-submission: <task title>` (`submit-task`), `Task-derivation:` / `Requirements-review:` / `Starting-state:` / `Recommendation-annotation:` / `Principle-capture: <milestone_id>`, `Milestone-definition:` / `Milestone-finish: milestone_<NN>_<slug>`, `Milestone-activation: milestone_<number>_<slug>`, `Goal-revision: <milestone_id>`. **Orchestrator commit granularity:** `complete-all-tasks` commits **per task** (subject `Tasklist-completion: <descriptor>`, the task `##` heading now in the commit **body**, not the subject, and path-scoped to the agent's handed-back change set plus the two task-list files — never `git add -A`), `answer-all-open-questions-with-recommendation` commits **per answer** (subject `Recommendation-answer: <Short Title>`, committed by the orchestrator), and `recommend-all-open-questions` and `derive-tasks` commit **once at the end of the run**. **No-op guard:** a committer whose pass changed none of its own paths (e.g. a `review-milestone-requirements` or `capture-milestone-principle-updates` pass that distilled nothing) stages nothing and commits nothing — no `--allow-empty` (the `shared/commit-procedure.md` dirty-own-path guard enforces this uniformly). **Two exemptions:** `init-milestone-base-workflow` and `migrate-workspace` stay **non-committing** (they leave changes staged for the user) because a consuming project may not be a git repo or wants its own commit boundaries. Skills that change no files (`discuss-milestone-goal`, `discuss-open-question`, `discuss-new-task`, `ask-in-milestone-context`) are unaffected. **Still true:** `capture-milestone-principle-updates` harvests **only** user-deliberated `Manual-answer:` bodies via `git log --grep='^Manual-answer: '`, and every other function-derived subject (`Recommendation-answer:`, `Alternative-answer:`, and all the rest) stays clear of that anchor by construction, so capture never harvests them.
- **Success-path console reporting is terse.** Every file-mutating, committing skill's success path prints **exactly one fixed terse status line** (e.g. "Milestone defined.", "All tasks completed.", "Recommendations embedded.") — carrying **no identifier** (no milestone id, task heading, Short Title, or commit subject) and **no next-step/handoff pointer** — instead of a prose re-narration of what it did, because the committed diff and `git log` are the durable record (re-narrating them to the console is redundant). An **orchestrator** prints **one such line for the whole run**, with **no per-item output** during its dispatch loop. Three classes of output deliberately **survive alongside** the terse line: (1) genuinely **git-absent decision-critical advisories** the commit never captured — `review-milestone-requirements`' convergence verdict and still-open list, `derive-tasks`' flag for any requirement it could not trace to a task, and the answer skills' newly-exposed-open-questions note — are still printed (only diff re-narration collapses); (2) a **no-op pass** whose `shared/commit-procedure.md` dirty-own-path guard fired prints a **distinct one-line** message stating nothing changed and briefly why (git holds no durable record of a no-op, so the console must carry it), never collapsing to the terse success line; (3) **failure and clean-stop paths** (parse errors, Short-Title/id mismatches, the `answer-open-question` redirect guard, no-matching-id stops) keep their **full explanatory messages**. Untouched entirely: the conversational skills (`discuss-milestone-goal`, `discuss-open-question`, `discuss-new-task`, `ask-in-milestone-context`) and the two non-committing exempt skills (`init-milestone-base-workflow`, `migrate-workspace`). Like the commit convention, this cross-cutting rule earns its **own standalone invariant** rather than a shared procedure file — there is **no** `shared/report-procedure.md`; the convention is authored **inline in each `SKILL.md`'s final reporting step**.
- `finish-current-milestone` must always run before `goto-next-milestone` — it records the completion and clears the current-milestone pointer to "none". `goto-next-milestone` checks for this "none" state and refuses to run without it. `capture-milestone-principle-updates` is the optional post-finish follow-up a user runs after finishing — a documented handoff, **not** a runtime recommendation `finish-current-milestone` prints (that runtime "recommends (never auto-runs)" print was retired under terse reporting).
- `capture-milestone-principle-updates` is the **new sole writer** of the principle store `milestones/answer_decision_principles.md` and runs *after* `finish-current-milestone` has already cleared the pointer to "none". Because the pointer is "none" by then, it resolves `<MILESTONE_DIR>` from the **last row of the `## Completed Milestones` table** in `milestones/README.md` — explicitly **not** via `shared/get-current-milestone.md`. It walks that milestone's manual answers with a path-scoped `git log --grep='^Manual-answer: ' -- <MILESTONE_DIR>/requirements.md` (the path is itself the lower boundary — it does not exist before `define-milestone-goal`). It distills the rationale in those commit bodies into generalizable keep/eliminate directives, deduping candidates against each other, then confirms each per-candidate revise-vs-add against the live store; under the skill-layer commit rule it **commits** its principle-store edit — path-scoped to `milestones/answer_decision_principles.md` (never `git add -A`) under subject `Principle-capture: <milestone_id>` via `shared/commit-procedure.md` — behind that procedure's dirty-own-path no-op guard, so a pass that distilled no new principle changes no file and commits nothing.
- Open questions in `requirements.md` must be fully resolved before `derive-tasks` can run.
- `ask-in-milestone-context` is the on-demand, **read-only** Q&A skill: it answers an informational question about the current milestone and never mutates any file. It is not a pipeline step — it is usable any time across requirements/automation/follow-up. It grounds answers about finished work in the **live deliverables** (with the `TASKS_DONE.md` entry as intent and `git log`/`git show` as a supporting lens — the task→commit mapping is best-effort, since completions now land under a `Task-completion:` subject from the `complete-task` skill or a `Tasklist-completion:` subject with the heading in the body from `complete-all-tasks`, not keyed on the heading in the subject line). When a concrete next action surfaces it **offers** the owning skill (`discuss-open-question` to decide a question, `submit-task`/`discuss-new-task` to file an issue, `discuss-milestone-goal` to reshape the goal, `complete-task` to do a pending task) but performs none of their work itself — the asking/acting split is the whole point.
- `specify-milestone-starting-state`, `derive-tasks`, and the shared completion procedure (run by both the `complete-task` skill and agent) read the project's environment context (the project's domain context, working conventions, available tools, and how work is verified as done) from `CLAUDE.md`. Run `/init` once at project setup so `CLAUDE.md` documents it.
- `derive-tasks` owns decomposition, coverage, **and** the writing of the task list — it is the single writer on the derivation path. It proves every requirement maps to a brief (traceability matrix), orders the briefs by dependency, then writes them **itself**, in that order, into `TASKS_TODO.md` using the template and authoring guidelines from `shared/task-format.md`. Nothing on this path is delegated to a subagent, and there is no second authoring pass: a brief and a finished task section are the same altitude, so writing the brief down *is* the authoring step. What it must not do is push a section past brief altitude — never a flow, a low-level design, a contract surface, or a structured done-ness section; the completer derives all of that against the live project.
- The **brief-level** task-section template lives in exactly one place: `shared/task-format.md`. That template is the `##` title heading, a 1–3 sentence description of what is to be achieved, why the milestone needs it, and how it would be verified (that last clause folded into the prose, never a labeled section), and the mandatory trailing `---` separator — and nothing else. There is deliberately **no** `Steps`, **no** `Provides`, **no** `Notes`, **no** `Success`, and no other structured done-ness heading under any name — see the altitude invariant below. The same file carries the four authoring guidelines, all format-independent and all carried over unchanged: unique 4–8 word title-cased **Title** (uniqueness is load-bearing — the completion procedure locates a task by case-insensitive partial heading match), **atomic scope**, **no open decisions**, and **quote numeric values, durations, thresholds, and configuration values** directly from `requirements.md`. Both authoring runners — `derive-tasks` and the `submit-task` skill — reference it via `${CLAUDE_PLUGIN_ROOT}` and must never duplicate, restate, or vary it, and `shared/complete-procedure.md` parses exactly what it defines; two authors plus one parser is what keeps it shared and rules out drift between the batch and ad-hoc paths by construction. It holds the **format only**: where the task list lives, what context an author loads before writing, and where in the file a section is placed all belong to the runners.
- `submit-task` is a **skill only** — it has no agent counterpart, and `complete-task` is the plugin's only remaining skill+agent pair. The skill authors the task section **inline** in the user's conversation (so the authoring context survives for follow-up), and it additionally owns the triage (dedup + scope) and the position decision (`before:`/`after:`/`append`), because those need the whole-task-list view. `derive-tasks` never calls it: the batch path writes its own briefs, so the two authoring runners share the format file and nothing else.
- The completion procedure — find task, load environment and derive the acceptance bar, carry out, verify against that derived bar, move TODO→DONE augmented with it — lives in exactly one place: `shared/complete-procedure.md`. Neither the `complete-task` skill nor the agent may duplicate or restate those steps; both reference the shared file via `${CLAUDE_PLUGIN_ROOT}`. The shared file is execution-neutral — it must not mention the `DONE`/`FAILED` return protocol, committing, or follow-up; those belong to the wrappers.
- `complete-task` exists as both a user-facing skill and an agent, differing only in *where* the shared procedure runs. The **skill runs it inline** in the user's conversation (so the work context survives for follow-up) and must never spawn the agent. The **agent runs it in an isolated subagent context** and adds the `DONE`/`FAILED` return protocol; it is what the `complete-all-tasks` orchestrator spawns per task. Choosing inline vs. isolated is the entire reason both exist — keep that the only difference.
- Every runner that reads or writes a milestone's task list resolves `<MILESTONE_DIR>` by following `shared/get-current-milestone.md` (which reads `milestones/README.md`) — `shared/complete-procedure.md`, `derive-tasks`, and the `submit-task` skill alike; none may use a hardcoded task-list path. `shared/task-format.md` resolves nothing: it defines the section format only, and milestone resolution now lives in its two authoring runners.
- Task altitude is split, and the dividing line is **what can be re-derived at completion time**. An authoring runner writes only what *cannot* be reconstructed from the milestone's goal + the live project: the title and the 1–3 sentence description (intent — what, why, and how it would be verified). Everything else belongs to `shared/complete-procedure.md`, which owns the flow and the **detailed design** (decided fresh against the live project and its deliverables) and, on top of that: it **derives the formal acceptance bar itself** from the task description plus the milestone's `requirements.md` — the task carries no authored acceptance criteria, so the derived bar, not anything in the task body, is what the work is verified against; it **resolves every cross-task reference by reading the prior task's live deliverable** in the project rather than a forward contract the task list promised (tasks run in dependency order, so that deliverable already exists by the time it is needed); and it **records the derived bar** in the `TASKS_DONE.md` entry, as a `**Verified:**`-labeled bullet list — one bullet per criterion, in the order verified, inside the same `##`/`---` section the TODO→DONE move writes — so every finished entry carries the brief plus the bar the work actually passed. The `**Verified:**` label is deliberately distinct from any authoring label, keeping the completion record from being read as an authoring contract and regrowing a done-ness section in `TASKS_TODO.md`. Keep task bodies minimal to save tokens; never push design detail — or a re-narration of the flow — back into authored tasks.
- **Skill Frontmatter**: Every user-facing skill (`SKILL.md`) must carry YAML frontmatter containing `name` and `description` keys. The transpilation script strictly requires this for Google Antigravity compatibility and will abort with a hard error if either is missing.

## Development

This project supports both Claude Code and Google Antigravity. The canonical source files (e.g. `skills/`, `agents/`) are authored at the repository root and are written for Claude Code.

To build the plugin for Google Antigravity, run the local transpilation step from the repository root:
`uv run scripts/migrate_skills_to_agy.py`

This will parse the Claude Code plugin source and generate the Antigravity-compatible version under `.agents/plugins/cairn/`.

## Milestone Workflow

This project uses the milestone-driven workflow. Each milestone lives at
`milestones/milestone_<N>_<slug>/` with `requirements.md`, `TASKS_TODO.md`, and
`TASKS_DONE.md`. `milestones/README.md` is the source of truth for which milestone
is current. Never advance the pointer without first running
`/finish-current-milestone`.
