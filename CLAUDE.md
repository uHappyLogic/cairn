# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A plugin (`cairn`) for Claude Code, Antigravity, and Codex that brings a milestone's important questions up to be decided before work starts, so execution can then be handed to agents. It ships as a set of skills, a few agents, shared procedures, and the stdlib-only Python tools under `tools/` (among them the open-question tool and the task-list tool, the only writers of each milestone's open-question document and of its two task files once they are created, and the fold tool through which the answer sweep records its decisions in `requirements.md`) that move a project from a vague idea through discussion, planning, completion, and archival — one milestone at a time.

## Commands

```bash
uv run scripts/build_hosts.py                           # rebuild hosts/ from core/ after any change under core/ or scripts/hosts/
uv run scripts/build_hosts.py --check                   # drift gate: fails if the committed hosts/ trees differ from a fresh build
uv run pytest                                           # Python tool suite under the pinned interpreter (.python-version)
uv run --no-project --python 3.9 --with pytest pytest   # the same suite at the 3.9 floor; run both before committing a tool change
uv run pytest agy_tests                                 # on-demand suite driving the installed agy against ~/.gemini/config/plugins/cairn; run before committing an Antigravity integration change
uv run scripts/set_version.py X.Y.Z                     # bump VERSION and its three mirrors; releases go through /release-plugin instead
```

## Skills and the workflow they encode

The skills form a linear pipeline; `docs/skill-reference.md` describes each one and `docs/workflow.md` the phases. Each skill's SKILL.md is its exact behaviour.

```
init-milestone-base-workflow        ← one-time bootstrap: git work-tree check first, then python3 ≥ 3.9, then milestones/ + milestones/README.md; commits under Workflow-bootstrap: milestones
discuss-milestone-goal              ← conversational, creates nothing
define-milestone-goal               ← creates the milestone directory with its four files
specify-milestone-starting-state    ← fills "Relevant starting state"
review-milestone-requirements       ← repeatable loop engine and sole author of <open-question> blocks; reports convergence
provide-alternatives-to-all-open-questions ← annotating pass 1: one read-only subagent per block lacking alternatives, embedded through the tool
recommend-all-open-questions        ← annotating pass 2: picks inline over the whole set, then sorts the document
discuss-open-question               ← conversation about one question; offers answer-open-question and modify-milestone-goal
answer-open-question                ← records a literal answer (Manual-answer:)
answer-open-question-with-recommendation ← records one question's embedded recommendation (Recommendation-answer:), inline
answer-all-open-questions-with-recommendation ← inline sweep in the tool's walk order, dispatching no agent, one commit per answer
answer-open-question-with-alternative ← records a named embedded alternative (Alternative-answer:); skill only
modify-milestone-goal               ← edits ## Goal and clears the picks it undermines with one non-transitive strip, committed together; surfaces the rest, never cascades
derive-tasks                        ← decomposes requirements.md into brief-level tasks; precondition: no open question
submit-task / discuss-new-task      ← ad-hoc task entry (author one brief / clarify into briefs)
complete-all-tasks / complete-task  ← orchestrator over the complete-task agent / inline single task
ask-in-milestone-context            ← read-only Q&A
finish-current-milestone            ← records completion, clears the pointer to none; capture is a conventional follow-up, never a precondition
capture-milestone-principle-updates ← on-demand harvester of one milestone's answer commits into the principle store
goto-next-milestone                 ← activates the lowest-numbered undone milestone without asking; requires the pointer to read none
```

## Milestone file structure

Each active milestone lives at `milestones/milestone_<N>_<slug>/` and contains exactly `requirements.md` (Goal, Relevant starting state, Decisions, Out of Scope — prose only), `open_questions.xml` (created empty with the milestone, then written only by the open-question tool, in its canonical form; empty means converged), `TASKS_TODO.md`, and `TASKS_DONE.md` (`##` headings + `---` separators; both created with the milestone, then written only by the task-list tool, in its canonical layout). `milestones/README.md` is the source of truth for which milestone is current. Milestones defined before the XML split (this repository's `milestone_01`–`milestone_27`) hold the three Markdown files only; there is deliberately no migration of and no compatibility with them.

## Invariants to preserve when editing skills

These are the design decisions a later editor must not "fix" back. The mechanics they name live in the runtime files, the tools and their tests, and `docs/`; only the rationale lives here.

- **The open-question tool is the only writer of `open_questions.xml` once it exists, not its sole reader.** The milestone-definition tool creates the empty document with its milestone directory; after that, every listing of or change to the question document is a tool call, invoked at every site as the one fixed command `python3 {{PLUGIN_ROOT}}/tools/open_questions.py <subcommand> <MILESTONE_DIR> …` (the resolved directory, never the file path or the pointer; free text on stdin as a quoted heredoc; never `python`). A user-invoked skill running inline in the conversation, or a shared procedure followed by one, that needs the whole set to reason over reads the file directly, for reasoning only; a dispatched agent never does — dispatched agents reach the question document only through the tool. That ban's placement scopes it to this one document, so it needs no carve-out for the other files an agent reads whole (the `complete-task` agent reads `TASKS_TODO.md` whole, both agents read `requirements.md` whole as prose). Runtime prose states the tool's contract in at most one sentence per site and never restates escaping, indentation, boundary tokens, or reconciliation mechanics. The pre-milestone-27 `awk`/`sed`/`grep` boundary-line idiom stays retired. There is no hand-edit exception anywhere: a stale alternative set or pick is cleared with the tool's `strip` / `strip --recommendation` and a re-run.
- **The task-list tool is the only writer of `TASKS_TODO.md` and `TASKS_DONE.md` once they exist, and changes no read.** The milestone-definition tool creates both files with the milestone directory; after that every write is one fixed command `python3 {{PLUGIN_ROOT}}/tools/task_list.py <subcommand> <MILESTONE_DIR> …` (`initialize` for `derive-tasks`, `insert` for `submit-task`, `move` for the completion procedure; free text on stdin as a quoted heredoc; never `python`), while every read stays as it was — whole-file prose reads by the completion procedure, `complete-all-tasks`, `finish-current-milestone`, `derive-tasks`, the triage skills, and `ask-in-milestone-context` — because the reads never failed: the move was the one step runners rewrote as code each time (about three in four of 202 measured completion agents wrote an ad-hoc slicing script, one needing a second script to repair a blank line), so the `##`/`---` parsing and the `**Verified:**` rendering moved into a tested tool and the chained call made the completion tail one turn. Runtime prose states the tool's output contract in at most one sentence per site and never restates its parsing or layout rules. Every write parses the whole file and renders it in one canonical layout, untouched sections included, because nothing ever checked the shared blank-line convention and drift is normalized silently on the first write rather than refused; the same render discards whatever stands above the first section and writes the file's fixed heading, never checking or refusing the preamble, since every writer commits its own write and a dropped line is in that commit's diff and recoverable by revert. A section ends at its `---` when one comes first and otherwise at the next heading or the end of the file, a section without one is accepted silently, and every section the tool writes carries its `---` (an insertion behind an unterminated section gets the separator that boundary needs). On re-parse a section's `---` is the one standing directly before the next heading or the end of the file — a `---` line is a separator only when the next non-blank line is a column-0 `## ` heading or the end of the file, every other `---` line is body text — and every column-0 `## ` line is a heading with no code-fence exemption: one bounded lookahead and no parser state, so a body `---` written verbatim never strands text between sections and no write refuses for it, while `insert`'s guarantee that piped body lines are never structure holds for its own call only. The tool matches every title (the section to move, a `--before`/`--after` anchor) by exact equality after whitespace- and case-folding, refusing a partial or shared title, because a tool that guessed could move the wrong section; the case-insensitive partial match stays in procedure prose, where step 1 resolves the user's name against its own whole read, lists the headings on no match, and passes the full heading on. Title uniqueness is checked in `TASKS_TODO.md` only, where the move locates sections, never against `TASKS_DONE.md` or across files, so a finished task is never refused at the move and follow-up work may reuse a done title. `insert` takes the title as an argument and only the body on stdin, composing the heading and the `---` itself, and every call states exactly one of `--end`, `--before`, `--after` in a required group with no default and no append subcommand, because position encodes dependency order and a call that forgot its position must fail (argparse's exit 2) rather than land silently at the end; an anchor naming no section is refused, and `submit-task` then stops quoting the `Error:` line. `initialize` reads the whole ordered list in the file's own section form in one process and replaces `TASKS_TODO.md` with no flag and no refusal for what it held, so the `Task-derivation:` commit records the list whole and in order or nothing, and what was replaced is already in the previous commit, its drop visible in that diff and recoverable by revert; the guard stays the skill's Preconditions line. `move` treats the bar as opaque Markdown — it writes the `**Verified:**` label, the bar trimmed of its outer blank lines, and the `---`, refusing only an empty bar — so the bar's bullet form stays the completion procedure's to write. `move` renders both contents in memory, replaces `TASKS_DONE.md` first and `TASKS_TODO.md` second, and writes `TASKS_DONE.md`'s original bytes back when the second replace fails, keeping the shared contract that a failure leaves both files unchanged; only a failed restore leaves the harmless superset (the entry in `TASKS_DONE.md` with the section still in `TASKS_TODO.md`, as fold-before-remove prefers a duplicate to a lost task), and its `Error:` line says so. The tool is one self-contained file with its own copies of the stdin reader, error type, main, and atomic writer, importing neither sibling (a parity test asserts it, and conformance to the shared output contract is pinned behaviourally only), so every rendered tool stays one runnable file copied byte-identical into each host; a later milestone may still extract a module. The tool touches no git, because the git step differs per runner and rides beside the call (see the committing invariant). Beyond an empty title, body, or bar it validates nothing of `core/shared/task-format.md` and writes what it is given verbatim, so that file stays the format's only home and no authored brief is refused for its wording. The retired four-call `Read`/`Edit` move, the ad-hoc move scripts (a Python slicing heredoc, `cat >>` plus a removal), `derive-tasks`' per-brief append, and `submit-task`'s append fallback on an unknown anchor must not be restored.
- **The fold tool is the answer sweep's writer of `## Decisions`, not that section's sole writer.** `core/tools/requirements.py` exists because a file edit cannot be chained with `remove` in one shell call (345 of 814 measured sweep folds, 42%, were ad-hoc `str.replace` scripts), so the sweep's batched call runs the one fixed command `python3 {{PLUGIN_ROOT}}/tools/requirements.py fold <MILESTONE_DIR> --section "<Heading>"`, the decision on stdin as a quoted heredoc, chained before the unchanged `remove`. Only the sweep calls it: the three single-question answer skills keep the answer core's Edit-based fold, and every other writer of `requirements.md` after the milestone-definition tool creates it still edits it by hand. Because the file keeps being written by hand, the fold is a byte-preserving splice, not the task-list tool's whole-file render: it reads the file only to find the landing point and writes back every byte it did not insert, normalizing nothing, so each `Recommendation-answer:` commit's `requirements.md` diff is exactly the folded decision. The body is opaque Markdown written verbatim with its outer blank lines trimmed, as `move` writes its bar, so every format rule (clean prose, no citation marker, the entry's shape matched to its subsection) stays in the answer core's fold step, its one home, and the tool has no rendering path. `--section` is required (argparse's exit 2), mirroring the task-list tool's required position group, because both recorded shapes of the section hold decisions only under a `###` heading and an optional one would add a placement branch that mis-files a decision or invents a third shape; a heading matching no subsection after whitespace and case folding is created at the end of `## Decisions`, never refused, so one call shape serves a fresh milestone's first decision and every later one, and a near-duplicate subsection stays visible in the commit diff. Beyond an empty heading or body and the baseline input failures it refuses only a file holding no column-0 `## Decisions` heading or more than one, with no duplicate no-op (a checkout of an uncommitted fold already gives a resume), because every refusal is a stop for the batched call. Like its siblings it is one self-contained file importing no sibling (a parity test asserts it) and touches no git; it lives in its own file named for its document rather than as a `remove --decision` inside the open-question tool, which stayed unchanged.
- **Tidy vs. record.** `review-milestone-requirements` is the sole author of question blocks and may remove one only as cleanup of already-recorded state (a decision that covers it, or an exact duplicate); when in doubt it flags rather than deletes. Its `## Decisions` consistency step stays on the tidy side: it reads the recorded decisions against each other and, for each conflicting pair, authors one block through the tool's `add` naming both entries' `###` headings and asking which stands, never editing either entry or deciding between them; the block rides in the pass's `Requirements-review:` commit with no new advisory, so the conflict holds convergence until it is answered; that step is where a contradiction is noticed, because the answer sweep forms no contradiction advisory. Recording a decision lives only on the answer side: `core/shared/answer-procedure.md` for the single-question skills, and the sweep's batched call, which carries out the same fold and removal by tool calls. This boundary is the whole reason the two stay separate.
- **Fold before remove.** In the answer core, and in each section of the sweep's batched call (which chains the fold ahead of `remove` behind `&&`), the decision is folded into `## Decisions` before the block is removed, so an interruption leaves the harmless superset (decision recorded, block still standing) rather than a lost decision. Do not swap the order back.
- **One reconciliation engine, strip on doubt.** `remove` is the only reconciliation, and both of its reconciling inputs ride its one write. `--option`: the answer core passes the lifted option id verbatim (never derived by parsing ANSWER), and a literal answer gets one prose verdict on whether it plainly settles on one of the block's own alternatives, passing nothing otherwise. `--undermined`: the standing picks on other questions that a hand answer undermines, reconciled as dependents no `<depends-on>` tag declares, in the same write as the tagged ones, transitively and keeping their alternatives. The named set exists because a tag is the only record of what a pick assumed and a pick formed before the answer cannot declare it, so without the naming the answer sweep would record a pick formed without that answer. The naming is judged in `core/shared/hand-answer-procedure.md`, which both hand-answer skills follow and which composes over the answer core, never in the core itself: the core stays a pass-through recorder that gained one input and no branch, and `answer-with-recommendation-procedure.md` (hence `answer-open-question-with-recommendation`) and the sweep's batched call pass nothing. The judgment reads the recommended option's text and the pick's one-line rationale against the answer (the option can no longer be carried out, or the stated reason no longer holds) without re-forming the recommender's judgment, and it runs on every hand answer: an answer matching the answered block's own pick is no exemption, because that pick says nothing about whether the other blocks' picks were formed against this outcome. The tool resolves every named title before it changes anything, refusing an unknown title (or the answered block's own) with the document unchanged so a mistyped name never silently leaves a stale pick standing, but it accepts a named block that carries no pick and leaves it exactly as it stands, seeding no transitive strip, since over-naming a pick-less block costs nothing and must not abort the answer. Costs are asymmetric — a stripped dependent keeps its alternatives and costs one recommendation re-run, a kept stale rationale becomes a wrong recorded decision — so doubt strips, in the `--option` verdict and the undermined-pick judgment alike. The cascade never clears an `<alternative>`; there is deliberately no separate `reconcile` subcommand; stripped, untagged, or named dependents get no console advisory and no line in the commit body (the commit diff records them and the next recommendation pass surfaces them by construction).
- **Two annotating passes, split at enumerate vs. pick.** The alternatives pass fans out one subagent per bare block, read-only toward the project except for its one scratch file (in parallel as each host's `ALTERNATIVES_PARALLELISM` value states, with no ordering and no cap of the orchestrator's own — siblings are scope only, never assumed settled, which is what makes parallelism and outliving later decisions safe), and embeds and commits the files they land in batches, one fixed shell call per batch: still one `Alternatives-annotation: <Short Title>` commit per question with no body, landed once per round where the host's `ALTERNATIVES_CONCURRENCY` value dispatches in capped rounds and once per wake-up where it dispatches in the background. The batch changes how many orchestrator turns the commits cost, never how many commits land. The recommendation pass dispatches no agents, reasons over its whole filtered set inline, writes blocks in any order, leaves standing picks untouched (idempotency is the `--without-*` filter plus the tool's refusal, never prose discretion), picks the best surviving option on a stale set and skips only a block no option of which survives, and once its picks are decided writes, commits, and sorts in one fixed shell call per batch. That call carries every picked block with no cap or splitting rule, each block running its own `embed --recommendation` process on a quoted heredoc followed, only on that embed's exit 0, by the block's own `lift`, whose line joins the commit body; a refused block is refused alone, the document unchanged for it, and prints its Short Title paired with the tool's `Error:` line while the rest land. The call then commits `open_questions.xml` once under `Recommendation-annotation: <milestone_id>` with the lifted lines as body (only when the body is non-empty), sorts, and commits the reorder as its own `Question-ordering: <milestone_id>` commit behind the dirty-path guard; a run with nothing to write runs the same call with no block section, so there is no branch and no second form. The refused blocks are corrected and re-sent together in at most one more call of the same shape, which commits and sorts again, and a block refused again is skipped into the advisory, so the pass commits once per batch call rather than once per run and a run is bounded at two batched calls and two annotation commits. The open-question tool stayed unchanged: one `embed` process per block keeps the per-block refusal and the tool's "a mutator prints nothing on success" contract, which a multi-block `embed` or an `embed` printing the lifted line would have broken for no turn the shell call does not already save. The batch replaced, in milestone 44, four separately described post-decision steps (one embed tool call per block, a lift per block, the annotation commit, the sort and its commit): across the twelve measured runs since the alternatives/recommendation split those cost a median of 6 post-decision tool turns against a two-turn floor, and those turns held 71% of a run's input, against an estimated saving of about 0.6M input tokens per milestone, 3.5% of the milestone budget. Both passes gather once (a run only adds children, so the set never shrinks under it), have no clean-tree precondition, and leave stale `<depends-on>` tags alone after a refresh (a tag records what a dependent assumed; only the answer-time cascade reconciles it). The retired per-question recommendation commit, the sequential recommend-agent sweep, its most-significant-first ranking, and the separately described embed, lift, commit, and sort steps must not be restored.
- **The two halves of the analytical core** (`alternatives-procedure.md`, `recommend-procedure.md`) stay two files because their grounding genuinely diverges: only the pick half loads the principle store (a weighted advisory factor, cited when it bore, never a filter or veto) and carries the sibling-disclosure duty and the stale-set rule; the enumeration half forms no preference. Neither carries XML markup or the "what would change your mind" layer — the writing runners own the rendering, `discuss-open-question` owns the conversation.
- **An alternative set is distinct and covering, with no count.** Step 2 of `alternatives-procedure.md` maps the decision space rather than shortlisting candidates: it names the axes of the underlying decision first (values taken from the decision, not from the list the wording offers; a degree is an axis; each premise the wording takes for granted is an axis valued accept or reject; every axis has a none position), builds each option as one position on every axis, and tests the result — distinct (every two options differ in substance on at least one axis) and covering (the set covers the underlying decision rather than the question's wording, not doing the thing included wherever honestly viable, postponing being one form of it and never a second option). The set is the only menu every later pick chooses from and it outlives the decisions after it, so a direction it misses is invisible downstream; the failure patterns the rule targets are near-duplicate options that differ only in wording or emphasis, an answer taking a direction no option represented (most often not doing the thing the options vary), a combination on an axis the set never laid out, and a premise every option shared. The retired "typically two to four" guideline must not be restored: a count is a shortlist size, not a completeness test — it invites padding up to its floor and trimming below what the axes require, and it hides a multi-axis question's growth instead of letting it show; the set's size follows from its axes and their viable combinations alone. The what-it-is field states the option's position on every axis, with no sentence limit and no reasons (those belong in the advantage and drawback), because distinctness and coverage are checkable only against stated positions and because that text is what `lift --alternative` folds into `## Decisions` and capture reads back as the option. Growth is stopped upstream instead: `review-milestone-requirements` authors each question as one choice, so a gap holding two independent choices becomes two small sets rather than one set of their product; the one exception is choices that constrain each other, asked together as one multi-axis question because split apart each question's options would hinge on the other's outcome, and there the enumeration weighs every combination and lists only the viable ones. The step names no test for detecting a second axis — detection is the author's judgment, like its other authoring rules — and sibling-owned axes are never varied, only named as a condition in the drawback, so the split does not leak back in through the options.
- **Element rendering.** The alternatives agent writes only `<alternative>` elements, as the whole content of its scratch file; the recommendation pass renders `<applied-principle>` (one per bearing principle), `<depends-on question option/>` (one per assumed sibling, no option-less form), and exactly one `<recommendation option>` as siblings, never children of one another. Citations and dependencies are kept out of the `<recommendation>` text so the recorded `## Decisions` prose is provenance-free by construction. Indentation, escaping, and child order are the tool's; only the extraction anchors matter.
- **The answer sweep is an inline single writer that orders by the tool's `walk`, walks it once, and records the whole run in one batched shell call.** It resolves `<MILESTONE_DIR>` once per run, and its setup is the fixed-call floor: one fixed shell call is the whole gather, order, and view of the question document (`list --with-question` for every block, recommendation-less ones included, then a `walk`-fed loop printing each walked id, its `lift` line, and its picked alternative's what-it-is through `lift --alternative`), `open_questions.xml` is never read with the file-reading tool, and `requirements.md` is read whole with the file-reading tool, never through shell output, in the same turn as that call as two independent tool calls — a sentence naming no capability, so it needs no slot and degrades to two turns on a host that serializes them. Each decision is written from the question text, the lifted line, and the what-it-is. The one fixed batched call then carries one section per walked question in walk order, never reordered, with no cap, so every commit that lands records a pick whose assumed siblings are already recorded. It opens with the stranded-fold guard: either milestone file holding any change, a stopped run's uncommitted fold or a hand edit alike, prints `dirty before start` and ends the call before any write, so no leftover rides into an answer's commit, while the rest of the tree may stay dirty since every commit is path-scoped to those two files. Each section lifts with only stderr silenced — a failed lift, its pick stripped by an earlier section's `remove`, is the silent skip, reported nowhere, since the commit diffs and the next recommendation pass cover a stripped block — then folds through the fold tool, removes with `--option` written as a literal the runner copied from the view's pick, never derived in the call, and commits under `Recommendation-answer: <Short Title>` with the lifted line as body, one commit per answer being what revert-then-re-answer needs. Any failure after the lift, a fold refusal included, leaves the tool's `Error:` line or git's message unredirected, prints `stopped at`, a tab, and the Short Title, and ends the call with the tree left resumable, never rolled back. Each landed commit prints the fixed marker `answer commit landed`, from which the report reads its status line, with no shell variable tracking state across sections; the call closes with a fixed header line and the completeness `walk`, so a clean run pays no extra turn for the check, and any id that walk prints is an anomaly, never a skipped-question advisory. The sweep records every pick as given and never judges it: it carries no mooting cascade (it fired once in 856 measured answers; an entry a decision moots waits for the next review pass, which cleans it up or flags it) and forms no contradiction advisory (the review pass's `## Decisions` consistency step notices a conflicting pair), so every section keeps one fixed shape. Its own file states every per-question mechanical step: it follows no procedure's tool steps, no longer follows `answer-with-recommendation-procedure.md`, whose intro names only `answer-open-question-with-recommendation`, and draws on `answer-procedure.md` only for its fold step's content rules and its analyse step's first two questions, as that core's intro says, so the rules keep one home, neither procedure gains a batched-path branch, and the core's inputs-as-given contract (shared with literal `answer-open-question`, which must never inherit lift behaviour) stays unchanged. There is no outer re-gather loop because recording only removes, and new questions a decision raises are left to the next review pass. The batch replaced, in milestone 48, a per-answer loop over a whole-document snapshot: across 88 measured runs (856 answers) it cost a median 2.22 turns per answer, because chaining the next question's `lift` and `locate` into the current commit call was never stated, 42% of its folds were ad-hoc scripts, the snapshot's cache re-reads were 31% of all sweep input, and a two-file shell read separated by `echo =====` lost a turn in 33 runs because zsh parses `=cmd` as an expansion, against a simulated −77% turns for the batched loop. The retired whole read of `open_questions.xml`, the per-answer `locate`, the `=====` separator, and the per-question commit made by following the commit procedure outside one call must not be restored.
- **`answer-open-question-with-alternative` is skill-only** (which alternative wins is human judgment, not sweepable), its lift-then-delegate is inlined rather than extracted into a single-consumer shared file (shared means two or more runners), and its guards are the `lift` call's `Error:` line quoted verbatim.
- **`answer-open-question` is literal-only plus a redirect guard**: the retired whole-string sentinel `record the recommendation` stops with a redirect (exact match, never substring); it is migration scaffolding, not a mode.
- **Answer subjects are provenance discriminators, not a harvest filter.** `capture-milestone-principle-updates` walks all three (`Manual-answer:`, `Alternative-answer:`, `Recommendation-answer:`), path-scoped to `open_questions.xml`; overrides are the signal for new principles, accepted recommendations are evidence only (the recommender's reasoning cannot supply the guideline it lacked), agreements are never prompted. Every other commit marker stays clear of those three anchors by construction. Capture reconstructs from the answered block's removed diff lines only, keyed on the tag (element-agnostic, so no per-element ignore list starts), reverses entities itself (the one un-escaping rule left in runtime prose), composes one whole-store rewrite, gates the commit (not the write) on a single confirmation, restores its own snapshot (not `HEAD`) on rejection, and never reaches the commit procedure on a nothing-captured path. It is decoupled from finish: never a precondition, never invoked by it.
- **Correcting a bad answer is revert-then-re-answer**, no dedicated skill: one commit = one answer makes the revert reopen the question; a principle that steered wrong is reconciled by the next capture run through its salvage ladder.
- **`modify-milestone-goal` edits only `## Goal`, clears only the picks it undermines, and never cascades** (surfaces the rest of the impact, points at review). In the same run as the goal edit it names, from its whole read of `open_questions.xml`, the standing picks the revision undermines by the same two tests as a hand answer, doubt stripping, and clears them with one `strip --recommendation` call that keeps every `<alternative>`, committing `open_questions.xml` with `requirements.md` under `Goal-revision:`; a pick formed under the old goal would otherwise reach the answer sweep as given. The clearing is not transitive — a block whose `<depends-on>` names a cleared block keeps its pick and its tag — because a tag records an assumed sibling outcome, which a goal revision does not settle (only the answer-time cascade reconciles tags), and so the tool needed no change. Beyond that one call it removes, adds, and rewords nothing: no decision, out-of-scope entry, task, or question block. It is offered by `discuss-open-question` and deliberately invisible to `answer-open-question`, because recording an answer and reshaping the objective are different acts.
- **`finish-current-milestone` always precedes `goto-next-milestone`**; the pointer clear rides in the same `milestones/README.md` edit as the summary so the none-state is committed, never left dirty.
- **`goto-next-milestone` activates the lowest-numbered undone milestone without asking.** A directory is undone when its zero-stripped number matches no `### Milestone N — Title` heading under `## Milestone History`; the `## Completed Milestones` table is never consulted, because it is never backfilled and a missing row would re-activate a finished milestone with no prompt left to catch it. Numbers are unique and monotone (`define-milestone-goal` takes max-plus-one and refuses a taken number), so the pick is deterministic, and the only stops are a pointer not reading `none` and no undone milestone. The retired single-candidate confirmation and multiple-candidate choice prompts must not be restored, nor a target argument added: the skill heads a headless chain, where a prompt has no one to answer it, and an unwanted defined milestone is skipped by removing its directory rather than by choosing around it.
- **Committing is a property of the skill layer.** Mechanics live only in `core/shared/commit-procedure.md` (dirty-own-path guard → path-scoped add → commit); the execution-neutral shared procedures stay commit-free. Every file-changing user-invoked skill commits exactly its own paths (never `git add -A`) under a function-derived `<Marker>: <descriptor>` subject; dispatched agents stage path-scoped at most and never commit (the alternatives agent stages nothing: its one write is a scratch file in the run's `mktemp -d` directory outside the repository, which no path-scoped add can reach); the alternatives pass's batch shell call commits each question it embedded itself, by the commit procedure's own three steps written into that call, one subject-only commit per question with git's success output silenced; the recommendation pass's batch shell call writes the same three steps into itself, committing `open_questions.xml` once per call under `Recommendation-annotation: <milestone_id>` with the lifted lines as body through the procedure's own second `-m` form (conditioned on a non-empty body, so a call that wrote no block commits no empty-bodied annotation), then the sort's reorder under `Question-ordering: <milestone_id>`, each landed commit announced by one fixed marker line with git's success output silenced; `complete-all-tasks` commits the index its agent staged, per task, with a nothing-staged guard, no `--allow-empty`; both completion runners commit subject-only under `Task-completion: <Task Title>`, the task's `##` heading copied exactly, because one unit of work gets one subject whichever runner makes it and the heading in the subject line lets history be searched without reading commit bodies, so the retired `Tasklist-completion:` marker with its heading-in-body commits must not be restored; the answer sweep's batched call writes the commit procedure's three steps into each question section, committing the milestone's `open_questions.xml` and `requirements.md` under `Recommendation-answer: <Short Title>` with the lifted line as body through the procedure's second `-m` form, git's success output silenced and each landed commit announced by one fixed marker line; each task-file writer chains its one task-list tool call with the git step it owns in one shell call behind `&&`, so a refused write stages and commits nothing — the `complete-task` agent its path-scoped `git add`, and the inline `complete-task` skill, `submit-task`, and `derive-tasks` the commit procedure's three steps written into the call, each landed commit announced by one fixed marker line with git's success output silenced — while `complete-procedure.md` shows the move command alone and names no git step, so the procedure stays commit-free and each runner's own file shows its complete call. There is no non-committing exemption: `init-milestone-base-workflow` checks for a git work tree first (git is the workflow's second prerequisite, beside Python) and commits its scaffold subject-only under `Workflow-bootstrap: milestones`, handing its paths over unchanged so uncommitted changes already in them (a `CLAUDE.md` just written by `/init`) ride in that commit by design, so a headless chain that starts with the bootstrap leaves nothing uncommitted; the retired exemption must not be restored. Dispatch sites address agents through each host's dispatch slot values, phrased descriptively: by the namespaced registry name (`cairn:<agent>`) in the Claude Code tree, by the bare agent name in the Antigravity tree, and in the Codex tree through a dispatch prompt naming the plugin's agent file. The old role-based commit split is retired.
- **Shell commands are written literally where a runner would shorten them.** Some shells (zsh by default) do not split an unquoted variable into words, so a path list held in one variable reaches `git status` or `git add` as a single argument naming no file, and a tool command held in a variable runs as one word naming no command; the shown commands were already literal, and the failure came from a runner rewriting them. The rule is stated, shell-neutral, at the sites that provoke it. `core/shared/commit-procedure.md` names each path literally in both the dirty-own-path check and the `git add` (every path its own argument on the command line, never held in a shell variable), and the `complete-task` agent's staging sentence restates it in matching wording, because the agent reads no commit procedure and stages the largest path set in the workflow, where a wrong staging is silent. Every runner that calls the open-question tool more than once writes the full fixed command on every call, never through a variable, alias, or function of its own defined to stand for the command or any part of it: one clause on the tool-contract sentence of `review-milestone-requirements`, both annotating passes, the answer sweep, `answer-procedure.md`, and the `provide-alternatives-to-open-question` agent (which reads only its own file, so no orchestrator's clause reaches it); the sweep's clause is worded to cover the calls inside its compact view's loop and its batched call's sections, which its own file states rather than a procedure's, so `answer-with-recommendation-procedure.md`'s single `lift` stays unedited. "Of its own" scopes the ban by origin, so the host-provided plugin-root reference in a rendered command falls outside it without being singled out and the clause reads the same in every host tree. The fix is a prose rule rather than a structural one such as a commit tool because the failure lies in how a runner chooses to write a command, not in any command the files show; a commit tool would add a second tool and change the contract of every committing skill, and it would still be invoked through a command line the runner writes, open to the same shortcut. The invariant is scoped to those sites, not a general ban on shell variables: the `capture-milestone-principle-updates` snapshot (`SNAPSHOT="$(mktemp)"`, used quoted as `"$SNAPSHOT"`) is outside it, because it is one quoted value that word splitting never reaches, not a path list or a tool command, so it is neither removed nor cited as a loophole; its reliance on shell state surviving between calls is a separate failure this rule does not address. The alternatives pass follows the same scoping: `mktemp -d`'s print is held as a path and written out in full in every later command, never kept in a shell variable across calls; its batch call is one fixed command shown in full and run exactly as shown, with only `<scratch dir>` and `<MILESTONE_DIR>` replaced by their paths, its `git status` and `git add` naming `<MILESTONE_DIR>/open_questions.xml` literally and its `embed` written as the full fixed tool command; and the loop variables inside that call (the file, its title, the captured error and git output) are outside the ban for the snapshot's reason — each is one quoted value per file, set and used within the one call, never a path list or a tool command. The recommendation pass's batch call follows the same scoping: one fixed command shown in full and run exactly as shown, with only `<MILESTONE_DIR>`, `<milestone_id>`, and each block section's Short Title and rendered elements replaced, its `git status` and `git add` naming `<MILESTONE_DIR>/open_questions.xml` literally and every `embed`, `lift`, and `sort` written as the full fixed tool command. Its per-block captured stderr is outside the ban for the snapshot's reason, and so is its commit body, although that value accumulates across the call rather than being set once per item: set empty at the top of the call, grown by each accepted block's lifted line through a literal-newline join (never `$'\n'` or `echo -e`), and passed quoted to the commit, it is still one quoted text value set and used within the one call, never a path list or a tool command, so word splitting never reaches it. The answer sweep's two calls follow the same scoping: each is one fixed command shown in full and run exactly as shown, the compact view with only `<MILESTONE_DIR>` replaced and the batched call with only `<MILESTONE_DIR>` and each question section's Short Title, heading, decision, and option replaced, its `git status` and `git add` naming `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md` literally and every tool call written as the full fixed command. The compact view's loop values (the walked id and its held lift line) and the batched call's per-section held line are outside the ban for the snapshot's reason — each is one quoted value per item, set and used within its one call, never a path list or a tool command — and no shell variable carries anything from one section to the next. The chained task-list calls follow the same scoping: each runner's call (`derive-tasks`, `submit-task`, the `complete-task` skill and agent) is one fixed command shown in full in that runner's own file and run exactly as shown, with only its placeholders replaced (the milestone directory and id, the titles, the heredoc body, list, or bar, the recorded paths), the task-list tool written as the full fixed command and every `git status` and `git add` naming each path literally, the agent's under its matching staging sentence; each call runs the tool once and holds no shell variable, so no multi-call clause is needed.
- **Success-path console reporting is terse.** One fixed identifier-free status line per run (no per-item output in a loop); `recommend-all-open-questions` alone has two, chosen in strict order by what the run committed, read from the fixed identifier-free marker line its batch calls print each time one of their commits lands (one for the annotation commit, one for the ordering commit), across every call of the run, re-send included, rather than from any test of the sort outcome by the runner. Its advisory carries, besides each block no option of which survives, each block its one corrected re-send refused again, with that second `Error:` line verbatim and the remedy of re-running the pass. The answer sweep reads its one status line the same way, from the marker its batched call prints per landed answer commit, and its two stops (the dirty start with its remedy, the stopped-at question paired with the error printed beside it) replace that line. Only git-absent decision-critical advisories survive alongside it (convergence verdict, untraceable requirement, the still-skipped questions the two annotating passes report, the answer sweep's completeness anomaly), no-op passes print one distinct line, and failure/clean-stop paths keep their full messages with the tool's `Error:` line quoted verbatim. The alternatives pass's advisory carries, besides each `FAILED:` and post-repair skip and each failed commit, the result of one closing `list --without-alternatives` call after the run's last batch: every gathered id it still prints that is not already in the advisory goes in under the fixed reason `no annotation landed`, because no `DONE` is cross-checked against the scan and that print is the only place a file that never landed shows; the same print chooses between `Alternatives embedded.` and the no-op line, so the status line is read from the document rather than from a count the orchestrator would have to hold. The rule is authored inline in each SKILL.md's reporting step; there is no `report-procedure.md`.
- **Task altitude.** Authoring runners (`derive-tasks`, `submit-task`, both over `core/shared/task-format.md`) write only what cannot be re-derived: a unique title and a 1–3 sentence brief. No `Steps`/`Provides`/`Notes`/`Success` sections ever. `core/shared/complete-procedure.md` derives the acceptance bar itself and passes it to the task-list tool's `move`, which renders it under the `**Verified:**` label in `TASKS_DONE.md`, a label kept distinct so it is never read as an authoring contract. `derive-tasks` delegates nothing; `submit-task` is skill-only; `complete-task` is the only skill+agent pair, differing only in inline vs. isolated. Every task-list runner resolves `<MILESTONE_DIR>` via `get-current-milestone.md`.
- **Environment context comes from `CLAUDE.md`** (`AGENTS.md` in the Antigravity and Codex trees, through the `CONTEXT_FILE` slot; `/init` once per project) for `specify-milestone-starting-state`, `derive-tasks`, and the completion procedure. The bootstrap never writes it and never writes the pointer.
- **Dispatched-agent return contracts.** A `FAILED` from the `complete-task` agent promises a resumable tree (partial work continued, never redone or reverted), not an untouched one — do not restore the old promise. The alternatives agent's return is a file, not a message. Its one write, the sole exception to its read-only contract, is `<scratch dir>/<Short Title>.xml` in the run's scratch directory, which the orchestrator creates once per run with `mktemp -d` (fresh and uniquely named under the system temp location, so no stale return or concurrent run collides with it; the same wording in every host tree, so it adds no slot; writable under Codex's workspace-write sandbox, which keeps `$TMPDIR` and `/tmp` writable by default). The agent writes under a temporary `.xml.part` name and renames into place with one `mv`, so a wake-up scan running while other agents still write never pipes a half-written file (the rename stays inside one directory, hence atomic). Its only final messages are the bare token `DONE` or `FAILED: <reason>`. The file is what stops a return travelling through the orchestrator's context twice — once arriving as the agent's final message, once re-typed into a heredoc for `embed` — so the orchestrator never holds a return at all. The final message is a token rather than the file's path because the path is fixed at dispatch (the Short Title exactly as given plus `.xml`, in a directory the orchestrator created), so the batch derives each title from the file name and has nothing to copy; a Short Title holding a path separator fails the write and surfaces as a `FAILED:` skip rather than a silent miss. The orchestrator's only judging is the last-line `FAILED:` verdict, which gets no repair; everything else is one fixed batch shell call that scans exactly the `*.xml` files directly inside the run directory, redirects each unedited into `embed --alternatives` (the tool slices and validates), commits each accepted question, prints one line per refused file or failed commit, and moves every piped file, accepted or refused, into a `processed` subdirectory, so no file is piped twice and the record of what was piped lives on disk, never in the orchestrator's context. Every refusal one batch call prints gets its one repair at once, all sent together in the same turn — continue the same agent session while its handle is still held, one fresh re-dispatch only once it is gone, the branches and the wait on the repairs written per host in the `ALTERNATIVES_REPAIR` slot — and the repaired file lands at the same path for a later batch with no special handling; whether a question has had its repair is the only thing tracked, and a second refusal or `FAILED:` is the per-question skip. A wait that returns before every awaited agent has ended waits again, without limit, so an expiry never skips a question. No `DONE` is cross-checked against the scan: a cross-check would need the per-agent list the batch exists to keep out of the orchestrator's context, and the closing `list --without-alternatives` call already catches every question whose file never landed, whatever its message said, leaving its block bare for the next run. The orchestrator deletes nothing — no scratch file, `processed` subdirectory, or run directory — and no delete or recursive-remove command enters the runner's prose, so a headless chain never meets a permission prompt for one and a refused return the advisory names stays on disk for inspection; the system's own temp handling reclaims the directory. The batch replaced, in milestone 43, the per-return pipeline, which judged, piped as a heredoc, repaired, and committed each return the moment it landed: across 21 measured runs that cost about 16 post-dispatch orchestrator turns per run, more than half of them text-only or silent, at a median 57k-token context with every return held twice, against an estimated 0.82M input tokens per milestone that batching and the smaller context save (1.17M counting one outlier run). Do not restore the per-return pipeline, a returned path, a `DONE` cross-check, or a cleanup step. The rule under both forms — pipe the whole unedited return to the tool, repair once, then skip — deliberately reversed the earlier discard-whole rule (eight of ten milestone-19 dispatches were lost to a grounding preamble), and the extraction moved into the tool in milestone 27; do not restore skip-only behaviour or move extraction back into prose. The pattern is scoped to that one agent: the one other dispatch site, `complete-all-tasks`, keeps a last-line token, and the recommendation pass and the answer sweep dispatch nothing and have no return to judge.
- **A dispatch prompt carries only what the orchestrator already holds and the agent cannot fetch itself.** This holds for both dispatched agents without qualification: `complete-all-tasks` passes the task's `##` heading text and nothing else, the alternatives orchestrator passes the question's Short Title, the resolved `<MILESTONE_DIR>`, and the run's scratch directory and nothing else, and each agent fetches the rest under that directory itself (its task section; its own block by `locate` and its sibling scope by `list --with-question`; `requirements.md`). The scratch directory passes the rule because the agent cannot fetch it: the orchestrator creates it per run, and it is passed on every host, unconditionally, so the prompt template and the agent file stay host-neutral with no branch on whether the value is present. The orchestrator holds no work context, so every extra slot is something it would have to gather and hold per dispatch only to hand over, and a value the agent can fetch is delivered twice when copied into the prompt (under the retired prompt with a `Question block:` slot the alternatives agent read its block in the prompt and again in its whole read of `open_questions.xml`); a fetch also gives the agent the live document rather than the orchestrator's snapshot. The retired `Question block:` slot and the orchestrator's per-question `locate` gather must not be restored, and the two `list` calls are the pass's whole gather. The rule constrains the prompt, not the agent's reading: what an agent may read whole is fixed per document by the invariants above.
- **Skill frontmatter.** Every SKILL.md and agent carries `name` and an unquoted `description` of one clause, 25 words or fewer, no colon or semicolon, loadable by `yaml.safe_load`; it is a routing label, never a record — provenance, mechanics, cross-references, and trigger lists are cut outright (their home is `docs/skill-reference.md`). No exceptions to the cap; an agent description keeps its invocation contract as a short clause.
- **Runtime files carry no editor-facing prose and name no host.** They hold only what the runner needs. The rule covers every rendered runtime file, slot values included: a value names no host, its own included, and reaches its host's mechanism through that host's own identifiers (tool names, config keys, file and command names), otherwise saying "this host" (the agents' Claude-only `color` key is stripped by the Antigravity and Codex definitions' data, the one structural exception). With it goes a development rule: a rendered tree never names another host's mechanism, in any file — the files rendered from `core/` and the host's own templates (README, CONTRIBUTING pointer, manifest, marketplace file, traffic workflow) alike, a contrastive mention of what this host does not use included; a link to the source repository is not a mechanism naming. It is a rule, not a check: `host-name-in-core` keeps scanning `core/` only, so a slot value or template that breaks it passes the build and is caught in review. A host's hands-on check is recorded in one place only, the dated block in the header comment of that host's `settings.toml`, naming the installed version checked and the points and values the run covered, which a later re-check updates; the comment above each slot entry says only what the value stands for and why, in mechanism terms, with no version, and no tool version or observed-behaviour fact enters this file. No `## Rules` sections: a rule lives in the step it constrains or in the opening paragraph. Rationale lives here. The tool sources follow the same rules (no bare `{{`, no host name even in a comment, no placeholder of their own) so each renders byte-identical into every host.
- **Host wording differences are named slots, never markers, duplicated files, or capability-conditional prose.** A sentence or phrase that differs between hosts is a `{{SLOT_NAME}}` placeholder in `core/`, filled from every definition's `[slots]` table; the `slot-declaration` check keeps the declared name sets identical across hosts and each name used in `core/`, and `unfilled-placeholder` catches a slot a host leaves undeclared. A slot is preferred over capability-conditional prose: `core/` never names a capability and leaves the runner to pick a branch at run time, because a branch the host lacks is dead text in its tree that a runner can still follow, so each host's tree describes only its own mechanism. Each value is written from that host's own hands-on check, never copied from another host's, and the trees of two hosts are not expected to agree: no byte-identity between host trees is kept or tested, and the build's rendering is tested by `tests/test_build_rendering.py` instead. The convention is one value file per slot under the definition's `slots/` subdirectory, bound inside `[slots]` as `NAME = { file = "slots/NAME.md" }` with the slot's comment above its entry, every value of every host held that way, the one-word and empty ones included; the build still accepts the inline string form and nothing refuses it, so the file form is a convention, not a check. A value carries no placeholder other than `{{PLUGIN_ROOT}}`, which is why `AGENT_TOOL` and `ALTERNATIVES_AGENT` were retired: their wording is written literally inside each host's `ALTERNATIVES_REPAIR` value. The alternatives pass's host-dependent passages are slots: `ALTERNATIVES_PARALLELISM`, the opening paragraph's phrase saying whether the per-question dispatches run together; `ALTERNATIVES_REPAIR`, the opening of the repair sub-step ahead of its fixed corrective message, fill rule, and one-repair cap (which stay in `core/`), holding the repair branches this host has and how the run waits on the repairs; and `ALTERNATIVES_CONCURRENCY`, the paragraph opening step 3, which also governs how the pass collects returns. Each host's `ALTERNATIVES_CONCURRENCY` is one single-mechanism paragraph describing only that host's dispatch and wait: the Claude Code and Antigravity values send every dispatch at once, none blocking, and run the batch call each time the run wakes with landed returns, no shell loop or event monitor serving as the wait; the Codex value dispatches rounds of at most the session's `agents.max_threads` cap, calls `wait_agent` until the round's last final message has arrived before batching once, and gives a refused round's repair set its own wait and batch before the next round, so repairs never share a wait or take a slot. `ALTERNATIVES_CONCURRENCY` and the repair wait in `ALTERNATIVES_REPAIR` are the pass's only host-dependent waiting wording; no slot was added for the batch, and the scratch directory, the dispatch prompt, and the agent file are host-neutral. The Antigravity values dispatch both agents by the bare names the tree's own `agents/` directory carries, with no file or build change added for agent loading. Codex runs both agents as its generic subagent told to read and follow the plugin's Markdown agent file, with no TOML file, registration step, or format conversion in the build, because Codex documents no way for a plugin to ship a custom agent.
- **Pre-split milestones** (`milestone_01`–`27`) get no migration and no compatibility: a question skill run against a milestone with no `open_questions.xml` stops on the open-question tool's `Error:` line.

## Development

The build loop, both test runs, the version bump, and the distribution repositories are documented in `CONTRIBUTING.md` under `## Development`; the release procedure in `.claude/skills/release-plugin/SKILL.md`. Points not recorded there:

- `hosts/<host>/` trees are pure build output: rebuild after any change under `core/` or `scripts/hosts/` and commit the rebuilt trees with that change, so `main` always passes `--check`. `--check` is run by a maintainer or CI, never a git hook; the CI workflow has no path filter (a `paths` list would be a hand-maintained copy of the build's input set) and is one job, never a matrix.
- The floor run bypasses the build tooling's `requires-python = ">=3.11"` on purpose; the tools need nothing from that project. Two bracketing runs replace a version matrix because stdlib availability is monotone across minors. The literal `3.9` has three homes: the README prerequisite, the bootstrap check, and the CI floor run. `tests/test_build_rendering.py` is the suite's one pinned-only test: the build imports `tomllib` and PyYAML, so the module skips itself at module level below Python 3.11, keyed on the interpreter version and before any import of the build, and the floor run reports it skipped while the pinned run never does; no pytest command, `conftest.py`, or `pyproject.toml` setting excludes it. It renders a synthetic `core/` through one synthetic definition in-process and covers rendering and the file-backed slot refusals, not `main`'s orchestration or the check set.
- Adding a host means adding a definition directory under `scripts/hosts/`; no host-specific Python exists. A host definition's `[layout]` must map all four `core/` directories, every one inside its `plugin_dir` (the path from the tree root to the runtime plugin root: empty for Claude Code and Antigravity, `plugins/cairn` for Codex), and it must declare every wording slot the other definitions declare, each value held by convention in its own file under the definition's `slots/` subdirectory (which template discovery skips), the inline string form still accepted.
- `set_version.py` writes nothing under `hosts/` (manifests are rendered from `VERSION` by the build). `/release-plugin` makes one `Release: <VERSION>` commit that changes only version slots and the `CHANGELOG.md` entry, then publishes each host tree with `git commit-tree` into `uHappyLogic/cairn-<host>`; those repositories and every `traffic-data` branch are never hand-edited. `TRAFFIC_TOKEN` is a fine-grained PAT on exactly the four repositories, kept in no local copy.
- Outside contributions are proposal-first (see `CONTRIBUTING.md`): the maintainer reserves the milestone with `/define-milestone-goal` on `main` only while their own pointer reads `none`, without activating it; the contributor runs the pipeline on a branch (net pointer change nil), syncs by merge only, and the pull request is merged as a merge commit so the milestone commits survive for release notes and capture.

## Milestone Workflow

This project uses the milestone-driven workflow. Each milestone lives at
`milestones/milestone_<N>_<slug>/` with `requirements.md`, `open_questions.xml`,
`TASKS_TODO.md`, and `TASKS_DONE.md`. `milestones/README.md` is the source of truth for
which milestone is current. Never advance the pointer without first running
`/finish-current-milestone`.
