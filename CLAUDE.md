# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A plugin (`cairn`) for Claude Code and Antigravity that provides a milestone-driven development workflow. It ships as a set of skills and a couple of agents that move a project from a vague idea through discussion, planning, completion, and archival — one milestone at a time.

The runtime layer is plain Markdown with no tests and no dependencies of its own. The only tooling is the two Python scripts under `scripts/`, run with `uv` (`pyyaml` is their one dependency, declared in `pyproject.toml` and pinned in `uv.lock`); the build's validation gate is the repository's only automated check, run locally and by the `.github/workflows/drift-gate.yml` workflow on every push and pull request.

## Skills and the workflow they encode

The skills form a linear pipeline. Each skill's SKILL.md defines its exact behaviour:

```

discuss-milestone-goal          ← optional sharpening conversation, creates no files
define-milestone-goal           ← creates milestones/milestone_<N>_<slug>/ with requirements.md, TASKS_TODO.md, TASKS_DONE.md
specify-milestone-starting-state ← fills "Relevant starting state" in requirements.md
review-milestone-requirements   ← repeatable loop engine: each pass reconciles existing questions against recorded decisions, surfaces new gaps, reports convergence; strips the embedded children of every `<depends-on>` dependent of a block it prunes or dedups (transitively, recording no decision); run repeatedly
recommend-all-open-questions    ← orchestrator (batch form of discuss-open-question): sweeps every question once (gathered via the boundary-line CLI), ranks the surviving ones most-significant-first by judgment over the gather alone, dispatches one read-only recommend-open-question subagent each strictly sequentially in that order, and embeds each accepted return's `<alternative>`/`<applied-principle>`/`<depends-on>`/`<recommendation>` child elements into the existing `<open-question>` block by whole-block-replacement Edit before the next dispatch, so later recommendations may build on already-embedded siblings and declare each such use as a `<depends-on question="..." option="..."/>` child (gate-checked to resolve against a still-present annotated sibling); sole mutator, commits its annotations once at the end of the run (subject Recommendation-annotation: <milestone_id>, path-scoped, behind the dirty-own-path no-op guard), idempotent skip of blocks already carrying a `<recommendation>` element, no clean-tree precondition

answer-all-open-questions-with-recommendation ← orchestrator: sweeps every question carrying an embedded recommendation, dispatches the file-editing answer-open-question-with-recommendation agent strictly sequentially (gather once in document order, walk the `<depends-on>` dependency graph from its origins — unresolvable edges dropped, same-depth ties in document order, a stranded cycle broken by promoting its document-order-first member to an origin — with per-question re-read/skip on already-cascaded or stripped blocks); the orchestrator commits each answer itself after the agent returns — one commit per answer (subject Recommendation-answer: <Short Title>), the agent records but never commits
```

## Milestone file structure

Each active milestone lives at `milestones/milestone_<N>_<slug>/` and contains exactly:

- `requirements.md` — Goal, Relevant starting state, decisions, open questions
- `TASKS_TODO.md` — pending tasks ordered by priority (highest first), `##` headings + `---` separators
- `TASKS_DONE.md` — completed tasks appended in the same format

`milestones/README.md` is the source of truth for which milestone is current.

## Invariants to preserve when editing skills

- `init-milestone-base-workflow` is the one-time bootstrap; it is additive and idempotent — it never overwrites an existing `milestones/README.md` or `CLAUDE.md`, only creating missing files and appending missing sections. It must leave `milestones/README.md` with a `Current milestone:` pointer line.
- `review-milestone-requirements` (renamed from the old `highlight-milestone-requirements-open-questions`) is the repeatable engine of the requirements-iteration loop and the **sole author** of `<open-question>` blocks: each pass **reconciles** the existing blocks against the recorded `## Decisions`, **surfaces** new gaps (authoring each as a well-formed `<open-question>` XML block appended under the single `## Open questions` section), and **reports convergence** (converged when no `<open-question>` block remains — exactly `derive-tasks`'s precondition, so open questions in `requirements.md` must be fully resolved before `derive-tasks` can run). It reads the whole `requirements.md` and reasons over it (reconcile/author are cross-document work, not the deterministic locate the CLI is for). It is the **only** skill besides the answer path that may remove a question block, and only as *cleanup of already-recorded state*: it may delete a block (in full, from its `<open-question …>` opening boundary line through its `</open-question>` closing boundary line) solely when it can cite a `## Decisions` entry that already covers it, or dedup an exact repeat — when in doubt it flags ("possibly resolved — confirm") rather than deletes, and every removal is reported. A prune or dedup removes its block **without recording any option**, so on **both** removal paths the pass then **strips the dependents** of the removed block: every surviving block whose `<depends-on question="…">` (attribute-name-anchored regex, entity-unescaped, case-folded) names it has every child between its `<question>` element and its `</open-question>` line deleted — all `<alternative>`/`<applied-principle>`/`<depends-on>`/`<recommendation>` children — leaving the bare wrapper and `<question>` for the next recommend sweep to regenerate, **transitively** over dependents of stripped blocks until no `<depends-on>` names a block removed or stripped in the pass. That stripping is the same uniform mismatch treatment `core/shared/answer-procedure.md` gives an option-less removal, decides nothing, never removes the stripped block, and adds nothing to the pass's report (the committed diff is its record). It **never records a decision or answers a question**: folding a decision into `## Decisions` and cascading to mooted siblings stays scoped to `core/shared/answer-procedure.md` (used by `answer-open-question` and `core/shared/answer-with-recommendation-procedure.md`). This boundary — tidy the questions section vs. record an answer — is the whole reason the two stay separate. The `## Open questions` section holds its blocks as raw XML — a deliberate trade of clean Markdown rendering for blocks that are deterministically queryable by the boundary-line CLI and parseable by future tooling — while the four prose sections (`## Goal`, `## Relevant starting state`, `## Decisions`, `## Out of Scope`) stay Markdown; blocks are never placed inline next to the requirement they concern, because keeping the whole question set in that one bounded region is what lets the answering and recommendation skills query it deterministically, and it is also why each authored `<question>` must stand on its own.
- The answer-recording mechanism (locate the `<open-question>` block by Short Title via the boundary-line CLI → fold the decision into `## Decisions` as clean prose → remove the whole `<open-question …>`…`</open-question>` block → cascade to mooted entries → reconcile the surviving dependents' `<depends-on>` tags) lives in exactly one place: `core/shared/answer-procedure.md`. `answer-open-question`, `core/shared/answer-with-recommendation-procedure.md`, and `answer-open-question-with-alternative` all reference it via `{{PLUGIN_ROOT}}` and never restate the steps. That shared file is **execution-neutral** — it never mentions arg-parsing, committing, or the capture chain — and its **input contract is three fields, the third optional**: a resolved SHORT TITLE, an ANSWER, and a **RECORDED OPTION** — the un-escaped `<recommendation option>` / `<alternative id>` value the caller lifted as the decision, when it lifted one. RECORDED OPTION's **presence is itself the comparison-mode discriminator** for the dependency reconciliation: supplied, the recorded option is held against each dependent's assumed option as an **exact id comparison**; absent, the core **judges** whether the ANSWER prose invalidates that assumed option. Both lifting callers already hold the id at the moment they delegate — `core/shared/answer-with-recommendation-procedure.md` passes the lifted `option`, `answer-open-question-with-alternative` passes the chosen alternative `id` — and `answer-open-question` **explicitly passes nothing** (a literal answer lifts no id, so the judgment mode applies); the core **never derives it by parsing ANSWER**, so the "`<option>` — `<rationale>`" anchor stays a caller-side rendering convention and never becomes a parse contract inside the core. **The fold precedes the removal**: step 4 folds the decision into `## Decisions` and step 5 then removes the **entire `<open-question …>`…`</open-question>` block** located in step 2 — from its opening boundary line through and including its closing boundary line, whether or not it carries embedded `<alternative>`/`<applied-principle>`/`<depends-on>`/`<recommendation>` children — as a deterministic line-range deletion driven by the boundary-line CLI over boundary lines **re-queried after the fold shifted them**. That order is deliberate and must not be swapped back: a failure or interruption between the two edits then leaves the harmless superset (the decision recorded while the question block still stands, which a later pass reconciles) instead of the lossy state where the block is gone and nothing records the decision, so the next sweep no longer gathers the question and it is silently lost. Removal covers both cases uniformly: a bare block with no embedded children shares the one `<open-question …>`/`</open-question>` boundary-token pair and is removed exactly the same way. Step 2's locating keys off the block's `id` attribute (case-folded, entity-unescaped, matched by attribute-name-anchored regex), step 3 (analyse) is unchanged, and step 6 (cascade) stays last: it folds each mooted entry's implied constraint before removing it, and **then reconciles dependents** — once the answered block and every mooted entry are gone, every surviving block whose `<depends-on question="…">` (same regex, unescaping, and case-folding as step 2) names a removed block takes exactly **one of two outcomes**. **Agreeing — remove the tag only**: the target is the answered block and the dependent's assumed `option` is the recorded one (equal un-escaped case-folded ids with RECORDED OPTION supplied; the ANSWER prose plainly leaving the assumed option standing without it) — that one `<depends-on …/>` line is deleted and the block's other children stand. **Disagreeing — strip the children**: everything else — differing ids, an inconclusive judgment, or a target removed as a mooted entry with **no option recorded** (an option-less removal is exactly the inconclusive comparison, so it routes into this branch rather than adding a third outcome) — deletes every child between the dependent's `<question>` element and its `</open-question>` line, leaving the bare wrapper and `<question>` for the next recommend sweep to regenerate. **Strip on doubt** is the rule: the costs are asymmetric (an extra dispatch is cheap and self-healing; a kept stale rationale becomes a wrong recorded decision only a revert undoes), so whenever the agreeing case cannot be affirmed the strip applies. Stripping is **transitive** over dependents of stripped blocks; a stripped block records no decision and is never removed; the reconciliation compares each dependent's assumed option against the option actually **recorded**, never against its target's live recommendation; and it prints nothing — a stripped or tidied dependent gets **no console advisory** from any answer skill (the answer commit's diff records it, and the cleared block is exactly the un-annotated state the next review or recommend pass surfaces by construction, so the note fails both halves of the git-absent-and-decision-critical test). The four edits (fold, removal, cascade, reconciliation) stay separate, and the file stays execution-neutral and silent.
- `recommend-all-open-questions` is the batch form of `discuss-open-question`. It gathers the `<open-question>` entries **once** and walks them **strictly sequentially, most-significant-first**, deliberately omitting the machinery a decision-recording sweep would need — no per-question live-re-check/skip against a mutating document, no outer re-gather loop, and **no clean-working-tree precondition** — precisely because it records **no decisions** and triggers **no cascades**, so the question set never shrinks under it. It gathers the questions via the boundary-line CLI (`awk`/`sed`/`grep` on the `<open-question …>`/`</open-question>` boundary lines, never `xmllint`) over the single `## Open questions` section, and **ranks the surviving questions most-significant-first by judgment over exactly what that gather yields** — each block's `id` and `<question>` text — reading **no more** of `requirements.md` to do it, because the orchestrator never reads the whole document to assemble context (the subagent is what grounds in the document); the ranking is a best-effort heuristic whose misses are absorbed by the prose fallback below. **Dispatch is sequential and embedding is per-question, never parallel and never postponed to the end of the run**: it dispatches one question, judges its return (including the single repair attempt, run immediately for that question), and embeds its accepted region **before dispatching the next**, so every later dispatch reads a `requirements.md` that already carries every earlier question's embedded children. That is what lets a later recommendation **build on sibling recommendations already embedded** — the former "recommendation independence" rule (independent, parallelizable dispatches; never feed one question's recommendation into another) is **retired** and must not be restored. Each such use is declared as a self-closing **`<depends-on question="Short Title" option="Option"/>`** child of the block, emitted **only for a sibling that already carries embedded children in the block the agent read**, naming that sibling's `id` and one of its `<alternative>` ids; a coupling on a sibling **not yet annotated** gets **no element** — no option is ever guessed and there is **no option-less tag form** — and is expressed as prose inside the affected `<drawback>` or the rationale (the accepted residual: answering such a later sibling strips nothing, guarded only by that prose). The acceptance gate's **seventh test** resolves every returned `<depends-on>` **one hop** against the still-present annotated sibling blocks and the target's `<alternative id>` lines (**no cycle test** — a cycle is reachable only through the hand-clear escape hatch and is tolerated, dissolving at the answer sweep's first cascade); a miss is an ordinary structural miss (reason string, one repair, skip only on a second failure) and the orchestrator **never drops or rewrites a returned element** to make it pass. It is the **sole document mutator**: it embeds each accepted set of child sub-elements **inside the existing `<open-question>` block** by **whole-block-replacement** `Edit` (not a CLI splice — constructing correctly-indented nested children is read-whole structural construction, where the CLI is weakest), inserting them between the `<question>` element and the closing `</open-question>` tag at a 2-space-per-level indent and leaving the `<open-question …>`/`</open-question>` boundary tags and the `<question>` element unchanged. It is **idempotent** — it skips any block already containing a `<recommendation>` element and annotates only those lacking one, which keeps re-runs cheap and preserves any hand-edits to an existing recommendation (the primary re-run motive being exactly the un-annotated set a later `/review-milestone-requirements` pass surfaces); the escape hatch for a stale recommendation is to delete that block's embedded `<alternative>`/`<applied-principle>`/`<depends-on>`/`<recommendation>` children (the `<open-question>` wrapper and `<question>` element intact) and re-run, and there is deliberately **no** `refresh`/selectable mode (it stays argument-free). **Stale tags after such a refresh are left alone**: when the regenerated block's new recommended option differs from what surviving dependents' `<depends-on>` elements assumed, the sweep leaves those dependents exactly as they are — no strip, no re-dispatch, no `option` rewrite, no mismatch advisory — because a `<depends-on>` records **what a dependent assumed**, not a pointer that must track its target, and reconciliation happens only in the answer-time cascade against the option actually recorded; a dependent the user also wants regenerated is covered by the same hand-clear. Following the skill-layer commit rule it **commits its own annotations once at the end of the run** (never inside the dispatch loop) — path-scoped `git add <MILESTONE_DIR>/requirements.md` (never `git add -A`) then a single commit under subject `Recommendation-annotation: <milestone_id>` via `core/shared/commit-procedure.md`, behind that procedure's dirty-own-path no-op guard so a sweep that annotated nothing commits nothing. The orchestrator owns **all** document mutation and the staging; its `recommend-open-question` subagent (one dispatch per question, the non-interactive twin of `discuss-open-question`) is **read-only** — it reads `requirements.md`, the live project, and the project-wide principle store to ground honest alternatives but returns only the ready-to-embed child sub-elements (the `<alternative>` elements, any `<applied-principle>` elements, any `<depends-on>` elements, then the single `<recommendation>` element — never the `<open-question>` wrapper or `<question>` element) as its final message, and the orchestrator does all embedding and staging. **Return judging is a four-stage per-return pipeline** — last-line verdict, extraction, acceptance gate, then one repair — specified in full in the dispatched-agent-return invariant below; this sweep is the one dispatch site in the plugin that contacts an agent a **second** time, and that single repair attempt is what makes an otherwise valid recommendation recoverable rather than skipped. Recovery is **silent**: a question annotated only after extraction stripped surrounding text, or only after the repair, gets **no console mention at all** — under the terse-reporting rule a recovered return is reported exactly like a clean one (an advisory must be both git-absent and decision-critical, and a recovered return changes nothing the user must decide), so only questions **still** skipped after the repair path reach the step-6 advisory and the step-5 all-skipped no-op wording. The subagent's read-only grounding sees the sibling `<open-question>` blocks as they stand when it reads, embedded children included, and a sibling that already carries them is a **legitimate input** it may build on and must declare.
- `core/shared/answer-with-recommendation-procedure.md` is the single source of truth for the "lift the embedded recommendation, then record it" logic, referenced (never restated) via `{{PLUGIN_ROOT}}` by both the `answer-open-question-with-recommendation` skill and its agent. It is **execution-neutral**: given a resolved SHORT TITLE it locates the `<open-question>` block via the boundary-line CLI, lifts its `<recommendation option="...">…</recommendation>` element — recombining the `option` attribute value with the element text as "`<option>` — `<rationale>`" (the old anchor form) under reverse entity-substitution (with a **no-`<recommendation>`-element guard** that stops without changes when the recommend sweep never annotated the block), then delegates to `core/shared/answer-procedure.md` with the derived ANSWER **and the un-escaped `option` value it lifted as RECORDED OPTION** — passed separately, so the core compares it as an exact id rather than parsing ANSWER. It **composes over** the recording core exactly as the `complete-task` skill and agent layer their shared procedure — the lift lives here, not in `answer-procedure.md`, so that core's **inputs-as-given contract** (ANSWER plus an optional RECORDED OPTION the caller either passes or omits, shared with literal `answer-open-question`, which must never inherit lift behavior) stays unchanged. The `answer-open-question-with-recommendation` skill + agent follow the established skill+agent pattern (one execution-neutral shared procedure, run **inline** by the skill so context survives, **in isolation** by the agent with the `DONE`/`FAILED` return protocol), but with a deliberate divergence from the read-only-subagent design of the plugin's other per-question subagents (e.g. `recommend-open-question`): here the **mutation** is what's isolated into the agent, not the reasoning. The recommendation is **pre-computed** by the recommend sweep, so there is no candidate elimination worth isolating; what dispatching a per-question **file-editing** agent buys the sweep orchestrator is keeping the expensive per-question edit out of its own context. It is the **recording** that is isolated into the agent, **not the committing** — under the layer rule the agent records the answer and stages it, and the orchestrator commits that staged index (see the next invariant). This inversion (mutation-in-agent, not read-only-subagent) is documented so a later editor does not "fix" the agent back toward the read-only-subagent norm.
- In `answer-all-open-questions-with-recommendation`, the file-editing **agent records and stages but never commits** — it folds the answer into `## Decisions`, `git add`s its one `<MILESTONE_DIR>/requirements.md` edit path-scoped (never `git add -A`), and returns a **bare** `DONE`/`FAILED` with no hand-back payload — and the **orchestrator commits that staged index itself** after the agent returns: a nothing-staged no-op guard, then a pathspec-less `git commit` under subject `Recommendation-answer: <Short Title>`, **one commit per answer** (preserving one-commit-=-one-answer). Because the agent hands nothing back, the orchestrator **lifts the `<recommendation>` text for the commit body itself, during its pre-dispatch re-check**, while the block is still in the document — once the answer is recorded the block is gone, so that re-check is the only place the lift can happen. Staging is not committing, so the agents-never-commit rule holds: this is the **ordinary** skill-layer arrangement (dispatched agents never commit; an orchestrator commits its agents' work, exactly as in `complete-all-tasks`) — milestone 10 reversed the earlier milestone-7 inversion in which the agent committed and the orchestrator did not. The orchestrator sequences its own dispatches — gather once **in document order** and **walk the dependency graph** rather than judging significance, and before each dispatch re-read `requirements.md` and skip the question when a prior answer's cascade already removed its block **or stripped its `<recommendation>`**, with `core/shared/answer-procedure.md`'s step-2 stop-on-missing-block as the backstop — running **strictly sequentially** because cascades mutate the shared document. The graph is built **over the gathered set alone**: each gathered block is a node and each of its `<depends-on question="…">` values (only the `question` value is read — the `option` value is the recording core's to reconcile) is an edge to the gathered block whose `id` matches; an edge whose target is **absent from the document or present without a `<recommendation>`** (so never gathered) is **dropped** — the gather is never widened, the tag stays in the document for the cascade, and a question left with no resolvable edge is an ordinary origin, because a `<depends-on>` records what a dependent assumed and only a recorded option can reconcile it, so an edge to a target this sweep will never answer carries nothing to act on. The walk is **by depth**: origins first, then every question whose every resolvable edge is already placed, **same-depth ties in document order** (same-depth questions cannot depend on one another, so the tie order can never change a cascade outcome — determinism and cost are the only criteria, and document order costs nothing, retiring the old "loosely most-significant-first" significance proxy). A **stranded set** — questions none of whose targets are yet placed, i.e. a `<depends-on>` cycle, reachable only through the recommend sweep's hand-clear escape hatch — is broken by **promoting its document-order-first member to an origin** and continuing the depth walk, repeated whenever the walk strands again; the cycle dissolves at the promoted question's cascade, and the residual (its rationale may be stale when recorded) is the same accepted forward-declaration risk shrunk to one question per cycle. The walk is **deterministic and total** for any graph shape, cycles included. Walking a target before its dependents is what lets each answer's cascade settle the dependents in turn (tag removed on agreement, children stripped otherwise), and a dependent so stripped is skipped by the re-check — the cascade doing its job, not a gap in the walk. That gathered order is walked **exactly once** and never wrapped in an outer re-gather loop: recording only ever *removes* questions or their children (cascades moot or strip them) and nothing adds questions mid-sweep, so a single ordered pass is the fixed point. It needs no clean-working-tree precondition — the agent's staging is path-scoped, so a dirty tree elsewhere stays out of the per-answer commit. Documented as its own invariant so it is not reverted toward agent-commits.
- Recommendation-derived answers — from **both** the single-question `answer-open-question-with-recommendation` skill and the sweep (whose orchestrator commits each answer) — commit under the distinct subject `Recommendation-answer: <Short Title>`, and **alternative-derived answers** — from `answer-open-question-with-alternative` — under `Alternative-answer: <Short Title>`. These subjects are **provenance discriminators, not a harvest filter**: `capture-milestone-principle-updates` walks **all three** answer subjects on a milestone's `requirements.md` and reads the subject to tell them apart. A `Recommendation-answer:` body is the `recommend-open-question` agent's rationale (batch-accepted on the sweep path), not user-deliberated reasoning, so capture reads it as an **accepted recommendation** — **evidence only** about entries already in the store (a removed `<applied-principle>` citation reinforces the cited entry and shields it from pruning or narrowing in that pass; an accepted rationale that contradicts an entry flags it for salvage) — and **never mines it for a new principle**, because the recommender's own reasoning cannot supply the guideline the recommender lacked. A `Manual-answer:` or `Alternative-answer:` that recorded a different option than the removed `<recommendation option>` named is the **override signal** from which new principles come: an `Alternative-answer:` body is only the chosen `<alternative>`'s what-it-is text (the recommend agent's rendering, no user rationale), so capture prompts for the override reason at harvest time, while a `Manual-answer:` body is prompted only when it is a bare literal answer with no stated reason. A manual or alternative answer that recorded the very option the recommendation named is an **agreement**, not an override — never prompted, its citations read as reinforcement — and a `Manual-answer:` whose block carried no recommendation at all (every pre-sweep answer) stays a principle source through its body. The distinct subject is the honest git-log provenance discriminator, matching the house style where the subject *is* the provenance marker — it is what keeps a recommendation-derived answer from ever being mistaken for hand-authored rationale, without any per-subject harvest filter.
- `answer-open-question-with-alternative` is the **sibling** of `answer-open-question-with-recommendation`: same recommend-sweep annotations, same recording core, differing **only** in which embedded element becomes the answer — the recommendation skill lifts the one `<recommendation>` the sweep picked, this skill lifts the `<alternative id="...">` the **user names** (arg split on the first `.`, Short Title before / target alternative id after, both case-insensitive against the respective `id` attributes — mirroring `answer-open-question`'s first-`.` split). Its purpose is to let a user **override the recommended option** or break a genuine tie. It derives ANSWER by recombining the chosen alternative's `id` with its **what-it-is text** as "`<id>` — `<what-it-is>`" (the recommendation form's exact analog), pointedly **excluding** the `<advantage>`/`<drawback>` children (trade-off analysis, not the decision), then delegates to `core/shared/answer-procedure.md` with that ANSWER and the un-escaped chosen `id` as RECORDED OPTION (so the cascade compares it as an exact id). Three deliberate divergences from the recommendation path, documented so they are not "fixed" back toward it: (1) it is **skill-only** — there is **no** agent and **no** `answer-all-open-questions-with-alternative` batch form, because choosing *which* alternative wins is per-question human judgment, not a rule an orchestrator could sweep (a sweep that always picks the recommended option is just the recommendation sweep); (2) with only one runner, the lift-then-delegate logic is **inlined in the skill** (composing over the multi-consumer `core/shared/answer-procedure.md`) rather than extracted into a single-consumer `core/shared/answer-with-alternative-procedure.md` — a shared file here would contradict the plugin's "shared = source of truth across ≥2 runners" convention; (3) it carries **two** clean-stop guards (no matching question id, or a block with no `<alternative>` elements / no alternative matching the named id), each listing the available ids and committing nothing. Its own locate step is a **read to derive the answer** — not the recording core's locate/remove step, which runs later inside the delegated `core/shared/answer-procedure.md`.
- `core/shared/recommend-procedure.md` is the single source of truth for the "alternatives + single recommendation for one question" analytical core, referenced (never restated) by both the `discuss-open-question` skill and the `recommend-open-question` agent via `{{PLUGIN_ROOT}}`. It is **execution-neutral** and holds only logical content: the grounding discipline (the live project over memory), the **Alternatives** requirement (2–4 genuinely realistic options, no strawmen/padding, each carrying what-it-is / key advantage / key drawback), and the single **Recommendation** (one option, direct hedge-free rationale, plus the name-what-breaks-the-tie rule). It is **principle-aware**: its grounding step reads the project-wide principle store `milestones/answer_decision_principles.md` **in place** (naming that fixed `milestones/`-root path directly — the confirmed principles are not a caller-supplied input alongside QUESTION), and a confirmed principle that bears on the question is a **weighted advisory factor** — a strong default in favor of the option it supports, which **merit may override only for a specifically stated reason**, and which is **cited** in the recommendation whenever it influenced the pick (never a binding filter or veto, never a candidate drop, never silently applied). When no principle bears, the alternatives+recommendation contract is exactly as in a project with no principles. Its grounding step also carries the **caller-neutral disclosure duty** that replaced the retired independence clause: a recommendation already attached to a still-unanswered sibling is legitimate input, and whenever the recommendation formed leans on such a sibling's recommendation it **names that sibling (its Short Title) and the option assumed** — the caller decides how that disclosure is rendered (`<depends-on>` elements in the agent, plain prose in the rationale for `discuss-open-question`), the same division of labor already used for principles, where the core states the citation obligation and the agent owns the markup. The core carries the duty without the sweep mechanics that give it teeth (the acceptance gate and the answer-time cascade), so a reader of the core alone sees the obligation without its enforcement; that is accepted. It carries **no** XML rendering markup and **no** "what would change your mind" section — the boundary is deliberate: `discuss-open-question` owns the WWCYM layer, the conversational framing, and the on-decision follow-up offers; the `recommend-open-question` agent owns the literal XML sub-element rendering (the 2-space-per-level child indentation, the sibling `<applied-principle>` elements, the `<depends-on>` elements, and the `<recommendation option="...">` element). This mirrors how `core/shared/answer-procedure.md` is execution-neutral while its wrappers own arg-parsing and committing. The store itself is consumed by this **recommendation core** rather than by an auto-answer engine: its data and per-entry format are unchanged, and `capture-milestone-principle-updates` remains its **sole writer**; only the consumer pointer moved, from a binding auto-answer sweep to the recommendation advisor that cites it.

Revert the answer's commit (by the one-commit-=-one-answer invariant the revert restores the reopened question block and removes the folded decision in one shot — the `Manual-answer:` commit for a manual answer, the `Recommendation-answer:` commit for a recommendation-derived one, the `Alternative-answer:` commit for an alternative-derived one), then re-record via `/answer-open-question` (or `/answer-open-question-with-recommendation` to re-lift a re-embedded recommendation, or `/answer-open-question-with-alternative` to record a different embedded alternative). Because a confirmed principle is now only a **weighted advisory factor** cited in recommendations — never a binding auto-answer — a principle that steered a recommendation wrong is reconciled the next time `capture-milestone-principle-updates` runs for that milestone (conventionally at its finish, never as a precondition): the corrective re-answer's `Manual-answer:` (or `Alternative-answer:`) commit is an override commit whose diff still carries the `<applied-principle>` citation that steered it, so capture reads the override rationale against that entry and takes the **salvage ladder** — narrow its scope clause, generalize it, replace it, and delete it only when nothing survives — inside the whole-store rewrite the user reviews with `git diff`. For an urgent "this principle is actively wrong, remove it now" case the user hand-edits the plain-Markdown store `milestones/answer_decision_principles.md` directly; capture imposes **no clean-store precondition** — it notices the uncommitted edits, asks once, composes its rewrite over the working-tree file rather than `HEAD`, and on rejection restores its pre-write snapshot (not `HEAD`), so the hand-edit survives either way.
- **Committing is a property of the skill layer.** The mechanics live in exactly one place — `core/shared/commit-procedure.md` (dirty-own-path no-op guard → path-scoped `git add` of the pass's own paths → `git commit` under its subject), referenced via `{{PLUGIN_ROOT}}` by every committer and never restated (the execution-neutral shared procedures `answer-procedure.md`, `answer-with-recommendation-procedure.md`, `complete-procedure.md`, `recommend-procedure.md` stay **commit-free**, as does the format-only `task-format.md`; commit logic lives in the wrappers). The two **agent-dispatching orchestrators** (`complete-all-tasks`, `answer-all-open-questions-with-recommendation`) are the one arrangement outside that reference: their agent has already staged the change set path-scoped, so they stage nothing and instead run the guard-and-commit half inline — a nothing-staged no-op guard, then a pathspec-less `git commit` under their subject. The rule: **every user-invoked skill that changes files commits exactly those changes**, staged path-scoped by explicitly named paths (**never `git add -A`**, no content inspection to choose the set), under its own distinct **function-derived `<Marker>: <descriptor>` subject** — a distinctive marker prefix, a colon and space, then a short descriptor, the marker derived systematically from that skill's distinctive function rather than drawn from an ad-hoc per-skill list and with no grandfathered exceptions, so the git log reads as self-describing provenance and every prefix is greppable — that stays clear of the three answer markers by construction (only the three answer skills carry a marker beginning `Manual-answer:`, `Alternative-answer:`, or `Recommendation-answer:` — the anchors `capture-milestone-principle-updates` greps for and reads as provenance — and a skill deriving a new marker picks one that names its function and does not collide with any of those anchors); **dispatched agents stage their own change set path-scoped but never commit** (staging is not committing; they return a bare `DONE`/`FAILED` with no hand-back payload); **an orchestrator commits the index its agent staged, after it returns.** **Dispatch naming:** an orchestrator addresses each dispatched agent by its **namespaced registry name** — the agent under this plugin's namespace, which Claude Code lists as `cairn:complete-task`, `cairn:recommend-open-question` and `cairn:answer-open-question-with-recommendation` — phrased descriptively at the dispatch site rather than frozen as a bare agent name, so resolution stays correct if the plugin is renamed or run under another host. The old role-based split ("a decision-recorder commits, a work-producer leaves changes staged," with its one-orchestrator/three-skills/one-agent counts) is **retired** — `complete-task`, `submit-task`, `derive-tasks`, `recommend-all-open-questions`, `modify-milestone-goal`, `define-`/`specify-`/`review-`/`goto-`/`finish-current-milestone`, and `capture-milestone-principle-updates` are all committers now. Per-skill subjects: `Manual-answer:` / `Recommendation-answer:` / `Alternative-answer: <Short Title>` (the three answer skills), `Task-completion: <task heading>` (`complete-task`), `Task-submission: <task title>` (`submit-task`), `Task-derivation:` / `Requirements-review:` / `Starting-state:` / `Recommendation-annotation:` / `Principle-capture: <milestone_id>`, `Milestone-definition:` / `Milestone-finish: milestone_<NN>_<slug>`, `Milestone-activation: milestone_<number>_<slug>`, `Goal-revision: <milestone_id>`. **Orchestrator commit granularity:** `complete-all-tasks` commits **per task** (subject `Tasklist-completion: <descriptor>`, the task `##` heading now in the commit **body**, not the subject, and committing the index the agent staged — its recorded change set plus the two task-list files — never `git add -A`), `answer-all-open-questions-with-recommendation` commits **per answer** (subject `Recommendation-answer: <Short Title>`, committed by the orchestrator), and `recommend-all-open-questions` and `derive-tasks` commit **once at the end of the run**. **No-op guard:** a committer whose pass changed none of its own paths (e.g. a `review-milestone-requirements` or `capture-milestone-principle-updates` pass that distilled nothing) stages nothing and commits nothing — no `--allow-empty` (the `core/shared/commit-procedure.md` dirty-own-path guard enforces this uniformly). **One exemption:** `init-milestone-base-workflow` stays **non-committing** (it leaves changes staged for the user) because a consuming project may not be a git repo or wants its own commit boundaries. Skills that change no files (`discuss-milestone-goal`, `discuss-open-question`, `discuss-new-task`, `ask-in-milestone-context`) are unaffected. **Still true:** the three answer subjects are the **only** markers `capture-milestone-principle-updates` walks — via a path-scoped `git log -E --grep='^(Manual-answer|Alternative-answer|Recommendation-answer): ' -- milestones/<milestone_id>/requirements.md` — and it reads the subject as a **provenance discriminator**, never as a harvest filter (`Manual-answer:` and `Alternative-answer:` mark the override signal it distills new principles from; `Recommendation-answer:` marks an accepted recommendation read as evidence only), while every other function-derived subject stays clear of those three anchors by construction, so capture never reads them.
- **Success-path console reporting is terse.** Every file-mutating, committing skill's success path prints **exactly one fixed terse status line** (e.g. "Milestone defined.", "All tasks completed.", "Recommendations embedded.") — carrying **no identifier** (no milestone id, task heading, Short Title, or commit subject) and **no next-step/handoff pointer** — instead of a prose re-narration of what it did, because the committed diff and `git log` are the durable record (re-narrating them to the console is redundant). An **orchestrator** prints **one such line for the whole run**, with **no per-item output** during its dispatch loop. Three classes of output deliberately **survive alongside** the terse line: (1) genuinely **git-absent decision-critical advisories** the commit never captured — `review-milestone-requirements`' convergence verdict and still-open list, `derive-tasks`' flag for any requirement it could not trace to a task, `submit-task`'s anchor-miss fallback advisory (nothing in the task list records that a `before:`/`after:` anchor missed), and the answer skills' newly-exposed-open-questions note — are still printed (only diff re-narration collapses), while a dependent block whose `<depends-on>` tag the cascade removed or whose embedded children it stripped gets **no** advisory from any answer skill (the answer commit's diff records it, and the cleared block is exactly the un-annotated state the next review or recommend pass surfaces, so it fails both halves of the git-absent-and-decision-critical test — and enumerating it would contradict the answer sweep's rule against listing recommendation-less questions); (2) a **no-op pass** whose `core/shared/commit-procedure.md` dirty-own-path guard fired prints a **distinct one-line** message stating nothing changed and briefly why (git holds no durable record of a no-op, so the console must carry it), never collapsing to the terse success line; (3) **failure and clean-stop paths** (parse errors, Short-Title/id mismatches, the `answer-open-question` redirect guard, no-matching-id stops) keep their **full explanatory messages**. Untouched entirely: the conversational skills (`discuss-milestone-goal`, `discuss-open-question`, `discuss-new-task`, `ask-in-milestone-context`) and the one non-committing exempt skill (`init-milestone-base-workflow`). Like the commit convention, this cross-cutting rule earns its **own standalone invariant** rather than a shared procedure file — there is **no** `core/shared/report-procedure.md`; the convention is authored **inline in each `SKILL.md`'s final reporting step**.
- `finish-current-milestone` must always run before `goto-next-milestone` — it records the completion and clears the current-milestone pointer to "none". `goto-next-milestone` checks for this "none" state and refuses to run without it. Finish's pointer-clear rides inside the **same** `milestones/README.md` edit as the completion summary, so the committed README already carries `Current milestone: none` and `goto-next-milestone`'s none-pointer precondition is recorded in git rather than left in a dirty tree. `capture-milestone-principle-updates` is **decoupled** from finish: it is an **on-demand** skill, runnable for any milestone id at any time, and its home in the "Ending a milestone" stage is a **convention** — finish is the natural moment to run it because a milestone's answer set is complete by then, and it is **never a precondition** (every answer commit lands during the requirements phase, so finish status carries no information the harvest needs; a run against a milestone still being answered harvests what exists so far, and a later run re-walks the same path to pick up the rest; backfill over long-finished milestones is explicitly allowed). It is a documented handoff, **not** a runtime recommendation `finish-current-milestone` prints (that runtime "recommends (never auto-runs)" print was retired under terse reporting), and `finish-current-milestone` never invokes it. It takes a **required `<milestone_id>`** — the directory name under `milestones/` exactly as `specify-milestone-starting-state` takes it, resolved as `milestones/<milestone_id>/` and validated **only** by the existence of that directory's `requirements.md` (a clean stop listing the present `milestone_*` directories otherwise); it never consults the current-milestone pointer, `core/shared/get-current-milestone.md`, or the `## Completed Milestones` table, and accepts no bare-number form. The id is consumed verbatim in three places: the path-scoped commit walk, the `Principle-capture: <milestone_id>` subject, and the repeat-capture guard's both-ends-anchored grep for that exact subject. Two **start-of-run guards** are each a one-line notice plus a single proceed confirmation, never a stop: a milestone that already carries a `Principle-capture: <milestone_id>` commit (only a committed capture is detectable — no empty commit records a no-op run, an accepted gap), and a store with uncommitted edits (on proceed the working-tree file, not `HEAD`, is the baseline the rewrite composes over). As the **sole writer** of `milestones/answer_decision_principles.md`, it walks the milestone's answer commits across **all three provenances** with a path-scoped `git log -E --grep='^(Manual-answer|Alternative-answer|Recommendation-answer): ' -- milestones/<milestone_id>/requirements.md` (the path is itself the lower boundary — it does not exist before `define-milestone-goal` — and the only boundary on the harvest), and because `core/shared/answer-procedure.md` removes the whole `<open-question>` block on answer, each commit's diff preserves as removed lines the `<question>`, every `<alternative>`, the cited `<applied-principle>` elements, and the `<recommendation option>` the user saw against the recorded decision. That diff read is **scoped to the answered block**: it locates the block among the removed lines by its `-<open-question id="…"` opening boundary and reads through its `-</open-question>` closing line, and **only the removed lines lying within those two boundaries feed the record** — every other removed line in the same diff, whether a whole sibling block the cascade mooted or a stray line the cascade cleared from a sibling block that still stands in the document (the orphan `<recommendation option>` / `<alternative id>` / `<depends-on>` lines its tidy and strip outcomes leave, exactly the tokens the reconstruct and agreement steps key on), is outside the answered block and contributes nothing. That one scoping sentence stays **element-agnostic** and never names `<depends-on>`, so no per-element "ignore this" list is started and the rule holds unchanged as further child elements are added. Each commit is classified by two tests: **agreement** (the recorded option against the removed recommended option — `non-override` when no recommendation existed, `agrees`, or `overrides`) and **body** (deliberated vs. bare, the same bare-cold-answer test phase 1 applies). **Override commits are the signal**: capture prompts for the override reason only where the body carries no user rationale (every non-agreeing `Alternative-answer:`, and a non-agreeing bare `Manual-answer:`), showing its best guess, one skippable prompt per commit, behind a one-shot accept-every-guess / skip-every-prompt / review-one-at-a-time choice so backfill over a forgotten milestone stays workable; a deliberated `Manual-answer:` is never re-prompted, an agreeing answer is never prompted (the why-did-you-prefer question would rest on a false premise), and a non-override `Manual-answer:` — every pre-sweep answer — is still a principle source through its body. **New principles come solely from override reasoning and deliberated manual bodies**; accepted recommendations (and agreeing alternative answers) are **evidence only** — a removed `<applied-principle>` citation reinforces that entry and shields it from pruning or narrowing in the pass, and an accepted rationale that contradicts an entry flags it for salvage. It distills those sources into generalizable keep/eliminate directives, drops the non-generalizable, dedups candidates **against each other** (a problem the retired per-answer capture never had), then composes **one whole-store rewrite** — adds, revisions, prunes, merges, generalizations, and shortenings together, so the store may **shrink as well as grow**: current reasoning takes precedence over an entry it contradicts, salvaged through a fixed ladder (narrow the scope clause → generalize → replace → delete only when nothing survives, tie broken by the shortest entry that still predicts both the prior citations and the override), every directive held to a soft 40–80-word target (flagged past about 100) under the "as short as it can be while still reading as an intuitive rule" test, no ceiling on entry count, and substantive changes gated on the harvested milestone's own evidence while form-only hygiene (shortening, merging plain duplicates) may reach any entry. It **snapshots** the baseline immediately before its one in-place write and prints **no diff and no store content**: the working tree is the review surface, the user reads `git diff`, requests changes in conversation (re-edited in place, no new snapshot), and **a single confirmation gates the commit, not the write** — there is no per-candidate or per-entry confirmation. On acceptance it commits path-scoped to `milestones/answer_decision_principles.md` (never `git add -A`) under `Principle-capture: <milestone_id>` via `core/shared/commit-procedure.md`, with a body of one short line per store change naming the change kind (add/revision/prune/merge/generalization) and the Short Title of the answer commit that drove it, composed at commit time against the final rewrite so it cannot drift from the diff; on explicit rejection it restores the **snapshot** (not `HEAD`, so a dirty-store proceed's hand-edits survive) and **exits without invoking `core/shared/commit-procedure.md` at all**, because that procedure's dirty-own-path guard would otherwise commit the user's surviving edits under capture's subject. The nothing-captured paths (empty commit range, no candidate and no flagged entry, a composed store identical to its baseline, a rejected rewrite) likewise never reach the shared procedure — they write nothing, commit nothing (no `--allow-empty`), and print one distinct line — which is what makes capture the second named no-op-pass case alongside `review-milestone-requirements`. Its restraint is deliberate: a principle informs *every* future recommendation, so a wrong or sloppy one corrupts the highest-value artifact in the loop, which is why it captures only genuinely reusable rules and never commits the store without the user's explicit review of the whole rewrite.
- `ask-in-milestone-context` is the on-demand, **read-only** Q&A skill: it answers an informational question about the current milestone and never mutates any file. It is not a pipeline step — it is usable any time across requirements/automation/follow-up. It grounds answers about finished work in the **live deliverables** (with the `TASKS_DONE.md` entry as intent and `git log`/`git show` as a supporting lens — the task→commit mapping is best-effort, since completions now land under a `Task-completion:` subject from the `complete-task` skill or a `Tasklist-completion:` subject with the heading in the body from `complete-all-tasks`, not keyed on the heading in the subject line). When a concrete next action surfaces it **offers** the owning skill (`discuss-open-question` to decide a question, `submit-task`/`discuss-new-task` to file an issue, `discuss-milestone-goal` to reshape the goal, `complete-task` to do a pending task) but performs none of their work itself — the asking/acting split is the whole point.
- `specify-milestone-starting-state`, `derive-tasks`, and the shared completion procedure (run by both the `complete-task` skill and agent) read the project's environment context (the project's domain context, working conventions, available tools, and how work is verified as done) from `CLAUDE.md`. Run `/init` once at project setup so `CLAUDE.md` documents it.
- `derive-tasks` owns decomposition, coverage, **and** the writing of the task list — it is the single writer on the derivation path. It proves every requirement maps to a brief (traceability matrix), orders the briefs by dependency, then writes them **itself**, in that order, into `TASKS_TODO.md` using the template and authoring guidelines from `core/shared/task-format.md`. Nothing on this path is delegated to a subagent, and there is no second authoring pass: a brief and a finished task section are the same altitude, so writing the brief down *is* the authoring step. What it must not do is push a section past brief altitude — never a flow, a low-level design, a contract surface, or a structured done-ness section; the completer derives all of that against the live project. It initializes `TASKS_TODO.md` to a clean header before writing the briefs, so its once-at-end path-scoped commit records exactly that run's derivation and its dirty-own-path no-op guard fires precisely when the run derived nothing.
- The **brief-level** task-section template lives in exactly one place: `core/shared/task-format.md`. That template is the `##` title heading, a 1–3 sentence description of what is to be achieved, why the milestone needs it, and how it would be verified (that last clause folded into the prose, never a labeled section), and the mandatory trailing `---` separator — and nothing else. There is deliberately **no** `Steps`, **no** `Provides`, **no** `Notes`, **no** `Success`, and no other structured done-ness heading under any name — see the altitude invariant below. The same file carries the four authoring guidelines, all format-independent and all carried over unchanged: unique 4–8 word title-cased **Title** (uniqueness is load-bearing — the completion procedure locates a task by case-insensitive partial heading match), **atomic scope**, **no open decisions**, and **quote numeric values, durations, thresholds, and configuration values** directly from `requirements.md`. Both authoring runners — `derive-tasks` and the `submit-task` skill — reference it via `{{PLUGIN_ROOT}}` and must never duplicate, restate, or vary it, and `core/shared/complete-procedure.md` parses exactly what it defines — the `complete-task` agent accordingly expects tasks as `##` sections in `TASKS_TODO.md`, each terminated by a `---` separator; two authors plus one parser is what keeps it shared and rules out drift between the batch and ad-hoc paths by construction. It holds the **format only**: where the task list lives, what context an author loads before writing, and where in the file a section is placed all belong to the runners.
- `submit-task` is a **skill only** — it has no agent counterpart, and `complete-task` is the plugin's only remaining skill+agent pair. The skill authors the task section **inline** in the user's conversation (so the authoring context survives for follow-up), and it additionally owns the triage (dedup + scope) and the position decision (`before:`/`after:`/`append`), because those need the whole-task-list view. `derive-tasks` never calls it: the batch path writes its own briefs, so the two authoring runners share the format file and nothing else.
- The completion procedure — find task, load environment and derive the acceptance bar, carry out, verify against that derived bar, move TODO→DONE augmented with it — lives in exactly one place: `core/shared/complete-procedure.md`. Neither the `complete-task` skill nor the agent may duplicate or restate those steps; both reference the shared file via `{{PLUGIN_ROOT}}`. The shared file is execution-neutral — it must not mention the `DONE`/`FAILED` return protocol, committing, or follow-up; those belong to the wrappers. `complete-task` exists as both a user-facing skill and an agent, differing only in *where* the shared procedure runs. The **skill runs it inline** in the user's conversation (so the work context survives for follow-up) and must never spawn the agent. The **agent runs it in an isolated subagent context** and adds the `DONE`/`FAILED` return protocol; it is what the `complete-all-tasks` orchestrator spawns per task. Choosing inline vs. isolated is the entire reason both exist — keep that the only difference.
- Every runner that reads or writes a milestone's task list resolves `<MILESTONE_DIR>` by following `core/shared/get-current-milestone.md` (which reads `milestones/README.md`) — `core/shared/complete-procedure.md`, `derive-tasks`, and the `submit-task` skill alike; none may use a hardcoded task-list path. `core/shared/task-format.md` resolves nothing: it defines the section format only, and milestone resolution now lives in its two authoring runners.
- Task altitude is split, and the dividing line is **what can be re-derived at completion time**. An authoring runner writes only what *cannot* be reconstructed from the milestone's goal + the live project: the title and the 1–3 sentence description (intent — what, why, and how it would be verified). Everything else belongs to `core/shared/complete-procedure.md`, which owns the flow and the **detailed design** (decided fresh against the live project and its deliverables) and, on top of that: it **derives the formal acceptance bar itself** from the task description plus the milestone's `requirements.md` — the task carries no authored acceptance criteria, so the derived bar, not anything in the task body, is what the work is verified against; it **resolves every cross-task reference by reading the prior task's live deliverable** in the project rather than a forward contract the task list promised (tasks run in dependency order, so that deliverable already exists by the time it is needed); and it **records the derived bar** in the `TASKS_DONE.md` entry, as a `**Verified:**`-labeled bullet list — one bullet per criterion, in the order verified, inside the same `##`/`---` section the TODO→DONE move writes — so every finished entry carries the brief plus the bar the work actually passed. The `**Verified:**` label is deliberately distinct from any authoring label, keeping the completion record from being read as an authoring contract and regrowing a done-ness section in `TASKS_TODO.md`. Keep task bodies minimal to save tokens; never push design detail — or a re-narration of the flow — back into authored tasks.
- **Skill Frontmatter**: Every user-facing skill (`SKILL.md`) must carry YAML frontmatter containing `name` and `description` keys. The host build (`scripts/build_hosts.py`) requires this on every host tree it renders — its `frontmatter-missing`/`frontmatter-invalid`/`frontmatter-keys` checks fail the whole selected build, writing nothing, if either key is missing or the block does not load. This bullet is the home of **every** rule governing the frontmatter `description` key, across all `core/skills/*/SKILL.md` and all `core/agents/*.md`. A description is **one short sentence of 25 words or fewer** naming only what that skill or agent does. **Shape:** a single independent clause — a qualifying rider set off by commas, an em dash, or parentheses is allowed, but the **semicolon and the colon are banned outright**, because those two marks introduce a second statement or an enumeration and are the route by which deleted material returns under the cap. **Parsing:** the raw frontmatter must load under `yaml.safe_load` with the `description:` line left **unquoted** (a plain YAML scalar — no colon-space, no leading indicator character, no trailing colon); the build has no re-quoting fallback — a `description:` line `yaml.safe_load` rejects fails its `frontmatter-invalid` check outright — and its `description-length` check enforces the 25-word cap below on every rendered tree. **Deleted, not relocated:** design provenance, mechanics (commit subjects, sequencing, dispatch counts, preconditions), cross-skill references, "Use when…" framing, and trigger-phrase lists are cut outright — a description is a **routing label, never a record**, so cut content carries no obligation to survive anywhere (cairn is invoked only by explicit slash command and is never auto-discovered, and `docs/skill-reference.md` and this file are the homes for that material). The 25-word cap is a hard pass/fail bar with **no exceptions**: a description that does not fit is reworded until it does, and overlap with a sibling skill is a wording problem to solve within the cap, never grounds for overage. An `core/agents/*.md` description keeps its **invocation contract**, compressed into that same sentence as a short clause naming what the prompt carries (the task's heading text, the question's Short Title); the separate "dispatched by X, not called directly by the user" note is provenance and is deleted.
- **Runtime files carry no editor-facing prose, and name no host.** The runtime layer (`core/skills/*/SKILL.md`, `core/agents/*.md`, `core/shared/*.md`) is loaded in full at run time, so it holds only what the runner acting on it needs. It is authored once for every host: every cross-reference uses the `{{PLUGIN_ROOT}}` placeholder that each host definition replaces with its own plugin-root literal (never a host's runtime syntax, and never followed by a resolve hint), and no `core/` file names a host — the build's `host-name-in-core` guard fails the whole build on one — so a sentence that depends on what a host can do names the **capability** (whether the host can continue a finished agent session; the agent's registry name under this plugin's namespace; the coding agent working in the repository) and never the host that has it. The one host-specific item is a field, not a sentence: the agents' Claude-only `color` frontmatter key stays in `core/` and is stripped by the Antigravity definition's `strip_frontmatter_keys` data, so the build carries structural rules only and no prose-rewrite rule that a rewording could silently stop matching. There are **no `## Rules` sections** anywhere in the layer: a rule that constrains one step lives in that step, and a rule that constrains the whole skill is a sentence in the file's opening description paragraph, never a bullet list under a heading. **Editor-facing rationale** — why a design is the way it is, what a later editor must not "fix" back — lives in these invariants and not in the runtime file, and a file **names its counterparts only in the one sentence its contract needs** rather than narrating their roles. Prose may be cut from a runtime file only where its content survives earlier in the same file, in a referenced shared procedure, or in an invariant here; point-of-use constraints, worked examples, and templates rendered once stay. YAML frontmatter `description` fields are outside this rule — the **Skill Frontmatter** invariant above is the home of every rule governing them.
- **Dispatched-agent return contracts are resumable and shape-checked.** A `FAILED` return from `complete-task` (agent) does **not** promise an untouched working tree — that promise was unimplementable once the task had edited files — but a **resumable** one: a failed or interrupted run leaves its partial work uncommitted in the tree, and `core/shared/complete-procedure.md`'s carry-out step treats any already-uncommitted changes as a previous run's partial work to **continue from, never redo or revert**. Do not restore the old untouched-tree promise. The read-only `recommend-open-question` agent's success return is the bare XML sub-elements with **no `DONE` line**, and its failure return ends in `FAILED: <reason>` with nothing else. Its **step 4 — and step 4 only** — is a **draft → self-check → emit** step: it opens by naming step 3's rendering as the draft (so that rendering can never be treated as the final message), its only test list is the same two shape tests the orchestrator runs (first non-whitespace text starts with `<alternative`, last non-whitespace text ends with `</recommendation>`), and the draft is revised until both pass. That rewrite **dropped the accumulated prohibition list whole** — the two tests subsume every entry of it — keeping only the positive "every grounding finding is spent inside the elements" redirect as drafting guidance, while leaving step 3's rendering specification (element shape, indentation, entity escaping) untouched by that rewrite — the `<depends-on>` element was added to step 3 later, under milestone 21, with step 4's two-test self-check still unchanged. `recommend-all-open-questions` no longer shape-checks the **raw** return: it judges every return in one fixed order as a single per-return pipeline — **last-line verdict, extraction, acceptance gate, then one repair**. (1) The **last non-whitespace line is read before any extraction**, and a line beginning `FAILED:` is an explicit failure — skipped with that reason and **never repaired**, even when an extractable region sits above it — which keeps one last-line-token convention across all three dispatch sites and is the only rule immune to a `FAILED:` token appearing legitimately inside element text; a `FAILED:` token anywhere else is then ordinary text. (2) Otherwise the region from the **first `<alternative` line through the last `</recommendation>` line** is extracted and everything outside it discarded — a stripped grounding summary or closing remark is not a failure in itself. (3) The extracted region passes a **single seven-test acceptance gate** combining the two boundary tests with five line-greps in the boundary-line CLI idiom (no `<open-question>`/`</open-question>`/`<question>`/`</question>` line, exactly one `<recommendation` opening line, at least one `<alternative id` line, an entity-unescaped case-folded `option` value equal to one of those `<alternative>` ids, and — the **seventh test** — every `<depends-on` line **resolving**: its `question` value equal to the `id` of an `<open-question>` block still present under `## Open questions` that carries embedded children, and its `option` value equal to one of that target block's `<alternative id` values, both compared entity-unescaped and case-folded), deliberately confined to the boundary tokens the downstream boundary-line CLI depends on so the gate needs **no XML parser and no second control path**; stray prose *between* the child elements is left to the agent's own self-check, because it breaks no consumer. Test 7 is the one test that **reaches outside the return into the document** — it re-slices the `## Open questions` section from the live file with the gather's boundary-line CLI, so the slice carries every earlier embed of the run — and it resolves **one hop only** (the target's own `<depends-on` lines are not followed), and adds **no cycle test** (a cycle is tolerated and handled by the answer sweep's origin promotion, keeping the gate the line-oriented check it was confined to). (4) Any miss — boundary or structural, a test-7 miss included — yields a reason string naming the failed test and takes **exactly one repair attempt**, never an immediate skip; a returned `<depends-on>` that fails to resolve is **never dropped or rewritten** by the orchestrator, which embeds a region exactly as accepted or not at all. The repair is **two-branch**: continue the **same** agent session where the host can continue a finished one (on Claude Code, `SendMessage` to the agent id the `Agent` tool returned, context intact, so the analysis is not redone), and only where the session cannot be continued — a host with no continuation equivalent, Antigravity today, or the handle is gone — **one fresh re-dispatch** with the same prompt plus the shape reminder; the runtime file keys the two branches on that capability and names neither host. The fresh re-dispatch is the continuation-**unavailable** fallback only; where continuation is available it is never the repair path. Repair happens **immediately, for that question** — the moment its return fails judging, and before the next question is dispatched — never by holding failed returns back and running the repairs as a second phase once the last first return has landed; because dispatch is sequential, the next dispatch simply waits until this question's repaired return has been judged and the question embedded or skipped, and at most one repair is spent per question. The corrective message is a **fixed one-paragraph template rendered once in the skill with a single slot**, filled with the same failed-test reason string the gate already derives (so the one attempt is aimed rather than blind, at no extra composition cost), naming the element order (`<alternative>`, `<applied-principle>`, `<depends-on>`, `<recommendation>`), quoting both shape tests verbatim and **never quoting the offending prose back**. Only a **second** failure is the **per-question skip** (block left byte-for-byte untouched, sweep continues, still-skipped Short Titles and reasons printed as a git-absent advisory alongside the terse line), never a run stop — so a prose, partial, or explanatory reply still can never reach the whole-block-replacement Edit, while a valid recommendation merely wrapped in surrounding text is now **recovered instead of dropped**. This **deliberately reverses** the earlier rule that a failing message "is discarded whole … never salvaged": the wording-only fix had already been applied once and the failure persisted (eight of ten dispatches in the milestone-19 sweep prefixed well-formed elements with a grounding summary and were skipped), so extraction plus one repair replaces it — do **not** restore the skip-only behaviour. The pattern is **scoped to this agent and this sweep**: `core/agents/complete-task.md`, `core/agents/answer-open-question-with-recommendation.md`, and the `complete-all-tasks` / `answer-all-open-questions-with-recommendation` orchestrators stay **byte-for-byte untouched**, because their contract is a **last-line token, not a whole-message shape** — prose above the token already passes, the returns carry no payload to salvage, and only trailing text *after* the token would reproduce the failure, which the repo records as never having occurred; extending extraction and repair to them would be precisely the general audit this change rules out.

## Development

This project supports both Claude Code and Google Antigravity from one source. The runtime layer — skills, agents, and shared procedures — is authored **once, host-neutrally, under `core/`**, and every host plugin is generated from it. Cross-references inside `core/` use the placeholder `{{PLUGIN_ROOT}}` (e.g. `{{PLUGIN_ROOT}}/shared/commit-procedure.md`) rather than any host's runtime syntax, and no file under `core/` names a host; the build guards both.

Each host is a **declarative definition directory** `scripts/hosts/<host>/` — `scripts/hosts/claude/` and `scripts/hosts/antigravity/` today. Its `settings.toml` declares, under one key set every host shares (a key with nothing to declare is left empty, never omitted): `plugin_name`; `plugin_root`, the literal that replaces `{{PLUGIN_ROOT}}` (`${CLAUDE_PLUGIN_ROOT}` for Claude Code, which resolves that variable to the installed plugin's root at load time; the workspace-relative path the Antigravity install extracts into, since Antigravity defines no plugin-root variable); `prose_drop_patterns`; `strip_frontmatter_keys` (the Antigravity definition strips the agents' Claude-only `color` key; the Claude definition strips nothing); `renames`; `exclude`; and the `[layout]` mapping each top-level directory of `core/` to its place in the host tree. Every other file in the definition directory is a template rendered to the same relative path in the host tree with its `{{VERSION}}` slot filled from the root `VERSION` file and its `{{NAME}}` slot from `plugin_name`: the Claude definition carries `.claude-plugin/plugin.json` and a `.claude-plugin/marketplace.json` with source `"."` (so a marketplace add of the distribution repository works with the same layout the monorepo root has always used), the Antigravity definition carries its schema-bearing `plugin.json`, and each carries the `README.md`, the slot-free `CONTRIBUTING.md` pointer, and the slot-free `.github/workflows/traffic-badges.yml` traffic-workflow template that land in its distribution repository — the pointer sends visitors to the root repository for issues, pull requests, and vulnerability reports, because a mirror cannot disable pull requests and a change made there would be overwritten by the next release, while `SECURITY.md` and `CODE_OF_CONDUCT.md` stay root-only and are never rendered or copied into a host tree. Adding a host means adding a definition directory; no host-specific Python exists, and the build applies every definition uniformly.

`uv run scripts/build_hosts.py [<host> ...] [--check]` is the one generic build. With no argument it builds every host whose definition directory exists; one or more host names build only those. It renders each selected host from `core/` into a temporary directory (placeholder substitution, frontmatter-key strips, renames, exclusions, the templates filled from `VERSION`, and a copy of the root `LICENSE`) and runs the **full validation gate** on the render before anything is written: `core/` names no host; every rendered `skills/<name>/SKILL.md` and `agents/<name>.md` has YAML frontmatter that `yaml.safe_load` accepts with `name` and `description`; every description is at or under 25 words; no `{{` is left anywhere in the tree outside a `${{` expression (the check is the one-character negative lookbehind `(?<!\$)\{\{` — a `{{` not immediately preceded by `$` — applied uniformly to every rendered file with no path-scoped exemption, template escape sequence, or definition key, so a GitHub Actions `${{ … }}` expression in a rendered workflow template passes while a bare `{{VERSION}}`, `{{NAME}}`, or `{{PLUGIN_ROOT}}` slot still fails the build); no other host's plugin-root literal appears in this host's tree; every occurrence of this host's own plugin-root literal followed by a path names a file in that tree; no frontmatter key the definition strips is still present; and every rendered manifest version slot, plus the root `marketplace.json` entry, carries exactly the `VERSION` literal. Any failure on any selected host exits non-zero listing every failing file and check, and no `hosts/<host>/` tree is touched; only when every selected host passes are the renders swapped into the committed `hosts/<host>/` trees. `--check` renders and validates the same way, then compares each render byte-for-byte against the committed `hosts/<host>/` tree, writes nothing, and exits non-zero listing the differing paths — the release's drift gate. The committed `hosts/claude/` and `hosts/antigravity/` trees are pure build output and are never hand-edited: rebuild after changing anything under `core/` or `scripts/hosts/` and commit the rebuilt trees with that change, so `main` always carries trees that match a fresh build. `--check` is what a maintainer or CI runs, never a git hook: the `.github/workflows/drift-gate.yml` workflow runs it on every push and pull request of the root repository, with no branch or `paths` filter (a `paths` list would be a hand-maintained second copy of the build's input set, the very drift the gate exists to catch), under `actions/checkout` and `astral-sh/setup-uv` pinned to full 40-character commit SHAs each followed by a `# vX.Y.Z` comment that is bumped by hand — no floating tag and no Dependabot — so a pull request always carries a drift-gate status and the README's `ci` badge reports `main`'s pushed HEAD.

The root `VERSION` file — the bare `MAJOR.MINOR.PATCH` literal on one line and nothing else — is the single source of truth for the plugin version. `uv run scripts/set_version.py <MAJOR.MINOR.PATCH>` writes it together with its three mirrored surfaces (`.claude-plugin/marketplace.json`'s entry, `pyproject.toml`, and `uv.lock`) in lockstep, all-or-nothing, and edits files only, never touching git or `gh`; it deliberately writes nothing under `hosts/`, because every host manifest and distribution README is rendered from its template with the version slot filled from `VERSION` by the build.

Releases are cut by the maintainer-only `/release-plugin <VERSION>` skill at `.claude/skills/release-plugin/SKILL.md` (outside `core/`, so no host build renders it). Its pre-flight runs `uv run scripts/build_hosts.py --check` and stops on any drift (remedy: rebuild, commit the sync as its own standalone commit, re-run) and checks with `gh repo view` that each host's distribution repository `uHappyLogic/cairn-<host>` exists, printing the exact creation commands rather than creating one; it then runs `set_version.py`, rebuilds, prepends the composed release notes to `CHANGELOG.md` as the `## <VERSION> — <YYYY-MM-DD>` entry (its milestone sections at `###`), stages `VERSION`, `pyproject.toml`, `uv.lock`, `.claude-plugin/marketplace.json`, `CHANGELOG.md`, and `hosts/` path-scoped, and makes one `Release: <VERSION>` commit that by construction changes only version slots and that changelog entry. From that commit on the committed entry, extracted from `HEAD:CHANGELOG.md`, is the notes' one source — shown at the pause and published to every release page on a fresh run and a resumption alike, so the changelog and the release pages carry identical text. After the monorepo push, bare `<VERSION>` tag, and GitHub release, it publishes each `hosts/<host>/` tree into its **distribution repository** — `uHappyLogic/cairn-claude` (the documented recommended install source) and `uHappyLogic/cairn-antigravity` — with git plumbing alone: `git commit-tree` on the tree object `HEAD:hosts/<host>` with the distribution `main` as sole parent (parentless on the first publish), pushed atomically to `refs/heads/main` and `refs/tags/<VERSION>`, followed by a GitHub release on that repository carrying the same notes. Those repositories are never hand-edited and carry no submodules; their issues, Discussions, wiki, and projects are disabled and each carries the rendered `CONTRIBUTING.md` pointer, so feedback routes here. Each of the three repositories (the monorepo included) also carries a `traffic-data` branch that only the `traffic-badges` workflow's daily `github-actions[bot]` pushes write (`totals.json` plus the two badge SVGs that the root README's first-screen adoption table reads for every repository and that each distribution README's two-badge strip above its title reads for its own) and that no build renders and no release touches, and holds the `TRAFFIC_TOKEN` repository secret — the maintainer's fine-grained PAT with Contents read-and-write on exactly these three repositories, kept in no local copy, so a re-set means regenerating the token on its settings page and running `gh secret set TRAFFIC_TOKEN` on all three together. The monorepo's own `.claude-plugin/marketplace.json` keeps pointing at `./hosts/claude` and is the maintainer's directory-marketplace source for running cairn straight from the working tree.

Outside contributions follow the proposal-first workflow `CONTRIBUTING.md` spells out, and the repository settings on `uHappyLogic/cairn` are set for it: Discussions and private vulnerability reporting are enabled, squash merges and the wiki are disabled, and blank issues are off so the issue chooser (bug, feature, and milestone-proposal forms plus the Q&A Discussions link) is the whole intake map. There is no plain-pull-request tier — a small fix is filed as an issue for the maintainer to make. A substantive change is filed as a proposal issue; the maintainer accepts it by running `/define-milestone-goal` on `main` **only while their own `Current milestone:` pointer reads `none`, and without activating it**, so the `Milestone-definition:` commit reserves `milestone_<N>_<slug>` and `main`'s pointer stays the maintainer's to hold; the contributor forks and branches from that commit, runs `/goto-next-milestone` first and the full pipeline through `/finish-current-milestone` on the branch (so its net change to the pointer line is nil), syncs from `main` by merge only — never rebase — and only while `main`'s pointer reads `none`, aborting a pointer conflict rather than resolving it, rebuilds `hosts/` and passes `--check`, and opens the pull request, which is merged as a merge commit so the milestone commits survive for release notes and for `/capture-milestone-principle-updates`, which the maintainer runs after the merge. An abandoned contribution leaves only its defined directory on `main`, reverted or left as a `/goto-next-milestone` candidate.

## Milestone Workflow

This project uses the milestone-driven workflow. Each milestone lives at
`milestones/milestone_<N>_<slug>/` with `requirements.md`, `TASKS_TODO.md`, and
`TASKS_DONE.md`. `milestones/README.md` is the source of truth for which milestone
is current. Never advance the pointer without first running
`/finish-current-milestone`.
