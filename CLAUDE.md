# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A Claude Code plugin (`cairn`) that provides a milestone-driven development workflow. It ships as a set of skills and a couple of agents that move a project from a vague idea through discussion, planning, completion, and archival — one milestone at a time.

## Repository layout

```
.claude-plugin/plugin.json   — plugin manifest (name, version, author)
.claude-plugin/marketplace.json — single-plugin marketplace manifest (installable via /plugin marketplace add uHappyLogic/cairn)
skills/<skill-name>/SKILL.md — one skill per directory; the SKILL.md is the full skill definition
agents/complete-task.md — task-completion subagent invoked by complete-all-tasks skill
agents/submit-task.md — task-authoring subagent invoked by derive-tasks (bulk)
agents/recommend-open-question.md — read-only recommendation subagent (non-interactive twin of discuss-open-question) invoked once per question by the recommend-all-open-questions orchestrator; returns a ready-to-embed Alternatives+Recommendation sub-block (bearing-principle citations rendered as `> **Applied principle:**` lines above the liftable `> **Recommendation:**` anchor), never edits documents
agents/answer-open-question-with-recommendation.md — file-editing subagent (the divergent one): lifts a question's embedded recommendation, records it via shared/answer-with-recommendation-procedure.md, and commits its own path-scoped answer under Recommendation-answer:, returning DONE/FAILED — invoked once per question by the answer-all-open-questions-with-recommendation orchestrator; isolates mutation (not reasoning) unlike the read-only answer/recommend subagents
shared/complete-procedure.md — single source of truth for the complete-one-task procedure, followed inline by the complete-task skill and in isolation by the complete-task agent
shared/submit-procedure.md — single source of truth for the author-and-insert-one-task procedure, followed inline by the submit-task skill and in isolation by the submit-task agent
shared/answer-procedure.md — single source of truth for recording an answer (locate question block by Short Title → remove the whole contiguous blockquote run → fold decision into ## Decisions → cascade), referenced by answer-open-question and shared/answer-with-recommendation-procedure.md (which composes over it with a lifted ANSWER)
shared/answer-with-recommendation-procedure.md — single source of truth for the lift-then-delegate procedure (locate the question's blockquote run → lift + strip its > **Recommendation:** anchor, with a no-anchor guard → delegate to shared/answer-procedure.md with the derived ANSWER), composing over the execution-neutral recording core; followed inline by the answer-open-question-with-recommendation skill and in isolation by the answer-open-question-with-recommendation agent
shared/recommend-procedure.md — single source of truth for the principle-aware "alternatives + single recommendation for one question" analytical core (execution-neutral, reads the fixed-path principle store in place, no >-blockquote markup), referenced by the discuss-open-question skill and the recommend-open-question agent
shared/get-current-milestone.md — single source of truth for resolving <MILESTONE_DIR> from the grep-able pointer line in milestones/README.md
milestones/answer_decision_principles.md — project-wide answering-principle store at the milestones/ root, shared across all milestones (above any <MILESTONE_DIR>); the loop's one fixed-path artifact
LICENSE                      — MIT license
README.md                    — authoritative workflow documentation and skill reference
```

No build system, no tests, no dependencies. Everything is plain Markdown.

## Skills and the workflow they encode

The skills form a linear pipeline. Each skill's SKILL.md defines its exact behaviour:

```
init-milestone-base-workflow    ← one-time bootstrap: create milestones/ + milestones/README.md
discuss-milestone-goal          ← optional sharpening conversation, creates no files
define-milestone-goal           ← creates milestones/milestone_<N>_<slug>/ with requirements.md, TASKS_TODO.md, TASKS_DONE.md
specify-milestone-starting-state ← fills "Relevant starting state" in requirements.md
review-milestone-requirements   ← repeatable loop engine: each pass reconciles existing questions against recorded decisions, surfaces new gaps, reports convergence; run repeatedly
recommend-all-open-questions    ← orchestrator (batch form of discuss-open-question): sweeps open/deferred questions once, dispatches one read-only recommend-open-question subagent each, embeds the returned Alternatives+Recommendation sub-block beneath the unchanged one-line header; sole mutator, mutate-but-do-not-commit (path-scoped stage), idempotent skip of already-recommended blocks, no clean-tree precondition
recommend-open-question         ← (agent, in agents/) read-only recommendation subagent: grounds in the live project and the principle store, returns one question's Alternatives+Recommendation sub-block (bearing-principle > **Applied principle:** citations above the liftable > **Recommendation:** anchor), never edits documents
discuss-open-question           ← structured conversation about one open question; sources its alternatives+recommendation core from shared/recommend-procedure.md and adds its own "what would change your mind" layer; on a decision offers answer-open-question, and if the goal itself must shift also offers modify-milestone-goal — when both apply, modify-milestone-goal runs first so the answer records against the revised goal
answer-open-question            ← records a literal-answer decision in requirements.md AND commits it (subject Manual-answer: <Short Title>, rationale in the body); no longer chains to capture. Literal-only: recording an embedded recommendation moved to answer-open-question-with-recommendation, and the retired sentinel "record the recommendation" (exact whole-string) is now a redirect guard that stops without recording and points there instead
answer-open-question-with-recommendation ← (skill) user-facing entry for one named question: lifts its embedded > **Recommendation:** anchor and records+commits it inline (subject Recommendation-answer: <Short Title>, path-scoped git add), running shared/answer-with-recommendation-procedure.md so the context stays for follow-up; never spawns the agent
answer-open-question-with-recommendation ← (agent, in agents/) file-editing subagent: runs shared/answer-with-recommendation-procedure.md in isolation and commits its own path-scoped answer under Recommendation-answer:, returns DONE/FAILED — dispatched per-question by the answer-all-open-questions-with-recommendation orchestrator
answer-all-open-questions-with-recommendation ← orchestrator: sweeps open/deferred questions carrying an embedded recommendation, dispatches the file-editing answer-open-question-with-recommendation agent strictly sequentially (gather once most-significant-first, per-question re-read/skip on already-cascaded blocks), one commit per answer; the agent commits — the orchestrator never does
modify-milestone-goal           ← revises the ## Goal of an already-defined milestone (act-only); edits Goal only, surfaces downstream impact, never cascades; offered by discuss-open-question, invisible to answer-open-question
derive-tasks                    ← decomposes requirements.md into ordered briefs, proves coverage, spawns submit-task agent per brief
submit-task                     ← (skill) user-facing entry for a single ad-hoc issue: triages + positions, then runs shared/submit-procedure.md inline so the authoring context stays for follow-up
submit-task                     ← (agent, in agents/) bulk per-task authoring for derive-tasks: runs shared/submit-procedure.md in isolation, returns DONE/FAILED
discuss-new-task                ← clarifies a vague/large issue into briefs, then hands off to the submit-task skill
complete-all-tasks              ← orchestrator: spawns complete-task agent per task, commits after each
complete-task                   ← (skill) user-facing entry for one ad-hoc task: runs shared/complete-procedure.md inline so the work context stays for follow-up
complete-task                   ← (agent, in agents/) single-task completion subagent: runs shared/complete-procedure.md in isolation, returns DONE/FAILED
ask-in-milestone-context        ← (on-demand, read-only) answers a free-form informational question grounded in the current milestone — goal, decisions, done/pending tasks, and the live code those tasks produced; never edits, offers a handoff when a concrete next action surfaces
finish-current-milestone        ← writes completion summary to milestones/README.md, clears current-milestone pointer to "none" in milestones/README.md, updates CLAUDE.md only for lasting changes; recommends (never auto-runs) capture-milestone-principle-updates
capture-milestone-principle-updates ← optional finish-time follow-up recommended by finish-current-milestone: distills answering principles from the just-finished milestone's Manual-answer: commits into the principle store; new sole writer of milestones/answer_decision_principles.md
goto-next-milestone             ← activates an already-defined milestone: scans milestones/ for a defined-but-not-yet-active directory, updates milestones/README.md to point to it
```

## Milestone file structure

Each active milestone lives at `milestones/milestone_<N>_<slug>/` and contains exactly:

- `requirements.md` — Goal, Relevant starting state, decisions, open questions
- `TASKS_TODO.md` — pending tasks ordered by priority (highest first), `##` headings + `---` separators
- `TASKS_DONE.md` — completed tasks appended in the same format

`milestones/README.md` is the source of truth for which milestone is current.

## Invariants to preserve when editing skills

- `init-milestone-base-workflow` is the one-time bootstrap; it is additive and idempotent — it never overwrites an existing `milestones/README.md` or `CLAUDE.md`, only creating missing files and appending missing sections. It must leave `milestones/README.md` with a `Current milestone:` pointer line.
- `answer-open-question` splits its arg on the first `.` — title before, answer after.
- `review-milestone-requirements` (renamed from the old `highlight-milestone-requirements-open-questions`) is the repeatable engine of the requirements-iteration loop: each pass **reconciles** the existing `Open question`/`Deferred` blocks against the recorded `## Decisions`, **surfaces** new gaps, and **reports convergence** (no `> **Open question` blocks remaining is exactly `derive-tasks`'s precondition; Deferred blocks may carry forward). It is the **only** skill besides the answer path that may remove a question block, and only as *cleanup of already-recorded state*: it may delete a block solely when it can cite a `## Decisions` entry that already covers it, or dedup an exact repeat — when in doubt it flags ("possibly resolved — confirm") rather than deletes, and every removal is reported. It **never records a decision or answers a question**: folding a decision into `## Decisions` and cascading to mooted siblings stays scoped to `shared/answer-procedure.md` (used by `answer-open-question` and `shared/answer-with-recommendation-procedure.md`). This boundary — tidy the questions section vs. record an answer — is the whole reason the two stay separate.
- The answer-recording mechanism (locate the question block by Short Title → fold the decision into `## Decisions` as clean prose → cascade to mooted entries) lives in exactly one place: `shared/answer-procedure.md`. `answer-open-question` and `shared/answer-with-recommendation-procedure.md` both reference it via `${CLAUDE_PLUGIN_ROOT}` and never restate the steps. That shared file is **execution-neutral** — it takes a resolved Short Title + answer and never mentions arg-parsing, committing, or the capture chain.
- `recommend-all-open-questions` is the batch form of `discuss-open-question`, but is **mutate-but-do-not-commit**, not committing. It gathers the Open/Deferred entries **once** and walks straight through, deliberately omitting the machinery a decision-recording sweep would need — no gather-order (cascade-parent-first proxy), no per-question live-re-check/skip against a mutating document, no outer re-gather loop, and **no clean-working-tree precondition** — precisely because it records **no decisions** and triggers **no cascades**, so the question set never shrinks under it. It is the **sole document mutator**: it embeds each returned recommendation sub-block directly beneath the **unchanged one-line question header** (which stays greppable on line 1), keeping the whole entry one contiguous `>` run with empty-`>` internal separation. It is **idempotent** — it skips any block already carrying a `> **Recommendation:**` anchor and annotates only those lacking one; the escape hatch for a stale recommendation is to delete that block's sub-block (header intact) and re-run, and there is deliberately **no** `refresh`/selectable mode (it stays argument-free). It stages only its own path-scoped `git add <MILESTONE_DIR>/requirements.md` (never `git add -A`) and stops; the durable git record is the eventual `Recommendation-answer:` commit (from `/answer-open-question-with-recommendation` or the `/answer-all-open-questions-with-recommendation` sweep, which lift the embedded anchor as the answer), not the transient recommendation scaffolding.
- The `recommend-all-open-questions` orchestrator owns **all** document mutation and the staging; its `recommend-open-question` subagent (one dispatch per question, the non-interactive twin of `discuss-open-question`) is **read-only** — it reads `requirements.md`, the live code, and the project-wide principle store to ground honest alternatives but returns only the ready-to-embed sub-block as its final message, and the orchestrator does all embedding and staging. **Recommendation independence:** the per-question dispatches are independent (a recommendation decides nothing, so nothing may build on one) and may be parallelized; "isolation" constrains the **orchestrator** — it never feeds one question's recommendation into another — and does **not** narrow the subagent's read-only grounding (which incidentally sees the one-line sibling question headers). What the subagent must never do is treat another question's recommendation as an input.
- `shared/answer-with-recommendation-procedure.md` is the single source of truth for the "lift the embedded recommendation, then record it" logic, referenced (never restated) via `${CLAUDE_PLUGIN_ROOT}` by both the `answer-open-question-with-recommendation` skill and its agent. It is **execution-neutral**: given a resolved SHORT TITLE it locates the question's blockquote run, lifts and strips the `> **Recommendation:** <chosen option> — <rationale>` anchor (with a **no-anchor guard** that stops without changes when the recommend sweep never annotated the block), then delegates to `shared/answer-procedure.md` with the derived ANSWER. It **composes over** the recording core exactly as `complete-task`/`submit-task` layer their shared procedures — the lift lives here, not in `answer-procedure.md`, so that core's **ANSWER-as-input contract** (shared with literal `answer-open-question`, which must never inherit lift behavior) stays unchanged.
- The `answer-open-question-with-recommendation` skill + agent follow the established skill+agent pattern (one execution-neutral shared procedure, run **inline** by the skill so context survives, **in isolation** by the agent with the `DONE`/`FAILED` return protocol), but with a deliberate divergence from the read-only-subagent design of the plugin's other per-question subagents (e.g. `recommend-open-question`): here the **mutation** is what's isolated into the agent, not the reasoning. The recommendation is **pre-computed** by the recommend sweep, so there is no candidate elimination worth isolating; what dispatching a per-question **file-editing** agent buys the sweep orchestrator is keeping the expensive per-question edit out of its own context. This inversion (mutation-in-agent, not read-only-subagent) is documented so a later editor does not "fix" the agent back toward the read-only-subagent norm.
- In `answer-all-open-questions-with-recommendation`, the file-editing **agent commits its own answer** — path-scoped `git add <MILESTONE_DIR>/requirements.md` (never `git add -A`), subject `Recommendation-answer: <Short Title>`, returning only `DONE`/`FAILED` — and the orchestrator **purely dispatches and sequences, never committing**. This is a **second, layered** divergence from `complete-task`'s "committing is the orchestrator's job": the agent owns the one-commit-=-one-answer guarantee (path-scoped staging so a dirty tree cannot contaminate its commit; no partial commit on `FAILED`, whose failure path leaves the tree as it found it). The orchestrator sequences its own dispatches — gather once most-significant-first (a cascade-parent-first proxy), and before each dispatch re-read `requirements.md` and skip the question when a prior answer's cascade already removed its block, with `shared/answer-procedure.md`'s step-2 stop-on-missing-block as the backstop — running **strictly sequentially** because cascades mutate the shared document. Documented as its own invariant so it is not reverted toward orchestrator-commits.
- Recommendation-derived answers — from **both** the single-question `answer-open-question-with-recommendation` skill and the sweep's agent — commit under the distinct subject `Recommendation-answer: <Short Title>`, which does **not** match the `^Manual-answer:` grep that finish-time `capture-milestone-principle-updates` walks, so capture **never harvests** them. The rationale: a recommendation-answer's commit body is the `recommend-open-question` agent's rationale (batch-accepted on the sweep path), not user-deliberated reasoning, so it must stay outside the capture grep — with **no** change to capture's grep logic. The distinct subject is the honest git-log provenance discriminator, matching the house style where the subject *is* the provenance marker.
- `shared/recommend-procedure.md` is the single source of truth for the "alternatives + single recommendation for one question" analytical core, referenced (never restated) by both the `discuss-open-question` skill and the `recommend-open-question` agent via `${CLAUDE_PLUGIN_ROOT}`. It is **execution-neutral** and holds only logical content: the grounding discipline (live code over memory), the **Alternatives** requirement (2–4 genuinely realistic options, no strawmen/padding, each carrying what-it-is / key advantage / key drawback), and the single **Recommendation** (one option, direct hedge-free rationale, plus the name-what-breaks-the-tie rule). It is **principle-aware**: its grounding step reads the project-wide principle store `milestones/answer_decision_principles.md` **in place** (naming that fixed `milestones/`-root path directly — the confirmed principles are not a caller-supplied input alongside QUESTION), and a confirmed principle that bears on the question is a **weighted advisory factor** — a strong default in favor of the option it supports, which **merit may override only for a specifically stated reason**, and which is **cited** in the recommendation whenever it influenced the pick (never a binding filter or veto, never a candidate drop, never silently applied). When no principle bears, the alternatives+recommendation contract is exactly as in a project with no principles. It carries **no** `>`-blockquote markup and **no** "what would change your mind" section — the boundary is deliberate: `discuss-open-question` owns the WWCYM layer, the conversational framing, and the on-decision follow-up offers; the `recommend-open-question` agent owns the literal blockquote rendering (the empty-`>` separation discipline, the `> **Applied principle:**` citation lines, and the `> **Recommendation:**` anchor text). This mirrors how `shared/answer-procedure.md` is execution-neutral while its wrappers own arg-parsing and committing.
- The `recommend-open-question` agent renders each confirmed principle that bore on the recommended pick as its own `> **Applied principle:** <Short Title>` line, stacked immediately **above** the last-line `> **Recommendation:**` anchor — **one line per bearing principle** (the multi-principle case is pure repetition of the single-line form, with no new label and no in-line list syntax, so each citation stays atomic and independently greppable), and **none at all** when no principle bears (the sub-block then renders exactly as it did before principle-awareness). The citation is **never** baked into the anchor rationale: because `/answer-open-question-with-recommendation` (and the `/answer-all-open-questions-with-recommendation` agent) lift only the `> **Recommendation:**` anchor verbatim, keeping it the run's last line holds the recorded `## Decisions` prose **provenance-free by construction**, and `shared/answer-procedure.md`'s whole-run removal clears the extra `> **Applied principle:**` lines on answer.
- The principle store `milestones/answer_decision_principles.md` is now consumed by the **recommendation core** — read in place by the principle-aware `shared/recommend-procedure.md` that both `/discuss-open-question` and the recommend sweep's `recommend-open-question` agent run — rather than by an auto-answer engine. Its data and per-entry format are unchanged, and `capture-milestone-principle-updates` remains its **sole writer**; only the consumer pointer moved, from a binding auto-answer sweep to the recommendation advisor that cites it.
- `answer-open-question` is **literal-only plus a redirect guard**. The old **record-recommendation mode** — the whole-string `record the recommendation` sentinel that located a block and lifted its `> **Recommendation:**` anchor as the `ANSWER` — is **removed** from this skill; lifting an embedded recommendation now lives in `answer-open-question-with-recommendation` (skill + agent, over `shared/answer-with-recommendation-procedure.md`). What survives here is a **targeted redirect guard**, not a live feature: after the first-`.` split, the parsed answer text is compared — trimmed and lowercased — against the retired sentinel `record the recommendation` as an **exact whole-string** match (**never a substring**, so a literal answer merely containing those words takes the literal path). On an exact match the skill **stops without recording or committing anything** and prints a redirect pointing at `/answer-open-question-with-recommendation`; this intercepts a migrating user's old command at the moment it would otherwise silently record the sentinel phrase as a decision, and its message doubles as discovery. It is targeted migration scaffolding that fits the skill's clean-stop-and-point pattern (like a Short-Title mismatch), not a revived mode. Any other (non-sentinel) answer text is a literal answer; the existing first-`.` split, the literal-answer path, and the `Manual-answer:` commit rules are unchanged.
- `shared/answer-procedure.md` step 4 removes the **entire contiguous `>`-prefixed run** containing the located header — the unchanged one-line header plus any recommendation sub-block the recommend sweep embedded beneath it (internal gaps rendered as empty `>` lines, bounded by the blank lines that separate entries) — not just line 1. This covers both cases uniformly: the bare one-line header with no sub-block is the degenerate single-line run removed exactly as before. Step 2's locating still keys off the unchanged one-line header, steps 3/5/6 (analyse / fold / cascade) are unchanged, and the file stays execution-neutral.
- `answer-open-question` records a decision and then **commits** it — it no longer chains to any capture skill. Principle capture has moved off the per-answer path to milestone finish (`capture-milestone-principle-updates`); the rationale behind each decision is preserved in the commit body so finish-time capture can distill it later.
- `modify-milestone-goal` is the **only** skill that mutates the `## Goal` of an already-defined milestone (`define-milestone-goal` writes it once at creation; `discuss-milestone-goal` is conversational and pre-creation). It is **act-only**: it edits the `## Goal` section and nothing else — never `## Decisions`, the question blocks, `## Out of Scope`, or the task lists. Because the Goal is the root of the requirements tree, the skill **surfaces but never cascades** the downstream impact (which Decisions/questions/Out-of-Scope/derived tasks the new goal may invalidate) and points the user at `/review-milestone-requirements` to reconcile — folding those consequences in silently would have too large a blast radius. It is offered by `discuss-open-question` (which still edits nothing itself — it proposes the revised goal and the user confirms) and is **deliberately invisible to `answer-open-question`**: recording an answer and reshaping the objective are different acts, and the answer path must never reach goal mutation. It records no answering principle (a goal change yields none) and does not commit.
- Correcting a bad recorded answer has no dedicated skill: it is the uniform **revert-then-re-answer** flow. Revert the answer's commit (by the one-commit-=-one-answer invariant the revert restores the reopened question block and removes the folded decision in one shot — the `Manual-answer:` commit for a manual answer, the `Recommendation-answer:` commit for a recommendation-derived one), then re-record via `/answer-open-question` (or `/answer-open-question-with-recommendation` when a fresh recommendation is re-embedded). Because a confirmed principle is now only a **weighted advisory factor** cited in recommendations — never a binding auto-answer — a principle that steered a recommendation wrong is reconciled at milestone finish: the corrective re-answer's `Manual-answer:` commit is picked up by `capture-milestone-principle-updates`, whose revise-vs-add-by-overlap discipline offers the corrected directive as a revision of the bad principle. For an urgent "this principle is actively wrong, remove it now" case the user hand-edits the plain-Markdown store `milestones/answer_decision_principles.md` directly.
- The `complete-task` agent expects tasks as `##` sections in `TASKS_TODO.md`, each terminated by a `---` separator.
- One orchestrator commits, **two** individual skills are the deliberate, documented committing exception (widened in milestone 7 from one to two — a bounded broadening, not a proliferating ad-hoc list), and one file-editing **agent** commits (the layered divergence documented in its own invariant above); every other individual skill never commits — including the `complete-task` skill, which leaves an ad-hoc task's changes staged for the user, and `capture-milestone-principle-updates`, which leaves its principle-store edit staged. The committing-vs-staging line tracks what a skill **produces**: a decision-recorder commits its decision atomically under a greppable subject, while a work-producer (`complete-task`/`submit-task`) leaves changes staged. `complete-all-tasks` (the one committing orchestrator) commits after each successful task. `answer-open-question` commits exactly its own path-scoped `requirements.md` manual-answer edit (`git add <MILESTONE_DIR>/requirements.md`, never `git add -A`) — subject `Manual-answer: <Short Title>`, the decision's rationale in the body. The second committing skill, `answer-open-question-with-recommendation`, likewise commits its own path-scoped `requirements.md` edit under subject `Recommendation-answer: <Short Title>`. Note the `answer-all-open-questions-with-recommendation` **orchestrator does not itself commit** — its per-question agent does — so the one-committing-orchestrator count holds.
- `finish-current-milestone` must always run before `goto-next-milestone` — it records the completion and clears the current-milestone pointer to "none". `goto-next-milestone` checks for this "none" state and refuses to run without it. `finish-current-milestone` also **recommends (never auto-runs)** `capture-milestone-principle-updates` as an optional post-finish follow-up.
- `capture-milestone-principle-updates` is the **new sole writer** of the principle store `milestones/answer_decision_principles.md` and runs *after* `finish-current-milestone` has already cleared the pointer to "none". Because the pointer is "none" by then, it resolves `<MILESTONE_DIR>` from the **last row of the `## Completed Milestones` table** in `milestones/README.md` — explicitly **not** via `shared/get-current-milestone.md`. It walks that milestone's manual answers with a path-scoped `git log --grep='^Manual-answer: ' -- <MILESTONE_DIR>/requirements.md` (the path is itself the lower boundary — it does not exist before `define-milestone-goal`). It distills the rationale in those commit bodies into generalizable keep/eliminate directives, deduping candidates against each other, then confirms each per-candidate revise-vs-add against the live store; it leaves its edit **staged** and does not commit.
- Open questions in `requirements.md` must be fully resolved before `derive-tasks` can run.
- `ask-in-milestone-context` is the on-demand, **read-only** Q&A skill: it answers an informational question about the current milestone and never mutates any file. It is not a pipeline step — it is usable any time across requirements/automation/follow-up. It grounds answers about finished work in the **live code** (with the `TASKS_DONE.md` entry as intent and `git log`/`git show "<task heading>"` as a supporting lens — the task→commit mapping is best-effort, since ad-hoc `complete-task` runs leave changes staged/uncommitted). When a concrete next action surfaces it **offers** the owning skill (`discuss-open-question` to decide a question, `submit-task`/`discuss-new-task` to file an issue, `discuss-milestone-goal` to reshape the goal, `complete-task` to do a pending task) but performs none of their work itself — the asking/acting split is the whole point.
- `specify-milestone-starting-state`, `derive-tasks`, and the shared completion procedure (run by both the `complete-task` skill and agent) read the project's environment context (tech stack, build/test commands, MCP tools, conventions) from `CLAUDE.md`. Run `/init` once at project setup so `CLAUDE.md` documents it.
- `derive-tasks` owns decomposition and coverage only; it must not author task bodies itself. It proves every requirement maps to a brief (traceability matrix), then submits briefs **in dependency order** to the `submit-task` agent with `POSITION: append`, spawning the agents **sequentially** (they all mutate the same `TASKS_TODO.md`).
- The task body template (`##` title, description, optional **Provides**, optional **Notes**, **Success**, trailing `---`) lives in exactly one place: `shared/submit-procedure.md`. The `submit-task` skill, the `submit-task` agent, and `derive-tasks` must not duplicate it. There is deliberately **no** `Steps` section — see the altitude invariant below.
- The author-and-insert procedure — find milestone, load context, author the task (template + authoring guidelines), insert at the given POSITION — lives in exactly one place: `shared/submit-procedure.md`. Neither the `submit-task` skill nor the agent may duplicate or restate those steps; both reference the shared file via `${CLAUDE_PLUGIN_ROOT}`. The shared file is execution-neutral — it takes BRIEF + POSITION, inserts at the POSITION it is given, and never decides global ordering, mentions the `DONE`/`FAILED` return protocol, triages, or follows up; those belong to the wrappers.
- `submit-task` exists as both a user-facing skill and an agent, differing in *where* the shared procedure runs **and** in what surrounds it. The **skill runs it inline** in the user's conversation (so the authoring context survives for follow-up) and must never spawn the agent; the skill additionally owns the triage (dedup + scope) and the position decision, because those need the whole-task-list view that `derive-tasks` does not delegate. The **agent runs it in an isolated subagent context** (taking BRIEF + POSITION from its prompt) and adds the `DONE`/`FAILED` return protocol; it is what `derive-tasks` spawns per brief in bulk. Neither may decide global ordering — the caller owns it.
- The completion procedure — find task, load environment, carry out, verify success criteria, move TODO→DONE — lives in exactly one place: `shared/complete-procedure.md`. Neither the `complete-task` skill nor the agent may duplicate or restate those steps; both reference the shared file via `${CLAUDE_PLUGIN_ROOT}`. The shared file is execution-neutral — it must not mention the `DONE`/`FAILED` return protocol, committing, or follow-up; those belong to the wrappers.
- `complete-task` exists as both a user-facing skill and an agent, differing only in *where* the shared procedure runs. The **skill runs it inline** in the user's conversation (so the work context survives for follow-up) and must never spawn the agent. The **agent runs it in an isolated subagent context** and adds the `DONE`/`FAILED` return protocol; it is what the `complete-all-tasks` orchestrator spawns per task. Choosing inline vs. isolated is the entire reason both exist — keep that the only difference.
- Both shared procedures (`shared/submit-procedure.md` and `shared/complete-procedure.md`) always resolve `<MILESTONE_DIR>` by following `shared/get-current-milestone.md` (which reads `milestones/README.md`) — they must never use a hardcoded task-list path.
- Task altitude is split, and the dividing line is **what can be re-derived at completion time**. The shared submit procedure authors only what *cannot* be reconstructed from the goal + live code: the `Description` (intent), the `Success` bar, the optional `Provides` (the forward contract — names/thresholds sibling tasks reference before this task is built), and the optional `Notes` (non-obvious gotchas that would cost the completer a discovery round). The shared completion procedure owns everything re-derivable — the flow itself and the **detailed design** (exact code, insertion points, assertion wording, decided fresh against the live codebase). The submit procedure must **not** author a step-by-step flow under any heading (no `Steps`); `Provides`/`Notes` are omitted entirely when empty. Keep task bodies minimal to save tokens; never push line-by-line build detail — or a re-narration of the flow — back into authored tasks.

## Milestone Workflow

This project uses the milestone-driven workflow. Each milestone lives at
`milestones/milestone_<N>_<slug>/` with `requirements.md`, `TASKS_TODO.md`, and
`TASKS_DONE.md`. `milestones/README.md` is the source of truth for which milestone
is current. Never advance the pointer without first running
`/finish-current-milestone`.
