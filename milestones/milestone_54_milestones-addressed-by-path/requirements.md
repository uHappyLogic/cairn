## Decisions

### The milestones tool

- **Discovery pattern.** The milestones tool counts every tracked match of `**/milestones/*/requirements.md` as a live milestone, with no exclusion rule, and the `tasks` join uses the same pattern. This repository takes its agy fixture out of the pattern instead: the fixture project's container is tracked under a name the pattern does not match (such as `tests/fixtures/agy_project/milestones.fixture/`), and the agy suite's `seeded_repo` fixture renames it to `milestones/` when it copies the project into its temporary repository, so the installed skills still find a normal root container there. `live` lists only this repository's own milestones, and `2202e59` keeps its placeholder in `tasks`, since history is not rewritten.

- **One tool.** All six queries (`live`, `gate`, `tasks`, `milestones`, `summary`, `record`) are subcommands of the one `core/tools/milestones.py`, which keeps its name, its one parser, its one `Error:` contract and help text, and its one git runner with the fixed `GIT_SETTINGS`. The discovery pattern is defined once in it and read by `live` and `gate`, by the live branches of `milestones` and `summary`, and by the `tasks` join once its root anchor is swapped for that pattern. No file is added under `core/tools/`; the tests stay in the existing `test_milestones_*` files on the conftest git fixtures, and the five `tasks` call sites stay unchanged. Any later split is left to whichever later milestone finds a reason for one.

- **`live` line.** Three tab-separated fields: the milestone path in its canonical printed form first, then a state field holding one of two fixed words, `started` or `defined`, then the title, read from the `requirements.md` heading, last. `live` runs the started test (one path-scoped `git log -1 --diff-filter=M` per live milestone) to fill the state field.

- **No `live` filter yet.** The `live` query lands in this milestone as the unfiltered list alone: it takes no PATH argument, and the resolution stop and the gate are its only callers. The PATH filter, with its scope-contains-or-lies-under rule, is not built here; it is left to step 4, the next milestone, to add with the starting-state refresh's in-flight read, the first caller that needs it, and that milestone also decides the filter's argument shape and semantics.

- **`milestones` line.** Four tab-separated fields in the draft's order: state, date, path, title, the title last. State is one of two words, `finished` or `live`. A finished milestone's date is its `Milestone-finish:` commit's author date as YYYY-MM-DD, the form `tasks` prints; a live milestone's date is the fixed placeholder `-`, the placeholder `tasks` prints for a milestone it cannot join. Newest first puts every live milestone above every finished one, the live lines among themselves in path order, then the finished lines by finish timestamp, newest first.

- **`summary` print.** One three-part shape for both states. The first line is a single field: the finish commit's author date for a finished milestone, the fixed word `live` for a live one. Then follows the finished body (title line, blank line, bullets) or, for a live milestone, the title from the `requirements.md` heading, a blank line, and the whole `## Goal` section body, verbatim with its outer blank lines trimmed, read from the working tree. Live is told from finished by the first line alone; no date is printed for a live milestone, and live and defined are not told apart.

- **`record` print.** Each milestone opens with its `milestones PATH` line printed verbatim at column 0, whatever fields that query's line carries. Beneath it every line is indented by four spaces: first the summary's bullets, with the finish body's title line and blank line dropped because the header line already names the title and date (for a live milestone, whatever `summary` prints for one), then one `tasks` line, verbatim, for each task that changed PATH, with no bars. No blank line or separator stands between milestones, so the next column-0 line is the next milestone, the boundary rule `tasks --with-body` uses. A milestone listed only because its scope contains PATH prints its header and summary alone. The query takes no bound, so `record .` prints every milestone the `milestones` query lists.

- **Shallow clones.** `gate` runs `git rev-parse --is-shallow-repository` first and, when it prints `true`, refuses with one `Error:` line on stderr and exit 1 naming the shallow clone and `git fetch --unshallow`. `milestones`, `summary`, and `record` make no check and state the limit in their help text and the docs as `tasks` does, and `tasks` is unchanged.

- **Trailers.** A trailing trailer block in a finish body is allowed, finish commits through the procedure by reference, and the commit tool is unchanged. On the reading side one rule covers every body the milestones tool prints: `summary`, `record`, and `tasks --with-body` all drop a trailing paragraph whose every line is `Token: value`, so a pre-flip task body that is only `Co-Authored-By:` (with `Claude-Session:` once) prints as a commit with no body.

- **`gate` output.** `gate` is an ordinary query under the unchanged contract: it prints the holders on stdout, one bare path per line, and exits 0 whether or not the scope is held, printing nothing when it is clear; only a failure exits 1, with one `Error:` line on stderr. The gate holds only through the runner's test for empty output, made either inside the one shell call (the print captured and tested empty ahead of the write behind `&&`) or as a separate check step before the write, as `derive-tasks` step 2 already tests `list` for empty.

### Milestone paths and resolution

- **Canonical path.** The canonical form keeps the trailing slash: the definition tool prints `<scope>/milestones/<slug>/` as today's `root_label` does, the `tasks` query's milestone field keeps the slash `milestone_of` gives it now, and every subject that names a milestone carries the path with the slash (`Milestone-finish: milestones/<slug>/`). A `--milestone` value that differs only by a missing slash is refused, on the procedure's no-match line with the `live` paths listed beneath it; since the existence test `<path>/requirements.md` passes for both spellings, the procedure adds one explicit check that the value ends in `/`.

- **Scope spelling.** The root is spelled `--at .`, and `./` is accepted as the same thing. The definition tool normalizes every scope lexically before forming the path, collapsing `.` components, duplicate and trailing slashes, and a leading `./`, and refuses an absolute path or one that climbs out of the repository with `..`. It then prints the canonical repo-relative form, which for the root is `milestones/<slug>/` and for a package is `pkg/milestones/<slug>/`, however the scope was typed.

- **Missing scope.** The scope must already exist as a directory in the working tree, tested on the filesystem since the tool touches no git; when it does not, or names a non-directory, the call is refused with one `Error:` line naming the scope as given and nothing is written. Only the `milestones/` container is created when missing. A milestone whose core does not yet exist is placed by first creating the scope directory by hand, or at the nearest existing ancestor.

- **Match test.** `--milestone <path>` matches whenever `<path>/requirements.md` exists in the working tree, with no check that the path sits under a `milestones/` container. A matched path outside any container resolves, and every skill that does not gate (starting state, review, both annotating passes, the answer skills, `ask-in-milestone-context`) runs on it. The scope question is settled at the gate: the `gate` query refuses a milestone path that has no container with one `Error:` line, so `derive-tasks`, `submit-task`, and both completion runners stop on it.

### Finishing a milestone

- **Removal through the commit tool.** The commit tool gains a removal input (for example a repeatable `--remove PATH` option) under which it runs `git rm -r -q -- PATH` itself as one more git write inside its retry schedule, before staging the other named paths and making the one pathspec commit over all of them. Finish runs only that one command, naming the milestone directory as the removal and the context file as an ordinary path when edited, under `Milestone-finish: <path>` with the summary as body.

### The migration skill

- **Re-run detection.** The walk reads two signals for each entry. If the directory still stands, the entry is migrated now, even when a path-form `Milestone-finish: <path>` subject is already in the log (a reverted migration). If the directory is gone and the log holds that subject, the entry is skipped as already migrated. If the directory is gone and no such subject exists, the entry is not treated as migrated and falls under the absent-directory handling recorded below.

- **Missing finish date.** Before its first commit the migration checks whether the repository is shallow and stops with a fixed line and a remedy (fetch the full history) if it is. In a complete history, an entry with no `Milestone-finish:` commit for its id takes the author date of the newest commit that changed its directory.

- **One confirmation.** Before its first commit `migrate-milestones` prints its whole plan: every `## Milestone History` entry it will finish, oldest first, each with the directory it removes and the author date its commit will carry, then what the closing commit removes and rewrites (`milestones/README.md`, a live milestone's `TASKS_DONE.md` if present, the context file's `## Milestone Workflow` section). It then asks once whether to proceed, as capture's step 7 asks once before its commit. Acceptance runs the whole walk and the closing commit with no further prompt; anything else ends the run on one fixed no-op line of its own, with no file changed and no commit made. The confirmation accepts or rejects the plan whole and edits no entry out of it.

### Contributor flow and release

- **Reservation on `main`.** The maintainer's reservation step stays, rewritten for paths: on accepting the proposal the maintainer runs `/define-milestone-goal --at <scope>` with the accepted goal on `main`, choosing the scope, and its `Milestone-definition: <path>` commit is the reservation. The contributor branches from that commit and runs the pipeline with `--milestone <path>`. The `/goto-next-milestone` step and the pointer conditions on reserving and merging go. An abandoned contribution is still cleaned up by reverting the definition commit, and the pull request template's milestone field names the reserved path.
