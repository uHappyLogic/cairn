# Milestone 48: Batched answer sweep with a fold tool

## Goal

Make the inline answer sweep (`answer-all-open-questions-with-recommendation`) record a whole run in one fixed batched shell call, shown in full and run as shown: for each walked question in `walk` order it lifts the pick, folds the decision under its `## Decisions` subsection through a new shell-callable fold command for `requirements.md`, removes the block with its option, and commits one `Recommendation-answer:` commit with the lifted line as body, skipping a failed lift silently and stopping on the first failure after a fold with the tree resumable. The sweep's setup collapses to its fixed-call floor, reading `requirements.md` whole and a compact view of the question document (id, question text, lifted pick) instead of the whole XML, dropping the per-answer `locate`, and retiring the `=====` separator that fails in zsh. The fold command is used by the sweep only and is not the sole writer of `## Decisions`; the three single-question answer skills keep their Edit-based fold; the rewritten sweep is hands-on checked in Claude Code only, with the Antigravity and Codex trees rendered and reviewed.

## Relevant starting state

### The answer sweep as it runs today

`core/skills/answer-all-open-questions-with-recommendation/SKILL.md` runs inline with no agent and no wording slot, so it renders into all three host trees identical but for `{{PLUGIN_ROOT}}`. Its steps are: resolve `<MILESTONE_DIR>` once; one `walk` call as the whole gather and order; one whole read of `open_questions.xml` and `requirements.md` with the file-reading tool, for reasoning only, with no fixed command shown for that read; then, per Short Title in turn, follow `answer-with-recommendation-procedure.md` from its `lift` (a failing lift is the silent skip, a succeeding one's print is held as the commit body), commit the two files through the commit procedure under `Recommendation-answer: <Short Title>` before the next question, and stop the whole run on a tool failure after a fold with the tree left as it is; then one end-of-run `walk` as the completeness check and the report (`Recommendations recorded.` or the no-op line, beside the contradiction pairs and the completeness anomaly). Its tool-contract sentence carries the clause requiring every tool call, the followed procedures' per-question `lift`, `locate`, and `remove` included, to be written out in full and never through a variable, alias, or function of the runner's own. The contradiction advisory is formed at fold time, one question at a time, against the live `## Decisions`.

### The two answer procedures and today's fold

`core/shared/answer-with-recommendation-procedure.md` lifts (`lift <MILESTONE_DIR> "<SHORT TITLE>"`, whose one printed line is ANSWER and whose text before the first spaced em dash is RECORDED OPTION) and delegates to `core/shared/answer-procedure.md`, which owns locate, analyse, fold, remove, cascade. Its fold (step 3) is a prose instruction with no tool behind it: add a concise statement under `## Decisions` of `requirements.md`, in the relevant existing subsection or a new one, as clean prose with no citation marker, as a separate targeted edit per decision and never a rewrite of the file, written before the `remove`. Its step 1 `locate` prints the block verbatim for step 2's reasoning and step 4's judgment, step 4 passes RECORDED OPTION to `remove --option` verbatim, and step 5's cascade is a bare `remove` per mooted entry. Both procedures state that they are followed by the single-question skills and, once per question, by the sweep: `answer-open-question-with-recommendation` follows the lift procedure, while `answer-open-question` and `answer-open-question-with-alternative` follow `hand-answer-procedure.md`, which composes over the same recording core, so all three fold the same way.

### Writers of requirements.md and the shape of its Decisions section

`core/tools/define_milestone.py` creates `requirements.md` from a fixed template: the `# Milestone N: title` heading, the goal under `## Goal`, then the empty `## Relevant starting state`, `## Decisions`, and `## Out of Scope` headings, each followed by one blank line. ### The open-question tool's reads and writes the sweep uses

`core/tools/open_questions.py` (1,270 lines) offers `walk` (the ids of the recommendation-bearing blocks, one per line, dependencies first), `lift` (one line `<option> — <rationale>`, an `Error:` on a block carrying no `<recommendation>`; `--alternative` lifts an alternative instead; there is no option-only print), `list --with-question` (id, one tab, question text, in document order, composing with the two `--without-*` filters), `locate` (the block verbatim), `remove --option` (refusing an option naming none of the block's own alternatives, reconciling tagged dependents in the same write), and `sort` (annotated blocks first in `walk` order, so on a sorted document `walk` prints the annotated prefix of `list`). No single call prints id, question text, and pick together; a compact view today is `list --with-question` plus one `lift` per walked id. The output contract the tests pin: a read prints bare un-escaped values (a tab separates two values, which no value can contain since every write folds whitespace), a mutator prints nothing on success, every failure is one `Error: <reason>` line on stderr with exit 1 and the document byte-for-byte unchanged, and a malformed invocation gets argparse's exit 2.

### Field measurement of the sweep

The gitignored report `temp/answer-sweep-efficiency-options.md` (2026-10-18), reproducible with the scripts under `temp/answer-sweep-analysis/`, measures 88 runs since 2026-10-01 (856 answers across seven projects). A median run is 8 answers, 22 turns (setup 5, loop 16, tail 1), 1.9M input tokens at 96.7% cache share, and 2.55 minutes; the loop costs a median 2.22 turns per answer because the one-turn form needs the next question's `lift` and `locate` chained into the current commit call, which the skill never states, and 345 of 814 folds (42%) were `python3 - <<'EOF'` `str.replace` scripts because a file edit cannot be chained with `remove`. The whole-document snapshot's cache re-reads are 31% of all sweep input (the XML's share 15%), 60 of 88 runs needed two or more read turns, and the `list --with-question` plus one `lift` per walked block view is 9–13× smaller than the XML; 33 of 88 runs lost a turn to a read command separating two files with `echo =====`, which zsh parses as an `=cmd` expansion; the cascade fired once in 856 answers, and one `remove` and one `lift` failed. The report's option 3 simulation (the loop as one batched call) gives −77% turns, −86% input, −68% cost-equivalent, and −48% wall-clock, and its open question is whether the fold lives in a separate tool beside `open_questions.py` or as a `remove --decision` inside it.

## Decisions

### Contradiction detection

The sweep forms no contradiction advisory: its upfront reasoning makes no contradiction judgment, the batched call prints no contradiction line, and the report carries no contradiction pairs, so the sweep's fold-time duty to record the pick anyway and hold the pair is retired. In this milestone `review-milestone-requirements` gains a `## Decisions` consistency step that reads the recorded decisions against each other and surfaces a conflicting pair as a gap, for example as an open question settling which entry stands, flagging the conflict without resolving it. The next review pass after a sweep is where a contradiction is noticed.

### Template test coverage

The batched call's shell template is exercised by an automated test in `tests/` that runs in CI under both pytest interpreters. It extracts the fixed call from a rendered host tree, fills its per-question placeholders for a golden fixture milestone copied into a temporary git repository, and runs the call under bash. It asserts one `Recommendation-answer:` commit per answered question, with the lifted line as body, path-scoped to `open_questions.xml` and `requirements.md`, and carrying the block's removal, and it asserts that a question whose lift fails is skipped silently. The stop path after a fold is not covered by the test and stays with the Claude Code hands-on check.

### Fold command home

The fold lives in a new self-contained stdlib-only Python 3.9+ tool file named for its document, `core/tools/requirements.py`, beside the three existing tools, with `fold` as its one subcommand for now, called as `python3 {{PLUGIN_ROOT}}/tools/requirements.py fold <MILESTONE_DIR> --section "<Heading>"` with the body on standard input and chained before the unchanged `remove` as `fold … && remove …`. The file carries its own copies of the stdin reader, error type, atomic writer, and main, imports no sibling (pinned by a parity test like the task-list tool's), and gets its own flat test files and conftest fixture. The open-question tool and its invariant stay unchanged, and the new tool gets its own short `CLAUDE.md` invariant.

### Fold write scope

The fold command is a byte-preserving splice: it reads the whole file only to locate `## Decisions` and the target landing point, inserts the decision text there with exactly the blank lines the two seams need (one blank line before and after the inserted block, adding one only where the neighbouring line is not already blank), and writes every other byte of the file back unchanged, normalizing nothing it did not write, so each `Recommendation-answer:` commit's `requirements.md` diff is exactly the folded decision. It departs from the task-list tool's whole-file render on purpose, because `requirements.md` keeps being written by hand and the fold is not its sole writer; the seam cases (end of file without a trailing blank line, a subsection holding no body yet, a section ending in a bullet list) are small, tested code.

### Fold body form

The fold command treats the body it reads on standard input as opaque Markdown: it writes it verbatim with only its leading and trailing blank lines trimmed, adding no bullet, bold lead, or paragraph wrapping of its own, as the task-list tool's `move` writes its bar. Every format rule stays in the answer core's fold step, where the three Edit-based skills already read it, and the runner chooses each entry's shape by matching the subsection it lands in: a prose paragraph where the milestone's Decisions use one subsection per decision, a `- **Lead.** text` bullet where they use topical subsections of bullets, so sweep folds and hand folds in one milestone take the same shape by the same judgment. The tool gains no rendering path for a prose section it does not otherwise parse.

### Missing subsection handling

A heading that matches no `###` heading under `## Decisions` is created, never refused: the fold command appends the `###` heading at the end of `## Decisions`, just before the next `##` heading, and folds the decision under it, while a heading that matches folds into the existing subsection. Headings are matched after whitespace and case folding, which catches most reworded repeats; a true near-duplicate subsection stays visible in the answer's commit diff. The same call shape therefore serves the first decision of a fresh milestone, whose `## Decisions` is created empty, and every later one, with no hand edit outside the batched call.

### Compact view command

The compact view is one fixed shell call with no tool change, shown in full and run as shown with only `<MILESTONE_DIR>` replaced: it runs `list --with-question` and then pipes `walk`'s print into a `while IFS= read -r` loop that prints each id followed by that id's `lift` line, every tool invocation written as the full fixed command. That call doubles as the sweep's gather and order, a failed lift prints its `Error:` line in place of the pick, and the loop variable is exempted by the shell-literal invariant's clause for the sweep as the batch calls' per-item values are. The open-question tool, its contract, and its test suite stay unchanged.

### Mooting cascade in batch

The mooting judgment and the cascade are dropped from the sweep's path entirely: the runner never asks whether a pick moots another entry, and the batched call carries only lift, fold, remove with the option, and commit for each walked question, so the template keeps one fixed section shape and the sweep stays a pure recorder of picks as given. An entry a recorded decision moots stays in `open_questions.xml`; if it carries a pick and its lift still succeeds, the run records it as given, and otherwise it waits for the next review pass, which removes a block a recorded decision covers as cleanup of recorded state or flags it.

### Status line source

The report step learns whether the batched call committed at least one answer from the call's own output: each question's section chains one fixed, identifier-free marker line (for example `answer commit landed`) behind its `git commit -q` with `&&`, so the call prints one marker per landed `Recommendation-answer:` commit, the form the two batched-call precedents and the task-list chains already use. The report prints `Recommendations recorded.` when at least one marker appeared and the no-op line when none did, and both of today's no-op causes stay (an empty step-1 `walk`, and every lift failing). No shell variable tracks state across sections, and on a stop the markers already printed show how far the run got.

### Fold refusal set

Beyond an empty body and the baseline input failures every sibling tool already has, the fold command refuses, with `requirements.md` byte-for-byte unchanged, only a file that holds no column-0 `## Decisions` heading or holds more than one, the same rule as the task-list tool refusing an anchor that names no section. The body is written verbatim, heading lines included, nothing of the prose is checked, and a body already present under `## Decisions` is folded again: there is no duplicate no-op, since a checkout of the uncommitted fold already gives a resume, and the smallest refusal surface gives the batched call the fewest stops.

### Subsection requirement

The fold command takes the `###` subsection heading as a required argument on every call, with argparse's exit 2 when it is missing, mirroring the task-list tool's required position group, so every decision lands under a named subsection of `## Decisions` and there is no form of the call that names none. Both recent shapes of the section hold decisions only under a heading, and an optional argument would add a placement branch whose no-heading path either mis-files the decision into the last subsection or invents a third shape of the section.

### Option value source

In the batched call the runner writes each section's `remove --option` value as a literal quoted argument when it composes the call, copied from the pick the compact view lifted for that block, which keeps the answer core's rule that the option reaches `remove` as an exact id never parsed from the answer text. Inside the call nothing derives or checks the option: the section's `lift` still runs first and its print is held only as the commit body and the skip test, and `remove` receives the value the runner wrote and still refuses an id outside the block's set. The value is live for every block whose lift succeeds, because a cascade strips a block's whole recommendation half or nothing, and the open-question tool is unchanged.

### Compact view block scope

The compact view covers every open-question block in the document: each block `walk` prints appears with its id, question text, and lifted pick, and every recommendation-less block appears too, with its id and full question text and no pick. The `list` print already carries every block's id and question text, so covering the recommendation-less blocks costs nothing while filtering them out would add a step to the fixed call, and after a full recommendation pass those blocks are the few it skipped.

### End-of-run walk placement

The completeness `walk` is written into the batched call as its last command, after the last question section, so a run without a failure costs one call for the loop and the check together and keeps the check that a hand-composed section was not dropped. A stop after a fold ends the call before the walk is reached, so a stopped run gets no walk, as today, where a walk after a stop would print only the stopped and unreached questions. One fixed header line printed before the walk separates its bare ids from the marker lines in the call's output.

### Fold refusal handling

A fold refusal is handled like a failure after a fold: the batched call stops at that question's section, records nothing more, and leaves the tree as it stands, which for the refused question is clean since the fold wrote nothing and the remove and commit never ran. The report carries the stop through the same path as any other stop, so there is one failure branch per section; a fix is applied by hand or in a later run and the sweep is re-run from the top. Walk order's dependencies-first guarantee therefore holds for every commit that lands, and no pick tagged on the refused question is recorded against an outcome that was never recorded.

### Stop report print

The batched call leaves every post-fold step's stderr unredirected, so the tool's own `Error:` line, or git's message for a refused commit, reaches the output exactly as printed, and on that failure the section prints one fixed line naming the question, such as `stopped at`, a tab, and the Short Title, before ending the call. Only the lift's stderr is silenced (`2>/dev/null`), so a failed lift stays the silent skip. No error text is held in a shell variable and no capture wrapper is added to the fold, remove, or commit steps; since every failure after a lift stops the call there is at most one failure per call, and the report step pairs the stopped-at line with the `Error:` line printed beside it, a multi-line git message reaching it verbatim.

### Sweep procedure references

The sweep's own file states every per-question mechanical step its batched call runs: the lift with its silent skip, the fold through the fold command, the remove with the lifted option, and the commit. It stops following `answer-with-recommendation-procedure.md` altogether, whose intro then names only `answer-open-question-with-recommendation`, and keeps a reference to `answer-procedure.md` only for the judgment the batched call cannot do: the fold step's rules on what the decision text says (clean prose, no citation marker, the live document's section names), the one home the Fold body form decision keeps them in, plus whatever form of the analyse step's questions the sweep keeps. The core's intro is reworded to say the sweep follows its fold-content rules and analyse step, not its tool steps, and the `CLAUDE.md` sweep invariant and the shell-literal clause are reworded to match. The rules are not copied into a second home, and the procedures gain no batched-path branches.

### Requirements read placement

`requirements.md` is read whole with the file-reading tool, never through shell output, and the skill tells the runner to send that read in the same turn as the compact view's fixed shell call, as two independent tool calls. The compact view call stays limited to the question document and keeps the shape its decision fixes, and the skill shows no shell command for the read. The sentence names no capability and degrades to today's two calls on a host that serializes them, so it is the same slot-free text in every host tree.

### Stranded fold guard

The batched call carries a clean-own-paths precondition: its first command, ahead of the first question's section, runs `git status --porcelain` on the milestone's `open_questions.xml` and `requirements.md`, each path its own literal argument, and if that prints anything the call prints one fixed line (for example `dirty before start`) and ends before any lift, fold, remove, or commit. Any staged or unstaged change counts, whatever its origin, a hand fix to `requirements.md` included, which must therefore be committed before a re-run. The report step prints this stop with the porcelain lines and the remedy (commit or discard the leftover, then re-run) in place of the status line. A stop after a fold still leaves the tree as it stands, never rolled back, and the compact view call is untouched. The guard sits inside the one template the decided test exercises, which adds a dirty-start case beside its other assertions, and the skill's sentence saying it needs no clean working tree narrows to these two files only, never the whole tree.

### Conflict surfacing form

The review pass's `## Decisions` consistency step authors one open-question block per conflicting pair through the open-question tool's `add`, its question text naming both entries' `###` headings under `## Decisions` and asking which entry stands, and the block is committed in the pass's `Requirements-review:` commit like any other new gap. The report gains no new advisory: the block shows only as a Short Title in the still-open list, and the convergence verdict is still read from the `list` print alone, so the conflict holds convergence and the `derive-tasks` precondition until the block is answered. The block then goes through the alternatives pass, the recommendation pass, and either the sweep or a hand answer like any other question, and no convergence rule or tool changes.

### Template extraction anchor

The batched-call test finds the call as the one fenced block of the rendered sweep file that holds a command only the call carries (the fold command), and fails when no fence or more than one fence holds it. It finds the per-question section by lines the call already needs: from the section's fixed opening line through the column-0 line that closes it, the same span the step's prose names to the runner as the lines written once per question, as the recommendation pass names its section. Everything from the fixed header line printed before the completeness walk to the end of the fence is the footer, written once. Nothing is added to the runtime file for the test: no marker comment, fence info string, shell comment lines, or split fences, so the author and the test read one stated boundary and an edit that breaks it fails the drift gate.

### Compact view test coverage

The compact view's fixed shell call gets an automated test of its own in `tests/`, run in CI under both pytest interpreters, that extracts the call from a rendered host tree, replaces `<MILESTONE_DIR>` with a golden fixture milestone copied to a temporary directory, runs the call under bash, and asserts its print: every block's id, tab, and question text in document order, recommendation-less blocks included, followed by each walked id and that id's lifted line in walk order. It runs under bash only, matching the batched-call test, and needs no git repository since the call writes nothing. The test finds this second fence by the same anchor rule as the batched call, a command only it carries (`list` with its question flag). The failed-lift branch, which no valid fixture can provoke, stays with the Claude Code hands-on check.
