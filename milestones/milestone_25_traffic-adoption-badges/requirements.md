# Milestone 25: Traffic Adoption Badges

## Goal

Publish adoption evidence in README.md as a table of albertoarena/github-traffic-badge badges — one row per repository (uHappyLogic/cairn, cairn-claude, cairn-antigravity), two columns (unique views, unique clones), and a caption stating the counts are cumulative from the workflows' first run and that the monorepo's clones include CI checkouts. Each repository runs a daily scheduled workflow (the action pinned to a full commit SHA, one step per metric writing a distinct SVG to the traffic-data branch): the monorepo's under .github/workflows/, each distribution repository's rendered from a scripts/hosts/<host>/ template into its hosts/<host>/ tree so releases publish it. The milestone stores the fine-grained PAT at temp/PAT as the TRAFFIC_TOKEN secret on all three repositories with gh secret set, seeds every traffic-data branch once via workflow_dispatch before the README references its badges, and verifies that the action's daily push keeps the distribution repositories' cron workflows from GitHub's 60-day inactivity disable.

## Relevant starting state

### README badge block

`README.md` opens with the banner image and one centred `<p>` of three shields.io badges — release (`github/v/release`), `ci` (reading `drift-gate.yml`'s status on `main`), and license — all `style=flat`, each wrapped in a link. The rest of the file is plain Markdown under `# Cairn` (`## Why Cairn?`, `## Installation`, `## How it works`, `## Workflow pipeline`, `## How skills commit`, `## Skill reference`, `## Contributing`, `## Self-dogfooding`, `## License`); it contains no Markdown table and no mention of traffic, adoption, or usage figures anywhere. The monorepo README is hand-authored; only the distribution READMEs are built from templates.

### Monorepo GitHub Actions

`.github/workflows/drift-gate.yml` is the only workflow: `on: [push, pull_request]` with no branch or path filter, `permissions: contents: read`, and its two actions pinned to full commit SHAs each followed by a `# vX.Y.Z` comment bumped by hand (no Dependabot); every run performs an `actions/checkout`. Repository settings: Actions enabled, all actions allowed, `sha_pinning_required` off, default `GITHUB_TOKEN` permissions read-only. The repository has a single branch, `main`, and no repository secrets.

### Distribution repositories

`uHappyLogic/cairn-claude` and `uHappyLogic/cairn-antigravity` each hold exactly one commit — the root commit `Release: 1.5.0` of 2026-09-17, tagged `1.5.0` — on their only branch `main`, with no workflows, no secrets, and issues, Discussions, wiki, and projects disabled; Actions is enabled on both with all actions allowed and read-only default token permissions. They change only when `/release-plugin` publishes: `git commit-tree` over the monorepo's `HEAD:hosts/<host>` tree object, pushed over SSH (`git@github.com:uHappyLogic/cairn-<host>.git`) atomically to `main` and the version tag, so between releases they receive no pushes at all. Nothing in the project records whether a workflow's own pushes count as repository activity for GitHub's 60-day scheduled-workflow disable.

### Host build and templates

Every file under `scripts/hosts/<host>/` other than `settings.toml` is a template rendered to the same relative path in `hosts/<host>/` (the walk is recursive and hidden directories render — `scripts/hosts/claude/.claude-plugin/` already does), substituting only the `{{VERSION}}` and `{{NAME}}` slots; `prose_drop_patterns`, `strip_frontmatter_keys`, and `exclude` apply to `core/` files only, and there is no per-template escape or opt-out. The validation gate's `unfilled-placeholder` check fails the whole build on any line containing `{{` in any rendered text file, templates included, so a workflow file using GitHub's `${{ … }}` expression syntax cannot pass the build as it stands. `--check` compares the render byte-for-byte with the committed trees and runs in CI on every push and pull request. Whatever the tree carries reaches consumers whole: the release publishes it verbatim, Claude Code marketplace installs clone the distribution repository, and the Antigravity install extracts the full `main` tarball into `.agents/plugins/cairn/`.

### The github-traffic-badge action

`albertoarena/github-traffic-badge` is a composite action (MIT, zero runtime dependencies, Node 20+, run with `node` on the runner) whose latest release is `v1.1.4` (2026-06-17) at commit `56f6f3e0ed586f14440561758b197ca57a38f480`, which the `v1` tag also points at; the default branch carries later unreleased commits (HEAD `63470f9`, 2026-07-05). Inputs: `token` (required — a PAT; the default `GITHUB_TOKEN` gets 403 on the Traffic API), `metric` (`views` | `clones` | `views-unique` | `clones-unique`), `label`, `color`, `style`, `output` (default `badge.svg`), `branch` (default `traffic-data`), `commit-message`, `base`, `abbreviated`, `lowercase`, `font-size`; outputs `total` and `badge-path`. Each run re-clones the data branch (orphan on first run) into a fresh temp directory over HTTPS using the same `token`, fetches both `/traffic/views` and `/traffic/clones` (the API's 14-day window), upserts both into one shared date-keyed `totals.json`, renders the one requested metric to `<output>`, then commits as `github-actions[bot]` and pushes with that token — so multiple steps with distinct `output` names share one `totals.json` and each step sees the previous step's push. A unique-metric total is the sum of per-day `uniques` over every day the branch has recorded, beginning with the 14 days the first run captured. The badge URL form is `https://raw.githubusercontent.com/<owner>/<repo>/traffic-data/<output>`.

### Token, secrets, and current traffic

`temp/` is gitignored; `temp/PAT` holds a 93-byte fine-grained token (`github_pat_` prefix, no trailing newline) that authenticates as `uHappyLogic`, for which the API returns no `github-authentication-token-expiration` header. It reads `/traffic/views` and `/traffic/clones` on all three repositories (HTTP 200), but a dry-run HTTPS push with it is refused on all three (`403`, permission denied), so as stored it lacks the contents-write access the action's push step uses. `gh` is logged in as `uHappyLogic` (scopes `gist`, `read:org`, `repo`; git protocol ssh), and no `TRAFFIC_TOKEN` — or any other — secret exists on any of the three repositories. The Traffic API's current 14-day figures: `cairn` 56 views / 9 unique, 398 clones / 112 unique; `cairn-claude` 4 / 2 views, 11 / 9 clones; `cairn-antigravity` 8 / 2 views, 6 / 4 clones — no data older than 14 days is retrievable.

## Decisions

### Host build and templates

The validation gate's `unfilled-placeholder` check tests for a `{{` not immediately preceded by `$` (the one-character negative lookbehind `(?<!\$)\{\{`) instead of any `{{`, so GitHub Actions `${{ … }}` expressions pass in any rendered file of any host while every slot of the plugin's own bare `{{UPPER}}` token family — `{{VERSION}}`, `{{NAME}}`, `{{PLUGIN_ROOT}}` — still fails the build. The gate stays one uniform check over every file: no path-scoped exemption, template escape sequence, or exempt-templates definition key is added, nothing in any `settings.toml` or template changes, and a workflow template under `scripts/hosts/<host>/` is the literal file GitHub will run (valid YAML, lintable, copy-pasteable). The build script's docstring and the CLAUDE.md clauses stating no `{{` anywhere are reworded to no `{{` outside a `${{` expression.

### Traffic workflow

Each copy of the traffic workflow declares `permissions: {}` — GitHub's documented syntax for disabling every scope of the job token — followed by a one-line comment that the job token is unused because the action reads the Traffic API and pushes with `TRAFFIC_TOKEN`. Neither `contents: write` (the action README's line, a leftover from its first day when `token` defaulted to `github.token`, kept verbatim through the same-day fix that made a PAT required) nor `contents: read` (drift-gate's grant, which serves a checkout this workflow never performs) is declared: the pinned action runs its ls-remote, fetch, and push over an x-access-token remote built from the `token` input and its `index.js` reads `INPUT_TOKEN` alone, so the job token does nothing and the block states that rather than copying a neighbour's grant. A step added later that does use the job token — a checkout of the repository, say — widens the block first.

Each of the two badge steps writes every rendering input explicitly and identically in all three workflow copies: `label` is the metric's column name typed lowercase — `unique views` and `unique clones`, as the header badges type `release` and `ci` — `color` is `3b82f6` on both (the README's own informational blue, the hex its License badge already uses; one colour, because the label already tells the two columns apart), `style` is `flat` written out rather than inherited from the action's default, so a pin bump cannot change the look silently (it is the same shields flat geometry the header badges use), and `output` is `views-unique.svg` and `clones-unique.svg` — each file named by its step's own `metric` value plus `.svg`, so the file name is the one token the workflow's metric line, the README badge URL, and a grep all share. A badge is served as its own file at its own URL, so its label must say what its number is, in the words the goal's column names already fixed; the GitHub Insights vocabulary (`unique visitors` / `unique cloners`) was passed over because one pair of nouns per cell beats a truer pair that disagrees with its own header.

The traffic workflow ships inside `hosts/<host>/` exactly as the goal places it and is accepted in installed plugin trees: every Claude Code plugin cache and every Antigravity `.agents/plugins/cairn/` extraction carries `.github/workflows/` as inert cargo, and each distribution copy opens with a leading comment stating that it runs only in `uHappyLogic/cairn-<host>` and does nothing in an installed copy. GitHub runs a scheduled workflow only from a repository-root `.github/workflows/` on the default branch, and the default branch is exactly what both install paths fetch, so a per-repository traffic workflow is inseparable from what consumers receive and can never run from a nested or cached copy; the only levers that would remove it — an `--exclude` flag on the documented Antigravity extraction command, which covers one host and only for consumers who type that command verbatim, or a plugin-subdirectory restructure of every distribution repository, out of all proportion to a file that cannot run anywhere but the distribution repository itself — are not taken. The byte-identical publish, the `--check` drift gate, and both README install commands stay as they are, and the host-tree contract naming README.md, CONTRIBUTING.md, and LICENSE as the tree's only non-plugin files widens to name the workflow beside them.

The traffic workflow exists as three hand-kept copies and that duplication is accepted: the monorepo's copy is hand-authored beside `drift-gate.yml` under `.github/workflows/`, and each distribution copy is its own template at `scripts/hosts/<host>/.github/workflows/`, rendered to the same relative path in `hosts/<host>/` by the one template rule already in force. No shared template source is added — neither a host-neutral template directory beside `scripts/hosts/` nor a `core/` directory mapped by `[layout]` to `.github` — and the build does not copy the monorepo's workflow into the host trees the way it copies `LICENSE`; the build, its docstring, both `settings.toml` files, and CONTRIBUTING.md are unchanged by this, and each definition directory stays the complete picture of what its host ships beyond `core/` and `LICENSE`. The copies are free to differ where they must — the distribution copies carry the inert-copy header naming their own repository while the monorepo copy carries none, and a per-repository cron offset is an ordinary edit — and the cost is accepted knowingly: an action SHA bump, a badge parameter, or the permissions block is edited three times by hand, kept in step exactly as the two CONTRIBUTING.md pointers and the README boilerplate already are, with a grep for `github-traffic-badge@` across all three copies as the check nothing automates, since `--check` compares each template only with its own rendered tree. A ~20-line file whose copies are meant to differ at the edges matches the shape the build already treats as one template per definition directory with no shared source; a shared template would add a third kind of source and touch five documents to remove only one copy, because the monorepo's workflow stays hand-authored whatever the build does; and the verbatim-copy route that would remove the duplication entirely forecloses the per-copy header and hard-codes a GitHub path the build otherwise never names.

Every copy of the traffic workflow is the file `.github/workflows/traffic-badges.yml` with `name: traffic-badges`, and its one schedule line is the cron `17 3 * * *` — daily at 03:17 UTC, commented as such — identical in the monorepo workflow and both distribution templates, so the three runs are not staggered. The stem names what the workflow publishes (the two badges, pairing with the traffic-data branch it writes) rather than the action that renders them, and it follows the monorepo's one precedent of a lowercase file stem naming the function and reused as the workflow name (`drift-gate.yml`, `name: drift-gate`) and as the stable URL component the README links from; the hour is the action's documented 03:00 UTC shifted seventeen minutes off the top-of-the-hour minute GitHub documents as delay- and drop-prone, landing at 05:17 on the maintainer's CEST clock before the day starts. The per-copy cron offset the duplication decision leaves open is not taken: the three runs share nothing — each pushes its own repository's traffic-data branch, and the token's 5,000-requests-per-hour budget dwarfs the four Traffic API calls a two-step run makes — so staggering would add a second hand-kept difference between the three copies for nothing. The upstream quick-start form (`github-traffic-badge.yml`, `name: Traffic Badge`, `0 3 * * *`) was passed over because its names describe the mechanism rather than the function and its minute is the one GitHub says to avoid.

### Token and secrets

The stored fine-grained token is extended in place rather than replaced: on its GitHub settings page, Contents: Read and write is added to its repository permissions for the three repositories, keeping everything already verified — user-owned, scoped to exactly `uHappyLogic/cairn`, `cairn-claude`, and `cairn-antigravity`, Administration: read, no expiration — so the 93-byte value at `temp/PAT` stays as it is and is the value stored as `TRAFFIC_TOKEN`. A second HTTPS push dry-run against all three repositories confirming the grant is the proof, so the secret the milestone stores is exactly the token whose access was verified; no replacement token is minted.

Once `TRAFFIC_TOKEN` is set on all three repositories, `temp/PAT` is deleted rather than kept: the task that runs `gh secret set` confirms with `gh secret list` that each repository carries the secret, then removes the file (verified by `test ! -e temp/PAT`) and records the deletion in its `TASKS_DONE.md` entry, since `temp/` is gitignored and nothing in git would otherwise record it. From then on the token exists only in GitHub's write-only secret store, and its recovery path is the Regenerate token button on the token's own settings page — a fresh value set on all three repositories together — so no local copy, keychain item, or other second store is kept for a re-set nothing in the milestone anticipates.

### Distribution seeding

The distribution repositories' workflows reach them by a mid-milestone patch release rather than a one-off hand push or a README table held until the release after the finish: once every task that changes `hosts/` has landed — the two workflow templates, the build-gate change they need, and any distribution README rewording — the tree is rebuilt and the maintainer runs `/release-plugin 1.5.1` between tasks, which with no milestone finish since 1.5.0 takes the skill's empty-range path and publishes each `hosts/<host>/` tree as a `Release: 1.5.1` commit. Only then does the milestone continue with the secrets, one `workflow_dispatch` per repository, the README table, and the inactivity evidence, so every traffic-data branch is seeded through the one documented route by which distribution `main` advances and no install ever carries a tree no tag names. The patch number is right because nothing in the plugin runtime changes for a consumer, matching the 1.0.1 precedent for a tooling-only release.

### README adoption table

The adoption table and its caption live in a new `## Adoption` section of `README.md`, placed after `## Skill reference` and before `## Contributing`, so it opens the project-level tail that follows the tool documentation: reach, then the invitation to join (Contributing), then the repository's own use of the workflow (Self-dogfooding), then the license. The table is a captioned measurement rather than a status badge — three repositories' cumulative counts under a caption whose caveats the goal fixes and further decisions may extend — which is project-level evidence of the kind the tail already holds and that a reader seeks by heading, so it is not inserted into the header badge block (a wordless strip of three one-line badges above the title, where a Markdown table cannot sit and today's single-digit distribution rows would lead the page for months), not placed between `## Why Cairn?` and `## Installation` (where a caveated table would separate the pitch from the install command, the two things every first visit is for), and not appended under `## Self-dogfooding` (whose subject is this repository running its own milestone workflow, unrelated to the distribution repositories' counts). The page's opening — banner, three status badges, title, pitch, install — stays exactly as it is.

The badge workflow's own daily fetch of the traffic-data branch is accepted and disclosed in the caption rather than removed or reduced. The pinned action fetches and queries only the repository running it, has no API-write mode, and rejects a negative `base`, so every way to shrink the number — a weekly cron, or a fork or bespoke script writing `totals.json` and the SVGs through the Contents API — abandons the goal's named action or its daily cadence, while the inflation is a fixed, known quantity: one unique clone and two clones per repository per day from the second run on, the same never-zero one-clone-one-unique floor the action's fetch leaves on its author's own repository. The action, its pinned SHA, the two-step job, and the daily cron stand exactly as the goal fixes them, and the caption's one clone caveat widens from the monorepo row to every row: clone counts include the badge workflow's own daily fetch of the traffic-data branch (one unique clone and two clones per repository per day), and the monorepo's additionally include CI checkouts — a stated floor a reader can net out against the same caption's start date. Daily is kept over weekly because each day is re-fetched on fourteen successive daily runs, so a scheduled run GitHub delays or drops costs nothing, whereas two missed weekly runs lose a week of data for good and the smaller floor would still need the same clause.

The adoption table is a GitHub-flavoured Markdown pipe table under the `## Adoption` heading, with the caption as the paragraph that follows it — not an HTML `<table>` in the header block's idiom, since every section below the horizontal rule is plain Markdown, a table under a Markdown heading needs neither centring nor a bound `<caption>` element, and a paragraph caption can carry the backticks and links its clauses call for. Its header row is repository | unique views | unique clones, and each of its three rows is labelled with the full owner/repo name — `uHappyLogic/cairn`, `uHappyLogic/cairn-claude`, `uHappyLogic/cairn-antigravity`, the form GitHub and the distribution READMEs write a repository in — as a Markdown link to that repository; short names are not used, because bare `cairn` under `# Cairn` names the plugin and the marketplace as readily as the repository, so the qualifier cannot be dropped for the one row the caption singles out. Each badge cell is the Markdown image at the badge's raw traffic-data URL with its column name as alt text, wrapped in a link to that repository's traffic-data branch page — the one public view of the number, holding the per-day `totals.json` every count is summed from and the daily `github-actions[bot]` commits, where Insights → Traffic is visible to push access alone — so every badge on the page links to what it reports on, as the three header badges do. Badges do not link to the workflow runs page (a run shows that a badge was regenerated, not what its number is made of, and the URL would hard-code the workflow file name), and no badge on the page is left unlinked.

### Inactivity evidence

The evidence that the daily traffic-data push keeps the distribution repositories' scheduled workflows clear of GitHub's 60-day inactivity disable is a precedent read-back, obtained inside the milestone: the verifying task reads, with read-only `gh api` calls against the public REST API, the live state of the action author's own repository `albertoarena/github-traffic-badge` — where since the last human commit on 2026-07-05 the only pushes are the action's daily `github-actions[bot]` commits to `traffic-data` (each a PushEvent attributed to the token's owner), every run of its scheduled traffic workflow is schedule-triggered, and there is no issue, pull request, tag, or release — and confirms that its scheduled workflow still reads state `active` past day 60 (day 75 at the time of the read); then, after each distribution repository's first scheduled run, it confirms the same signal on that repository — `pushed_at` advanced and a public PushEvent on `refs/heads/traffic-data` — recording the dated observations in this decision and in the task's `**Verified:**` entry. The documentation states the rule but never defines the activity it keys on, and inside the milestone's days the distribution repositories' own state is trivially active, so the one observation that settles the question now is a public repository already past day 60 on nothing but this action's daily push — the same action, the same PAT-authenticated push to a non-default branch, the same public-repository rule, seeded by one `workflow_dispatch` as the milestone plans — and the same-signal read on each distribution repository, which the mid-milestone release makes possible inside the milestone, closes the gap between the precedent and this deployment. A documentation citation alone is an argument rather than evidence, and a deferred day-61 check on the distribution repositories themselves — the runner-up — lies outside the milestone and would only re-observe what GitHub's warning email (sent about a week before an inactivity disable) and a stalled badge already announce; the read is accepted as a one-time observation, with those two signals as the only notice of a later disable.
