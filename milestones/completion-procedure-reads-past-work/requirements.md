# Completion procedure reads past work

## Goal

`core/shared/complete-procedure.md` names the milestones tool's `tasks <path> --with-body` query, its full fixed command shown, as the discretionary read of why a file is the way it is before editing it, with `show <milestone path>` as the follow-up for a decision's own words. The read is triggered by a file the task edits rather than creates whose shape the milestone's `requirements.md` does not explain, and is taken at step 2 for the files the task names up front, where what it surfaces may fix a criterion, and at step 3 for the edits only, the acceptance bar never re-deriving on it. The milestones tool stays unchanged and no test is added for the read; the docs, the `CLAUDE.md` invariants, and the rebuilt host trees follow, and `ideas/milestones_addressed_by_path.md` records step 5 as done, the choice of `tasks` over `record` included, and carries the written plan for the field measurement that decides whether the read stays discretionary: what is counted, over which runs, and the result that makes the read required.

## Decisions

### The past-work read

- **Failed read.** A failure of either call of the read, the `tasks <path> --with-body` call or the `show <milestone path>` follow-up, is treated as the read not taken, whatever the reason, the `-` path field that `show` refuses included: the runner carries on with the task from `requirements.md`, the context file, and the live material, and prints no fixed line. The inline `complete-task` skill tells the user in prose that the past-work read failed, quoting the one `Error:` line verbatim, as `ask-in-milestone-context` does; the `complete-task` agent, whose only final messages are `DONE` and `FAILED:`, carries on and reports nothing about it. The procedure states this in a clause of its own, because its opening never-skip rule would otherwise push a runner to return `FAILED:`. A failed read costs what an untaken one costs, since the read is discretionary and the starting state and the context file carry the protection, and a git-level fault still stops the task at the scope gate or the commit.

- **Past decision against the brief.** When the read surfaces an earlier milestone's decision or verified bar that carrying out the task as briefed would undo, and this milestone's `requirements.md` does not address it, the earlier decision governs how the work is done wherever the brief can still be met: among the ways of meeting the brief the runner picks one that leaves the earlier decision or bar intact, and the read may fix a criterion to that effect. Only where every way of meeting the brief undoes the earlier decision does the brief govern and override it, as the later-recorded decision of a converged milestone. The runner never stops for it and nothing is flagged, so the procedure gains no stop and no fixed line.

- **Criterion source.** Every criterion the step-2 read fixes names what it was formed against, inside its own `- ` bullet: the abbreviated hash from the `tasks` line when a task commit's diff or bar fixed it, and the milestone path from that line's third field when a decision that `show` printed fixed it. Step 2 states the rule once and step 5's form sentence lets a bullet carry the reference, so the `Task-completion:` commit body stays the bar alone, one bullet per criterion, and the read shows in every body `tasks --with-body` prints back.

- **Deleted, renamed, and moved files.** Deleting, renaming, or moving a file that already exists counts as editing it. The read is taken under the same condition as for an edit, `requirements.md` not explaining the file's existence or place, at step 2 for the files the task names up front and at step 3 for the rest. The query is `tasks` on the path the file has before the task, which the procedure states in one clause, because the tool follows no rename (its log reads set `log.follow=false`): the new path carries no history from before the move, while the old path, still in the tree when the read is taken, lists every task commit that changed it. The tool stays unchanged.

- **Context file.** Only the milestone's `requirements.md` counts as explaining a file's shape: its goal, its `## Relevant starting state`, and its recorded decisions. What the context file says about the file, however fully it gives the reason (in this repository a `CLAUDE.md` invariant), does not count, so an edited file whose shape `requirements.md` does not explain triggers the `tasks <path> --with-body` read even when the context file explains it. The procedure says this in one clause of its trigger sentence.
