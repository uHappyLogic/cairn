# Milestone 49: Noted contradictions and superseding fold

## Goal

When a single-question answer skill's analyse step finds that the decision it records conflicts with a standing `## Decisions` entry, it saves the pair under a new `## Noted contradictions` section of `requirements.md`, where the next `/review-milestone-requirements` pass turns each note into one open question asking which entry stands and deletes the note; the answer sweep keeps forming no contradiction judgment of its own. Answering a conflict question rewrites the superseded entries instead of appending a correction: the fold tool gains a replace mode the sweep uses for such a question, and the single-question skills' Edit-based fold rewrites by rule, since bending an existing entry to match a recorded answer is permitted. `/derive-tasks` keeps its precondition and is never blocked by a noted contradiction; it gains only a tie-break rule that where two decisions cannot both hold, the later-recorded entry governs the brief and nothing is flagged.

## Relevant starting state

### The requirements document and its writers

`requirements.md` has exactly four sections — `## Goal`, `## Relevant starting state`, `## Decisions`, `## Out of Scope` — created by `core/tools/define_milestone.py` from a fixed template; `review-milestone-requirements` restates that four-section structure in its own "document structure" block, and `CLAUDE.md`'s milestone file structure names the same four as prose only. The file has no sole writer: `specify-milestone-starting-state`, `modify-milestone-goal`, and the three single-question answer skills edit it by hand with the file-editing tool, and the answer sweep writes it through the fold tool only. Readers that take it whole are `derive-tasks`, both annotating passes, `review-milestone-requirements`, `discuss-open-question`, `ask-in-milestone-context`, `finish-current-milestone` (which extracts the goal and the key decisions for the history entry), and both dispatched agents; `capture-milestone-principle-updates` never reads the file, reconstructing each recorded decision from the added lines of the answer commit's `requirements.md` hunk. The pre-split milestones `milestone_01`–`milestone_27` carry a fifth heading, `## Open questions`, that no skill reads any more, so a fifth section already exists in the repository's own history without any skill breaking on it.

### The fold tool

`core/tools/requirements.py` (358 lines, Python 3.9+, stdlib only, self-contained) has one subcommand, `fold <MILESTONE_DIR> --section "<Heading>"`, the decision on stdin. Its model of the file: the section is the one column-0 `## Decisions` line (whitespace- and case-folded) running to the next column-0 `## ` line or the end of the file, with no code-fence exemption; inside it every column-0 `### ` line opens a subsection running to the next one or the section's end; `--section` matches a heading by exact equality after folding, the first of two matches winning; a missing heading creates the subsection at the section's end. The splice inserts the body after the last non-blank line of the landing subsection, adds only the blank lines its two seams need, keeps the file's line endings, and writes every other byte back unchanged, so a fold's diff is exactly the decision. It can only append: nothing in it locates, replaces, or deletes an existing entry's text. Refusals, each leaving the file unchanged, are an empty heading, an empty body, a missing or non-UTF-8 file, and a file with zero or more than one `## Decisions` heading; a mutator prints nothing on success and every failure is one `Error:` line on stderr with exit 1. Its tests are six flat files under `tests/` (`test_requirements_{body,contract,landing,parity,refusals,splice}.py`) over the golden fixture `tests/fixtures/requirements.md`, which holds both recorded decision shapes (one prose paragraph per subsection, and topical subsections of `- **Lead.** text` bullets) and a decoy subsection outside `## Decisions` sharing a decision's heading. The tool renders byte-identical into every host tree under `hosts/<host>/tools/`.

### The answer core and the three single-question skills

`core/shared/answer-procedure.md` is the recording core that `answer-open-question`, `answer-open-question-with-alternative` (both through `hand-answer-procedure.md`), and `answer-open-question-with-recommendation` (through `answer-with-recommendation-procedure.md`) follow inline. Its analyse step (step 2) asks four questions, the fourth being whether the answer contradicts or supersedes anything already written, and states that the analysis is not itself written into the document. Its fold step (step 3) adds a concise statement under `## Decisions`, in a fitting existing subsection or a new one, matched to the subsection's entry shape, and says nothing about editing an existing entry; its closing paragraph forbids otherwise rewriting or restructuring `requirements.md`. Each skill's report step prints one terse line plus a single git-absent advisory, "any new open questions the answer may have introduced", surfaced but never added; a contradiction has no named place in that report, and in the field the runner mentions one at its own discretion. One October 8 single-answer run on another project rewrote the superseded sentence itself during the fold, so the Edit-based fold already does by runner judgment what no rule asks of it. The commit subjects are `Manual-answer:`, `Alternative-answer:`, and `Recommendation-answer:` with the milestone's two files path-scoped.

### The answer sweep

`answer-all-open-questions-with-recommendation` views the question document through one fixed shell call: `list --with-question` prints every block's id, a tab, and its question text, then a `walk`-fed loop prints each recommendation-bearing id, its lifted `<option> — <rationale>` line, and its picked alternative's `<option> — <what-it-is>` line. `requirements.md` is read whole in the same turn. The runner composes each question's decision text and `###` heading from those prints, drawing on the answer core's fold-content rules and the first two analyse questions only, and records every pick as given: the skill states it forms no contradiction judgment and runs no mooting cascade, leaving both to the review pass. The batched call has one fixed section shape for every walked question — `lift` with stderr silenced, `requirements.py fold --section "<Heading>"` on a quoted heredoc, `remove --option`, the three commit steps, `answer commit landed` — with no branch per question kind, and a failure after the lift stops the call resumably. `tests/test_sweep_batched_call.py` extracts that call from the rendered Claude Code tree as the one fence holding the fold command, splits it at the `if pick=` opening and the column-0 `fi &&` closing, and runs it under bash over the `tests/fixtures/sweep` milestone; `tests/test_sweep_compact_view.py` does the same for the view.

### The review pass and the shape of a question block

`review-milestone-requirements` reads both documents whole for reasoning, prunes a block only against a citable covering decision, dedups, surfaces new gaps through the tool's `add`, and since milestone 48 runs a `## Decisions` consistency step (step 4): two entries conflict when both cannot hold as written, and for each conflicting pair no standing block flags it authors one block through `add` whose question names the `###` heading each entry sits under, states what each says, and asks which stands, never editing either entry. The block rides in the `Requirements-review:` commit and appears only as a Short Title in the still-open list. A block has no kind marker: `add` takes only the id and the question text, the document format allows no attribute beyond `id`, and the only way a later runner can tell a conflict question from any other is its question text, which the sweep's view prints in full. The review pass's convergence verdict is `list` printing nothing, which is also `derive-tasks`' precondition, so a conflict block holds task derivation until it is answered.

### `/derive-tasks`

Its one precondition is an empty `list` (step 2), which stops the run naming the open Short Titles. It reads `CLAUDE.md`, `requirements.md` whole, every file the starting state references, and `task-format.md`; derives brief-level tasks; and proves coverage with a requirement-to-brief matrix in which every requirement maps to at least one brief, a gap becoming a brief or a noted already-satisfied item. Nothing in it reads `## Decisions` entries against each other, names a tie-break between two entries, or flags a conflicting pair; its one git-absent advisory is an untraceable requirement. In 62 runs recorded on this machine since October 2 across seven projects, none named a conflict between two recorded decisions.

Between October 2 and the milestone 48 release on October 18 the sweep still printed a contradiction advisory; it fired in 20 runs across five projects, 12 of which went straight to `/derive-tasks` and 8 to a review pass. Where a pair reached task derivation, one entry won silently and both stayed in `requirements.md`: this repository's `milestone_43` still holds "Batch input selection" (the scan runs only after every agent has ended) beside "Wait expiry handling" (the scan runs per wake-up), and the later entry is what shipped. The review consistency step has fired once since October 18, on another project: its block gained alternatives and a recommendation, was swept, and the sweep's fold appended a paragraph opening "The sole-edit clause above is corrected to …" under the older heading plus a sentence correcting a clause that lives in a different subsection, both original sentences standing. ### Statements that currently fix the pieces this milestone moves

`CLAUDE.md` invariants state that the fold tool "is a byte-preserving splice, not the task-list tool's whole-file render", that "the tool has no rendering path", that only the sweep calls it while the single-question skills keep the Edit-based fold, that the sweep "never judges" a pick and forms no contradiction advisory, and that `review-milestone-requirements` "stays on the tidy side", never editing either entry of a conflicting pair. `docs/skill-reference.md` (review and sweep entries), `docs/workflow.md` (the requirements-loop paragraph), and `docs/design-claims.md` (the fold-tool mentions at lines 10, 125, and 131) describe the same contract. Any change under `core/` requires `uv run scripts/build_hosts.py` and a commit of the rebuilt `hosts/` trees; a tool change requires both pytest runs.

## Decisions

### Noted contradictions section

- **Entry content.** Each entry under `## Noted contradictions` holds the two `###` headings of the conflicting `## Decisions` entries, with enough of each entry's lead or opening words to tell them apart where they share a heading or sit among several bullets, plus one sentence in the answer skill's own words stating what each entry says and why both cannot hold. The note carries no ready-made question text; the review pass authors the block from the note.

- **Position.** `## Noted contradictions` sits directly after `## Decisions` and before `## Out of Scope`, so the file's order is Goal, Relevant starting state, Decisions, Noted contradictions, Out of Scope. The fold tool's `## Decisions` section then ends at the `## Noted contradictions` heading, and a subsection it creates lands immediately above that heading. The position is stated wherever the file's structure is stated: the definition tool's template if the section is created with the milestone, the review pass's document-structure block, and `CLAUDE.md`'s milestone file structure.

- **Leftover notes at finish.** `/finish-current-milestone` does not change. It reads nothing new and reports nothing about `## Noted contradictions`; any entries still under that section stay in the finished milestone's `requirements.md` exactly as written, the skill still creates or modifies nothing in `<MILESTONE_DIR>/`, and completion is recorded as today with the one `Milestone finished.` line.

- **Creation.** The milestone-definition tool and its template stay unchanged at four sections. The first note-writing step that records a conflict in a milestone inserts the `## Noted contradictions` heading together with its note; when the review pass turns the last standing note into an open question and deletes it, it deletes the heading too, so the section exists only while at least one note stands. The structure statements in `review-milestone-requirements` and `CLAUDE.md` keep the four sections and add one optional fifth, present only while a note stands.

### Note writing in the answer core

- **Home of the note-writing step.** The step that writes a noted contradiction lives in the shared answer core `core/shared/answer-procedure.md`, as its own numbered step acting on what the analyse step's fourth question (contradicts or supersedes anything already written) found, landing after the fold and before the block's removal. It applies unconditionally, so all three single-question skills write a note: `answer-open-question` and `answer-open-question-with-alternative` through `hand-answer-procedure.md`, and `answer-open-question-with-recommendation` through `answer-with-recommendation-procedure.md`. Neither composing procedure changes, and the core gains a step but no new input and no branch; the sweep's draw on the fold step's content rules never reaches the new step.

- **Note versus rewrite.** The analyse step judges each contradiction it finds. When the new answer plainly supersedes the old entry, because the answer is clearly meant to replace it, the fold rewrites the conflicting text of that other question's entry in place in the same targeted edit pass and writes no note. When the answer does not plainly settle which entry should hold, the old entry stays as written and a note is written; doubt notes. The answer core's ban on otherwise rewriting `requirements.md` gains this one exception.

### Fold tool replace mode

- **Granularity.** Replace mode always works on a whole `###` subsection and takes no further argument. The subsection is found the way `fold` already finds it: the column-0 `### ` line matched by `--section` after whitespace and case folding, running to the next `### ` line or the end of `## Decisions`. Everything between the heading line and the subsection's end is replaced with the stdin text, written verbatim with its outer blank lines trimmed; the heading line and every byte outside the subsection stay as they are. In a topical subsection of `- **Lead.** text` bullets, the runner's heredoc carries the whole new body, unchanged bullets included.

- **Invocation.** Replace is a second subcommand of `requirements.py` with its own name, `replace <MILESTONE_DIR> --section "<Heading>"`, the new text on stdin. It has its own argparse parser, help text, and refusal set, and reuses the file's internal readers, `## Decisions` locator, and atomic writer. `fold` stays exactly as it is, append-only, with its contract, call shape, and six test files untouched.

- **Missing subsection.** `replace` matches `--section` against the `###` headings under `## Decisions` with the same whitespace- and case-folded exact equality `fold` uses. When no subsection matches, it prints one `Error:` line on stderr naming the heading, exits 1, and leaves `requirements.md` byte-for-byte unchanged. It never creates a subsection, so a replace can only rewrite an entry that already exists; `fold` keeps its create-at-end behaviour.

### Conflict questions in the sweep

- **Recognition.** The signal is the question text. `review-milestone-requirements` step 4 opens every conflict question's text with one fixed phrase, stated once in that step, in a form that also names the two `###` headings of the pair. The sweep recognizes a conflict question when the question text printed by its compact view's `list --with-question` starts with that phrase, an exact-prefix check the runner makes when it composes the section; a block written before the convention falls back to the ordinary append section. The Short Title rules, the document format, and the open-question tool stay as they are.

- **Call count.** Every conflict question's section of the batched call carries exactly one `replace` call for exactly one subsection, the one holding the losing entry, chained ahead of `remove`. The sweep never rewrites a second subsection: the winning entry and any knock-on clause elsewhere stay as written, and a residual conflict is left to the next review pass's `## Decisions` consistency step to flag as a new question. Every section thus keeps a fixed number of tool calls, the conflict section differing from an ordinary one only in `replace` standing where `fold` stands.

### Task derivation tie-break

- **Later-entry determination.** `/derive-tasks` finds the commit that added each entry's lines in `requirements.md`, by blame or a pickaxe search path-scoped to that file, and treats the entry from the newer commit as the later-recorded one, for any conflicting pair. File position is never used for order, and the note under `## Noted contradictions` is not consulted for it.

- **Scope.** The tie-break rule covers every pair of `## Decisions` entries that cannot both hold. Every pair listed under `## Noted contradictions` is taken as conflicting as noted, without re-judging; any other pair the runner itself finds conflicting while building the briefs and the coverage matrix is resolved the same way, and the later-recorded entry governs. Nothing is flagged for either kind.

### Conflict answer record

- **Rewrite only.** The rewrite of the superseded entry is the whole record of a conflict answer, in every runner: no separate decision statement is folded anywhere under `## Decisions`, the sweep's conflict section swaps its `fold` call for the `replace` call, and the single-question skills' Edit-based fold edits the losing entry in place and adds nothing. `capture-milestone-principle-updates` stays unchanged and takes the rewritten entry's added lines in the `requirements.md` hunk as the commit's recorded decision.

### Review pass handling of notes

- **Clean up against recorded state only.** The review pass does not re-judge whether a noted pair conflicts; it checks each note only against what is already recorded. If a standing block already flags the pair, or if either named entry no longer stands as the note describes it (its heading is gone, or it has been rewritten so the two now hold together), the note is deleted with no block, as cleanup of recorded state. Every other note is authored as noted, one block per note, and then deleted.
