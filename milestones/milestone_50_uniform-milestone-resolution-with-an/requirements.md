# Milestone 50: Uniform milestone resolution with an override flag

## Goal

Every skill that operates on a milestone resolves it the same way: through the shared pointer procedure by default, or through one optional leading --milestone <milestone_id> flag that names a milestone directory and overrides the pointer. specify-milestone-starting-state loses its required positional id and joins the sixteen pointer-resolving skills under this rule, get-current-milestone.md gains the override as its one input, a named override that matches no milestone directory stops on an error line with no fallback to the pointer, an override is honoured even when the pointer reads none, and complete-all-tasks forwards the override to its dispatched agent. capture-milestone-principle-updates keeps its required positional id as the stated exception. The docs that spell the old argument (the skill-reference heading, the headless chain line and placeholder list in ways-of-using-cairn.md) are updated, and CLAUDE.md records the resolution rule as an invariant.

## Relevant starting state

### The shared pointer procedure

`core/shared/get-current-milestone.md` is the single source of truth for resolving `<MILESTONE_DIR>`. It has no input: it finds the one line in `milestones/README.md` whose prefix is `Current milestone:`, stops when the value is the bare token `none` ("do not attempt to read a milestone directory"), and otherwise extracts the backtick-quoted path (`milestones/milestone_<N>_<slug>/`) as `<MILESTONE_DIR>`. It is rendered unchanged into every host tree (it carries no slot) and is referenced by fifteen skills plus `core/shared/complete-procedure.md`. Nothing in it validates that the extracted directory exists.

### The sixteen pointer-resolving skills

Fifteen SKILL.md files carry a step-0 sentence of the shape "Follow `{{PLUGIN_ROOT}}/shared/get-current-milestone.md` to resolve `<MILESTONE_DIR>`. Never use a hardcoded path." (some say "hardcoded task-list path"): `answer-open-question`, `answer-open-question-with-recommendation`, `answer-open-question-with-alternative`, `answer-all-open-questions-with-recommendation`, `ask-in-milestone-context`, `complete-all-tasks`, `derive-tasks`, `discuss-new-task`, `discuss-open-question`, `finish-current-milestone`, `modify-milestone-goal`, `provide-alternatives-to-all-open-questions`, `recommend-all-open-questions`, `review-milestone-requirements`, `submit-task`. The sixteenth, `complete-task`, reaches the procedure through step 1 of `complete-procedure.md`, which it follows inline. Two of the fifteen extend the sentence with their own handling of a `none` pointer: `finish-current-milestone` stops with "no active milestone to finish", and `ask-in-milestone-context` answers from `## Milestone History` instead of dead-ending. `answer-all-open-questions-with-recommendation` adds "Resolve it once per run and hold it", and `complete-all-tasks` resolves once before its per-task loop. Every one of these skills' Usage blocks says "No arguments" or lists only its own positional text (a Short Title, an answer, a goal, a task name, a question); no skill in the plugin takes a `--`-prefixed flag today, so there is no precedent for flag parsing in the runtime prose.

### The two positional-id skills

`specify-milestone-starting-state` (`core/skills/specify-milestone-starting-state/SKILL.md`) takes a required positional `<milestone_id>`, the directory name under `milestones/`; its step 1 resolves `milestones/<milestone_id>/requirements.md` and, when the file does not exist, stops with "milestone not found" and a pointer to `/define-milestone-goal`. It never reads `milestones/README.md`. `capture-milestone-principle-updates` takes the same required positional id and documents its own validation in step 1: it stops when no id is given, resolves `milestones/<milestone_id>/`, lists the `milestone_*` directories present when `requirements.md` is missing, uses the value verbatim with no bare-number resolution, and feeds the id into its repeat-capture grep, its path-scoped commit walk, and its `Principle-capture: <milestone_id>` commit subject. Its Usage text cross-references the other skill: "exactly as `/specify-milestone-starting-state` takes it".

### The completion dispatch and the agent's own resolution

`complete-all-tasks` resolves `<MILESTONE_DIR>` in its step 0 and then dispatches one `complete-task` agent per task through two host slots, `COMPLETE_TASK_DISPATCH` and `COMPLETE_TASK_PROMPT_INSTRUCTIONS`, with a prompt fence whose only variable line is `Complete the task named: "<TASK_NAME>"`; each host's dispatch value says the prompt "contains only the task name". The agent (`core/agents/complete-task.md`) reads no prompt field but the task name and follows `complete-procedure.md`, whose step 1 resolves the milestone from the pointer again, independently of the orchestrator. The one dispatch site that already forwards a resolved directory is the alternatives pass: its prompt fence carries `Milestone directory: <MILESTONE_DIR>` beside the Short Title and scratch directory, its three `ALTERNATIVES_DISPATCH` slot values each say to pass "the `<MILESTONE_DIR>` resolved in step 0", and the agent's file documents "Milestone directory" as one of its three prompt values. CLAUDE.md's dispatch-prompt invariant states the rule that a prompt carries only what the orchestrator holds and the agent cannot fetch itself, and names the task heading as `complete-all-tasks`' whole prompt.

### Milestone directories and their validation

Directories are created only by `core/tools/define_milestone.py`, named `milestone_<NN>_<slug>` (two-digit zero-padded number, slug of up to five folded title words, so this milestone's own directory is truncated to `milestone_50_uniform-milestone-resolution-with-an`); the tool recognizes a milestone entry by the regex `milestone_([0-9]+)_(.+)`. `milestones/README.md` writes the pointer as the full relative path with a trailing slash. The three stdlib tools take `<MILESTONE_DIR>` as a positional argument and refuse a missing document with `Error: <path> does not exist`, where the path is the joined file path (`open_questions.xml`, `TASKS_TODO.md`, `requirements.md`); none of them checks that the directory itself is a milestone, and no tool resolves the pointer. `goto-next-milestone` reads the pointer line directly (not through the procedure) to require `none` before writing it, and `define-milestone-goal` never touches the pointer. Pre-split milestones `01`–`27` have no `open_questions.xml`, and the stated design is that a question skill pointed at one stops on the tool's `Error:` line.

### Docs and tests that spell the argument

`docs/skill-reference.md` heads the entry for this skill `specify-milestone-starting-state <milestone_id>` (line 17) and the capture entry `capture-milestone-principle-updates <milestone_id>` (line 51), each a `###` heading spelling the positional argument, and its capture entry calls the id "required". `docs/ways-of-using-cairn.md` line 7 defines five placeholders, `<milestone_id>` among them, "exactly as the skill reference spells it in `specify-milestone-starting-state <milestone_id>`"; line 20 says the bootstrap chain hands over "`<milestone_id>` the directory `define-milestone-goal` created"; and line 33, in the Starting-a-milestone chain, runs `claude -p "/cairn:specify-milestone-starting-state <milestone_id>"` right after `goto-next-milestone`, the only chain line carrying that placeholder. The same page gives the per-host invocation forms (`/cairn:<skill>` on Claude Code and Antigravity, `$cairn:<skill>` single-quoted on Codex) and says angle brackets mark the only substituted text. `docs/workflow.md` names the skill with no argument in its Mermaid node and mentions `capture-milestone-principle-updates <milestone_id>` twice in prose. CLAUDE.md's skill table and `## Invariants` section describe resolution only in passing ("Every task-list runner resolves `<MILESTONE_DIR>` via `get-current-milestone.md`" inside the Task-altitude bullet) and carry no invariant on how a milestone is resolved or overridden. No test under `tests/` exercises skill arguments or the pointer procedure; the on-demand `agy_tests/test_plugin_root_resolution.py` relies on `submit-task`'s step 0 following the shared procedure as the vehicle for its plugin-root check.

### Build constraints on the files this touches

Every SKILL.md is rendered byte-for-byte into the three host trees apart from `{{PLUGIN_ROOT}}` and the declared slots, and the build's checks require frontmatter of exactly `name` plus a `description` of at most 25 words (`REQUIRED_FRONTMATTER_KEYS` and `DESCRIPTION_WORD_CAP` in `scripts/build_hosts.py`); extra frontmatter keys are neither required nor refused, and no skill uses one. Runtime files name no host and carry no capability-conditional prose, so any wording that differs per host must be a new slot declared identically in all three `settings.toml` files. `hosts/` must be rebuilt and committed with any `core/` change for the drift gate to pass.

## Decisions

### Flag-parsing rule home

The rule for recognizing a leading `--milestone <milestone_id>` in a skill's invocation text and separating it from the skill's own positional text is stated once, in `get-current-milestone.md`, which every pointer-resolving skill's step 0 already references. In addition, each skill that takes positional text of its own carries one clause at its own parse point (its parse step, or its step 0 where it has none) telling the runner to strip a leading `--milestone` value by that procedure before reading the rest, so the flag is never folded into a Short Title, an answer, a goal, a task name, or a question. The skills that take no positional text keep only their step-0 reference to the procedure.

### Per-skill flag documentation

Every skill under the uniform resolution rule spells the optional leading flag at both of its per-skill sites, and no separate general statement is written. Each of the sixteen SKILL.md Usage fences shows the flag in its invocation form (for example `/submit-task [--milestone <milestone_id>] <issue description>`, or `/finish-current-milestone [--milestone <milestone_id>]`), and the prose under the fence describes it, so every "No arguments." line is replaced. Each matching `###` heading in `docs/skill-reference.md` spells it the same way. `specify-milestone-starting-state` gets the same optional form in place of its required positional id. `capture-milestone-principle-updates` stays as it is, with its required positional id.

### Override existence test

The check that a named `--milestone` override matches a milestone is that `milestones/<milestone_id>/requirements.md` exists, which also implies the directory exists. This is the same test `specify-milestone-starting-state` and `capture-milestone-principle-updates` apply to their positional id today, so the override and the capture exception accept the same milestones, pre-split ones included, while a stray or half-made directory is refused before any skill reads from it. The shared procedure stops on its error line when the file is missing, with no fallback to the pointer.

### Unmatched-override error content

The error line for a `--milestone` override that matches no milestone directory names the value it was given, and the stop then lists every `milestone_*` directory present under `milestones/`, as `capture-milestone-principle-updates` prints today, because a miss on an exact name is almost always a mistyped or truncated slug and the exact names are what a retry needs. It carries no pointer to `/define-milestone-goal`.

### Pointer-path validation

When no `--milestone` override is given, the pointer's path stays unchecked, as `get-current-milestone.md` handles it today: the procedure extracts the backtick-quoted path from `milestones/README.md` and hands it on as `<MILESTONE_DIR>` with no existence test. The existence check runs only on a `--milestone` override. A pointer naming a missing directory is caught downstream, by the first tool call's `Error: <path> does not exist` line or by the skill's own failed file read, since the pointer is written only by `goto-next-milestone` and `finish-current-milestone` from directories that exist.

### Finish under override

`finish-current-milestone` honours any matching `--milestone` override, whatever the pointer reads, and its pointer-clearing step becomes conditional: the pointer is overwritten with `none` only when the finished milestone is the one it names. If the pointer reads `none` it stays `none`, and if it names a different milestone it is left pointing there, untouched, because finishing a milestone must never deactivate a different one. Its stop on a `none` pointer applies only when no override is given. The history entry, the Completed Milestones row, and the `Milestone-finish:` commit are written as today in every case, and the CLAUDE.md invariant on the pointer clear is narrowed to say the clear happens exactly when the pointer names the finished milestone.

### Override forwarding to the completion agent

`complete-all-tasks` passes the `<MILESTONE_DIR>` its step 0 resolved (from the override when one was given, from the pointer otherwise) on every dispatch, as a fixed `Milestone directory: <MILESTONE_DIR>` line in the prompt fence beside the task-name line, following the alternatives pass, so both dispatch sites share one unconditional prompt shape and no agent can diverge from the directory the orchestrator commits for. The `complete-task` agent file documents that line as a prompt value, and the agent uses the path as given with no resolution of its own. `complete-procedure.md` step 1 takes a supplied directory as given and runs the shared pointer procedure only when none is supplied, which is the case for the inline `complete-task` skill. The three hosts' `COMPLETE_TASK_DISPATCH` values stop saying the prompt "contains only the task name", and CLAUDE.md's dispatch-prompt invariant names the directory beside the heading.

### Chain-line invocation form

The Starting-a-milestone chain of `docs/ways-of-using-cairn.md` runs `/cairn:specify-milestone-starting-state` with no argument, so it resolves the milestone the preceding `goto-next-milestone` line just wrote into the pointer and the chain's lines stay on one milestone by construction. No chain line carries `<milestone_id>` any more, so the placeholder is removed from the notation paragraph's list (five placeholders become four), and the Setting-up chain's closing clause "with `<milestone_id>` the directory `define-milestone-goal` created" is dropped. The page says nothing about the `--milestone` flag; the flag is documented where every skill argument is, in the skill reference.
