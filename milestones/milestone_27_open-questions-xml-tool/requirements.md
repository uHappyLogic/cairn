# Milestone 27: Open Questions XML Tool

## Goal

Split the `## Open questions` section out of `requirements.md` into a sibling `<MILESTONE_DIR>/open_questions.xml` — a well-formed XML document under one root element, created empty by `define-milestone-goal`, whose "no `<open-question>` child remains" state is the convergence verdict and the `derive-tasks` precondition — and ship one stdlib-only Python tool inside the plugin (rendered into every host tree, invoked via `{{PLUGIN_ROOT}}`, and the file's sole writer) that owns every deterministic operation over that document: list, locate, add, lift, remove, embed with fragment validation replacing the seven-test acceptance gate, `<depends-on>` reconciliation in exact-id mode with transitive strip, dependent-strip on prune, and the answer sweep's dependency-graph walk. Rewire every skill, agent, and shared procedure that touches open questions from the `awk`/`sed`/`grep` boundary-line idiom onto tool invocations so that runtime prose keeps only judgment (authoring text, significance ranking, judgment-mode reconciliation for literal answers) and the entity-escaping, indentation, and whole-block-replacement contracts become the tool's internals — the aim being maximal token efficiency — while `capture-milestone-principle-updates` keeps its diff-line reconstruction, repointed at the new file. Give the tool a pytest suite run under `uv` in CI beside the drift gate, document Python 3.9+ as a prerequisite checked once by `init-milestone-base-workflow`, sync `CLAUDE.md`, `README.md`, and `docs/`, and provide no migration of or compatibility with pre-split milestones.

## Relevant starting state

### The `<open-question>` block and where it lives

Open questions are raw XML blocks under a single `## Open questions` section of `<MILESTONE_DIR>/requirements.md`, beside the four prose sections. `define-milestone-goal`'s template seeds `## Goal`, `## Relevant starting state`, `## Decisions`, and `## Out of Scope` only; `review-milestone-requirements` creates the section the first time it authors a block, so on disk it sits last, after `## Out of Scope`, and its empty heading survives once every block is answered. Every one of the 27 milestone directories holds exactly `requirements.md`, `TASKS_TODO.md`, and `TASKS_DONE.md`; 24 of the `requirements.md` files carry the heading and none carries a live block, so the annotated shape exists only in git history (for example the removed lines of `1cdddec`, `Recommendation-answer: Distribution badge form`). An authored block is three lines — a single-line `<open-question id="Short Title">` opening tag at the base column, one `<question>` child at a 2-space indent, `</open-question>` — and the recommend sweep grows it in a fixed child order: `<alternative id="…">` (what-it-is text, then `<advantage>` and `<drawback>`), `<applied-principle>`, self-closing `<depends-on question="…" option="…"/>`, and one `<recommendation option="…">`. Attribute values and element text are escaped with the five predefined entities, ids are compared case-folded after un-escaping, and no file declares a root element, an XML prolog, or a schema.

### The boundary-line CLI idiom and its runtime restatements

No runtime file invokes an executable today: `core/` holds Markdown only (`find core -type f ! -name '*.md'` returns nothing). Every deterministic operation over the question set is instead prose telling the runner to drive `awk`/`sed`/`grep` over the `<open-question …>`/`</open-question>` boundary lines and never `xmllint`, restated in each consumer: `core/shared/answer-procedure.md` (locate by `id="([^"]*)"`, re-query after the fold, line-range removal, dependent reconciliation with transitive strip), `core/shared/answer-with-recommendation-procedure.md` (locate and lift `<recommendation>`), `answer-open-question-with-alternative` (locate and lift an `<alternative>`), `discuss-open-question` (locate, then read the whole document), `recommend-all-open-questions` (gather once, the seven-test acceptance gate over the returned region with its eight reason strings and one-slot repair template, embed by whole-block-replacement `Edit` at 2-space indents), `answer-all-open-questions-with-recommendation` (gather in document order, drop unresolvable edges, depth walk with origin promotion, per-question re-check that also lifts the commit body), `review-milestone-requirements` (author, prune, dedup, transitive dependent strip), and `derive-tasks` (its precondition is a scan for any `<open-question` line, and its stop message lists the Short Titles). The five-entity un-escaping rule (`&amp;` last) is spelled out in six of those files. The `recommend-open-question` agent renders the child elements itself, indents them, escapes them, and self-checks the two boundary shape tests; the `answer-open-question-with-recommendation` agent stages `<MILESTONE_DIR>/requirements.md` path-scoped and returns bare `DONE`/`FAILED`.

### Indirect readers of the question set

`core/shared/recommend-procedure.md` reads `requirements.md` for the sibling blocks' embedded recommendations and the principle store `milestones/answer_decision_principles.md` in place. `ask-in-milestone-context` lists "any remaining open questions" among what it reads from `requirements.md`, `modify-milestone-goal` reports which open questions a goal change settles, opens, or moots, and `submit-task` and `discuss-new-task` only point at `/discuss-open-question`. `finish-current-milestone` and `goto-next-milestone` never read a question, and `goto-next-milestone` detects a defined milestone by its directory alone.

### Commit and provenance contracts on the question path

`core/shared/commit-procedure.md` takes an explicit PATHS set (guarded by `git status --porcelain -- <PATHS>`, staged by name, never `git add -A`), and every question skill passes `<MILESTONE_DIR>/requirements.md` as its sole path, under `Requirements-review:`, `Recommendation-annotation:`, `Manual-answer:`, `Recommendation-answer:`, and `Alternative-answer:` subjects. `capture-milestone-principle-updates` walks `git log -E --grep='^(Manual-answer|Alternative-answer|Recommendation-answer): ' -- milestones/<milestone_id>/requirements.md`, reads each commit with `git show <hash> --format='%s%n%n%b' -- milestones/<milestone_id>/requirements.md`, and reconstructs the answered block from the diff's removed lines between `-<open-question id="…"` and `-</open-question>` while reading the recorded decision from the added lines; it also treats pre-block-form blockquote answers (`> **Deferred — …:**`) as the no-recommendation case.

## Decisions

### `open_questions.xml` document shape

- The root element of `open_questions.xml` is a bare `<open-questions>` — no XML declaration and no attributes. The empty file `define-milestone-goal` creates is that one empty root, and every `<open-question>` block sits one level inside it exactly as it stood under the old heading. An undeclared document is UTF-8 by the XML spec and stdlib ElementTree reads and writes it that way by default, the directory already names the milestone, and a declaration or root attribute stays available later as an additive change no reader breaks on.

### Tool placement in the plugin tree

- The Python tool lives in a new top-level `core/tools/` directory, and both host definitions add `tools = "tools"` to their `[layout]` so it renders to `{{PLUGIN_ROOT}}/tools/` on every host. A program the runner executes is a different artifact kind from a procedure it follows, and the plugin keeps one top-level directory per kind, so this fourth directory keeps the `core/shared/*.md` procedure rules exact, gives the tool and any test layout beside it a home with rules of its own, and costs one build-validated line in each host `[layout]`. The name is `tools` rather than `bin` or `scripts` because it names what the runner does with the contents, reads as plain English, and overloads no directory the repository already reserves for maintainer build tooling.

### Tool interpreter command

- Every invocation site runs the tool as `python3 {{PLUGIN_ROOT}}/<tool path> …` — one fixed, deterministic command with nothing restated per site — and the once-per-project bootstrap check in `init-milestone-base-workflow` executes `python3` to read its version, probing `python` only when that fails so its message can say the interpreter exists under the other name and must be exposed as `python3`. `python3` is the name PEP 394 guarantees and the one the stock macOS and Debian-family shells the agent usually runs in actually have; the platforms where only `python` exists are exactly what the bootstrap check is for, and probing the second name there — asking the user to expose it as `python3` — buys a per-site probe's coverage at no per-site cost. No invocation site carries a fallback expression, and the runtime prose never consults `python`.

### Tool file resolution

- Every tool invocation takes the already-resolved `<MILESTONE_DIR>` as an argument, and the tool joins it with the one file name it owns, `open_questions.xml`; the caller resolves the milestone exactly as it does today through `get-current-milestone.md`, and the tool never reads `milestones/README.md`. The tool sits below the skills exactly where the shared procedures do, and that layer takes resolved inputs from its caller — every question skill already holds `<MILESTONE_DIR>`, `define-milestone-goal` must write a milestone the pointer does not name, and a pytest case then needs only a `tmp_path` — so passing the directory keeps one pointer parser in the plugin and one file name inside the tool. The argument is the directory rather than the document path because the goal already binds the tool to `<MILESTONE_DIR>/open_questions.xml` and its creation, so the shorter argument the prose already carries wins.

### Tool output and error contract

- Every read prints only the un-escaped value the runner needs, one item per line: set queries (list, the dependency walk) print bare ids in document or walk order, locate prints the block verbatim as the file holds it, and lift prints the recombined answer text (`<option> — <rationale>` or `<id> — <what-it-is>`). Every mutator (create, add, embed, remove, reconcile) prints nothing on success. Every failure is exactly one `Error: <reason>` line on stderr with exit status 1 (a malformed invocation keeps argparse's native usage message and exit 2), a non-zero exit guarantees the document is byte-for-byte unchanged, no traceback ever reaches the runner, and an empty set is empty stdout with exit 0 — emptiness is data, never a failure. The runner is an LLM reading a console, so the contract that costs it the fewest tokens per call and the least decoding is bare un-escaped values on stdout and nothing at all from a mutator, with failure carried by the two signals every process already has; that reason line fills the repair template's slot verbatim, a failing lift is the answer sweep's re-check and skip in one call, an empty set staying exit 0 means no consumer ever mistakes a converged document for an error, and which checks and mutations the tool exposes may still change without changing the form of what is printed — which is what rules out a verdict token that would only duplicate the exit status a process already has.

### Tool text input channel

- `add` and `embed` keep their short identifiers (the Short Title among them) as ordinary arguments and read their one free-text body — the question text, the returned fragment — from standard input, which every runtime invocation site supplies as a quoted-delimiter heredoc (`<<'EOF' … EOF`); the tool reads `sys.stdin.buffer` and decodes it as UTF-8 itself, refuses a terminal stdin with an error so a call that forgot its heredoc fails instead of blocking, and reads exactly one body per call. There is no path argument and no `--from` flag: `< file` redirection and `subprocess.run(input=…)` give a saved file and the pytest suite the same entry at no code cost, so a second channel would be code without a consumer. The body is the one input that is prose or XML rather than an identifier, so it travels by the channel that carries bytes untouched — a quoted heredoc passes a multi-line fragment full of backticks, `&apos;`, and `${…}` verbatim with nothing expanded, in one shell call and with no per-call escaping by the runner, the same idiom the coding agent's shell tool already relies on for multi-line content — and the channel is indifferent to whether `embed` receives the agent's whole message or only the extracted region, because both travel the same way.

### Clearing a stale recommendation

- The tool gains a `strip` subcommand that takes one or more Short Titles beside the milestone directory every other subcommand takes and, for each named block, deletes every child between its `<question>` element and its `</open-question>` line — the `<alternative>`, `<applied-principle>`, `<depends-on>`, and `<recommendation>` children — leaving the wrapper and `<question>` intact; it touches no dependent and no `<depends-on>` tag that names the block, rejects an unknown id with the document unchanged, and does nothing on a block already bare. Clearing a stale recommendation is that one call followed by a re-run of `/recommend-all-open-questions`, whose skip rule regenerates the now recommendation-less block. There is no hand-edit exception — the on-disk document is always the tool's own output, with no caveat on the sole-writer clause anywhere it is stated — and no skill wraps the subcommand: a skill around it is an additive step to take only if the hatch, unexercised in every commit to date, ever becomes routine. The strip is the same per-block primitive the tool already performs internally for the transitive strip in `<depends-on>` reconciliation and the dependent-strip on prune — one behaviour serving the reconciliation walk transitively and the user one block at a time — so exposing it costs an argparse entry and a test, and in return the user gets an id-validated one-line call in place of an eye-located multi-kilobyte edit on the one file whose escaping and indentation are tool-internal, and a half-deleted block the tool would refuse at every later call cannot arise.

### Reconciliation on removal

- `remove` takes an optional `--option <recorded option>` and, after deleting the named block, reconciles that block's dependents in the same write: with the option, a surviving block whose `<depends-on>` names the removed id with an equal un-escaped, case-folded option loses that one tag and every other dependent of the removed id is stripped; without it — a mooted sibling, a review prune or dedup — every dependent is stripped; both transitively over the dependents of stripped blocks, before the single write. There is no separate `reconcile` subcommand. Every removal the plugin performs is followed by reconciliation and none ever skips it, and a removal with no recorded option is exactly the strip-every-dependent case under strip-on-doubt, so the one optional flag covers the answered block, a mooted sibling, a prune, and a dedup with one call and one write each and makes "no removal leaves a dangling tag" hold by construction; reconciling one removed block per call in any order reproduces the set-at-once outcome of the reconciliation step because a strip is monotone and subsumes the tag drop, whereas a separate `reconcile` would break the tie on its second call buying nothing any caller wants while adding a forgettable step whose omission is silent and lets the answer sweep record a dependent's stale recommendation. The literal-answer path's judged-agreeing dependents are the one case left to route, on top of this strip-all default.
- The literal-answer path routes that case through the same flag and the tool gains nothing for it: the recording core's judgment mode collapses to one verdict per answer — whether ANSWER plainly settles on one of the answered block's own `<alternative id>` values — and the procedure passes that id as `remove … --option`, so the exact-id engine untags the dependents that assumed it and strips the rest; an answer that settles on no listed alternative (or a hand-cleared target with none) passes nothing, which is the bare `remove` and its strip-all default. The tool rejects an `--option` naming none of the removed block's alternatives, so a mistyped judgment fails loudly with the document unchanged rather than stripping silently, and the core's judgment-mode contract is restated as judging one settled id from the block's alternatives — a judgment made in prose against the closed set the runner already holds, never a parse of ANSWER, a line an editor must keep drawn. A dependent's tag records an option, not a claim about that dependent, so every per-dependent verdict the literal path could form is the one verdict of whether the answer settles on that option — exactly the comparison `remove --option` already makes — which gives one engine and one write for every answer path, makes a literal answer reconcile exactly as a lifted one would on the same document, and needs no dependent enumeration, no new flag, and no multi-call window; the one thing per-dependent verdicts could add — keeping a dependent whose assumed option the answer only arguably preserves — is precisely the doubt case strip-on-doubt says to strip, which is what rules out a repeatable `--agree` flag on `remove` and per-dependent `untag`/`strip` primitives applied around the removal alike. The accepted cost is that an answer agreeing in substance but matching no listed id — a refinement, a partial answer, or a target regenerated with renamed alternatives after the tags were embedded — strips every dependent, a re-dispatch each.

### Capture's per-commit read

- `capture-milestone-principle-updates` keeps its log filter on `open_questions.xml` alone and reads each answer commit with one `git show` that names both files — `-- <MILESTONE_DIR>/open_questions.xml <MILESTONE_DIR>/requirements.md` — so the removed lines of the `open_questions.xml` hunk feed the block reconstruction and the added lines of the `requirements.md` hunk fill `recorded_decision` exactly as today; the per-commit record, the `Manual-answer:` agreement test with its "the body or the added `## Decisions` entry" fallback, and the fresh-option best guess stay unchanged for one added pathspec on one command. The recording core writes the decision into `## Decisions` by contract and the one-commit-=-one-answer invariant carries that fold beside the block removal in the same commit, so the `requirements.md` hunk is the only source that still holds the decision itself on the deliberated `Manual-answer:` path, whose body is reasoning by contract and whose `agrees`/`overrides` class sets the reinforcement shield. A body-alone read would weigh a wrongly shielded or unshielded store entry against about a fifth of a read the removed block dominates anyway, and a provenance-conditional second pathspec would save a paragraph per commit at the cost of the first per-provenance rule in a diff read that has kept every rule it carries uniform, so one uniform show wins.

### CI Python versions for the tool's test suite

- CI runs the tool's pytest suite twice in one job and never as a matrix: a pinned run, `uv run pytest` in project mode under the interpreter `.python-version` names (3.13 today) against the pytest the locked `dev` group serves, and a floor run, `uv run --no-project --python 3.9 --with pytest pytest`, which bypasses the build tooling's `requires-python = ">=3.11"` (the stdlib-only tool needs nothing from that project) and resolves the last pytest that supports 3.9. `pyproject.toml`, `uv.lock`, and the build scripts stay untouched; the pinned run carries no version literal, so a pin bump is one file, and the floor run's literal `3.9` is the floor's third home beside the README prerequisite and the bootstrap check. The 3.9 floor is a promise the README makes and the bootstrap check enforces, so CI must run the suite under it or the promise is checked by nothing — and the tool is written on the pinned 3.13, exactly where a `match` or an `X | None` slips in unnoticed and first fails at a user's stock 3.9.6 after bootstrap has passed them. Because stdlib availability is monotone across minors, the two bracketing runs catch every too-new-for-the-floor and removed-by-the-pin slip, whether the suite imports the tool or drives it through `sys.executable`, which is what rules out a five-leg matrix whose interior runners could fail only on a version-specific stdlib bug; lowering the project floor falls out because it rewrites build tooling for an interpreter it never runs under. Two pytest majors are in play (8.4 under 3.9, 9 under 3.13 today), so the suite stays on the API both share.

### `embed` extraction ownership

- `embed` accepts the recommend agent's whole final message on stdin and extracts the fragment itself — slicing from the first `<alternative` line through the last `</recommendation>` line before it parses and validates, discarding the text outside that region, a slice that is the identity on a clean return — and the orchestrator keeps only the last-line verdict: a return whose last non-whitespace line begins `FAILED:` is skipped unrepaired, as at every dispatch site, and every other return is piped to `embed` whole. Extraction is a deterministic line-range operation keyed on the fragment's own boundary tokens and, on the milestone-19 evidence, the common case rather than the exception, so it belongs in the tool — a short slice before the parse `embed` performs anyway, the identity on a clean return so it needs no mode, pytest-covered, and the source of every repair reason, the two extraction misses included, as one `Error:` line from one place — while the last-line `FAILED:` verdict stays with the orchestrator because it is agent protocol shared with the two tool-less dispatch sites and its outcome (skip, never repair) is a control decision only the orchestrator takes, which is what rules out handing the tool the whole judging pipeline. The surrounding prose the orchestrator re-emits is a paragraph against a multi-kilobyte fragment, far cheaper than a line-range rule kept in prose.

<open-question id="Canonical serialization format">
  <question>What on-disk formatting does the tool guarantee when it writes `open_questions.xml` — one element per line at a fixed indent per level, and which entity escapes — so that git diffs and capture&apos;s removed-line reconstruction stay line-oriented?</question>
  <alternative id="Canonical writer, five entities">
    The tool re-renders the whole document from its parsed tree on every write through its own small serializer: one element per line at exactly 2 spaces per depth (the root at column 0, each `&lt;open-question&gt;` at 2, its `&lt;question&gt;`, `&lt;alternative&gt;`, `&lt;applied-principle&gt;`, `&lt;depends-on …/&gt;`, and `&lt;recommendation&gt;` children at 4, and inside an alternative the what-it-is text on its own line above `&lt;advantage&gt;` and `&lt;drawback&gt;` at 6), every text value folded to one line (whitespace runs and newlines collapsed to a single space, ends trimmed), self-closing tags written `/&gt;` with no space, and all five predefined entities (`&amp;amp;`, `&amp;lt;`, `&amp;gt;`, `&amp;quot;`, `&amp;apos;`) substituted in element text and attribute values alike.
    <advantage>Byte-determinism by construction — the same tree always writes the same bytes whatever the input looked like (the agent&apos;s fragment, a hand-edit, an older write), so a diff shows exactly the elements that changed and every child stays one greppable line for capture&apos;s removed-line reconstruction; the agent&apos;s own indentation and escaping stop being load-bearing because `embed` parses the fragment and re-renders it; the five-entity rule is the single convention every consumer already reverses (`&amp;amp;` last) and one `xml.sax.saxutils.escape` call with the two extra entities produces it for text and attributes alike; and `write(read(x)) == x` on a golden file is the whole format test.</advantage>
    <drawback>A serializer of the tool&apos;s own — a short walk over a fixed element set, but code to own and test — instead of stdlib output; every apostrophe in prose is stored as `&amp;apos;`, so the raw file and its diffs are noisier to a human than XML requires; and the one-line fold means no text value can ever carry a line break, a constraint the current one-line convention never needed but a hard one.</drawback>
  </alternative>
  <alternative id="Canonical writer, minimal escapes">
    The same serializer and layout, escaping only what XML requires — `&amp;amp;` and `&amp;lt;` in text (`&amp;gt;` too, as ElementTree does) plus `&amp;quot;` inside attribute values — so an apostrophe is never escaped and a double quote is escaped only inside attributes.
    <advantage>The raw file and every diff line read as prose — a possessive stays `root&apos;s`, a quoted term stays `&quot;tools&quot;` — at no parser cost, since ElementTree un-escapes whichever form it meets and capture&apos;s five-way reversal is a no-op on entities that never occur.</advantage>
    <drawback>Two escape rules where one would do (text and attribute values differ), the on-disk form then diverges from the five-entity rule every runtime file and the agent&apos;s fragment rule state, so a raw-line reader that never parses must know the writer&apos;s policy to know what a bare `&apos;` or `&quot;` in a line means; and the readability gain lands where it is least needed, because the raw file&apos;s readers are the tool, the recommend agent, and `git diff`, none of which trips on `&amp;apos;`.</drawback>
  </alternative>
  <alternative id="Stock ElementTree pretty-print">
    The tool parses with `xml.etree.ElementTree`, mutates the tree, and writes with `ET.indent(space=&quot;  &quot;)` followed by `ElementTree.write`, accepting whatever layout and escapes the stdlib emits.
    <advantage>No serializer code at all — parse, `indent`, write, every call present since Python 3.9 (`ET.indent` arrived in 3.9, exactly the documented floor) with well-formedness guaranteed by the library.</advantage>
    <drawback>It cannot produce the block shape: `ET.indent` leaves mixed content alone, so an `&lt;alternative&gt;` whose what-it-is text precedes its children renders as `&lt;alternative id=&quot;A&quot;&gt;what it is&lt;advantage&gt;…&lt;/advantage&gt;` on one line with `&lt;drawback&gt;` on the next, and re-reading an already-indented file drifts the first child&apos;s indent (verified on CPython 3.13.5) — the one-element-per-line guarantee fails on exactly the element capture reads as &quot;the element&apos;s own text before its first child&quot;; its escape set is a third convention (`&amp;gt;` escaped, `&apos;` and text `&quot;` not) and self-closing tags gain a space (`&lt;depends-on … /&gt;`); the only cures are a custom writer, which is Canonical writer, five entities, or moving the what-it-is text into a leaf child, which changes the block schema the goal fixes and every reader of it.</drawback>
  </alternative>
  <alternative id="Line splice, no re-render">
    The tool never re-serializes: it treats the file as lines, locates blocks by their boundary lines, validates each fragment it is handed by parsing it in memory, and splices or deletes line ranges byte-for-byte, so the file&apos;s formatting is whatever its writers supplied — checked, never normalized.
    <advantage>Untouched blocks never change a byte, so a diff is exactly the spliced range and nothing else, a hand-edit outside the target block survives verbatim, and it is the most direct port of the boundary-line prose into Python.</advantage>
    <drawback>It guarantees no format at all — the layout and escapes are the union of what each writer passed (the agent&apos;s fragment indentation, a hand-edit, a differently indented `add`), so &quot;fixed indent per level&quot; can only be enforced by rejecting every deviating fragment (with a repair round each time) or left inconsistent; and every operation is line arithmetic over a document the tool also parses, two representations that must agree — the fragility the goal moves into one tool to retire, relocated rather than removed.</drawback>
  </alternative>
  <recommendation option="Canonical writer, five entities">The guarantee the question asks for exists only if the writer normalizes, and the stdlib pretty-printer cannot render the mixed-content `&lt;alternative&gt;` one element per line, so the tool must own a small fixed-shape serializer in any case; owning it makes every write a full canonical re-render — same tree, same bytes, whatever the agent, a hand-edit, or an older write supplied — with every child one greppable line at 2 spaces per depth under the bare root and no column-0 exception for the blocks (every raw-line reader keys on the tag, not the column), and the five-entity rule wins the tie against minimal escaping because it is one rule for text and attributes, the convention every consumer already reverses, and the raw file&apos;s readers (the tool, the agent, `git diff`) pay nothing for it.</recommendation>
</open-question>
