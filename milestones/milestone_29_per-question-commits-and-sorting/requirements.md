# Milestone 29: Per-question recommendation commits and question sorting

## Goal

Change the recommend sweep's commit granularity from one commit per run to one commit per embedded question, mirroring the answer sweep: after each successful `embed`, the orchestrator commits `open_questions.xml` path-scoped under `Recommendation-annotation: <Short Title>` with the lifted recommendation line as the body, and a skipped question commits nothing. Add a `sort` subcommand to `open_questions.py` that rewrites the document with the annotated blocks first in `walk`'s order (origins, then dependents by depth, same-depth ties and un-annotated blocks in stable prior document order) and every `<recommendation>`-less block last, reusing the walk algorithm so `walk` is by construction the annotated prefix of `list` on a sorted document; the serializer itself keeps writing blocks in their existing order, so no other write reorders anything. The recommend sweep runs `sort` once after its last dispatch and commits the reorder as its own `Question-ordering: <milestone_id>` commit behind the dirty-own-path guard, so a human reviewing the document reads the questions whose answers cannot be nullified by a dependency first.

## Relevant starting state

### The recommend sweep's commit step

`core/skills/recommend-all-open-questions/SKILL.md` embeds per question and commits once per run. Step 3 dispatches one read-only `cairn:recommend-open-question` agent per un-annotated block, strictly sequentially, and judges each return through a fixed pipeline — last-line `FAILED:` verdict, then one `embed` call over the whole message piped as a quoted heredoc, then exactly one repair (a `SendMessage` continuation where the host allows it, else one fresh re-dispatch) — embedding or skipping the question before the next dispatch. Step 4 then runs `{{PLUGIN_ROOT}}/shared/commit-procedure.md` once, after the last question, with PATHS `<MILESTONE_DIR>/open_questions.xml` and SUBJECT `Recommendation-annotation: <milestone_id>`, and states explicitly that committing never happens inside the dispatch loop. Step 5 prints the one terse line `Recommendations embedded.` plus a still-skipped advisory, or a distinct no-op line when the dirty-own-path guard fired because no `embed` wrote. The skill is idempotent through `list --unannotated` (step 1b), so a re-run annotates only the blocks still lacking a `<recommendation>`, and the `strip` hatch (step 2) is the only way to regenerate one. The orchestrator itself is the writer here — no agent stages anything — so the commit-procedure path (path-scoped `git add`, then commit) is the one in use, not the agent-staged-index path.

### The per-item commit model already in the plugin

`core/skills/answer-all-open-questions-with-recommendation/SKILL.md` step 2 is the existing one-commit-per-question orchestrator: before each dispatch it runs the tool's `lift <MILESTONE_DIR> "<Short Title>"`, holds the printed "`<option>` — `<rationale>`" line as the commit body, and after the agent's `DONE` commits the agent-staged index under `Recommendation-answer: <Short Title>` with `git commit -m "<subject>" -m "<body>"` behind a `git diff --cached --quiet` nothing-staged guard, one commit per answer. `complete-all-tasks` commits per task under `Tasklist-completion:` with the task heading in the body. `core/shared/commit-procedure.md` is the shared guard → path-scoped stage → commit step and takes only PATHS and SUBJECT; the body lines are described as "any body lines the caller supplies". The tool's `lift` works on any annotated block, so the same line is available immediately after a successful `embed`.

### The open-question tool's document order and `walk`

`core/tools/open_questions.py` keeps blocks in the order of `document.questions`: `render_document` writes them in that list order, every mutator is `load_document` → mutate the parsed tree → `save_document` (an atomic temp-file rename in `_write_bytes`), `add` appends, and `embed`, `strip`, and `remove` leave every surviving block in place. `walk_order(document)` already implements the target ordering over the annotated blocks only: gathers the `<recommendation>`-bearing blocks in document order, builds edges from `<depends-on question>` values to gathered blocks (edges to absent or un-annotated blocks dropped, the `option` value never read), places origins first, then repeatedly every block whose every edge is placed, same-depth ties in document order, and promotes the document-order-first remaining block when stranded; it returns `Question` objects, and `cmd_walk` prints their ids. Un-annotated blocks are outside `walk_order` entirely. Subcommands are registered through `add_subcommand(name, func, help)` in `build_parser`, with the module docstring's `Subcommands:` list and the format/contract prose as the documented surface; a mutator prints nothing on success, and every failure is one `Error:` line with the document unchanged. No subcommand today reorders blocks, and nothing in the runtime prose or docs promises any ordering beyond "document order".

### Consumers of document order

`list` and `list --unannotated` print in document order; the recommend sweep's `locate` prints in the order named and its dispatch order is a judgment ranking, independent of document order; `walk` uses document order only for tie-breaks and cycle promotion; the review pass and every whole-document reader (`discuss-open-question`, `ask-in-milestone-context`, `modify-milestone-goal`, the recommend agent) read the file in place. `capture-milestone-principle-updates` walks answer commits with `git log -E --grep='^(Manual-answer|Alternative-answer|Recommendation-answer): ' -- milestones/<milestone_id>/open_questions.xml` and reads the answered block's removed lines keyed on its `<open-question id="…">` tag, never its position, so a commit under any other subject touching that file is never walked and a relocated sibling in a diff contributes nothing.

## Decisions

### Sort on every run

The recommend sweep runs the tool's `sort` as a fixed end-of-run step on every run that found questions: an empty `list --unannotated` print and an all-skipped dispatch loop both fall through to it rather than exiting to the no-op line, and the dirty-own-path guard is the sort's only no-op test. A `Question-ordering: <milestone_id>` commit therefore lands exactly when the sort moved a block, so "sorted after the sweep" is a postcondition of every run rather than of the annotating moment, and a bare re-run is the one way to restore the order the answer path's tag drops and strips disturb; on an already-sorted document the sort is the identity, so an idempotent no-op run still commits nothing. The invariant "a sweep that annotated nothing commits nothing" narrows to "annotated nothing and moved nothing".

### Commit body through the shared procedure

`core/shared/commit-procedure.md` gains a third, optional input, BODY — zero or more body lines the caller supplies as a git commit argument it has already resolved, never a policy the procedure decides. Its commit step runs `git commit -m "<SUBJECT>" -m "<BODY>"` when a body is given and subject-only otherwise, so how a body reaches git is owned by the single source of truth for the commit step rather than restated per caller. The recommend sweep hands over the lifted "`<option>` — `<rationale>`" line as BODY for each per-question `Recommendation-annotation: <Short Title>` commit exactly as it hands over PATHS and SUBJECT, its body-less `Question-ordering: <milestone_id>` commit takes the same procedure with no BODY, and the body-supplying callers already in the tree (`answer-open-question`, `answer-open-question-with-alternative`, `answer-open-question-with-recommendation`, `capture-milestone-principle-updates`) and every body-less caller pass through the one unchanged path. The prose describing the procedure's contract as PATHS-and-SUBJECT (CLAUDE.md and the docs) is updated to name the optional third input.

### Report line when only the sort commits

The recommend sweep carries a second fixed terse success line, `Questions reordered.`, printed when no `embed` wrote but the sort's `Question-ordering: <milestone_id>` commit landed. Its report step picks the line by what the run committed, in a strict order: an embed wrote — `Recommendations embedded.`; else the sort committed — `Questions reordered.`; else the distinct no-op line with its reason. The still-skipped advisory prints alongside whichever line is chosen. Every line thus stays true and identifier-free — the success line keeps meaning there are new recommendations to answer, the no-op line keeps meaning nothing was committed, and the reorder line matches the git log — so the terse-reporting invariant and the docs entry carry a stated carve-out for this one skill's two success lines and their selection rule, and the new string is kept in sync across CLAUDE.md, docs/skill-reference.md, and both host trees.
