# Milestone 26: README landing page

## Goal

Turn the root `README.md` from a 6,500-word reference document into a landing page: drop the banner so the first screen is the release/CI/license badges and the adoption block, a generic host-neutral one-liner, a single simplified mermaid diagram of one milestone loop (define → review → recommend → answer → derive → complete, a stand-in until a later milestone records the demo GIF), and per-host installation, followed by a host-neutral "Why Cairn?" and a short "Design principles" block built from selected design claims. Move the phase narrative with its six mermaid diagrams, the skill reference, the commit conventions, and the answer-principle-learning loop into a new `docs/` directory, promote `temp/cairn-design-claims.md` into it as a committed page the principles block links to, and update every cross-reference in `CLAUDE.md` and `CONTRIBUTING.md` that named those README sections. Rework the two distribution README templates under `scripts/hosts/*/README.md` to the same shape — one-liner, that repository's adoption badges, installation, and the redirect to the root repository for contributors — and rebuild `hosts/` so `build_hosts.py --check` passes.

## Relevant starting state

The one internal anchor is `[Skill reference](#skill-reference)` in the pipeline intro. The pipeline's "Iterating milestone requirements" paragraph already carries the boundary-line-CLI / query-where-it-pays rationale, and a `### The answer-principle-learning loop` subsection (three bullets: teaching flow, recommendation advisory, correction loop) sits inside the skill reference between `review-milestone-requirements` and `discuss-open-question`. ## Decisions

### Root README first screen

The adoption block moves to the first screen as the existing three-row pipe table — six badges, each row the linked owner/repo name, each badge linking to its repository's `traffic-data` branch — with the `## Adoption` heading dropped; the table stays because a badge's own label names only its metric, so the row label is what says which repository it counts. Its caption shrinks from three sentences to one sentence of about two lines that keeps the four facts a reader of the displayed numbers needs: counts are cumulative since 2026-09-04, unique counts are summed per day so a returning visitor counts again, the badge workflow's own fetch adds one unique clone per repository per day, and the monorepo's clones include its CI checkouts. No badge strip and no partial promotion of the monorepo's pair: the whole three-repository block sits on the first screen, since the distribution rows, not the monorepo's, are the counts an install moves.

The title block keeps the bold "Mark the path from idea to shipped." as the lead under `# Cairn` and replaces the subtitle "Milestone-driven development for any kind of work." with the host-neutral one-liner "Milestone-driven development for your coding agent — any kind of work, one milestone at a time." The subtitle seat is where the one-liner belongs: it is that line's host-neutral successor, adding whom Cairn is for and the one-milestone-at-a-time motif in wording that reads across any kind of work, and the two lines render as one paragraph on GitHub, so it adds no first-screen line. The bold tagline stays because it renders inline at no first-screen cost and, with the banner gone, is the last visible trace of the trail-marker metaphor behind the name. The same one-liner sentence goes verbatim into both distribution README templates under their `# Cairn for <Host>` titles.

The first-screen `## Installation` section keeps the two per-host subsections — each its intro sentence and command block, the Antigravity one with its pinning sentence — and the shared `### Bootstrap your project`; only the marketplace-migration paragraph with its second command block leaves the first screen, becoming a short section of its own below the fold (its seat among the below-the-fold sections is settled separately), reached from one bold pointer line in the Claude Code subsection. The two items differ in kind: the bootstrap step is mandatory before any other skill and belongs beside the commands it follows, while the migration paragraph, thirty percent of the section, is written for someone who has already installed, so demoting only the latter gives the first screen the per-host installation the goal names without splitting the install path. The note is moved rather than deleted because the monorepo marketplace still serves every pre-1.5.0 install and nothing else records the switch commands; it can go in a later release once that audience has switched. The cairn-claude template is split the same way, so its install subsection stays word for word identical to the root's.

The banner image file `.github/assets/readme/cairn-banner.png` is deleted with the reference: the task that drops the `<p align="center">` banner paragraph from `README.md` also removes the file in the same commit, taking the now-empty `.github/assets/` directory with it, so no commit leaves the reference gone and the file stranded. Its only consumer is the README line the goal removes, the distribution trees never carry it, and git history already holds it permanently — deletion reclaims nothing from a clone and loses nothing recoverable — so the tree keeps no orphan binary under a README-named directory for a use nobody has named; the social preview, if ever wanted, is a resized upload through repository settings that history can source as well as the tree, and the demo GIF the goal defers is a different asset that starts the assets directory fresh.

The simplified first-screen mermaid diagram draws the six verbs — define, review, recommend, answer, derive, complete — chained by plain arrows, plus one dashed return edge from answer back to review carrying the convergence condition (until no open questions remain), the same dashed repeat-until-satisfied edge the docs' requirements diagram draws; it has no finish step and no milestone-return edge. The requirements iteration is the one fact the six verbs cannot convey and the mechanism the design claims rest on, and a single short arc buys it, while the milestone cycle is already stated in words by the subtitle's "one milestone at a time" and would cost a seventh node and a chain-wide arc to draw. The diagram keeps the shared `%%{init: …}%%` theme block the six phase diagrams carry: invisible when rendered, it keeps the summary in the same font, line color and curve style as the six diagrams it expands into, its wrappingWidth setting is what keeps the return edge's label on one line, and it contains no `{{`, so it would pass the host build's placeholder check should a distribution template ever carry the diagram.

The design-principles block presents three entries — the claims the goal's named novelties map to: the records are machine-readable (claim 11), each decision has a record in git (claim 2, carrying claim 12's provenance subject), and advice gets better with each milestone (claim 5) — each the claim line verbatim as it heads the promoted page, so it matches the heading it links to, followed by one sentence of the design behind it in the README's own voice, and one closing link to the page for all nineteen. The block exists to show an evaluating engineer what is novel, and the novelty is in the mechanism, so the design sentence is not optional and the selection is the three mechanisms nothing else on the first screen can show — machine-readable question blocks, one answer = one commit with a provenance subject, and the principle store — while the loop itself stays with the diagram and "Why Cairn?"; three entries of about a hundred words keep the block short, and the promoted page, keeping all nineteen numbered claims in their own wording with design paragraphs and metrics, holds the depth one link away and gives each verbatim claim line a heading to match.

### Root README below the fold

All four existing sections stay below the design-principles block, with Self-dogfooding moved up one seat: `## How it works`, `## Self-dogfooding`, `## Contributing`, `## License`. `## How it works` keeps its three-file paragraph and gains one closing sentence linking `docs/workflow.md` and `docs/skill-reference.md` — the pipeline intro's only anchor leaves with the pipeline, and How it works is the last tool-level section on the page — and no other section text changes. The relocated marketplace-migration note sits as a short `##` section of its own between Contributing and License: an appendix reached from its pointer line in the Installation section, out of every scrolling reader's path and removable later without moving anything else. All four sections earn their seat — the model, its live instance, the routing surface, the license — and the milestone makes them contiguous for the first time, an adjacency the join-then-showcase order milestone 25 recorded never weighed; Self-dogfooding is read in flow and belongs right after the model it instantiates, while Contributing is found by heading and belongs where a README reader expects it, last before License.

### Docs pages

The moved sections split across two pages under `docs/`, beside the promoted design-claims page: `docs/workflow.md` carries the six phase sections with their diagrams, followed by How skills commit and The answer-principle-learning loop as sibling sections (the loop promoted out of the skill reference), and `docs/skill-reference.md` carries the per-skill and per-agent entries. The split follows how the content is read — one narrative page that runs as run, record, learn, and one lookup page — under the repository's established terms (workflow, skill reference) rather than a generic guide or reference label. Every heading's text is kept, so the existing anchors survive as path-prefixed links (`docs/workflow.md#how-skills-commit`, `docs/skill-reference.md#review-milestone-requirements`) and re-pointing `CLAUDE.md`, `CONTRIBUTING.md`, and the pipeline intro is a path swap; a reader of the reference page reaches the loop by a link out.

The design-claims file is promoted into `docs/` as a frame edit with the claims kept: the 19 claims keep their wording, six-group order, **Design** paragraphs, and **Metric** lines in Simplified Technical English, word-for-word, because they already state what the plugin does and seed the planned eval suite. Only what addresses the wrong reader changes: the self-describing intro becomes one orienting paragraph for a repository reader — what the list is, why it is written in a controlled register, that each Metric names the test that would check the claim, and that no test suite in the repository runs them yet; the closing note keeps its reader-facing half (claims 17–19 concern the plugin's own code, not a user's project) and drops the benchmark-versus-showcase aside; and the one sentence the live plugin contradicts — claim 12's "the work tree is clean after each skill", contradicted by the non-committing bootstrap skill and by the partial-work-stays rule — is corrected in the same register. That is the smallest edit that turns a working note into a documentation page, with the README design-principles block left to do the reader-facing paraphrase.

The two skill-reference entries milestone 15 recorded as stale are corrected as the reference moves to `docs/skill-reference.md`, rather than moved verbatim for a later milestone or folded into a re-verification of all 25 entries: the `goto-next-milestone` heading loses its `<number> <title>` arguments and its body says the skill activates an already-defined milestone — scans `milestones/` for a defined-but-not-yet-active directory, points `milestones/README.md` at it, and creates nothing — and `finish-current-milestone`'s closing sentence names `/define-milestone-goal` and then `/goto-next-milestone` as what runs next, with the wording drawn from the two skills' own opening paragraphs and the `CLAUDE.md` pipeline map. This milestone rewrites the reference's home, so it is the one time the two entries are in scope by construction rather than by a sweep's falsification rule, and the fix is about sixty words that already exist elsewhere; a full re-verification is a task-sized audit whose only known findings are these two, so it is not done. The `goto-next-milestone` heading is the one heading whose text changes in the move; nothing in the repository links to its anchor, so the change breaks no link.

### Distribution README templates

The two distribution README templates under `scripts/hosts/*/README.md` carry exactly the four items the goal enumerates — the one-liner under `# Cairn for <Host>`, that repository's two adoption badges, the host's installation section, and the generated-do-not-edit note that redirects contributors — over the existing source-pointer and license tail, with no loop diagram, no "Why Cairn?" text, and no design-principles block; the link to `uHappyLogic/cairn` the opening sentence already carries is where a reader goes for the pitch. Milestone 23 made the distribution README the install page of the recommended source and accepted exactly one hand-aligned duplicate for the installer's self-sufficiency, and none of the three elements serves that reader: the diagram is a stand-in the demo GIF will retire, and the two prose sections are pitch kept in step by hand and release-lagged on pages with four unique views each. Should the maintainer want the workflow drawn on the install page anyway, the diagram is the only element worth copying, since it alone copies verbatim, build-clean and link-free.
