# Milestone 44: Batched recommendation embeds in one shell call

## Goal

The recommendation pass's post-decision mechanics become one fixed shell call, shown in full in `recommend-all-open-questions` and run exactly as shown: for every picked block it runs the existing `embed --recommendation` heredoc followed by that block's `lift`, then commits `open_questions.xml` once under `Recommendation-annotation: <milestone_id>` with the lifted lines captured as the body, then sorts the document and commits the reorder behind the dirty-path guard. Each `embed` stays its own process, so every valid block is written and each refused block prints its own `Error:` line while the rest land and commit; the runner corrects only the refused blocks and re-sends them in one more call of the same shape, which commits and sorts again, so a run commits once per batch call rather than once per run. The open-question tool is not required to change, but a tool change that shortens the call (a multi-block `embed --recommendation` that prints the lifted line per accepted block) is in scope if it earns its place. `CLAUDE.md`, `docs/`, and the rebuilt host trees restate the pass accordingly.

Out of scope: the alternatives pass, the answer sweep, a task-list tool for the completion move, and any change to how picks are formed.

## Relevant starting state

### The recommendation pass's post-decision steps

`core/skills/recommend-all-open-questions/SKILL.md` runs inline, dispatches no agent, and after its picks are decided (step 3) carries out four separately described steps: step 4 writes each picked block with one `embed --recommendation` call whose rendered elements travel on a quoted heredoc (`<<'EOF'`), in any order, treating a refusal as a rendering slip to fix and re-run as the same call; step 5 runs one `lift` per annotated block, gathers the printed lines as the commit body, and follows the shared commit procedure once under `Recommendation-annotation: <milestone_id>`; step 6 runs `sort` once and commits the reorder under `Question-ordering: <milestone_id>` behind the dirty-own-path guard, never testing the outcome itself; step 7 prints one of two success lines or the no-op line, chosen in strict order by what the run committed, with the still-skipped blocks (no option surviving a recorded decision) as the only advisory. Nothing in the skill is one shell call today: each embed is described as its own tool call, and a refusal stops nothing but is re-sent on its own. The skill's opening paragraph already carries the clause that every tool call is written out in full, never through a variable, alias, or function of the runner's own. The file uses only the `{{PLUGIN_ROOT}}` placeholder (eleven occurrences) and no wording slot, so the three host trees render it identically apart from the plugin-root value.

### The open-question tool's `embed`, `lift`, and `sort`

`core/tools/open_questions.py` (stdlib-only, Python 3.9+, about 1,270 lines) takes one block per `embed` process: `embed --recommendation <MILESTONE_DIR> "<Short Title>"` reads the whole message from standard input (a heredoc or a redirected file; a terminal, closed, or non-UTF-8 stdin is refused), slices from the first `<applied-principle`, `<depends-on`, or `<recommendation` line through the last `</recommendation>` line, parses and validates the fragment (exactly one `<recommendation>` naming one of the block's own `<alternative>` ids, every `<depends-on>` resolving to another block's alternatives, a target carrying alternatives and no recommendation yet), checks the block state before reading stdin, and rewrites the whole document in canonical form through a temporary file and a replace. No multi-block form of `embed` exists. `lift <MILESTONE_DIR> "<Short Title>"` prints exactly one line, `<option> — <rationale>` with an em dash, un-escaped, and fails on a block carrying no `<recommendation>`. `sort` rewrites only when a block moved. The tool's contract, stated in its module docstring and enforced by `tests/test_contract.py`: a mutator prints nothing on success and exits 0, and every failure is exactly one `Error: <reason>` line on stderr with exit 1 and the document unchanged, never a traceback.

### The tool's test suite

`tests/` holds one flat file per subcommand or concern: `test_embed.py` (72 tests), `test_lift.py` (21), `test_sort.py` (23), `test_contract.py` (11), with the tool run as a subprocess through the `run_tool` fixture in `conftest.py` and golden fixtures `annotated`, `bare`, `empty`, and `entities` under `tests/fixtures/`. The embed tests cover both shapes end to end: byte-for-byte reproduction of stripped fixtures, fragment slicing past surrounding text, every refusal class, the stdin contract (terminal, closed, non-UTF-8, verbatim read with nothing expanded), and write-once-or-never atomicity. A tool change is gated by both pytest runs (the pinned interpreter and the 3.9 floor) and by CI's single job running `--check` then both.

### The batched alternatives pass (milestone 43 precedent)

`core/skills/provide-alternatives-to-all-open-questions/SKILL.md` step 3d is the one existing batch call: a fixed shell script shown in full and run "exactly as shown, with only `<scratch dir>` and `<MILESTONE_DIR>` replaced", a `find … | while IFS= read -r f` loop that redirects each scratch file into `embed --alternatives`, then carries out the commit procedure's three steps literally inside the loop (`git status --porcelain -- <path>`, `git add <path>`, `git commit -q -m "Alternatives-annotation: $t"`), one subject-only commit per question, git's success output silenced. The call prints nothing when every file embedded and committed, and otherwise one line per refused file or failed commit (`<Short Title>`, a tab, the `Error:` line or git's first line), which fills the one repair and then the advisory; the pass tracks per question only whether it has had its repair. Its loop variables (`f`, `t`, `err`, `out`) are each one quoted value set and used within the one call, which CLAUDE.md's shell-literalness invariant scopes outside the ban on holding a tool command or a path list in a variable. The inputs there are files an agent wrote; the recommendation pass's inputs are elements the runner renders in its own turn, with the heredoc as the prescribed carrier.

### The shared commit procedure

`core/shared/commit-procedure.md` is three steps: a dirty-own-path guard (`git status --porcelain -- <PATHS>`, each path a literal argument), a path-scoped `git add`, and `git commit -m "<SUBJECT>"` with an optional second `-m "<BODY>"` the caller supplies already resolved and the procedure forwards verbatim; no `--allow-empty`, and a guard that fires means stage nothing, commit nothing, report the no-op. It carries no wording slot. Runners carry it out themselves in their own turns; the alternatives batch is the only site that writes its three steps into a shell call.

The log holds 63 `Recommendation-annotation:` commits and 14 `Question-ordering:` commits (the ordering commit lands only when `sort` moved a block). Each annotation body is the lifted lines verbatim, one `<option> — <rationale>` line per annotated block; the milestone 43 run on 2026-10-08 recorded eight such lines in one commit. ### Measured cost of the current shape

A local transcript measurement from October 2026 (kept outside the repository) covered the twelve recommendation runs since the alternatives/recommendation split: embed calls per run ranged from 2 to 16; seven of the twelve runs already issued every embed in one turn (seven of nine Fable 5.1 runs, none of the three Opus 5 runs); post-decision tool turns had a median of 6 against a two-turn floor (range 3 to 61, the outlier a 16-embed run that spent 16 turns on embeds), and those turns held 71% of a run's input. The estimated saving of batching to the floor is about 0.6M input tokens per milestone, 3.5% of the milestone budget. The same measurement notes that an `embed` printing the lifted line on success would depart from the tool's "a mutator prints nothing on success" contract.

## Decisions

### The open-question tool

- The open-question tool, its tests, and its contract stay unchanged: no multi-block form of `embed --recommendation`, no lift-printing flag, and no new subcommand or output shape. The batched shell call runs one `embed --recommendation` process per picked block, each with its own quoted heredoc, followed by one separate `lift` per block whose embed succeeded. A refused block is refused by its own process with the document unchanged for that block, while the other blocks' processes still write.

### The batched shell call

- The lifted lines are carried to the annotation commit in one quoted shell variable, set empty at the top of the batched call and grown inside it. Each block's `lift` runs only inside the branch its `embed --recommendation` opens on exit 0, and its printed line is appended with an explicit newline join written in shell-neutral form, so a refused block never reaches `lift` and adds no line. The lift follows its own embed, block by block. After the dirty-own-path guard and the path-scoped `git add`, the call commits with `git commit -q -m "Recommendation-annotation: <milestone_id>" -m "$body"`, the commit procedure's own second `-m` form, and that annotation commit is conditioned on a non-empty body so a zero-block call never commits an empty-bodied annotation. The variable is one quoted text value set and used within the one call, never a tool command or a path list; the shell-literalness invariant's wording in `CLAUDE.md` is extended to cover a value that accumulates across the call.

- When an embed inside the batched call refuses a block, the call pairs the refusal with its block itself: each embed's stderr is captured into one quoted value per block (`2>&1` inside a command substitution, set and used within the call), and when the embed exits non-zero the call prints one line for that block, its Short Title, a tab, then the tool's `Error:` line. Accepted blocks print nothing of their own. The open-question tool is unchanged, and the same pairing covers every refusal class, whether or not the `Error:` line names the block, so the shape matches the alternatives pass's batch call.

- One batched shell call carries every picked block of the run, however many there are. The skill states no cap on blocks per call and no splitting rule; the only further calls a run makes are the corrected re-sends of refused blocks, each of the same shape and each committing and sorting.

- A run makes at most one corrected re-send call: every block the first batched call refuses is corrected and re-sent together in one more call of the same shape, and a block that call refuses again is skipped. The skipped block is reported in the end-of-run advisory with its Short Title and that second `Error:` line verbatim and the remedy of re-running the pass, which re-picks it because it still carries no recommendation. The run's success line is chosen as usual from what it committed, so a run is bounded at two batched calls and two annotation commits, mirroring the alternatives pass's repair-once-then-skip rule.

- A run with no block to write (every block already carried a recommendation, or every candidate was skipped for having no surviving option) runs the same fixed batched shell call as every other run, with its per-block embed-and-lift section repeated zero times: the annotation part writes and lifts nothing and its commit, conditioned on a non-empty body, does not fire, and the call goes on to sort and commit the reorder under `Question-ordering: <milestone_id>` exactly as a full run does. The skill shows one call, well-formed with no block section in it, and has no branch and no second form for the zero-pick case.
