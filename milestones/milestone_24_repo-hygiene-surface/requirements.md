# Milestone 24: Repo Hygiene Surface

## Goal

Give the cairn repository the hygiene surface a first-time visitor scans for. Add a GitHub Actions workflow that runs `uv run scripts/build_hosts.py --check` on every push and pull request, with a CI badge beside the release badge; a root `CONTRIBUTING.md` (edit `core/`, rebuild, invariants live in `CLAUDE.md`), `SECURITY.md`, `CODE_OF_CONDUCT.md`, bug and feature issue templates, and a pull-request template; a `CONTRIBUTING.md` template in each host definition that renders into the host tree and points contributors at the root repository; an in-repo `CHANGELOG.md` backfilled from every existing GitHub Release and thereafter maintained by `/release-plugin`, which prepends each release's composed notes and stages the file in the `Release: <VERSION>` commit so the changelog, the monorepo release, and the distribution releases carry identical notes; and Discussions enabled on the root repository. `FUNDING.yml` and release cadence are out of scope.

## Decisions

### Contributor workflow

An outside contribution is proposal-first, then a contributor-run milestone on a maintainer-reserved slot. A substantive change is proposed as an issue or Discussion; acceptance is the maintainer running `/define-milestone-goal` on `main` with the accepted proposal — only while their own current-milestone pointer is `none`, and never activating it there — which reserves the milestone number. The contributor branches from that define commit, runs `/goto-next-milestone` in the fork as the first step, and runs the full requirements-and-task pipeline through `/finish-current-milestone` there, so the branch's net change to the pointer line is nil and `main`'s pointer stays the maintainer's to hold; an abandoned contribution leaves only its defined directory on `main`, reverted or left as a `goto-next-milestone` candidate; the pull request is merged with a merge commit — squash merges are disabled on the repository — so the milestone commits survive for release notes and for `/capture-milestone-principle-updates`, which the maintainer runs after the merge. There is no plain-pull-request tier: small fixes are filed as issues for the maintainer to make.

The contributor may merge `main` into the milestone branch before running `/finish-current-milestone` only while `main`'s `Current milestone:` line reads `none` — checkable with `git show origin/main:milestones/README.md` — and a sync attempted while the maintainer's milestone is live conflicts on exactly that line, which the contributor answers by aborting the merge and waiting, never by resolving it; after `/finish-current-milestone` the branch reads `none` again and any merge from `main` is safe. The sync is a merge, never a rebase, because a rebase replays the goto commit, whose patch conflicts against any live `main` even after finish. The hazard is a three-way-merge fact — git takes the branch's `none` whenever the branch's last merge base carried a live pointer and `main` still does — so the rule worth recording is the one git enforces: with every merge base reading `none`, the finished branch's pointer line equals its base and `main`'s value wins at every merge with nobody reading it, a sync from a live `main` conflicts on that line as a stop signal where a free-sync rule fails silently, and a post-finish sync is always safe, so the contributor keeps the pull request button-mergeable and drift-gate-checked, which GitHub withholds from a conflicted pull request. The rule has the shape the define step already takes — a contributor milestone is touched in the maintainer's `none` window — and the log shows those windows recur every day or two and last hours to weeks while a maintainer milestone runs hours to a day, so the wait is short. Never syncing would win only if a contributor branch could merge before the maintainer finished another milestone, which a full requirements-and-task pipeline cannot count on, and free sync only if the maintainer's live windows were long enough to block contributors for days, which the log shows they are not.

### Repository settings

Disabling squash merges on `uHappyLogic/cairn` is a task of this milestone, not a setting the maintainer flips by hand: the repository-settings brief that enables Discussions and private vulnerability reporting also runs `gh repo edit uHappyLogic/cairn --enable-squash-merge=false` (or the equivalent PATCH field), verifies by reading `allow_squash_merge` back as `false`, and records that read-back among its `TASKS_DONE.md` entry's Verified bullets. A repository setting that a decision states as fact and that git never records is exactly what this repository has always turned into a task with a read-back — milestone 13's description edit, milestone 23's distribution-repository edits, and this milestone's own Discussions and private-vulnerability-reporting toggles — and here the toggle is one extra flag beside the Discussions enable, so the task costs nothing while its `TASKS_DONE.md` entry is the only place the flip and its verification will ever be written down. The hand flip would be the choice only if the setting were needed before the milestone's tasks run, and nothing needs it before `CONTRIBUTING.md` publishes the merge-commit contract that depends on it.

The unused wiki is disabled on `uHappyLogic/cairn` in the same repository-settings task: the brief that enables Discussions and private vulnerability reporting adds `--enable-wiki=false` — the flag milestone 23 already ran on both distribution repositories — to its `gh repo edit` call, reads `has_wiki` back as `false`, and records that read-back among its `TASKS_DONE.md` entry's Verified bullets, so the root repository joins `cairn-claude` and `cairn-antigravity` in switching off a feature nothing uses. The question's visitor-facing motive is already met — GitHub hides an empty wiki from everyone without write access, so no visitor sees the tab today — but the flag still earns its place because it costs nothing on a `gh repo edit` call the settings task already runs with a read-back, it makes the in-tree documentation rule (`README.md` authoritative, `CLAUDE.md` invariants, the changelog this milestone adds) a setting instead of a habit by closing the one surface where a page could start documentation outside the commit conventions and the drift gate, and it matches the distribution repositories milestone 23 already configured. Leaving the wiki enabled would be right only if a wiki page were foreseen, and none is, while re-enabling stays one flag away. The empty tab a first-time visitor does see is Projects (Open 0, Closed 0), which this decision does not cover; the same flag line can carry it if the maintainer wants that tab gone too.

Enabling Discussions on `uHappyLogic/cairn` keeps GitHub's default category set. The repository-settings task runs the one `has_discussions=true` API toggle the security-policy decision pairs with the private-vulnerability-reporting enable, reads `has_discussions` back as `true` among its `TASKS_DONE.md` entry's Verified bullets like every earlier repository-setting task, and leaves the six categories GitHub creates — Announcements, General, Ideas, Polls, Q&A, Show and tell — exactly as they come: no category is pruned, renamed, or added, and no `.github/DISCUSSION_TEMPLATE/` category form is written. Any intake route that points at Discussions names the default Q&A category by its fixed slug `q-a` (`discussions/new?category=q-a`), and nothing else is pointed at. With proposals on their own issue form, the only intake route that can point at Discussions is a questions route, and the default set already carries the answerable Q&A category that route would name — so a contact link can be written before the toggle runs and points at a category that exists by construction — whereas categories have no create, update, or delete API, so any curation is web-UI hand work no command records, taken on a guess about a community with no discussions yet. Pruning the unused defaults earns its clicks only once real threads show which categories go unused, and a Proposals category only if the proposal route ever moves off the issue form.

The sentence-and-pointer form would win only if the README carried the handoff, which it does not and should not gain, since the README stays the adopter's landing page and the contributor material is moving out of it.

### Continuous integration

The drift-gate workflow triggers on `push` and `pull_request` with no branch filter and no `paths` filter, so the gate runs on every commit reaching any branch of the root repository, on every pull request, and on each release tag push. Filtering is deliberately not done: the gate finishes in 0.2 seconds inside a half-minute free job, so filtering buys nothing measurable, while a `paths` list would be a hand-maintained second copy of the build's input set — the very drift the gate exists to catch — and a path-skipped run would leave a pull request with no status. Every push and pull request is the goal's literal wording, and the two-event trigger has nothing to curate.

The drift-gate workflow pins both its actions — checkout and uv setup — to full 40-character commit SHAs, each followed by a `# vX.Y.Z` comment naming the release it resolves, bumped by hand whenever the maintainer wants a newer release, with no Dependabot configuration. The major-tag half of the question is no longer on offer for one of the two actions: setup-uv stopped publishing major and minor tags at v8.0.0 in March 2026, citing the tj-actions tag-retargeting attack, so `@v10` does not resolve and the only floating tag left is a v7 frozen six months and three majors back; for the other, checkout, the floating tag is a movable pointer on non-immutable releases that GitHub itself re-pointed across every supported major in July 2026 to ship a change marked BREAKING. A full SHA is the one reference neither action's maintainers nor an attacker can move, it is the form setup-uv's README uses in every example, and the version comment keeps the line as readable as a tag, so the workflow runs exactly the code the maintainer read at the cost of two hand-bumped lines — the same posture as `uv.lock`'s hash-pinned pyyaml. Neither form fixes the uv version anyway — setup-uv installs the latest uv unless `pyproject.toml` names a `required-version` — so the pin buys action provenance while the lockfile already supplies the gate's reproducibility. Full-version tags would win only if checkout's releases were immutable, and Dependabot only if the repository accepted plain pull requests, which the contributor-workflow decision rules out.

The CI badge is a third shields.io workflow-status badge in the README's existing centred `<p>` row, `https://img.shields.io/github/actions/workflow/status/uHappyLogic/cairn/<workflow-file>?branch=main&event=push&style=flat&label=ci`, wrapped in a link to the workflow's runs page filtered to `main` (`actions/workflows/<workflow-file>?query=branch%3Amain`), where `<workflow-file>` is the drift-gate workflow's file name the CI task fixes. Both sources report the same runs — shields.io's workflow-status badge fetches GitHub's own `badge.svg` with branch and event passed through and re-renders the status it extracts — so the source is only a question of the row and the scope only a question of the URL: the badge sits beside a release badge that is shields flat, and a native badge's dark gradient panel with its Actions icon would be visibly a second family where the shields form matches panel, geometry, font, and README-owned lowercase label exactly, while the third-party exposure a native badge would avoid is already carried by the release badge next to it, so avoiding it buys nothing. Pinning `branch=main&event=push` makes the badge say the one thing a README visitor should read from it — the drift gate on `main`'s pushed HEAD — where the parameterless default-branch rule is the same today, with `main` the only branch and no pull request ever opened, but leaves the contributor pull-request runs the CI trigger admits to a head-branch filter the reader cannot see. The native badge would win only if the row dropped shields.io altogether, and the parameterless form only if the default branch were expected to be renamed.

### Security policy

`SECURITY.md` directs vulnerability reports to GitHub private vulnerability reporting only — the root repository's Report a vulnerability form — and the milestone enables private vulnerability reporting on `uHappyLogic/cairn` with one `gh api --method PUT` toggle of the same kind as the Discussions enable. Private reporting puts each report where the fix happens, as a draft advisory with a private thread and a publish step, instead of in a gmail inbox. No email address appears in the file: the maintainer publishes none today, and a fallback address is a one-line addition should one ever be wanted, so nothing is lost by leaving it out. The supported-versions table names the latest release only and states that every fix ships as a new release to both distribution repositories — the one honest value, because the sixteen releases are strictly linear, the release skill publishes only `main`'s HEAD, and both patch releases (1.0.1, 1.1.1) landed on the newest minor.

### Distribution tree hygiene files

`SECURITY.md` and `CODE_OF_CONDUCT.md` stay root-only: neither is rendered as a template nor copied through the build into any host tree, and each host tree carries exactly the three non-plugin files it already has or the goal gives it — the `README.md` template, the copied `LICENSE`, and the `CONTRIBUTING.md` pointer template — with the README's generated-do-not-edit paragraph and that pointer as a distribution visitor's route to the root, the `CONTRIBUTING.md` template naming the root's private vulnerability reporting form for security reports beside the issue route. The two files govern interaction surfaces that exist only on the root — the issue tracker, Discussions, and the private vulnerability reporting form enabled on `uHappyLogic/cairn` alone — while the distribution repositories are plugin trees published verbatim with issues, wiki, projects, and Discussions disabled by design, so the goal's asymmetry is principled: `CONTRIBUTING.md` is rendered because a pull request is the one interaction a mirror cannot disable and a pointer there prevents work the next release would overwrite, whereas no report and no conversation can happen on a mirror, so a `SECURITY.md` or `CODE_OF_CONDUCT.md` there could only repeat what the README paragraph and the `CONTRIBUTING.md` pointer already say. Every file added to a host tree also ships inside the plugin to every consumer, the root's issue chooser gains GitHub's own Report a security vulnerability line the moment private reporting is enabled, and milestone 23 recorded that search lands on the monorepo and a distribution repository is only what a user installs from. Pointer templates per host would win only if the distribution repositories were where security reports were expected to originate, and an account-level default-files repository only if every public repository of the account should carry cairn's policy, which it should not.

### Issue templates

The bug and feature issue templates are YAML issue forms, not Markdown templates. Host, cairn version, and skill invoked are the three facts a cairn bug cannot be reproduced without and exactly what free text loses, and required form fields are the only mechanism that guarantees them on a repository with no issues yet and no triage history to fall back on. The host is a two-value dropdown mirroring `scripts/hosts/`, and the version and skill are free-text inputs, so no field enumerates the 21 skills a list would have to track. The one cost is the `gh` CLI gap — it does not detect YAML forms — which a reporter crosses with `gh issue create --web`; a Markdown template would only paper over that gap, since `gh` pre-fills sections it does not enforce, so Markdown would be chosen only if terminal-filed issues were expected to be the main channel.

The proposal that precedes a contributor-run milestone is filed through a third YAML issue form beside the bug and feature forms — not through a Discussions category and not through the feature form. Its required fields are what acceptance consumes: a goal statement in the shape a milestone `## Goal` takes, the motivation, what is in and out of scope, and a checkbox committing the proposer to run the milestone in a fork through `/finish-current-milestone`. A proposal is a work item in waiting whose acceptance produces a milestone and whose pull request should close it, which is what an issue is and a discussion is not: the filing itself yields the `/define-milestone-goal` input and the run-it-yourself commitment the contributor workflow hinges on, on the object GitHub treats as a work item — labels, an assignee, and `Closes #N` from the contributor's pull request — so `CONTRIBUTING.md` and the pull-request template can name "the proposal issue" concretely. Neither feature-form variant can require those fields without dragging every small ask through them, and keeping proposals on an issue form leaves Discussions free for the questions a blank-issues config would route there, with no hand-made category to curate.

A `.github/ISSUE_TEMPLATE/config.yml` beside the forms sets `blank_issues_enabled: false` and carries one contact link — name Ask a question, url `https://github.com/uHappyLogic/cairn/discussions/new?category=q-a`, about usage and how-to questions — and no security link, because the chooser gains GitHub's own Report a security vulnerability line by itself once private vulnerability reporting is enabled. Required fields are the only mechanism that guarantees host, version, and skill on a repository with no issues yet, and the blank-issue link at the foot of the chooser is that guarantee's opt-out — closed for readers by one line while the maintainer keeps a Maintainers-only blank option. With proposals on their own form, the security line added by GitHub itself, and Discussions' default Q&A category the answerable home a question needs, the one visitor a closed chooser would strand is the one with a question, and a single contact link at the fixed slug `q-a` is that door: one four-line file makes the chooser the whole intake map, the small-fix report is a feature-form entry or a question rather than a reason to reopen the forms, and the `gh` and API bypasses that still create blank issues are the gap the forms decision already accepted rather than a new one. Keeping blank issues would be right only if reports fitting no form were expected to be common, which the bug and feature forms plus a question door on a repository with no history gives no reason to expect.

### Pull-request template

The pull-request template asks for the milestone and checks its artifacts: a single `.github/PULL_REQUEST_TEMPLATE.md` opens with two fill-in lines — the reserved milestone id (the `milestone_<N>_<slug>` directory name the maintainer's `Milestone-definition:` commit created on `main`) and `Closes #<proposal issue>` — followed by a reviewer checklist of what a finished contributor milestone leaves in the tree: `milestones/<id>/requirements.md` with no `<open-question>` block, `TASKS_TODO.md` with no task section, `TASKS_DONE.md` carrying every task with its Verified bullets, `milestones/README.md` with the milestone's history entry and the pointer at `none`, one `Milestone-finish: <id>` commit on the branch, `CLAUDE.md` touched only for lasting changes, and `hosts/` rebuilt (which the drift-gate status check confirms). Every pull request this repository will receive is a contributor-run milestone — the contributor-workflow decision leaves no plain tier, the maintainer commits straight to `main` and has opened no pull request in the repository's history, and the drift gate already machine-checks the generic items on every pull request — so the template's only job is the check CI cannot make, that the branch carries the reserved milestone's finished artifacts, and asking for the milestone id and the proposal issue names exactly the two inputs the post-merge steps consume: the id feeds `/capture-milestone-principle-updates`, the `Milestone-finish:` commit feeds the release notes, and `Closes #N` closes the proposal form's issue, over an artifact list the pipeline fixes. A generic checklist would win only if plain-fix pull requests were expected, which the contributor-workflow decision rules out.

### Changelog

`CHANGELOG.md` puts a plain version-date heading over each release's body verbatim: a title, a one-line note that each entry is that release's notes verbatim, newest first, and per release a heading of the form `## <VERSION> — <YYYY-MM-DD>` (the em-dash style of the `milestones/README.md` history headings) directly over the release body, whose milestone sections sit at `###` so they nest under it. There is no Unreleased section and no reference-link list; the body's `**Full Changelog**` line is the compare link. The goal fixes the entry body as the release's composed notes, identical across the changelog and the three release pages, which rules out the categorised body that is Keep a Changelog's substance and leaves only its skeleton to borrow — and that skeleton costs more than it reads: an Unreleased section nothing fills between releases, a reference-link list duplicating the body's own Full Changelog line, and three edits per release in place of one prepend. The plain heading keeps the release write to one prepend below the title with no other slot in the file, and the backfill to a loop over `gh release view --json body` with the `publishedAt` date as each heading's date. The one shape change is that `/release-plugin` step 5 composes the milestone sections at `###` from this release on, and the eight existing sectioned bodies (0.9.8 through 1.4.0) are demoted once in the backfill, so the entry stays byte-identical to the body — which is also what a later reread from the file needs should the release body ever be read back from `CHANGELOG.md`.

The backfill carries the eight link-only releases, 0.9.0 through 0.9.7, verbatim: each entry is the plain version-date heading over the body exactly as `gh release view` returns it, however thin — a lone `**Full Changelog**` compare link, or nothing at all where the published body is empty — with no notes reconstructed from the milestone history or commit ranges and no release page edited. The goal names the existing releases as the backfill's source and requires the changelog and the release pages to carry identical notes, and under the plain heading over the verbatim body that is a single `gh release view` loop that holds for all sixteen entries with no exception. Reconstructing would turn eight entries into a September rewrite a reader cannot distinguish from notes that shipped, and the only way to reconstruct without breaking identity would be to rewrite eight published release pages — the one thing that would change the choice, taken only if the maintainer wants those pages rewritten. The compare link still gives each early entry its commit range, and `milestones/README.md` already holds the condensed per-milestone story.

The eight sectioned monorepo release pages, 0.9.8 through 1.4.0, are edited to match the changelog rather than left one heading level apart from it: the backfill task first demotes their nine `##` milestone-section lines to `###` with one `gh release edit --notes-file` loop whose PATCH carries the body alone and changes no other line — the distribution repositories hold no release, so those eight pages are the whole set — and only then runs the uniform sixteen-tag `gh release view` loop that writes `CHANGELOG.md`, recording among its `TASKS_DONE.md` entry's Verified bullets that every entry read back from the file equals its page body byte for byte. Both paths leave the same words on every page and differ only in whether nine heading markers are moved once, and moving them is what makes the identity hold for all sixteen entries by construction: the backfill is a pure copy with no transformation, the changelog's verbatim note needs no qualifier, and the release series renders at one heading level instead of splitting at 1.4.0 for good, at the cost of a lossless, reversible edit loop over pages the repository already hand-edited on 2026-09-07 when the legacy tags were renamed, with no reader-visible trace left on a page. The link-only backfill's no-page-edited stance guards against rewriting content a reader saw ship, which a heading marker is not; accepting the divergence would be right only if published release bodies were held immutable, and the 2026-09-07 repoint shows they are not.

Once the `Release: <VERSION>` commit exists, the release body is the committed changelog entry: the entry for `<VERSION>` extracted from `HEAD:CHANGELOG.md` — the lines under its `## <VERSION> — <YYYY-MM-DD>` heading up to the next `##` heading, blank lines trimmed — so `/release-plugin` step 7 shows and step 8 publishes that text on a fresh run and a resumption alike, and the changelog, the monorepo release, and the two distribution releases stay identical even when a run fails between creating them. Step 5 composes the body only on a fresh run; a resumption skips it whole and reads the entry back rather than recomposing a condensed rewrite that could hand a distribution release notes differing from a monorepo release already created. Under the plain heading form the extraction is a fixed line range and the body is byte-identical to the entry. A pre-mutation gate beside the tag-existence check requires that no entry for `<VERSION>` exists on a fresh run and that exactly one exists at `HEAD` on a resumption — one grep that flips on resumption — so a stale unpublished Release commit buried below `HEAD`, which would otherwise gain a duplicate entry in a later commit that succeeds, stops in pre-flight instead. The accepted cost is that the skill must state the extraction rule exactly, and that a resumption's skipped step 5 leaves its cross-check and empty-range confirmation un-rerun, resting on the committed entry as the evidence they passed.

The maintainer may revise the release notes at the step-7 pause, and the skill amends the unpushed `Release: <VERSION>` commit in-run rather than stopping. Step 7 takes a revision as a third answer beside publish and stop: while the Release commit is still unpushed — after a fetch, `git merge-base --is-ancestor HEAD origin/main` fails — the skill applies the maintainer's stated revision to the `<VERSION>` entry in the working `CHANGELOG.md` (an edit the maintainer already made by hand in that file counts the same), stages that one path with `git add -- CHANGELOG.md`, amends with `git commit --amend --no-edit` so the `Release: <VERSION>` subject the resumption keys on is untouched, re-extracts the entry from `HEAD:CHANGELOG.md`, shows it again in full, and asks again; once `origin/main` carries the commit — a resumption past step 8a — a revision request is a stop naming that reason, and step 6d's one-commit sentence names this as the run's only amend. Making the release body the committed changelog entry is what makes a revision possible at all — before it, an edit request stopped the run and a re-run recomposed the same condensed rewrite at step 5, so the veto was the only lever — and once the notes are a file the run wrote inside a commit the run made, revising them at the run's own review point is the skill's job rather than a remedy owed by the maintainer: the drift stop sends the maintainer away because the fix is to content the skill does not author, whereas the notes are its own output. An amend of an unpushed commit is the local work step 7 already says a `git reset` undoes, it stays path-scoped to `CHANGELOG.md` and keeps the subject the resumption keys on, step 8 still publishes what `HEAD` records, and checking `origin/main` before amending states the frozen-after-push case up front instead of leaving pre-flight 2c to catch a hand amend that has already gone wrong. A stop-and-hand-amend path would win only if the skill were held never to rewrite even an unpushed commit, and a review before the commit only if the review were meant to move ahead of the write, which the decision that step 7 shows what git records argues against.
