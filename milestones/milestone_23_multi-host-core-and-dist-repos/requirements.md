# Milestone 23: Multi-Host Core And Dist Repos

## Goal

Restructure cairn into a host-neutral `core/` (skills, agents, shared procedures, with a neutral plugin-root placeholder) from which a single build script generates every host plugin into a committed `hosts/<host>/` tree, starting with Claude Code and Antigravity, each from its own manifest template, rewrite rules, and validation, so that adding a host means adding a template rather than a transpiler; the root `skills/`, `agents/`, `shared/`, and `.agents/` trees are removed and the monorepo marketplace repointed at `./hosts/claude`. Extend the release procedure so each release also publishes every `hosts/<host>` tree into its own distribution repository (`cairn-claude`, `cairn-antigravity`) as one ordinary commit tagged with the release version, with no submodules and no hand-edits to those repos, and make `cairn-claude` the documented recommended install source.

## Relevant starting state

### Plugin source layout and the Claude Code manifests

The repository root *is* the Claude Code plugin: `.claude-plugin/plugin.json` (name `cairn`, version `1.4.0`, author) sits beside `.claude-plugin/marketplace.json`, whose single `plugins[]` entry has `"source": "."` and carries its own `version` field. The runtime layer is three root directories — `skills/` (21 skill directories, each a `SKILL.md` with `name`/`description` frontmatter), `agents/` (3 agent files with `name`/`description`/`color` frontmatter), and `shared/` (7 execution-neutral procedure files). Cross-references between them use the Claude Code runtime variable literally: 45 occurrences of `${CLAUDE_PLUGIN_ROOT}/shared/<name>.md` across the layer, naming all 7 shared files, and 18 files additionally carry the prose hint ``(run `echo "$CLAUDE_PLUGIN_ROOT"` if you need to resolve the path)`` after such a reference. No other `${CLAUDE_PLUGIN_ROOT}` form exists. Claude Code supports a marketplace `source` of the form `./<subdir>` and resolves `${CLAUDE_PLUGIN_ROOT}` to that subdirectory; `plugin.json` also accepts `skills`/`agents`/`commands` path arrays relative to the plugin root.

### The Antigravity transpiler and its generated tree

`scripts/migrate_skills_to_agy.py` (Python, `pyyaml` via `uv`, `pyproject.toml` package `cairn-tooling`) is the only host build. It writes `.agents/plugins/cairn/` in place: a generated `plugin.json` (`$schema` `https://antigravity.google/schemas/v1/plugin.json`, description hard-coded as `Ported plugin for cairn`, version copied from `.claude-plugin/plugin.json`), then copies `skills/`, `agents/`, and `shared/` verbatim except for two rewrites — every `${CLAUDE_PLUGIN_ROOT}` becomes the workspace-relative literal `.agents/plugins/cairn` and the resolve hint is dropped. It validates each skill's frontmatter (`name` and `description` present, `yaml.safe_load`-able, with a re-quoting fallback for a bare `description:`), skips any skill directory whose name ends in `-workspace` (no such directory exists today), and copies a root `.mcp.json` to `mcp_config.json` if present (none exists). The generated tree is tracked in git (32 files) and is regenerated by hand and by the release; nothing under it is host-specific beyond the manifest and the path literal. Antigravity expects the plugin at `.agents/plugins/<name>/` inside the consuming workspace.

### Host-specific content inside the runtime layer

The skills are otherwise host-neutral, with four named exceptions. `recommend-all-open-questions` describes its repair step as two branches keyed on host capability — Claude Code's `SendMessage` to a held agent handle, or one fresh re-dispatch "under Antigravity" — and, like `complete-all-tasks` and `answer-all-open-questions-with-recommendation`, addresses dispatched agents by the namespaced registry name (`cairn:<agent>`) phrased descriptively as "the namespaced registry name under this plugin's namespace". `init-milestone-base-workflow`'s CLAUDE.md template opens with "guidance to Claude Code". The `agents/*.md` frontmatter carries a `color` key that only Claude Code reads. Nothing in the layer resolves paths other than through `${CLAUDE_PLUGIN_ROOT}`.

### Version and release tooling

`scripts/set_version.py <MAJOR.MINOR.PATCH>` writes exactly four version literals — `.claude-plugin/plugin.json`, the `marketplace.json` entry, `pyproject.toml`, and `uv.lock` — and deliberately never writes the generated Antigravity manifest. The maintainer-only release skill at `.claude/skills/release-plugin/SKILL.md` (449 lines, outside the shipped tree) runs pre-flight gates (clean tree, `main` not behind origin, no untracked files under `skills/`, `agents/`, `shared/`), validates the version, composes notes from `Milestone-finish:` commits, then runs `set_version.py` followed by the transpiler, checks generated-tree drift under `.agents/plugins/cairn/`, stages the four version surfaces plus `.agents/plugins/cairn/` path-scoped, makes one `Release: <VERSION>` commit, and publishes check-then-do: push `main`, push a bare `<VERSION>` lightweight tag, `gh release create` on `uHappyLogic/cairn`. Tags are bare (`1.2.0`, `1.3.0`, `1.4.0`); the last release is `1.4.0` at `9f7eaef`. The skill knows only one repository and one remote.

### Distribution and installs

`README.md`'s Installation section documents one install path: `/plugin marketplace add uHappyLogic/cairn` in Claude Code, then `/init-milestone-base-workflow`. On this machine the `cairn` marketplace is registered as a `directory` source pointing at the live working tree `/Users/lucask/workspace/cairn` with `autoUpdate: true`, so Claude Code reads `.claude-plugin/marketplace.json` from the checkout as it changes; two other local projects have `cairn@cairn` installed from the plugin cache pinned to versions `1.4.0` and `1.0.0`. `gh` is authenticated as `uHappyLogic` over SSH with `origin` at `git@github.com:uHappyLogic/cairn.git`; the repositories `uHappyLogic/cairn-claude` and `uHappyLogic/cairn-antigravity` do not exist. There is no Antigravity install documentation beyond the transpiler note.

### Documentation surfaces that describe the layout

`CLAUDE.md` (symlinked as `AGENTS.md`) carries a `## Repository layout` block naming root `skills/`, `agents/`, `shared/`, and `.claude-plugin/`, a `## Development` section describing the transpiler and `.agents/plugins/cairn/` as the build output, and a long invariants list whose entries reference the runtime files by those root paths and `${CLAUDE_PLUGIN_ROOT}`. `README.md`'s `## Development` section states that the canonical sources are authored at the root "for Claude Code" and that Antigravity is built from them. Both files also reference a `migrate-workspace` skill (as a non-committing exemption and a catalog extension point) that has no directory under `skills/`. Every `Milestone-finish:` record since milestone 15 ends with "the Antigravity tree under `.agents/plugins/cairn/` was regenerated".

### Known gaps

There is no `core/` directory, no neutral plugin-root placeholder, no per-host manifest template or validation layer, no `hosts/` tree, no publish step to any distribution repository, and no distribution repositories.

## Decisions

### Host build

Each host is declared to the build as a declarative definition directory, `scripts/hosts/<host>/`, holding a settings file (the plugin-root placeholder replacement value, prose patterns to drop, frontmatter keys to strip, output layout and file renames, excluded paths) beside that host's manifest template files with version and name slots. One generic build script discovers the definitions by directory scan and applies them uniformly, so no host-specific Python exists and a definition can be validated before any build runs. Every host difference the current transpiler performs is a substitution, a rename, an exclusion, a frontmatter-key strip, or a manifest slot, and all of them fit this data schema; per-host prose rewrites, if any are adopted, fit it as pattern-replacement pairs. Adding a host means adding a definition directory. Only a host rule needing real logic beyond literal or regex substitution would justify a Python module per host, and no such rule is anticipated.

The neutral plugin-root placeholder in `core/` files is the mustache-style double-brace token `{{PLUGIN_ROOT}}`, which each host definition replaces with its own value (`${CLAUDE_PLUGIN_ROOT}` for Claude Code, `.agents/plugins/cairn` for Antigravity) by plain literal substitution. The double-brace form is inert in Markdown prose, inline code, and fenced shell blocks alike, and its shape cannot be mistaken for any host's runtime syntax, so both validation checks — no unreplaced placeholder (any `{{` in a generated tree) and no foreign variable syntax in another host's tree — are a one-line grep. The Claude-specific resolve hint that follows some references is settled separately and is unaffected by this choice.

The build script is `scripts/build_hosts.py`, named for its distinctive responsibility of building host trees and matching `set_version.py`'s verb-object naming rather than a generic `build.py` or the mechanism-and-one-host `migrate_skills_to_agy.py`. It is invoked as `uv run scripts/build_hosts.py [<host> ...] [--check]`: with no argument it builds every host whose definition directory exists under `scripts/hosts/` into `hosts/<host>/`, one or more host names build only those, and `--check` renders the selected hosts into a temporary directory and compares them byte-for-byte against the committed `hosts/<host>/` trees, writing nothing and exiting non-zero with the differing paths listed — the non-mutating comparison a drift check needs. `scripts/migrate_skills_to_agy.py` is deleted outright in the same change that removes the root trees it reads (no deprecation shim or alias is kept), because its inputs and output path cease to exist in this milestone and its only three callers — `README.md`, `CLAUDE.md`, and the release skill — are in-repo files rewritten here to the new command; a shim would preserve a command nobody outside the repository runs while silently changing what it produces.

Host-conditional prose in `core/` is handled by making the prose host-neutral and stripping the one non-prose site by data. The three prose sites that name a host today — the two-branch repair step's naming of Claude Code's `SendMessage` and Antigravity, the `cairn:` registry-name mentions at the dispatch sites, and the init template's Claude Code wording — are reworded once in `core/` to name capabilities and the plugin's own namespace but never a host (the repair step keyed on whether the host can continue a finished agent session versus cannot, the dispatch sites naming the agent's registry name under this plugin's namespace, the init template addressing the coding agent working in the repository), guarded by a build-validation grep that flags any host name inside `core/`. The one site that is a field rather than a sentence, the agents' Claude-only `color` frontmatter key, is dropped for hosts that do not read it by the host definition's declarative frontmatter-keys-to-strip rule, so the Claude tree keeps its colors, the Antigravity tree carries nothing Claude-only, and the build carries structural rules but no prose rules — no rule in the build ever needs real logic, which also confirms the data-definition tie-breaker of the host definition mechanism. Three of the four sites are already capability-keyed sentences with the host names as parenthetical examples, and the Antigravity tree has run on them verbatim since milestone 15, so stripping the examples costs nothing at run time, whereas a prose rewrite rule would silently stop matching on the first rewording. The one existing prose-drop rule, the Claude resolve hint, is left to the separate resolve-hint decision; a core that names no host makes removing it from core the consistent outcome, but that question is settled on its own.

The Claude-specific resolve hint — the ``(run `echo "$CLAUDE_PLUGIN_ROOT"` if you need to resolve the path)`` parenthetical that follows plugin-root references in 18 core files (24 occurrences) — is removed from `core/` entirely, so every host tree carries only the rewritten plugin-root reference and no host definition carries a hint-drop rule. It is the one remaining host-named sentence once the other prose sites are neutralized, and it is dead weight even on Claude Code, where the reference is substituted at load time and the echo prints nothing, so deleting its occurrences once costs less than a drop rule every future host must carry plus an exemption in the no-host-name guard that the neutral core otherwise makes a one-line check.

The per-host validation is a full gate whose failure aborts the whole selected build: every selected host is rendered into a temporary directory and run through the complete check set before anything is written — frontmatter present and `yaml.safe_load`-able with `name` and `description` keys, every description at or under 25 words, no `{{` left anywhere in the tree, no other host's plugin-root literal anywhere in this host's tree, every occurrence of this host's own plugin-root literal followed by a path resolving to a file in that same tree, and no frontmatter key the host definition strips still present — plus one pre-render guard that `core/` names no host. Any failure on any host exits non-zero listing every failing file and check, and no `hosts/<host>/` tree is touched. Every check is a one-line grep or a frontmatter read once the placeholder is the double-brace token and each host definition declares its own plugin-root literal and stripped keys — unreplaced is any `{{`, foreign is any other host's literal, dangling is this host's literal followed by a path that does not exist in the tree, the cap is a word count on a field the build already parses — so the two guards the host-conditional prose decision introduced (no host name in `core/`, no stripped key in a host tree) complete the set at no extra mechanism. The abort covers the whole selected build because the release commits every `hosts/<host>/` tree as one version and a build that writes some trees and not others hands it a state it must never commit, while rendering to a temporary directory and swapping only after all checks pass is the same primitive the `--check` mode already needs.

Build drift is a release stop, not an absorbed advisory. Once `hosts/claude/` is the tree the marketplace serves and each `hosts/<host>/` is what a distribution repository publishes verbatim, a committed tree that differs from its `core/` build is a mismatch `main` must not carry into a tag, so a fifth pre-flight gate runs `uv run scripts/build_hosts.py --check` before `set_version.py` touches anything; any committed `hosts/<host>/` tree that differs byte-for-byte from a fresh build of `core/` at the current version stops the release with the differing paths listed, the maintainer rebuilds and commits the sync as its own standalone commit, then re-runs. After the version bump the release rebuilds in place and stages `hosts/`, so the Release commit changes only version slots by construction and the absorbed-drift advisory is deleted. The pre-commit convention stays a documented rebuild-before-commit practice, with `--check` as the thing a maintainer or CI runs, never a git hook. The non-mutating `--check` mode is exactly this gate's primitive; three drift-free releases show it will almost never fire, and when it does the remedy is the same standalone sync commit the repository already used once, keeping every Release commit a pure version bump and every distribution commit traceable to the source commits that changed it.

### Plugin version

A root `VERSION` file holding the bare `MAJOR.MINOR.PATCH` literal and nothing else is the single source of truth for the plugin version: `scripts/set_version.py` writes it, and the build script reads it to fill the version slot of every host manifest template. The version is the one value every host manifest template, the release skill, and the version script all touch and nothing else in the repo owns, so it lives in a file that holds exactly that value and is readable by `cat`, Python, or any future build without a parser or a packaging convention; reading the plugin's release identity out of its build tool's package metadata in `pyproject.toml` was the tie-breaker against that alternative. Every other version literal — `pyproject.toml` and `uv.lock`, kept in lockstep by `set_version.py`; the root `marketplace.json` entry; and whatever manifest is placed under `hosts/claude/` — is a rendered or mirrored surface downstream of `VERSION`, never a second source.

### Distribution repositories

The `uHappyLogic/cairn-claude` and `uHappyLogic/cairn-antigravity` repositories are created once, by the maintainer, during this milestone, with a recorded `gh repo create` per host — public, with a description, and deliberately empty (no `--license`, `--add-readme`, or `--gitignore`), so the first publish commit becomes the root commit and `main` becomes the default branch as the first pushed branch under whichever publish mechanism is adopted — followed by `gh repo edit` to add topics and disable issues, wiki, and projects so feedback routes to the source repository. Provisioning a public repository is a deliberate, irreversible, twice-ever act that belongs to the maintainer, not to a bootstrap script that would run twice nor to a publish step whose contract is to push what already exists and stop on any disagreement; an initial README or license commit made by `gh` would force the first publish onto foreign history. The license is the `LICENSE` file the published `hosts/<host>/` tree carries, not a repository setting. The release skill gains a pre-flight stop that checks each host's distribution repository exists with `gh repo view` and, when one is missing, prints the exact creation command rather than creating the repository, giving the release its existence guarantee while recording the command at the one place a future host's maintainer will look.

`hosts/claude/.claude-plugin/` carries a generated `marketplace.json` with source `"."` beside the generated `plugin.json`, both rendered by the build from template files in the Claude host definition with their version slot filled from the root `VERSION` file, so a marketplace add of `cairn-claude` works with the same `.claude-plugin/` layout the monorepo root has proven since 1.0.0; the monorepo root keeps its own hand-held `marketplace.json` with source `"./hosts/claude"`, whose version `set_version.py` goes on writing as a mirrored surface. Neither marketplace file is authoritative — `VERSION` is — so the version script writes only its mirrored surfaces, the build renders the dist manifest from its template, and validation asserts that every rendered manifest slot and the root marketplace entry carry exactly the `VERSION` literal. A marketplace add of `cairn-claude` needs a `.claude-plugin/marketplace.json` at that repository root, and since the distribution repository is `hosts/claude/` published verbatim, that file must be a generated member of `hosts/claude/` — one more template in the Claude host definition with a version slot, exactly like `plugin.json` — while removing the root marketplace is not viable because it defeats the recommended-install-source goal that keeps the monorepo marketplace pointing at `./hosts/claude`.

<open-question id="Dist repo README content">
  <question>What does each distribution repository&apos;s README contain — per-host install instructions, a generated-do-not-edit notice, a pointer to the source repository and release tag, the license — and does the build generate it per host from a template so it lands in hosts/&lt;host&gt;/ like any other file?</question>
  <alternative id="Per-host template rendered by build">
    Each host definition directory carries a README.md template beside its manifest templates, rendered by the build with the VERSION slot filled from the root VERSION file into hosts/&lt;host&gt;/README.md like any other generated file; it holds a one-paragraph statement of what the repository is, a generated-do-not-edit notice routing issues and pull requests to uHappyLogic/cairn, that host&apos;s install instructions, a pointer to the source repository and the release tag and release URL derived from VERSION, and a license line naming MIT and pointing at the LICENSE file the build copies into the same tree.
    <advantage>It is the exact mechanism the Claude manifests already use — one more template file with one version slot in the definition directory — so the README is byte-identical under the drift gate, lands in the dist repository verbatim as part of the published tree object with nothing extra in the publish step, tells a reader on the recommended install source how to install and where to report, and a new host gets its README by adding a template rather than code.</advantage>
    <drawback>The install instructions live in two places — the root README.md and each host template — so the still-open Install documentation sibling must settle their wording once and keep both aligned by hand, and the rendered README changes on every release because it carries the version literal, which is the one content the source commit SHA cannot join since the Release commit does not exist when the build runs.</drawback>
  </alternative>
  <alternative id="Shared README in core with host slots">
    A single README template in core/ is copied into every host tree, with host-specific values — host name, install instructions, dist repository name — supplied as fields in each host&apos;s settings file and substituted as additional tokens beside the plugin-root placeholder.
    <advantage>The common paragraphs (do-not-edit notice, source pointer, license) exist once and can never diverge between hosts, and adding a host means filling a few fields rather than authoring a page.</advantage>
    <drawback>Multi-line install instructions become string values inside a settings file, which is the worst place to author prose, and the build gains a second token family beyond the one placeholder the layer settled on; it also puts a file into core/ that is a template rather than runtime prose the runner reads, blurring what core/ is.</drawback>
  </alternative>
  <alternative id="Hand-authored file preserved by build">
    hosts/&lt;host&gt;/README.md is written by hand and committed under the output tree, with the build and its --check told to leave that one path alone.
    <advantage>Free-form prose edited in place with no template slots, and the build touches nothing it did not generate.</advantage>
    <drawback>It breaks the property that hosts/&lt;host&gt;/ is a pure build of core/ — the drift gate needs a per-path exemption, the README cannot carry the version or release pointer without a hand edit per release, and a hand-edited file under the generated tree is exactly the state the goal&apos;s no-hand-edits rule and the per-host validation exist to exclude.</drawback>
  </alternative>
  <alternative id="No README in dist repositories">
    The distribution repositories carry only the plugin tree; provenance lives in the snapshot commit body and the GitHub release, and the root README.md remains the sole install documentation.
    <advantage>Nothing to template and nothing to keep aligned with the root README, so the dist tree is the plugin and no more.</advantage>
    <drawback>The repository the goal makes the documented recommended install source renders no landing page — a reader sees a directory listing with no install command, no notice that the tree is generated, and no visible pointer to where changes are actually made — which is the first thing GitHub shows and the one surface neither the commit body nor a release page replaces.</drawback>
  </alternative>

<open-question id="Dist publish mechanism">
  <question>How does the publish step turn hosts/&lt;host&gt;/ into one ordinary commit on the distribution repository&apos;s main branch — a git subtree split pushed to the remote, or a snapshot copy into a fresh clone committed under a fixed subject such as Release: &lt;VERSION&gt; — and how is the commit body composed?</question>
  <alternative id="Plumbing snapshot commit">
    The publish step builds the distribution commit inside the monorepo with git plumbing: it takes the tree object git rev-parse HEAD:hosts/&lt;host&gt; already stored at the Release commit, fetches the distribution remote&apos;s main into FETCH_HEAD (absent on an empty repository, so the first publish becomes a parentless root commit), runs git commit-tree on that tree with FETCH_HEAD as sole parent and a composed message, and pushes the resulting commit to refs/heads/main and refs/tags/&lt;VERSION&gt; on the distribution remote, with no clone, no temporary directory, and no file copy.
    <advantage>Byte-identity is by construction rather than by copying — the distribution commit&apos;s tree is the same object as hosts/&lt;host&gt;/ at the Release commit, so no dotfile, deletion, or stray-file rule can drift — and that same fact makes the already-published test a one-line comparison of the dist tag&apos;s tree against HEAD:hosts/&lt;host&gt;, the check-then-do shape every other publish artifact already uses.</advantage>
    <drawback>commit-tree and FETCH_HEAD are less familiar than clone-and-commit, the fetch pulls the distribution repository&apos;s objects into the monorepo&apos;s object store, and the maintainer never sees a checked-out working copy of what is about to be pushed beyond hosts/&lt;host&gt;/ itself.</drawback>
  </alternative>
  <alternative id="Fresh clone snapshot copy">
    The publish step clones the distribution repository into a temporary directory (git init plus remote add while it is still empty), deletes everything there except .git, copies hosts/&lt;host&gt;/ in, stages the whole tree, commits under the fixed subject with a composed body, pushes main and the tag, and removes the directory.
    <advantage>Every command is everyday porcelain a maintainer can re-run by hand, and the temporary checkout is an inspectable copy of exactly what will be pushed.</advantage>
    <drawback>Identity with hosts/&lt;host&gt;/ depends on the copy being right — the dot-directory .claude-plugin/ the Claude tree carries, files removed since the last release, anything a shell glob misses — and on a whole-tree git add the plugin&apos;s conventions otherwise forbid, while each release pays a full clone and a temporary directory that must be cleaned up on every failure path.</drawback>
  </alternative>
  <alternative id="Subtree split push">
    The publish step runs git subtree split --prefix=hosts/&lt;host&gt; to synthesize a branch holding every monorepo commit that touched that tree, pushes that branch to the distribution repository&apos;s main, and tags its tip &lt;VERSION&gt;.
    <advantage>The distribution repository carries a real per-file history whose commits map one-to-one onto the source commits that changed the tree, using a stock git command and no message composition at all.</advantage>
    <drawback>It publishes one commit per source commit that touched hosts/&lt;host&gt;/ — every rebuild sync commit and every Release commit since the last publish, with their monorepo subjects and bodies copied verbatim — rather than the one ordinary commit per release the goal names; the body cannot be composed because subtree copies messages, the split is recomputed over the entire history each release and diverges into a forced push after any rewrite of main, and the tree at intermediate split commits is only as trustworthy as the drift gate that guarded them.</drawback>
  </alternative>
  <recommendation option="Plumbing snapshot commit">The distribution commit should be the tree object hosts/&lt;host&gt;/ already is at the Release commit, committed with git commit-tree onto the fetched distribution main (or as a root commit onto the deliberately empty repository the creation sibling provides) under the subject Release: &lt;VERSION&gt; with a fixed provenance body composed from values the run already holds — the source commit as uHappyLogic/cairn@&lt;SHA&gt;, the published path hosts/&lt;host&gt;/, and the monorepo release URL derived from &lt;VERSION&gt; — and never the release notes, which stay on the GitHub release; this is the only mechanism that makes byte-identity a property of the object model rather than of a copy step, it needs no clone or temporary directory, and because the drift gate guarantees that tree is a fresh build of core/, the one-line tree comparison it enables is exactly the already-published state the still-open Dist publish resumption sibling describes.</recommendation>
</open-question>
<open-question id="Dist publish resumption">
  <question>How does the dist publish fit the release skill&apos;s check-then-do resumption model — where it sits relative to the monorepo tag push and GitHub release, what state marks a host as already published (a tag on the dist remote at a commit whose tree matches hosts/&lt;host&gt;/), and what happens when a dist repository already carries that tag on a different tree?</question>
  <alternative id="After GitHub release, per host">
    The dist publish becomes step 8d of the release skill, run once per host in host-definition order only after the monorepo main push, tag push, and GitHub release have each been skipped or done: for each host the run queries git ls-remote --tags on that host&apos;s dist remote for refs/tags/&lt;VERSION&gt; — no output means unpublished, so it fetches dist main, builds the commit-tree snapshot, and lands it with one atomic push to refs/heads/main and refs/tags/&lt;VERSION&gt;; output means it fetches that tag and compares its commit&apos;s tree id against git rev-parse HEAD:hosts/&lt;host&gt;, skipping the host on equality and stopping with both tree ids and the dist tag&apos;s commit SHA on any difference, never moving or deleting the dist tag.
    <advantage>It is the dependency order the publish step already follows — the dist commit&apos;s provenance body cites the source commit SHA that lands in (a) and the release URL that exists only after (c), so the derivative is published only once everything it names resolves — and the tree-id comparison is the exact already-published state the snapshot mechanism makes a one-line check, with the atomic push guaranteeing that a dist tag exists exactly when dist main carries the same commit, so no half-published host can arise between re-runs.</advantage>
    <drawback>A successful run has a window of seconds, and a run stopped at a dist host has a window until the next re-run, in which the monorepo release announces a version the recommended install source does not yet carry; a reader who reaches the release page first can arrive at cairn-claude before its tag lands.</drawback>
  </alternative>
  <alternative id="Before the monorepo tag">
    The dist publish runs between (a) push main and (b) push the monorepo tag, with the same per-host tree-id check and stop-on-mismatch rule, so the monorepo tag and GitHub release are created only after every distribution repository already carries &lt;VERSION&gt;.
    <advantage>The monorepo release never announces a version its install sources lack, and the monorepo tag doubles as a marker that the whole publication, dist repositories included, completed.</advantage>
    <drawback>The dist commit body then cites a release URL that does not exist yet, and a disagreement in a derivative repository blocks the source repository&apos;s own tag and release, inverting the step&apos;s existing rule that an artifact is created only after what it refers to exists; on a stop the pushed main sits untagged while foreign repositories already carry the version tag.</drawback>
