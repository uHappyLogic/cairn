## Decisions

### The milestones tool

- **Anchor subject.** `since` takes as a milestone's anchor the latest commit whose subject opens with `Starting-state:`, whatever follows the marker, among the commits that changed `<path>requirements.md`. The milestone is identified by the path-scoped file filter alone and the marker names the kind, as `tasks` selects every `Task-completion:` subject and joins the milestone from the file list rather than from the subject's descriptor, so a starting state committed under the earlier bare-directory-name subject is found the same way as the path form, and the tool names no legacy form.

- **Sibling preparation commits.** In its broad form, without `--milestones`, `since` leaves out a commit when every path it changed lies inside the directory of another milestone that is live and `defined` now, read from the tree as `live` reads it. Every commit of a currently started sibling counts, one that touches only its own directory included, and so does every commit of a finished one, its finish included. A commit touching any path outside such a directory counts in full, so the broad form stays a superset of `--milestones`.

- **Show argument.** `show` takes only `MILESTONE_PATH` and prints that milestone's `requirements.md` whole: from the working tree when the milestone is live, from the finish commit's parent when it is finished. It takes no FILE argument. The question document and the task list are served by no query, and no file-absent case arises, since every milestone, those from before the question-document split included, holds `requirements.md` at its finish parent.

- **Scope argument.** The starting-state procedure and the review pass pass the milestone path they already resolved, as a runner does to `gate`, and the tool derives the scope: the path is read lexically as `gate` reads MILESTONE_PATH and refused with an `Error:` line when it names no directory directly inside a `milestones/` container. `live` gains an optional MILESTONE_PATH and with it lists every other live milestone, started or defined, whose scope equals, contains, or lies under the named one's, the named milestone left out as `gate` leaves it out; with no argument it prints what it prints today. `milestones` gains a separate milestone-path form beside its unchanged `milestones PATH`, a flag or a distinct argument so that a PATH keeps today's reading, whose overview is the one `milestones <scope>` would print.

- **Goal revisions.** A goal revision recorded after the anchor is a reason to explore again, in the broad form only and detected by subject: `since` without `--milestones` also lists the milestone's own `Goal-revision: <path>` commits after the anchor, so `specify-milestone-starting-state`, and with it the refresh line every execution chain opens with, explores again under the revised goal instead of ending on its no-op line. `since --milestones` keeps listing only other milestones' task and finish commits, so the task-entry writers do not refresh on a revision alone, and `modify-milestone-goal` is unchanged.

### The starting-state procedure

- **Record read depth.** The record read stays two tiers and reads no verified bar: for each milestone whose overview line bears on the goal, the procedure reads its finish summary through `summary` or its recorded decisions through `show`, and makes no `tasks --with-body` call. Past tasks reach the starting state only as the titles the overview and the summaries already carry, and the milestones tool gains nothing for bars.

- **Unchanged refresh.** Nothing records an exploration that changed nothing. The anchor moves only when a refresh changes the `## Relevant starting state` section, so every later run in the same stale window explores again: the skill on each re-run, `derive-tasks` on each entry, and `submit-task` on every task submitted, until a commit lands or the milestone finishes. The repeat is stated as an accepted cost in the procedure and the docs; the commit tool, `since`, and the skill's two fixed lines stay unchanged, and no state is added anywhere.

- **Read failure.** Any failed milestones-tool call of the starting-state procedure (`since`, `milestones`, `summary`, `show`, or `live`) is one unclassified condition in all three of its runners, `specify-milestone-starting-state`, `derive-tasks`, and `submit-task`: the run stops on a fixed line with the call's `Error:` line verbatim beneath it, before any edit of `## Relevant starting state`, any pick clearing, and any commit. In `derive-tasks` and `submit-task` this stops the whole writer, so no task-list write and no task commit follow.

- **Pick-clearing failure.** The `strip --recommendation` call stays after the section edit. When it fails, each of the three runners first makes one corrected re-run, with the named Short Titles fixed against the `Error:` line, since the tool refuses an unknown title with the document unchanged. A second failure stops all three on one fixed line the procedure owns, with the second `Error:` line verbatim below it and the edit left uncommitted, and a stopped writer makes no task-list write.

### The task-entry writers

- **No anchor.** When `since --milestones` prints nothing, `derive-tasks` and `submit-task` explore nothing and make no starting-state commit: each goes on to its own reads and write with the `## Relevant starting state` section as it stands, empty or filled, and prints nothing about it. Only `specify-milestone-starting-state` reads no output as a first run; at task entry, no output means there is no anchor to measure from.

- **Gate position.** In both writers the scope gate runs twice, each time as its own step following `check-scope-gate.md`: once at the front, directly after resolution and before the staleness check, the reads, a refresh, and the authoring, and again directly ahead of the fixed write call, where it stands today, on every run. Either check closing stops the run under the procedure's one fixed line with nothing further written, and a refresh commit that landed before a closed second check stays committed. A `derive-tasks` run that derives no brief skips the second check as it skips the write, and the fixed write calls stay gate-free.

### The review pass

- **Overview bound.** The overview is bounded by a count applied in the tool: `milestones` gains an optional flag (for example `--last N`) that keeps every live line and only the N newest finished lines, by finish timestamp, the order the query already sorts them in. The review pass's one fixed call writes N as a literal, on the order of ten. Without the flag the query prints what it prints today, so `record`, `/release-plugin`, and every other reader are unchanged.

- **Overview read failure.** A failed overview call, meaning any non-zero exit, the tool's `Error:` line and git's failure alike, is one condition never classified by its wording, and it stops the pass at its inventory step, before any prune, dedup, new block, or note deletion. The pass prints one new fixed, identifier-free stop line of its own as its report's first line with the `Error:` line quoted verbatim beneath it, makes no commit, and prints neither the still-open list nor the convergence verdict. The new line gets its row in the `## Fixed console lines` table.

### Chains and the benchmark draft

- **Execution chain lines.** Each of the three chains that derive and complete tasks carries exactly one alternatives line, one recommend line, and one sweep line between its opening review and its derivation line, in that order, and nothing after the sweep. "Executing tasks" gains the alternatives and recommend lines ahead of its sweep. "Answering the questions that matter to you" gains an alternatives line after its hand-answer lines and ahead of its existing recommend line. "Putting more intelligence into a stuck milestone" keeps its own alternatives, recommend, and sweep lines as that pass. The new lines take the model and effort settings the "Starting a milestone" chain gives them.

- **Benchmark chains.** Both cairn deliveries of `ideas/benchmark_for_cairn.md` keep their one starting-state line in place and their lists unchanged. The draft's chain text gains one statement of why: the existing line already stands where the ways-of-using rule puts the refresh, directly ahead of the first review pass, and in a single-milestone run nothing outside the milestone's directory lands between it and derivation, so a second line would end on the no-op line every time. The expected-lines list takes the new no-op line from the skill reference's table.

### The host-suite test

- **Second milestone's state.** The second, overlapping milestone reaches the host already finished. Test-side code local to the new test, a helper or seeding variant beside the unchanged `seeded_repo`, builds the history on top of the seed in this order: the first milestone's `Starting-state: <path>` commit, then the second milestone's files added, its `Task-completion:` commits, and its `Milestone-finish: <path>` commit removing its directory, made through the plugin's commit tool. Only one host process runs, `/cairn:derive-tasks --milestone …`. The shared one-commit seed and the other host tests that use it are left as they are.

- **Acceptance runs.** Completing this milestone requires a passing run of the whole host suite, the new test included, against each of the three hosts (`--host claude`, `--host antigravity`, `--host codex`). The task that runs it starts, once the rebuilt tree is committed, by refreshing each host's installed copy on the maintainer's machine with that host's documented install. A host that fails is fixed inside this milestone before it finishes.
