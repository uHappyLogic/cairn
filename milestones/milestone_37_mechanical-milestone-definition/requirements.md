# Milestone 37: Mechanical milestone definition

## Goal

Make /define-milestone-goal fully mechanical. A new stdlib-only Python tool, core/tools/define_milestone.py, takes the title as --title and the goal text on stdin. It works out the milestone number and slug (kebab-case, first 5 words of the title), checks for conflicts, and creates all four milestone files itself: the empty open_questions.xml and the three Markdown files. Creating open_questions.xml moves out of the open-question tool, whose create subcommand is removed, so that tool only works on documents that already exist. It prints the commit subject and the four file paths ready to hand to the commit procedure. On failure it prints one Error: line and leaves nothing behind. The model's only work in the skill is choosing the title, passing the tool's output to the commit procedure and reporting the result.

## Relevant starting state

### The `define-milestone-goal` skill

The skill lives at `core/skills/define-milestone-goal/SKILL.md` and takes one argument, `<overall_goal_description>`, the free-text goal. Its six steps are all model work: step 1 scans `milestones/` for `milestone_<NN>_*` directories, strips leading zeros, takes max-plus-one, and zero-pads to two digits (a cold start yields `01`); step 2 asks the model to invent a 3–5 word kebab-case slug capturing the goal; step 3 refuses a number already taken under any slug; step 4 runs `python3 {{PLUGIN_ROOT}}/tools/open_questions.py create milestones/milestone_<NN>_<slug>` first, stops on its `Error:` line or a missing interpreter before writing anything else, then writes `requirements.md` (heading `# Milestone <N>: <title>`, the integer number, the goal under `## Goal`, then empty `## Relevant starting state`, `## Decisions`, `## Out of Scope`), `TASKS_TODO.md` (`# TASKS TODO`), and `TASKS_DONE.md` (`# TASKS DONE`); step 5 hands the four paths and the subject `Milestone-definition: milestone_<NN>_<slug>` to the commit procedure; step 6 prints the fixed `Milestone defined.` line or a distinct no-change line. The template names a `<title>` for the heading but no step derives it, so the model chooses it freely: the 37 existing headings mix Title Case (`Public Release Preparation`) and sentence case (`Committing Bootstrap`, `Non-interactive milestone activation`). The skill never touches `milestones/README.md` or `CLAUDE.md`. Its last change was a milestone-27 `Tasklist-completion:` commit that introduced the `create` call.

### The open-question tool

`core/tools/open_questions.py` is one 1,241-line stdlib-only module (Python 3.9+), the only file under `core/tools/`, with no `__init__.py` and no package. It exposes at module level `DOCUMENT_NAME` (`open_questions.xml`), `ToolError`, the `Document` and `Question` dataclasses, `render_document`, `document_path`, `load_document`, `save_document`, and `_write_bytes` (temp file in the target directory renamed over the target, mode preserved), plus `main(argv=None)` and `build_parser()`. Its `cmd_create` refuses an existing document with `Error: <path> already exists`, otherwise runs `os.makedirs(..., exist_ok=True)` and saves an empty `Document()`, which renders as `<open-questions/>\n`. Its `main` reconfigures stdout and stderr to UTF-8, maps `ToolError` and `OSError` to one folded `Error: <reason>` line on stderr with exit status 1, catches every other exception the same way, and leaves argparse's usage message with exit status 2 for malformed invocations; mutators print nothing on success. Free text arrives only on stdin through `read_body`, which reads `sys.stdin.buffer` once, decodes UTF-8, and refuses a terminal or closed stdin. The module docstring calls `open_questions.xml` "the one file this module owns" and the tool never reads `milestones/README.md`. No existing code scans milestone directories, derives a slug, or writes any Markdown file.

### The tool's test suite and CI

`tests/` holds `conftest.py` and one `test_<subcommand>.py` per subcommand plus `test_contract.py`, with golden fixtures under `tests/fixtures/` (`annotated`, `bare`, `empty`, `entities`). `conftest.py` pins `TOOL = REPO_ROOT / "core" / "tools" / "open_questions.py"`, sets `sys.dont_write_bytecode = True` so no `__pycache__` lands under `core/tools/`, and provides `run_tool(*args, stdin=...)` (a `sys.executable -B` subprocess) and `milestone_dir(name)` (a fixture copy under `tmp_path`). `pyproject.toml` puts `core/tools` on `pythonpath`, so tests also `import open_questions` directly. `test_create.py` covers the silent write, directory creation, the existing-document refusal, and the serializer identity; `test_contract.py` covers the shared exit-status and one-error-line contract. The suite runs twice, `uv run pytest` and `uv run --no-project --python 3.9 --with pytest pytest`, and `.github/workflows/drift-gate.yml` runs `--check` then both in one job.

### Host build and rendering of `core/tools/`

Both `scripts/hosts/claude/settings.toml` and `scripts/hosts/antigravity/settings.toml` map `tools = "tools"`, so every file under `core/tools/` renders as UTF-8 text into `hosts/<host>/tools/` at the same relative path; both host trees currently hold exactly `open_questions.py` there. The build decodes every core file as text and applies its checks to all of them: no bare `{{` (so a Python source may not contain `{{` outside a `${{` expression), no host name as its own word, and every plugin-root literal followed by a path must name a file in the tree. `{{PLUGIN_ROOT}}` renders to `${CLAUDE_PLUGIN_ROOT}` on Claude Code and to the workspace-relative `.agents/plugins/cairn` on Antigravity; a second file under `core/tools/` would land beside the existing one in both trees.

### Existing milestone directories and naming data

`milestones/` holds `milestone_01_public-release-prep` through `milestone_37_mechanical-milestone-definition`, every name `milestone_<NN>_<slug>` with a two-digit zero-padded number and a slug of two to five hyphenated lowercase words. `requirements.md` headings read `# Milestone <N>: <title>` with the integer number. Milestones 1–27 lack `open_questions.xml`. `core/shared/get-current-milestone.md` defines the pointer format in `milestones/README.md` (`Current milestone: none` or a backticked `milestones/milestone_<NN>_<slug>/` path); `goto-next-milestone` reads done numbers from `### Milestone N — Title` headings under `## Milestone History` and picks the lowest undone directory by zero-stripped integer.

### The commit procedure's inputs

`core/shared/commit-procedure.md` takes PATHS (the caller names them structurally, never by diffing), SUBJECT in `<Marker>: <descriptor>` shape, and an optional BODY. It runs `git status --porcelain -- <PATHS>` as the dirty-own-path guard, stages exactly those paths, and commits subject-only or with the body. The define skill today supplies the four paths and the subject itself.

### Prerequisite checks and documentation naming the skill or the tool

`init-milestone-base-workflow` step 2 checks `python3 --version` for 3.9 or later and justifies it by naming `python3 {{PLUGIN_ROOT}}/tools/open_questions.py`; `README.md` states the same two prerequisites (git work tree, Python 3.9+ as `python3`). `CLAUDE.md` describes the plugin as shipping "one stdlib-only Python tool" and `CONTRIBUTING.md` calls the open-question tool "the one program"; `docs/workflow.md` names `tools/open_questions.py` as the question document's one writer. `docs/skill-reference.md` has one `define-milestone-goal` entry describing the four files, the `create`-first ordering, and the commit subject. `docs/ways-of-using-cairn.md` runs the skill headlessly as `claude -p "/cairn:define-milestone-goal <goal>"` in its milestone-starting chain; `discuss-milestone-goal` hands off by suggesting `/define-milestone-goal "<refined goal>"`; `CONTRIBUTING.md` has the maintainer reserve a contributor's milestone with the skill on `main`. `goto-next-milestone`, `init-milestone-base-workflow`, `finish-current-milestone`, `ask-in-milestone-context`, `capture-milestone-principle-updates`, and `specify-milestone-starting-state` each mention the skill once as the definition step, none describing its internals.

## Decisions

### Creating open_questions.xml

- define_milestone.py writes the empty `open_questions.xml` (`<open-questions/>` followed by a newline) itself, with its own atomic write, and imports nothing from open_questions.py. The `create` subcommand and `cmd_create` are removed from the open-question tool, which from then on works only on documents that already exist. A test checks that define_milestone.py's output parses with `open_questions.load_document` and equals `render_document(Document())`, so the two tools cannot drift apart on the empty document's bytes. The sole-writer rule is reworded: define_milestone.py creates the document, and the open-question tool is its only writer after that.
