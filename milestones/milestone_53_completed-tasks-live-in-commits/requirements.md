# Milestone 53: Completed tasks live in commits

## Goal

Make a completed task's whole record its `Task-completion:` commit, as "Carrying it out › 2. Completed tasks live in commits" of `ideas/milestones_addressed_by_path.md` proposes, delivering that step whole and nothing of step 3. `TASKS_DONE.md` goes: the task-list tool's `move` becomes `remove`, which removes one section and renders no bar and ignores a `TASKS_DONE.md` standing beside the list, the milestone-definition tool creates three files, and the verified bar becomes the body of the task's commit, written by the inline `complete-task` skill as its own commit's body and by the `complete-task` agent as a second fixed-name file beside `paths.txt` that the orchestrator's existing commit-from-file call passes as the body and moves into `processed` with it. The read-only milestones tool, `core/tools/milestones.py`, is born with `tasks PATH` in the draft's general form as its only query and everything a first query fixes, its read-only git contract, line shape, `Error:` line, tests on the shared git fixtures, and parity test; every reader of `TASKS_DONE.md` (`finish-current-milestone`, `derive-tasks`, `ask-in-milestone-context`, `submit-task`, `discuss-new-task`) reads `tasks` instead, every remaining mention of the file in runtime files, templates, docs, and tests goes, and the invariants, the fixed-call and parallel tests, and the rebuilt hosts follow. The milestone's last task revises the draft's Carrying it out, rewriting step 2 as a done section recording what landed and revising step 3 with whatever this milestone discovered; the pointer, `milestones/README.md`, finish's README entry, and the commit tool's contract are untouched.

## Decisions

### Shallow clones and `tasks`

`tasks` makes no shallow check: it prints whatever the path-scoped log yields, in a shallow clone and a complete one alike, with no stop line, no warning, and no test of the case. The limit, that a shallow clone's truncated log omits older task commits without sign, is stated only in the tool's `--help` text and the docs, and the draft's "Limits to state up front" paragraph in `ideas/milestones_addressed_by_path.md` is revised to match in place of its stop line. Detection is left to a later milestone, such as the one adding the history-side queries whose readers depend on finish commits a shallow clone would cut the same way, or to none if no field run meets the case.

### The `Task-completion:` commit body

The body of a `Task-completion:` commit holds nothing beyond the acceptance bar: exactly its `- ` bullets, one per criterion, with no brief, no label line, and no other field. The brief is recorded only where the removed section already leaves it, as the removed lines of `TASKS_TODO.md` in the same commit's diff, and the subject carries the title, so the subject plus the bar is the whole handover a reader's judgment needs and no text is re-typed where it could drift.

### Passing the bar to the inline commit

The inline `complete-task` skill's one fixed shell call opens by capturing the acceptance bar from a quoted heredoc through command substitution into one quoted value, written in the group-fed form `{ bar="$(cat)"; } <<'EOF'`, the `- ` bullets, then `EOF`, the form the recommendation pass's batch call already uses, because it parses on bash 3.2 where the nested `bar="$(cat <<'EOF'` form fails on an apostrophe; the capture is chained by `&&` ahead of the `remove` command, and the commit tool's command then passes the value as `--body "$bar"`. No file is written, no turn is added, the runner escapes nothing, and the commit tool's contract gains no body-file option.

### `tasks` body layout

When `tasks` runs with its body flag, every task line stays at column 0 in the shape it has without the flag, and each line of the commit's body is printed beneath it indented by one fixed prefix of four spaces, as `git log` indents a message, with the body's outer blank lines trimmed and nothing else changed. A task whose commit carries no body (one completed before the bar moved into commits) is its task line alone, with nothing beneath it and no placeholder, so the next column-0 line is the next task; the boundary needs no lookahead, cannot collide with anything a body holds, and one parser serves both forms.

### `tasks` milestone join

`tasks` assigns a commit's milestone by the root-anchored `milestones/*/TASKS_TODO.md` pattern over the commit's file list, in one file-list read with no diff parse, which joins all 174 recorded commits, the two touching a fixture `TASKS_TODO.md` under `tests/fixtures/` included. A commit whose file list holds no matching file, or more than one, is still printed, its milestone field holding one fixed placeholder in place of a path, so the line keeps its date and task title and a hand-made anomaly stays visible on the print rather than dropping a task commit from a query defined as every one that changed the path. The discovery pattern the root-anchored one will be swapped for is the next milestone's to set.

### `tasks` subject selection

`tasks` selects only commits whose subject opens with `Task-completion:` and takes the title from the subject after the marker. The 222 retired `Tasklist-completion: complete one milestone task` commits, which carry the task heading in their body, are never read by this query, and nothing in this milestone promises a later reader for them: every reader this milestone moves onto `tasks` reads a milestone no legacy commit touches, and the older record stays readable in the finished milestones' own `TASKS_DONE.md` files until the migration removes them. The tool's help text and contract state where the record starts (the first `Task-completion:` commit, 2026-09-02, `milestone_15`), so an older milestone or path that lists nothing is a documented limit, not a silent gap.

### `tasks` empty result

When no task commit changed PATH, `tasks` makes one further read-only check, only on that empty result: whether PATH exists in the working tree or was touched by any commit in history (one more path-scoped `git log` limited to one commit). If it does, the tool prints nothing and exits 0, keeping the family's print-nothing, exit-0 shape for the routine empty milestone so no chained reader breaks. If it exists in neither, the tool refuses with one `Error:` line on stderr naming PATH as given and exits 1. History counts as existence, so a deleted path or a later-removed milestone directory whose task commits remain is never refused.

### The readers' `tasks` calls

Every one of the five readers that replace their `TASKS_DONE.md` read runs `tasks` on its milestone directory with the body flag, unconditionally, at the step that read `TASKS_DONE.md` today: `finish-current-milestone` at step 2, `derive-tasks` for its coverage matrix, `ask-in-milestone-context` among its reads, and `submit-task` and `discuss-new-task` in their triage reads. No reader reads titles alone and no reader chooses per run, so one fixed call shape at five sites keeps each reader the evidence its whole read gave it, with no per-reader rule or run-time choice a test cannot pin; a milestone's bars are a few bullets per task, so the extra print is small.

### Guarding an empty acceptance bar

Once `remove` reads no bar, two shell tests guard it, so every route to an empty body is refused before a section goes or a commit lands. First, each runner's own fixed completion call (the inline `complete-task` skill's and the agent's step-5 call) opens with a shell test that the bar holds a non-blank line, chained ahead of `remove` behind `&&`, so an empty bar prints one fixed line, removes no section, and commits or writes nothing; the runner fixes the bar and runs the call again, as it does after a refused `move` today, the test replacing the refusal `move` gave at the same point. Second, the orchestrator's step-2c call adds `body file absent` and `body file empty` tests beside its two path-file tests, copying the pattern it already runs on the path file for the one place the bar crosses a process boundary; either one commits nothing and stops the run under the existing `Task run stopped — a completed task could not be committed.` line, with the test's own line printed below it, so no new fixed console line is needed. `remove` reads no bar, and the commit tool's contract is unchanged.

### Where the bar's record form is stated

The acceptance bar's record form (one `- ` bullet per criterion, in verification order, written as each stood when it passed, neither re-derived nor summarized) stays stated once, in `core/shared/complete-procedure.md`, as prose beside the bare `remove` at step 5 or folded into step 2's hold-it-verbatim sentence, worded as the form of the bar the procedure hands to the runner, with the destination named only as the record the runner's own file writes and no git step, commit, or body named, so the procedure stays commit-free. The inline `complete-task` skill's fixed call and the agent's body-file heredoc show the bar as `- ` bullet placeholders and refer to the procedure for the form, adding no prose rule of their own; with the body being the bar alone, that one sentence states the whole body's shape.

### `tasks` line fields

Each line of the `tasks` query carries four fields: the commit's abbreviated hash as git's `%h` prints it, then the date as YYYY-MM-DD, the milestone path, and the task title, separated by single tab characters, the title last. The tab is the tools' existing listing separator and keeps a spaced title unambiguous, and the leading hash lets a reader reach a task's diff, where the brief now lives, with one `git show` instead of a subject search.

### Readers on a failed `tasks` call

`finish-current-milestone` and `derive-tasks` both treat a failed `tasks` call (the tool refusing, or git unavailable) as a stop, exactly as each already treats a failed open-question `list` call: `finish-current-milestone` stops on a fixed line of its own, `Cannot finish the milestone: the completed-task read failed.`, and `derive-tasks` on one of its own, `Cannot derive tasks: the completed-task read failed.`, each with the tool's one `Error:` line quoted verbatim below it, writing and committing nothing; the two new lines join the `## Fixed console lines` table and its test. No reader classifies the failure: a refusal and an absent git are one condition with one line, and an empty milestone is not a failure, so a fresh milestone never trips it.

Of the three other readers, `submit-task`, the one that writes and commits, stops on a failed `tasks` call on a new fixed line of its own in its `Task not submitted — …` family, with the tool's `Error:` line quoted verbatim below it, and that line joins the `## Fixed console lines` table and its test, because its duplicate check against completed work would otherwise be incomplete and a failed read could land a duplicate of a completed task. `ask-in-milestone-context` and `discuss-new-task` proceed without the completed-task record: each tells the user in prose that the completed-task read failed, quoting the `Error:` line, and carries on from its other reads (`requirements.md`, `TASKS_TODO.md`, the live deliverables), printing no fixed line, which keeps the conversational skills' exemption from fixed lines.

### Mentions outside the goal's categories

Of the mentions of `TASKS_DONE.md` outside the runtime files, host templates, docs, and tests the goal names, only the pull request template's checklist item is rewritten, to the commit form beside its Milestone-finish item, because it is the one surface outside the goal's categories a person acts on and a compliant pull request would fail it as written. `ideas/benchmark_for_cairn.md` is left as written: it is a dated design draft that names Cairn's files as the plugin had them when it was written and points at the plugin's documentation for anything the harness matches, so its three passages wait until the benchmark is next revised or until the pointer's removal changes the same passages. Nothing else outside the goal's categories is touched, and historical records stay as written.

### Landing the flip

The retirement of `move` lands in one task that changes together the task-list tool's `remove`, the completion procedure's step 5, the inline `complete-task` skill's call, the `complete-task` agent's step-5 call, and the orchestrator's step-2c call, with the rebuilt hosts and the tests that run those calls. That task stands first in the derived list, and its brief says it is completed alone by the inline `/complete-task`: its runner records its own bar through the new call it has just written, `remove` plus a commit carrying the bar as `--body`, and not through the `move` the skill it loaded showed. `/complete-all-tasks` is then started in a fresh session for every remaining task, so no orchestrated run crosses the flip, every bar lands in its commit whichever way agent files load, and this milestone's `TASKS_DONE.md` stays the empty template.

### Passing the bar from the agent

The `complete-task` agent's step-5 call opens exactly as the inline `complete-task` skill's recorded call does, capturing the bar once from one quoted heredoc into one quoted shell value in the group-fed form `{ bar="$(cat)"; } <<'EOF'`, the `- ` bullets, `EOF`; the non-blank test runs on that value, chained by `&&` ahead of `remove`; only after `remove` succeeds does the call write the value to the fixed-name body file beside `paths.txt` and then write `paths.txt` from its own quoted heredoc. Nothing reaches the scratch directory unless the test and `remove` both pass, so both runners share one bar-handling form, the bar typed once and tested as written, and the empty-bar guard's writes-nothing wording and the agent's write-nothing-else contract hold without a carve-out.
