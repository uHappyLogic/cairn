# Milestone 39: Literal shell commands without variables

## Goal

Stop Cairn runs from failing where a shell does not split an unquoted variable into words. Add a shell-neutral prose rule at the two provoking sites: `core/shared/commit-procedure.md` names each path literally in both the dirty-own-path check and the `git add`, never through a shell variable; and the multi-call open-question tool sites (`review-milestone-requirements`, the two annotating passes, the answer sweep, and `answer-procedure.md`) write the full fixed command on every call, never through a variable, alias, or function. The rationale is recorded in the `CLAUDE.md` invariants. Done when `hosts/` is rebuilt, `--check` passes, and both pytest runs pass. A structural fix, such as a commit tool, is out of scope.

## Relevant starting state

### Commit procedure

`core/shared/commit-procedure.md` (52 lines) is the only home of the commit mechanics and is followed by 17 skills. Its inputs are named as uppercase placeholders — **PATHS**, **SUBJECT**, optional **BODY** — and its two path-taking commands are written with the set as a single token: the step-1 guard as "for example `git status --porcelain -- <PATHS>`" and the step-2 staging as "`git add <PATHS>`, naming each path explicitly". Step 2 already forbids `git add -A` and tree-wide selection, but nothing in the file says the paths must appear literally on the command line or forbids holding them in a shell variable, and step 1 carries no "name each path" wording at all. Callers supply PATHS as one to four paths, most often `<MILESTONE_DIR>/open_questions.xml` and `<MILESTONE_DIR>/requirements.md` together.

### Multi-call open-question tool sites

The five sites the goal names each invoke the tool several times per run, every call shown in its own fenced block with the full command `python3 {{PLUGIN_ROOT}}/tools/open_questions.py <subcommand> <MILESTONE_DIR> …`: `review-milestone-requirements` (`remove`, `add`, `list`), `provide-alternatives-to-all-open-questions` (two `list` calls, `strip`, `embed --alternatives` once per return), `recommend-all-open-questions` (three `list` calls, `strip --recommendation`, `embed --recommendation` and `lift` once per block, `sort`), `answer-all-open-questions-with-recommendation` (two `walk` calls, plus the per-question calls of the procedures it follows), and `core/shared/answer-procedure.md` (`locate`, `remove`, cascade `remove`). The contract sentence each site carries states the tool is the sole writer and how it reports; none says the command is to be written out in full on every call, and none mentions a variable, alias, or function. `core/shared/answer-with-recommendation-procedure.md` (one `lift`) and `core/shared/recommend-procedure.md` also carry the command but are not among the named sites.

### Host rendering of the command

The build replaces `{{PLUGIN_ROOT}}` with each host's `plugin_root` literal from `scripts/hosts/<host>/settings.toml`: `${CLAUDE_PLUGIN_ROOT}` for the Claude host and the workspace-relative `.agents/plugins/cairn` for Antigravity, 31 command occurrences in each rendered tree. The Claude-rendered command therefore already contains one host-provided variable reference, unquoted, as shipped. Runtime files under `core/` name no host and no shell, and the build's validation gate rejects a bare `{{` in any rendered file.

### Existing shell-variable use in runtime prose

The only runtime file that itself instructs a shell variable is `core/skills/capture-milestone-principle-updates/SKILL.md`, which holds a temporary snapshot path in `SNAPSHOT="$(mktemp)"` and uses it quoted (`"$SNAPSHOT"`) in its copy, restore, and cleanup commands. No file under `core/` currently mentions variables, aliases, functions, or word splitting as something to avoid.

### CLAUDE.md invariants

The rationale homes are the bullets under `## Invariants to preserve when editing skills`. The open-question-tool bullet already calls the invocation "the one fixed command" with "never `python`", and the committing bullet states path-scoped staging and "never `git add -A`"; neither records anything about literal paths, shell variables, or the failure this milestone targets. `AGENTS.md` is a symlink to `CLAUDE.md`.

### Build and verification

`hosts/claude/` and `hosts/antigravity/` are committed build output of `core/`, regenerated by `uv run scripts/build_hosts.py` and gated by `--check`. The pytest suite under `tests/` covers only the Python tools in `core/tools/` and asserts nothing about skill or procedure prose; it runs under the pinned interpreter and at the 3.9 floor, and CI (`.github/workflows/drift-gate.yml`) runs `--check` and both pytest runs in one job.

## Decisions

### Tool-site rule

- **Placement.** The full-command rule is stated once per file, as a clause added to the tool-contract sentence each of the five multi-call sites already carries in its opening paragraph; all five files are handled the same way and no fenced call gets anything beside it. In `review-milestone-requirements` and `answer-procedure.md` that sentence already spells out the full command, so the clause sits next to it; in the two annotating passes and the answer sweep, whose opening paragraph names the tool without showing the command, the clause refers to the full command as shown in each fenced block. A runner decides to set up a variable or function when it starts the run, which is when it reads the opening paragraph, and the tool's contract stays at one sentence per site with no copies to drift.

### Literal-path rule

- **Agent staging.** The literal-path rule extends to the `complete-task` agent's staging site, stated directly in the "Staging contract" section of `core/agents/complete-task.md`: its existing `git add` sentence ("naming each path explicitly") gains the same shell-neutral wording the commit procedure gets — each path appears literally on the command line, never through a shell variable. The commit procedure keeps its own statement of the rule, the two sentences are kept in matching wording, and the agent reads no extra file. The agent stages the largest path set in the workflow and a wrong staging there is silent; restating follows the pattern already used for the `git add -A` ban in both files.
