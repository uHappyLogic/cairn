# Milestone 28: Ways of using Cairn

## Goal

Promote the untracked `temp/CAIRN_USAGE.md` into a tracked `docs/ways-of-using-cairn.md`: a single extensible page of goal-oriented command-chain snippets (for example starting a milestone, a mixed-agent requirements review, putting more intelligence into a stuck milestone, executing tasks), each under one fixed per-way template (a `##` heading naming the goal, one or two sentences on when to use it and what it yields, then the chain as a fenced block). The chains are generalized for any reader: private aliases, local paths, and project-specific milestone ids become placeholders or documented equivalents, and the headless flags (`--dangerously-skip-permissions`, `--model`, `--effort`, `--add-dir`) are kept with one sentence explaining what each means. The page presents mixing along every available axis, hosts (Claude Code and Antigravity on one repository), models, and effort levels, as mechanics the reader can combine, without asserting benefit claims that belong to `docs/design-claims.md`. The README's "How it works" section links to it beside the existing docs links; `CONTRIBUTING.md` is not modified, and the page's template is what lets a later contribution (such as an ultracode-driven multi-milestone way) be added as one more section.

## Relevant starting state

### The draft under temp/

`temp/CAIRN_USAGE.md` is untracked (`temp/` is gitignored) and titled "Cairn usage lookup". It holds a `## Claude Code` section of six `###` snippets — "Fable based first run", "Opus based First run", "Subsequent runs", "Execute tasks", "Finish", "Just put more intelligence and execute" — and a `## Antigravity` section of one unheaded fenced block, every line a headless `claude -p "/cairn:<skill>"` or `agy -p "/cairn:<skill>"` invocation. Every Claude Code line carries `--dangerously-skip-permissions --model "<opus|fable>" --effort <high|xhigh|max>`, and every Antigravity line carries `--dangerously-skip-permissions --add-dir "/Users/lucask/workspace/cairn"`. It contains material that cannot ship as written: a private `claude-wait` shell alias with no definition, that absolute workspace path, two project-specific milestone ids (`milestone_02_youtube-watch-only`, `milestone_87_gdd-settlement-structure-note`), a `goto-next-milestone` invocation passing a milestone id although the skill is argument-free (it discovers the candidate itself), one `-c` continuation flag on a single `review-milestone-requirements` line, an unterminated fenced block (two backticks) closing the last Claude Code snippet, and an empty-prompt `agy -p ""` line. No snippet mixes the two hosts on one milestone; the model mix exists only within the Claude Code snippets (Fable for starting state, review, and derive; Opus for recommend, answer, complete, and finish).

### The docs/ pages and their frame

`docs/` holds three pages: `workflow.md` (the six-phase pipeline as mermaid diagrams over the shared state nodes D0–D5, then `## How skills commit` and `## The answer-principle-learning loop`), `skill-reference.md` (one `###` entry per skill headed by its usage form, e.g. `### \`specify-milestone-starting-state <milestone_id>\``, 23 entries), and `design-claims.md` (19 claims under six `##` groups, each a `###` claim line over a **Design** paragraph and a **Metric** line). Each page opens with a `#` title and a one-paragraph intro that names its sibling pages. Milestone 26 is the precedent for this milestone's move: it promoted `docs/design-claims.md` from an untracked `temp/` note word for word, changing only the frame (an orienting intro for a repository reader), and its layout is recorded as one entry of the `CLAUDE.md` repository-layout block, which today carries exactly three `docs/` entries. None of the three pages, `README.md`, `CONTRIBUTING.md`, or the two host README templates mention headless invocation, `-p`, `--model`, `--effort`, `--add-dir`, or `--dangerously-skip-permissions`; the skill reference documents skills only in their slash form.

### The README link surface

`README.md`'s `## How it works` section ends with the one sentence "How the skills move a milestone through those files is described in [docs/workflow.md](docs/workflow.md), and what each skill does is in [docs/skill-reference.md](docs/skill-reference.md)." — the only place the README links the two narrative docs pages; `docs/design-claims.md` is linked from `## Design principles` instead. `## Installation` documents the two hosts by their install commands only (`/plugin marketplace add uHappyLogic/cairn-claude` then `/plugin install cairn@cairn`; a `curl | tar` extraction into `.agents/plugins/cairn` for Antigravity) and never names either host's CLI binary, so `agy` as the Antigravity command appears nowhere in the tree. The two distribution README templates under `scripts/hosts/<host>/README.md` carry the same install and bootstrap sections and a `## Source` pointer back to the root repository, no usage material.

### Skill invocation surface the snippets map onto

Every snippet line names a skill under the `cairn:` namespace, the form the Claude Code host lists them in; the skill reference and `workflow.md` name them bare. The skills the draft chains are all argument-free except `specify-milestone-starting-state <milestone_id>` (which the draft calls without its argument), and `goto-next-milestone` refuses to run unless the pointer reads `none`, so the draft's "first run" chains assume a milestone already defined and finished-before state. The requirements loop the snippets repeat (review → recommend → answer-all, until `review-milestone-requirements` reports convergence) is the `### Iterating milestone requirements` phase of `workflow.md`; `derive-tasks` stops with the still-open list when any question remains, which is why every "execute" snippet in the draft is preceded by an `answer-all-open-questions-with-recommendation` line. Each committing skill commits its own path-scoped change under a function-derived subject, so a chain of headless runs leaves one commit per skill in the git log regardless of which host or model ran it — the property that makes mixing hosts on one repository safe to describe, since both hosts write the same files through the same skills and the same tool.

### Contribution path a new way would take

`CONTRIBUTING.md` has two sections, `## Contributor workflow` (the proposal-first path: every pull request is a contributor-run milestone, no plain-pull-request tier) and `## Development` (the build loop). The goal keeps it unmodified, so a contributed way would arrive through the existing proposal-issue-then-milestone route; there is no lighter doc-only path, and the page's per-way template is the only structure a contributor would be handed.

## Decisions

### Host layout within a way

Each way is one fenced block in which every line is a concrete invocation naming its host binary (`claude` or `agy`) with that host's real flags, the host chosen per line exactly as the model and effort are. A single-host way names one host throughout; a mixed-host way names both in the one block, so it is an ordinary section under the same per-way template. The page's legend states once how a line is swapped to the other host (`claude` to `agy`, `--model`/`--effort` for `--add-dir`), and every line stays runnable as written. No way is split into per-host blocks, no host placeholder stands in for the binary, and there is no separate way per host.
