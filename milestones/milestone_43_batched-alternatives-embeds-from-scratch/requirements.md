# Milestone 43: Batched alternatives embeds from scratch files

## Goal

The alternatives pass stops re-typing agent returns and stops spending one orchestrator turn per return. The `provide-alternatives-to-open-question` agent writes its checked `<alternative>` elements to one scratch file outside the repository and ends its session with that file's path as its final message, or `FAILED: <reason>` as before, so a return no longer travels through the orchestrator's context twice. The orchestrator embeds and commits in batches rather than per return: it pipes every landed file into `embed --alternatives` and commits every question that embedded, all in one shell call, keeping one `Alternatives-annotation: <Short Title>` commit per question, the one-repair path (continuation where the host can, one re-dispatch where it cannot) with the repaired return arriving the same way, and the per-question skip. Where the host offers a blocking wait, the orchestrator wakes once per run: it names the run's scratch directory in the dispatch prompt, waits in one call until every dispatched agent's return has landed there or ended in a failure, and then embeds and commits the whole set in one shell call; where the host offers no such wait, it batches every time it wakes with landed returns. That waiting sentence is the one host slot, with the per-wake-up form as the value for a host without a blocking wait; the open-question tool does not change. `CLAUDE.md`, the agent file, the skill, and `docs/` restate the agent's contract as read-only toward the project with that one scratch file as the exception, and the per-return pipeline as a batch, once per run or once per wake-up by host.

Out of scope: batching the recommendation pass's embeds, a task-list tool for the completion move, the `complete-task` agent's return contract, the headless chains' model and effort settings in `docs/ways-of-using-cairn.md`, and any change to what the alternatives agent enumerates.

## Relevant starting state

### The alternatives pass as it runs today

`core/skills/provide-alternatives-to-all-open-questions/SKILL.md` gathers the question set once (`list`, then `list --without-alternatives`), dispatches one read-only subagent per bare block with a prompt holding only the Short Title and `<MILESTONE_DIR>`, and runs a fixed per-return pipeline the moment each return lands: a last-line `FAILED:` verdict (the only judging the orchestrator does itself), the whole return piped to `embed --alternatives` as a quoted heredoc, exactly one repair on refusal (continue the same agent session where the host can, one fresh re-dispatch where it cannot, with a fixed corrective message carrying the `Error:` line), then a per-question commit through `core/shared/commit-procedure.md` under `Alternatives-annotation: <Short Title>` with no body. Returns are judged one at a time, so no embed or commit interleaves with another's. Step 4 prints one of two fixed lines (`Alternatives embedded.` or a distinct no-op line) plus an advisory listing only the questions still skipped after their repair. The step's host-dependent wording sits in four slots: `ALTERNATIVES_CONCURRENCY` (the paragraph opening step 3), `ALTERNATIVES_DISPATCH`, `ALTERNATIVES_AGENT`, and `AGENT_TOOL`; the Claude Code and Antigravity values say every dispatch runs together and each return is handled as it lands, and the Codex value keeps at most the session's `agents.max_threads` cap in flight, closing each question's agent with `close_agent` once its pipeline has finished.

### The alternatives agent's contract

`core/agents/provide-alternatives-to-open-question.md` tells the agent it reads and reasons and never writes: "never edit `open_questions.xml`, `requirements.md`, or any other file". It reaches the question document through exactly two tool calls (`locate` on its own Short Title, `list --with-question` for sibling scope), reads `requirements.md` whole, follows `core/shared/alternatives-procedure.md`, renders the `<alternative>` children, self-checks the draft against the two anchor tests (first non-whitespace text `<alternative`, last `</alternative>`), and ends its session with that draft as its whole final message, or with `FAILED: <reason>` as its final line and nothing else. Its frontmatter description reads "Enumerates the honest alternatives for one open question, invoked with that question's Short Title as the prompt", inside the 25-word cap. Its median output is about 3.8k tokens and its final message about 1.1k.

### The open-question tool's `embed`

`embed --alternatives <MILESTONE_DIR> "<Short Title>"` reads the whole message from standard input (a terminal stdin is refused; a file redirect or heredoc is accepted), slices from the first `<alternative` line to the last `</alternative>` line, discards text above and below, validates (no wrapper or `<question>` line, no text outside the elements, at least one `<alternative>`, no recommendation-half or unknown element, a target block carrying no `<alternative>` yet), rewrites the block in canonical form, and prints nothing on success; every miss is one `Error:` line on stderr with exit 1 and the document unchanged. `tests/test_embed.py` holds 72 tests over this contract. The goal leaves the tool unchanged.

### How returns reach the orchestrator on Claude Code (measured)

The `Agent` tool runs subagents in the background: the dispatch's tool result is a stub, and each agent's completion arrives later as a `<task-notification>` carrying `<task-id>`, `<tool-use-id>`, an `<output-file>` path, `<status>`, and a `<result>` holding the agent's whole final message HTML-escaped. The `<output-file>` is a symlink to the agent's full JSONL transcript (about 250 KB for one alternatives agent), with the final message JSON-encoded inside its last assistant record, so it is not the return and cannot be piped into `embed` as it stands. Notifications arriving while the orchestrator is mid-turn or inside a tool call are queued and delivered together: across the 21 alternatives runs in this repository's transcripts (2026-09-22 to 2026-10-04), 162 agents produced 179 notifications delivered in 90 wake-ups (groups of up to seven), and the orchestrator then took about 16 post-dispatch turns per run, more than half of them text-only or silent, at a median context of 57k tokens. Re-measured against a floor of two turns per wake-up, per-wake batching plus the context shrink (returns no longer in notifications, no heredocs in context) saves about 1.17M input tokens per milestone over all 21 runs and 0.82M without the one outlier run, against the 1.1M the report claimed for a one-turn batch; the remaining post-dispatch input at that floor is about 0.92M per milestone. The analysis and its parser live under `temp/` (`mechanization-token-efficiency-report.md`, `mechanization-analysis/`), which `.gitignore` excludes.

### Waiting and scratch primitives per host

On Claude Code, a foreground `Bash` call blocks up to 600000 ms and `sleep` ran when tried in this session despite the system note saying foreground sleep is blocked; `Bash` with `run_in_background` and `Monitor` (an event stream from a script's stdout, expiring after at most 30 minutes) both return at once and deliver notifications later, each notification a wake-up. Each session has a scratchpad directory named in the system prompt under `/private/tmp/claude-<uid>/<project>/<session>/scratchpad`. The repository records of Codex only what its slot values and README carry: dispatch through `spawn_agent`, closing through `close_agent`, no waiting tool named anywhere under `scripts/hosts/codex/`, `docs/`, or `core/`, and a workspace-write sandbox that keeps `.git` read-only, with nothing recorded about whether a temporary directory outside the workspace is writable. The repository holds no Antigravity-specific knowledge of how agent returns are delivered or whether a blocking wait exists; its tree is byte-identical to the Claude Code tree by construction.

### Host slots and the build

`scripts/build_hosts.py` fills every `{{SLOT}}` in `core/` from each definition's `[slots]` table in `scripts/hosts/<host>/settings.toml`; its `slot-declaration` check fails when a declared name appears nowhere in `core/` or the three hosts declare different name sets, and `unfilled-placeholder` fails on any `{{` left in a rendered tree, so a new slot must be declared by all three hosts and used in `core/`. `CLAUDE.md` records that the Claude Code and Antigravity slot values are the exact pre-Codex wording, keeping those two trees byte-identical as the slot mechanism's end-to-end test, and that no pytest covers it. `hosts/<host>/` is committed build output; `uv run scripts/build_hosts.py --check` is the drift gate CI runs beside both pytest runs.

### Where the current behaviour is recorded

`CLAUDE.md` carries the per-return pipeline in its "Dispatched-agent return contracts" bullet (judge each return as it lands, one repair, then skip; extraction in the tool since milestone 27, with skip-only behaviour and prose extraction named as not to be restored), the two-value dispatch prompt in "A dispatch prompt carries only what the orchestrator already holds and the agent cannot fetch itself", the agents' never-commit rule under "Committing is a property of the skill layer", the full-command-on-every-call clause for the agent under "Shell commands are written literally", and the two-annotating-passes bullet (commits per question with no body, parallel dispatch with no cap and no ordering). `docs/skill-reference.md` describes the pass and the subagent in their two entries; `docs/design-claims.md` claims 13 (the orchestrator holds no work context and gets only a bare `DONE`, a bare `FAILED`, or the ready-to-embed elements), 15 (a bad subagent return gets one repair, then a skip, never a run stop), and 18 (host-dependent sentences name the capability, never the host) state the properties the pass is built on; `docs/workflow.md` places the pass in the convergence loop; and `docs/ways-of-using-cairn.md` runs it in every headless chain as one `claude -p` line on `opus` at `--effort high`, where orchestrator and agents share one model setting.

### Commit mechanics the change rides on

`core/shared/commit-procedure.md` is path-scoped by construction: a dirty-own-path guard over the named paths, `git add` of exactly those paths written out as separate arguments, then a subject-only or subject-plus-body commit. The alternatives pass names only `<MILESTONE_DIR>/open_questions.xml`, so a file outside the repository never reaches a commit, and the pass needs no clean tree. Dispatched agents stage path-scoped at most and never commit; the alternatives agent stages nothing.

## Decisions

### Claude Code wait

The Claude Code value of the waiting wording is one capability-conditional sentence rather than the name of one primitive. Where the agent tool offers a blocking dispatch form, the orchestrator sends every dispatch in one message in that form, so the message returns only when every agent has ended, and it then embeds and commits the whole set in one shell call. Where the agent tool offers no blocking form, the orchestrator batches every time it wakes with landed returns. In both arms every dispatch goes out in one message, so the fan-out stays concurrent. No foreground shell loop, background shell loop, or event monitor serves as the wait on Claude Code.

### Scratch directory location

The orchestrator creates the run's scratch directory with `mktemp -d`, a fresh uniquely named directory under the system temp location honouring `$TMPDIR`. Every host tree uses the same wording, so the location adds no host slot. The directory belongs to one run only and no other run reuses it, so no stale return or concurrent run can collide. Codex's workspace-write sandbox keeps `$TMPDIR` and `/tmp` writable by default (its `exclude_tmpdir_env_var` and `exclude_slash_tmp` keys exist to remove them), so the temp location is writable there too; the session scratchpad is not used.

### Codex wait form

The Codex tree gets the single-wait form, applied one round at a time. The orchestrator dispatches up to the session's `agents.max_threads` cap, then waits in one call through Codex's own `wait_agent` tool (which takes a `timeout_ms` and returns once every requested agent's result is available) until every agent in that round has written its scratch file or ended in a failure. It embeds and commits the round's landed files in one shell call, closes the round's agents with `close_agent` once their pipelines finish, and dispatches the next cap-sized round until no question is left. The orchestrator wakes once per round rather than once per return; the idle tail of a round costs wall-clock only.
