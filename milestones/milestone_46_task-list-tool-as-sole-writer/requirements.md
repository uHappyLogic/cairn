# Milestone 46: Task-list tool as sole writer

## Goal

Add a stdlib-only Python 3.9+ task-list tool under `core/tools/` that becomes the only writer of a milestone's `TASKS_TODO.md` and `TASKS_DONE.md` once `define_milestone.py` has created them: it moves one task section TODO→DONE with its `**Verified:**` bar read from stdin for the completion procedure, inserts a positioned section for `submit-task`, and initializes and appends sections for `derive-tasks`, so the `##`/`---` parsing and the Verified rendering leave runtime prose for a tested tool and the ad-hoc move scripts are retired. Every runner that writes a task file chains the tool call with the git step it owns in one shell call, the `complete-task` agent its path-scoped `git add` and the inline runners their commit procedure, so the completion tail becomes one turn. The tool touches no git, reads of the task files stay as they are, and the milestone ships the tool, its tests under both interpreters, the updated prose, docs, and `CLAUDE.md` invariants, and the rebuilt host trees passing `--check`.

## Relevant starting state

### The task files and their shape

`core/tools/define_milestone.py` creates `TASKS_TODO.md` and `TASKS_DONE.md` with its milestone directory, each holding only its heading line (`# TASKS TODO`, `# TASKS DONE`) and one blank line; all 46 milestone directories in this repository carry exactly those two headings. `core/shared/task-format.md` fixes a task section as a `##` title heading (4–8 title-cased words, unique within the file), a 1–3 sentence description, and a trailing `---` separator, and states that `complete-procedure.md` parses sections by that separator. A finished entry in `TASKS_DONE.md` is the same section with a `**Verified:**` label and one `- ` bullet per criterion inserted between the body and the `---`; the 292 entries across the repository all carry that exact label. The recent files share one blank-line convention — a blank line after the heading, after the body, after the label, after the last bullet, after each `---`, and the file ending in `---` plus one newline — but nothing checks it. Pre-split milestones get no compatibility, and one of them (`milestone_13`) holds a done entry without its `---`.

### The writers of the task files today

Three runners write the task files, all through prose and the host's file-editing tools. `derive-tasks` (step 6) initializes `TASKS_TODO.md` to its heading and (step 7) appends one section per brief in dependency order, committing once at the end of the run under `Task-derivation: <milestone_id>`. `submit-task` (steps 3 and 5) inserts one authored section at `append`, `before: <Task Title>` (ahead of that heading line), or `after: <Task Title>` (behind that section's `---`), falls back to `append` with a one-line advisory when the anchor title matches no section, never reorders existing sections, and commits under `Task-submission: <task title>`. `core/shared/complete-procedure.md` step 5 moves a section as four tool calls — `Read` and `Edit` of `TASKS_TODO.md` to cut the section from its `##` line through its `---`, then `Read` and `Edit` of `TASKS_DONE.md` to append it with the Verified block in the template the step shows — after step 1 located the section by case-insensitive partial heading match and, on no match, stopped listing the available headings. Every other skill that touches the files (`complete-all-tasks` re-reading the top `##` heading per iteration, `finish-current-milestone` checking `TASKS_TODO.md` holds no `##` section, `submit-task` and `discuss-new-task` triage, `ask-in-milestone-context`) reads them whole as prose.

### How the move is carried out in practice

The move is the one step in the completion procedure that runners rewrite as code each time. Across the 202 completion-agent transcripts measured on 2026-10-08 (the uncommitted report under `temp/`, a directory git ignores), about 150 agents wrote an ad-hoc Python heredoc slicing the section by `str.index` on the heading and the separator, about 30 used `cat >>` plus a removal, and about 32 used two `Edit` calls; the most common tail is a move turn followed by a separate stage-and-status turn, the turns after the first move hold about 8% of an agent's input (roughly 103k tokens at an 80k median context), and the move payload is 732 tokens at the median. The four most recent agents, on milestone 45, each wrote such a script, one of them running a second script to restore the blank line between a `---` and the next heading, and every one staged in the following turn with `git add` naming its paths and the two task files. The report's estimate for a tool that lets the staging ride in the move's shell call is about 0.4M input tokens per milestone (2.4%) plus about 600 output tokens per task.

### The staging and commit steps the move precedes

The `complete-task` agent stages after the procedure completes — `git add` of the recorded created/edited paths plus `<MILESTONE_DIR>/TASKS_TODO.md` and `<MILESTONE_DIR>/TASKS_DONE.md`, every path written out as its own argument and none held in a shell variable, only on the success path, never committing — and `complete-all-tasks` commits that index per task under `Task-completion: <heading>` behind a nothing-staged guard. The inline `complete-task` skill, `submit-task`, and `derive-tasks` commit through `core/shared/commit-procedure.md` (dirty-own-path guard with `git status --porcelain -- <paths>`, path-scoped `git add`, `git commit -m "<SUBJECT>"` with an optional second `-m` body), which names each path literally for the same word-splitting reason. The two batched passes of milestones 43 and 44 are the precedent for chaining: each shows one fixed shell call in full in its SKILL.md, run exactly as shown with only its placeholders replaced, in which every tool invocation is the full fixed command and the commit procedure's three steps are written into the call. Every multi-call site of the open-question tool carries the clause that the full command is written on every call, never through a variable, alias, or function of the runner's own.

### The existing tools and their shared conventions

`core/tools/open_questions.py` (1,270 lines) is the sole writer of `open_questions.xml`: one subcommand per concern, `MILESTONE_DIR` as the first positional argument (resolved by the caller; the tool never reads `milestones/README.md`), free-text bodies read once from `sys.stdin.buffer` as UTF-8 with a terminal, closed, or non-UTF-8 stdin refused, ids compared whitespace-folded and case-folded, and a fixed contract: a read prints bare values one per line, a mutator prints nothing on success, every failure is exactly one `Error: <reason>` line on stderr with exit 1 and the document byte-for-byte unchanged, a malformed invocation gets argparse's exit 2, and no traceback ever reaches the caller. Its one write path renders the whole document and replaces the file through a temporary file in the same directory (`tempfile.mkstemp` then `os.replace`, keeping the target's mode). `core/tools/define_milestone.py` (348 lines) repeats those conventions with its own `ToolError`, stdin reader, and atomic writer, imports nothing from the open-question tool (a parity test enforces this), and prints two lines on success. Both are stdlib-only Python 3.9+, carry no `{{` placeholder and name no host, so the build copies them byte-identical into every host's `tools/` directory (`plugins/cairn/tools` under Codex), and runtime prose invokes them as `python3 {{PLUGIN_ROOT}}/tools/<tool>.py <subcommand> <MILESTONE_DIR> …` with bodies piped as quoted heredocs, never `python`.

### Tests and the build loop

`tests/` holds one flat `test_<concern>.py` per subcommand or concern, driven end-to-end as subprocesses through the `conftest.py` fixtures `run_tool`, `run_define`, `milestone_dir` (copies of the golden fixtures `annotated`, `bare`, `empty`, `entities` under `tests/fixtures/`), and `workspace`; `pyproject.toml` adds `core/tools` to `pythonpath` and `conftest.py` disables bytecode writing so no `__pycache__` lands under `core/`. `test_contract.py` pins the shared output contract and `test_define_parity.py` pins the empty document the two tools share. The suite runs twice before a tool change is committed — `uv run pytest` under the pinned 3.13 interpreter (548 tests) and `uv run --no-project --python 3.9 --with pytest pytest` at the floor (544 passed, the build-rendering test skipped) — and CI's single `drift-gate` job runs `uv run scripts/build_hosts.py --check` then both. `hosts/<host>/` trees are build output, rebuilt and committed with any change under `core/` or `scripts/hosts/`, and `--check` refuses drift; no host slot touches the completion move, the only completion-related slots being the dispatch and prompt-opener pair (`COMPLETE_TASK_DISPATCH`, `COMPLETE_TASK_PROMPT_INSTRUCTIONS`), whose prompt carries only the task heading.

### Documentation surfaces describing the move

`CLAUDE.md` names the two tools in its repository layout (the paragraph above it uses count-free wording for the tools), states the task files' structure under `## Milestone file structure`, and carries the move in three invariants: Task altitude (`complete-procedure.md` derives the bar and records it as `**Verified:**`), skill-layer committing (the agent stages path-scoped, the orchestrator commits, the literal-path staging sentence), and the open-question tool bullet (the `complete-task` agent reads `TASKS_TODO.md` whole). `docs/skill-reference.md` has one entry each for `derive-tasks`, `submit-task`, `complete-all-tasks`, and `complete-task` describing the section shape and the commits; `docs/workflow.md` describes derive and completion in its phase narrative and its committing paragraph; `docs/design-claims.md` claim 7 names the `**Verified:**` bullets and claim 11 (the records are machine-readable) names only `open_questions.xml` as tool-written. `README.md`, `CONTRIBUTING.md`, the host README templates, and `milestones/README.md` describe the task files as prose Markdown and the tools in count-free wording, and `CONTRIBUTING.md` step 7 already requires both pytest runs when a milestone touches a tool.

## Decisions

### The acceptance bar the move reads

The move subcommand reads the derived acceptance bar on standard input as opaque Markdown. It writes the `**Verified:**` label, then the piped text verbatim with only its leading and trailing blank lines trimmed, then the `---` separator. It refuses an empty bar and checks nothing else: it neither splits the bar into criteria nor checks or adds bullets, so the bullet form of the bar stays the completion procedure's to write.

### Section boundaries in the task files

The tool takes a `##` section to end at its `---` line when one comes first, and otherwise at the next `##` heading or the end of the file. A call involving a section with no `---` succeeds and prints nothing, like any successful mutator; the tool neither refuses it nor reports it. Every section the tool writes or moves, including an entry appended to `TASKS_DONE.md`, carries its `---`, and when an insertion lands directly behind an unterminated section the tool writes the separator that boundary needs, so the inserted section never runs into the one before it.

### The tool's file name

The task-list tool is `core/tools/task_list.py`: a singular, document-named noun after the `open_questions.py` precedent, taken from the "task list" wording the goal, the skill descriptions, and the docs already use for `TASKS_TODO.md` and `TASKS_DONE.md` together. Every runtime command reads `python3 {{PLUGIN_ROOT}}/tools/task_list.py <subcommand> <MILESTONE_DIR> …`, and the tests and the conftest runner take the matching `task_list` prefix.

### Title uniqueness within TASKS_TODO.md

The tool refuses, with one `Error:` line and both files unchanged, any insert or append (the briefs `derive-tasks` writes included) whose folded title equals a section `TASKS_TODO.md` already holds, because that file is the one where uniqueness is load-bearing: the move locates a section by its heading there. A move into `TASKS_DONE.md` is never checked against the entries it already holds, and no cross-file check is made at authoring time, so a finished task is never refused at the move and follow-up work may reuse a done title.

### Initializing over existing tasks

The initialize subcommand replaces whatever `TASKS_TODO.md` holds, with no flag, no refusal, and no output on success, carrying today's `derive-tasks` behaviour over unchanged: the skill calls it unconditionally, and the guard stays where it is today, in the skill's Preconditions line saying it replaces the file's contents. Every writer of `TASKS_TODO.md` commits its own write, so whatever initialize replaces is already in the previous commit and the `Task-derivation:` diff records exactly what was dropped, recoverable by revert.

### Where the chained completion call is shown

Step 5 of `complete-procedure.md` shows the task-list tool's move command alone, with the bar on a quoted heredoc, and says that the runner runs it in one shell call chained with the git step its own file shows; the procedure contains no git. The `complete-task` agent file and the `complete-task` skill each show their own complete fixed call in full: the same move command written verbatim, then `&&` and the runner's git step, the path-scoped `git add` for the agent and the commit procedure's three steps written into the call for the skill, as the batched passes write them into theirs.

### The move's failure state

The move renders both new file contents in memory before touching either, replaces `TASKS_DONE.md` first and `TASKS_TODO.md` second through the same-directory temporary-file writer, and if the second replace fails it writes `TASKS_DONE.md`'s original bytes back through the same writer, so the call ends with one `Error:` line, exit 1, and both files byte-for-byte as they were, keeping the shared contract that every failure leaves the files unchanged. Only if that restore also fails does the superset (entry in `TASKS_DONE.md`, section still in `TASKS_TODO.md`) remain, and the `Error:` line then says so. A re-run after a clean failure is an ordinary move, and the rollback is exercised in the tests by a monkeypatched replace.

### No shared helper module

The task-list tool is one self-contained file carrying its own copies of the stdin reader, `ToolError`, the one-`Error:`-line main with its describe/fail path, and the same-directory atomic writer, written for its own needs (keeping the target's mode, as `open_questions.py` does, since it rewrites existing files). `open_questions.py`, `define_milestone.py`, and the build stay untouched, so every rendered tool remains one runnable file copied byte-identical into each host and no run imports a sibling. The parity precedent is extended: a test asserts the new tool imports neither sibling, and its conformance to the shared output contract is pinned only behaviourally by its own subprocess tests, with no check that the copies match the siblings' text. A later milestone may still extract a module; this one does not.

### How the tool matches a task title

The tool matches every title it is given (the section to move and a before/after anchor alike) against the `##` headings only by exact equality after whitespace-folding and case-folding, the open-question tool's id comparison; anything else, a partial name or two sections sharing the folded title included, is refused with one `Error:` line and both files unchanged, and the tool prints nothing on success. The completion procedure keeps its case-insensitive partial match in prose: step 1 resolves the user's partial name against its own whole read of `TASKS_TODO.md` (listing the headings on no match, as today) and the runner passes the full heading it located to the move, as `complete-all-tasks` already does by passing the exact heading.

### How derive-tasks writes its briefs

Inside its one shell call, `derive-tasks` runs no separate append. A single initialize process reads the whole ordered list on standard input, in the task file's own `##` heading / body / `---` form, validates every section, and replaces `TASKS_TODO.md` with the heading followed by the list in one atomic write, so the list lands whole and in dependency order or, if anything is refused, the file is left byte-for-byte as it was before the run and the `Task-derivation:` commit can never record a partial or reordered plan. Append keeps a one-section form only for `submit-task`'s use, if any.

### An anchor naming no section

The tool refuses a before or after anchor that names no section in `TASKS_TODO.md` with one `Error:` line and the file unchanged, keeping its full output contract, and `submit-task` drops its append fallback altogether: on that refusal it inserts nothing, commits nothing, and stops, quoting the tool's `Error:` line verbatim so the user can re-run with a correct anchor. Position encodes dependency order, so a task never lands anywhere but where the runner decided.

### Task format validation scope

Beyond refusing an empty title or body, the insert and append subcommands write whatever title and body they are given verbatim, a body line that reads as a `---` separator or a `## ` heading included, and the move copies its section as it stands. The tool checks no rule of `task-format.md`, structural or quantitative: title length and case, sentence count, and the ban on sub-headings and labeled sections all stay with the authoring skills exactly as today, so `task-format.md` remains the format's only home and no authored brief is ever refused for its wording.
