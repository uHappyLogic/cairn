# Milestone 52: Same-tree commits with pathspec and retry

## Goal

Make every skill-layer commit record exactly its own change set and survive another run's git lock, so several `complete-all-tasks` runs can share one working tree, as "Carrying it out › 1. Same-tree commits" of `ideas/milestones_addressed_by_path.md` proposes, plus the orchestrator's commit-from-file pulled forward from its second milestone. The commit procedure commits with its paths as the pathspec and repeats each failed git write a bounded number of times before passing git's message on, every call that inlines its three steps follows, and the completion agent stops staging and instead writes the paths it created or edited to a file in the run's scratch directory, which `complete-all-tasks` creates with `mktemp -d`, passes on every dispatch, and commits each task from in one call, its whole-index guard retired. The completion procedure's resumption rule names another run's live work beside a previous run's partial work; one simple test runs two milestones' tasks in parallel in one repository and asserts each commit carries only its own paths; the committing and return-contract invariants and the docs follow; the task-list tool, `TASKS_DONE.md`, the commit body, the milestones tool, and the pointer are untouched.

## Relevant starting state

### The shared commit procedure

`core/shared/commit-procedure.md` is the single home of the skill-layer commit step. It takes three resolved inputs, PATHS, SUBJECT, and an optional BODY, and runs three steps: a dirty-own-path guard (`git status --porcelain -- <PATHS>`, every path its own argument), a path-scoped `git add <PATHS>`, and `git commit -m "<SUBJECT>"` with an optional second `-m "<BODY>"` and no pathspec, so the step's closing promise that nothing outside PATHS is committed rests on the index holding nothing else. No step is repeated on failure: a git refusal passes straight through to the caller as git's message. Seventeen files under `core/` reference the procedure; eleven follow it by reference, and six write its three steps into one shell call of their own (listed next). `complete-all-tasks` is not among the seventeen: its commit step is written in its own file and names no procedure.

### The six calls that inline the three steps

Each of these is one fixed shell call "written out in full exactly as shown", with git's success output silenced by `-q` and a fixed marker line echoed after each landed commit, from which the skill's status line is read. The answer sweep's batched call (`answer-all-open-questions-with-recommendation`) runs the guard, `git add`, and `git commit -q -m "Recommendation-answer: <Short Title>" -m "$pick"` once per question section over the milestone's two files, echoing `answer commit landed`, and a git failure prints `stopped at` and ends the call. The recommendation pass's batch call commits `open_questions.xml` under `Recommendation-annotation: <milestone_id>` and then `Question-ordering: <milestone_id>`, echoing `annotation commit landed` and `ordering commit landed`. The alternatives pass's batch call commits inside a `while` loop, one `Alternatives-annotation: <Short Title>` commit per embedded file, capturing `git add … && git commit -q …` into `out` and printing the title and git's first line on failure, which the pass reports as a failed commit with no repair. The inline `complete-task` skill chains `task_list.py move` with the guard, `git add <recorded paths> <MILESTONE_DIR>/TASKS_TODO.md <MILESTONE_DIR>/TASKS_DONE.md`, and `git commit -q -m "Task-completion: <Task Title>"` (`completion commit landed`); `submit-task` chains `insert` with a commit under `Task-submission:` (`submission commit landed`); `derive-tasks` chains `initialize` with a commit under `Task-derivation:` (`derivation commit landed`). None of the six commit lines carries a pathspec, and none retries.

### The completion agent and its orchestrator

`core/agents/complete-task.md` takes two prompt lines, the task name and `Milestone directory: <MILESTONE_DIR>`, follows `complete-procedure.md`, and under its "Staging contract" runs step 5 as one fixed call chaining the `move` with `git add` of the recorded paths plus both task files, so the orchestrator's commit is path-scoped "without needing anything back from you"; it never commits, stages nothing on a refused move, and its final line is the bare token `DONE` or `FAILED: <reason>`, a `FAILED` leaving partial work in the tree for a later run to resume. `core/skills/complete-all-tasks/SKILL.md` dispatches one agent per top task through the `{{COMPLETE_TASK_DISPATCH}}` slot (the `Agent` tool with `cairn:complete-task` on Claude Code, `invoke_subagent` with `TypeName` `complete-task` on Antigravity, a generic `spawn_agent` told to read the agent file on Codex, the latter prefixing the prompt through `{{COMPLETE_TASK_PROMPT_INSTRUCTIONS}}`) with a two-line prompt fence and, on `DONE`, commits "the index the agent staged" in step 2c: a `git diff --cached --quiet` guard, then `git commit -m "Task-completion: <TASK_NAME>"` with no pathspec. It creates no scratch directory, holds no path list, and prints `Task run committed nothing — no task staged a change.` when every guard found nothing staged. The Antigravity agent's tool list comes from the `{{AGENT_WRITE_TOOLS}}` slot (`run_command`, `write_to_file`, and the rest); the Claude Code and Codex values are empty.

### The scratch-directory pattern the alternatives pass already uses

`provide-alternatives-to-all-open-questions` step 3a runs `mktemp -d` once per run before the first dispatch and holds the printed path as `<scratch dir>`, written out in full in every later command; its dispatch prompt carries `Scratch directory: <scratch dir>` as a third line on every host, and the `ALTERNATIVES_DISPATCH` slot values name the three prompt values. `core/agents/provide-alternatives-to-open-question.md` writes `<scratch dir>/<Short Title>.xml.part` and renames it into place with one `mv`, ending with `DONE`; the orchestrator's batch call scans `*.xml` directly inside the directory, pipes each file to `embed`, and moves it into a `processed` subdirectory, deleting nothing. CLAUDE.md's dispatch-prompt invariant records that the scratch directory passes the "only what the orchestrator holds and the agent cannot fetch" rule at that one site, and that `complete-all-tasks` passes the heading and the directory "and nothing else".

### The completion procedure's resumption rule

`core/shared/complete-procedure.md` step 3 opens with "Uncommitted changes already in the tree may be a previous run's partial work": the runner inspects what is uncommitted before editing, continues from whatever bears on the task and carries its paths, and leaves the rest untouched, reverting nothing. The same step has the runner keep a running list of every path it creates or edits, recorded as each edit is made and never reconstructed by diffing. Step 5 shows the `move` command alone and ends with "Run this command in one shell call chained with the git step your runner's own file shows", so the procedure itself names no git step. Another run's live work is not named anywhere in it.

### Git as it behaves here

The machine runs git 2.50.1; the bootstrap checks only `git rev-parse --is-inside-work-tree` and no version. Checked in a scratch repository on 2026-10-29: with two paths staged, `git commit -m … -- a` commits only `a` and leaves `b` staged; `git commit --pathspec-from-file=<file>` and `git add --dry-run --pathspec-from-file=<file>` both read the pathspec from a file, the dry run printing `add 'b'` for the changed path only; and with a stale `.git/index.lock` present, `git add` fails at once with exit 128 and the message `Unable to create '…/.git/index.lock': File exists.` followed by git's advice to remove it by hand. `core.filesRefLockTimeout` is unset, so the ref lock keeps git's default wait and the index lock has none. The draft `ideas/milestones_addressed_by_path.md` records the same checks on 2026-10-28 and 2026-10-29 together with the leak they bound: two completion runs in one tree, where run B's staged files ride into run A's `Task-completion:` commit and B then finds nothing staged. The README notes that Codex's workspace-write sandbox keeps `.git` read-only, so every staging or commit step there asks for approval.

### Tests touching git and the fixed calls

`tests/test_sweep_batched_call.py` is the suite's only test that builds a git repository: it extracts the sweep's batched call from the rendered `hosts/claude/` tree as the one fence holding the fold command (and the conflict section from the one fence holding `replace`), fills its sections from the golden `tests/fixtures/sweep/` milestone, and runs it under `bash -c` in a `tmp_path` repository whose environment exports `CLAUDE_PLUGIN_ROOT` to the tree root, puts a `python3` wrapper for the suite's interpreter on `PATH`, and isolates git (`GIT_CONFIG_NOSYSTEM`, a `/dev/null` global config, fixed author and committer identity). It asserts one `Recommendation-answer:` commit per answered question whose `--name-only` is exactly the two milestone files, with an edited tracked `README.md` and an untracked `notes.txt` left in the tree. Its `environment`, `repo`, `git`, and `run_call` helpers live in that file; `tests/conftest.py` carries no git fixture, and `test_sweep_compact_view.py` is the only sibling of the same shape. No test runs two calls at once, holds an `index.lock`, or seeds more than one milestone. `tests/test_fixed_console_lines.py` checks every row of `docs/skill-reference.md`'s `## Fixed console lines` table, including the `complete-all-tasks` no-op row quoted above, against every host tree. `agy_tests/test_subagent_write_tools.py` dispatches `complete-task` on Antigravity with the two-line prompt its `completion_prompt` helper builds and takes "both task files staged and nothing committed" as its pass signal; it runs on demand only and is required before committing an agent-file change. The suite runs under pinned Python 3.13 and at the 3.9 floor.

### Where the current contracts are written down

CLAUDE.md's committing invariant states that dispatched agents stage path-scoped at most and never commit, that `complete-all-tasks` commits the index its agent staged per task behind a nothing-staged guard with no `--allow-empty`, and that each task-file writer chains its tool call with the git step it owns; its return-contract invariant states the `FAILED` resumable-tree promise and that the alternatives agent's return is a file. `docs/workflow.md` `## How skills commit` says dispatched subagents "stage their own change set path-scoped and return" and an orchestrator "commits the index its agent staged"; `docs/skill-reference.md`'s `complete-all-tasks` and `complete-task` entries repeat the staging wording, and its fixed-lines table holds the orchestrator's five lines and the inline skill's two. `docs/design-claims.md` claim 12 says each skill stages only its own paths and the tree is clean after each skill, claim 15 that a failed task leaves partial work for the next run, claim 9 that tasks run one at a time, and claim 2 that the `tests/` suite runs the commits-per-decision check on the batch answer skill's shell call. The draft's "Carrying it out › 1" scoped the first milestone to the pathspec, the retry, the six callers, and the resumption rule, leaving the orchestrator's commit-from-file and the agent's return file to its second milestone, which this milestone's goal pulls forward.

### Known gaps

No runtime file repeats a git write on failure, no completion runner creates or passes a scratch directory, the completion agent writes no return file, no test builds two milestones in one repository or runs two task lists in parallel, and the resumption rule names only a previous run's partial work.

## Decisions

### Commit tool

A new stdlib-only, self-contained commit tool under `tools/` (Python 3.9+, importing no sibling, rendered byte-identical into every host) replaces the commit procedure's three steps with one invocation: given the paths, the subject, and an optional body, it runs the dirty-own-path guard, the path-scoped `git add`, and `git commit` with the paths as its pathspec, repeats each git write on failure a bounded number of times before passing git's message on after the last attempt, and prints a fixed result for the no-op. `commit-procedure.md` reduces to that one command, the seven fixed calls (the answer sweep's batched call, both annotating passes' batch calls, the inline `complete-task` skill, `submit-task`, `derive-tasks`, and the orchestrator's new commit call) replace their inlined three steps with it, and the eleven skills following the procedure by reference run it as their one git tool call. The CLAUDE.md invariants change to match: the committing invariant places the commit mechanics in the tool rather than in `commit-procedure.md`, the rule that a tool touches no git is scoped to the document writers so the commit tool may run git writes, and the shell-literal invariant's sentence setting a commit tool aside is reworded.

A git write repeats only when git exits with 128, its fatal-error code, which is the code a held `index.lock` produces. Exit 1 passes on at once: a hook refusal, nothing to commit, or a commit pathspec matching no file. The exit status is the only thing tested, and no message text is read.

### Parallel test

The one parallel test extracts two calls from the rendered tree: the completion agent's step-5 fixed call, which chains the `move` with the write of the path list the orchestrator commits from, and the orchestrator's commit-from-file call. For each of its two milestones the test makes the task's edits, runs the agent's call with that milestone's recorded paths substituted, and then runs the orchestrator's call on the path file the agent's call left behind; the two milestones' agent-then-orchestrator sequences run concurrently in one repository, and each resulting `Task-completion:` commit is asserted to carry only its own paths. The test writes no path file of its own, since a test-written file would pass a format mismatch between the agent's write and the orchestrator's read, and it does not run the inline `complete-task` skill's call. The agent's step 5 therefore stays one fixed shell call chaining the move with the path-list write, so both halves of the interface this milestone creates can be extracted and run as written.

### Documentation

The docs cover only the same-tree concurrency they already describe: they record the pathspec, the retry, and the commit-from-file mechanism, and state that the existing "Preparing the next milestone while the current one runs" chain of `docs/ways-of-using-cairn.md` no longer leaks a completion agent's files into the answer sweep's or an annotating pass's commit. Design claim 12 is reworded from a clean tree after each skill to per-commit hygiene, each commit carrying only its own paths, because a preparation run beside a live completion run already leaves the tree dirty. Claim 9, that tasks run one at a time, stays as written. Two `complete-all-tasks` runs sharing one tree are left unstated in this release and no new chain is added, until the scope gate that keeps two runs' cores apart lands in its later milestone.
